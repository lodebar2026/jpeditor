# 架构

> **为什么这么分层、哪些决策不要推翻**。要做什么见 [需求.md](需求.md)；
> 每个模块的入口与判据见 [模块/](模块/)；阈值与踩坑全录在 [实现/](实现/)。

## 1. 架构决策（已定，勿轻易推翻）

| # | 决策 | 理由 |
|---|---|---|
| A1 | **渲染用 SVG**（不是 Canvas 2D / CanvasKit） | 页面树（`PageItem`/`Group`/`GraphicPath`/`GraphicLine`/`TextFrame`）直接映射 SVG DOM；矢量、可点选、可导出 |
| A2 | **「在哪测量就在哪绘制」** | 排版期用浏览器 `getBBox` / `getComputedTextLength`（`src/common/measure.ts`），与渲染同一引擎，天然一致。**不需要原生字体测量、不需要 CanvasKit、不需要 DPI 位图缩放** |
| A3 | **逻辑全在前端 TS** | 排版/渲染/模型/编辑都在 TS，同一套代码跑 Web 与桌面 |
| A4 | **Rust 只做原生加速** | PDF 导出（`svg2pdf` + `lopdf`）、ONNX 推理（比 wasm 多线程快 ~3×）、macOS MIDI 播放；文件 IO 与对话框用 Tauri 插件 |
| A5 | **有底本就增量 patch，绝不重生成** | `.jpwabc`/`Score` 承载的信息比 MusicXML 少，整体重生成 = 把底本降采样一遍 |

## 2. 分层

```
源格式（可编辑文本）   .jpwabc  .123 .abc   文本谱       MusicXML
                          │      └──┬─┘        │             │
解析                   jpword/   abcfamily/  pu/parse   score/musicxml
                          │         │          │             │
语义模型                  │   model/doc.ts     │             │
                          │    ::ScoreDoc      │             │
                          └──────→ score/score.ts::Score ←────┘   pu/ast.ts::PuDoc
                                （汇流点，当前有损）               mixed/model.ts::MixedScore
                                                    │
识别（另一条入口）   omr/ staffomr/ rasteromr/ ──→ MusicXML ──┘
                                                    │
排版                   layout/  jianpu/  pu/  mixed/  pdflayout/
                                                    │
页面树 PageItem ──→ layout/walk.ts::walkPageItem ──→ 四个消费者
                                                    │
输出                  SVG │ PNG │ PDF │ PPTX │ MIDI │ MusicXML │ 成书 PDF
                                                    │
样式（横切）      LayoutOptions │ PuMetrics │ BookStyle   ← 三套尺子，待收敛
```

## 3. 两个共用契约

**改这两处要格外当心——它们是多条路的交汇点。**

### 3.1 `PagePainter`（`src/layout/pagepainter.ts`）

```ts
interface PagePainter { pageCount; pageSize(i); renderPage(i): SVGSVGElement }
```

三个排版器（`JinpuPainter` / `PuPainter` / `MixedPainter`，加 `ExpandedPainter`）都实现它，
编辑器铺页逻辑只依赖它。**高亮不在接口里**——三者语义不同。

### 3.2 `walkPageItem`（`src/layout/walk.ts`，54 行）

页面树的**唯一遍历骨架**，四个消费者共用：SVG DOM 两路（`svgVisitor` / `mixedVisitor`）、
成书 DrawList（`pdflayout/browser.ts`）、PPTX 形状（`editor/pptx.ts`）。

> 骨架只管「怎么走」，**坐标与颜色语义由各自 visitor 决定**——`mixedVisitor` 把 matrix 加在**叶子**上、
> 线与文字写死 black、只递归 Group；`svgVisitor` 每个 item 都产生 `<g>`、颜色取 item、无条件递归。
> **这些差别不许收进骨架。**

## 4. 数据流

| 源 | 路径 |
|---|---|
| `.jpwabc` | `JpwFile.fromString` → ANTLR（`Jpwabc.g4`）→ `fromJpw` → `Score` → `JinpuPainter` → SVG |
| `.123` | `parse123` → `ScoreDoc` →（`pu/slots.ts` 排版行视图）→ `PuPainter`（原样）／`scoreDocToScore` → `ExpandedPainter`（展开） |
| 文本谱 | `parsePu` → `PuDoc` → `puToScoreDoc` → `ScoreDoc` → 同 `.123`（`PuDoc` 另留给乐句重排改写原文） |
| MusicXML | 打开：`loadScoreDoc` → `ScoreDoc` → 同 `.123`（简谱档）／`loadMixedXml` → `MixedScore` → `MixedPainter`（五线谱/混排），**无代码区**；改动经 `toxml.ts` 整份重写。成书与识别核对仍走 `loadMusicXml` → `Score` |
| `.abc` | `parseAbc` → `ScoreDoc` → 同 `.123`；读不动才回落 `abcToMusicXml` |
| 简谱图片/PDF | OMR 管线 → `RecognizedScore` → MusicXML / 文本谱原文 / `.jpwabc` |
| 五线谱 PDF | `staffomr`（矢量）／`rasteromr`（位图）→ MusicXML → 混排视图 |
| 成书 | MusicXML → `Score` → 排版引擎 → 页面树 → DrawList → PDF |

## 6. 两条主线

### 6.1 模型主线（当前最大结构债）

`Score` 是四条源格式的汇流点，但**装不下力度、渐强渐弱、多声部并排**；和弦要分路看：

| 路径 | 和弦 |
|---|---|
| MusicXML → `Score` | **留得住**（`Chord.harmony` 字段，实测 568/568 首的 `<harmony>` 都在） |
| 文本谱 → `Score`（`scoreDocToScore`） | **丢**。同一首《圣哉三一歌》经 Score 得 0 个 `<harmony>`、直出得 28 个——所以文本谱导出 MusicXML **绕开 Score 直出** |
| `Score` → `.jpwabc`（`scoreToJpwabc`） | **丢**（jpwabc 语法本就装不下，刻意不扩） |

`.jpwabc` 那条基准路在成书对比中被停用，就是因为最后这一步装不下和弦与 slur。

**收敛已开始**：`src/model/doc.ts` 的 `ScoreDoc` 就是那个装得下的语义模型，123 先用上它，
四个模型的分工与终局见 [模块/模型-scoredoc.md](模块/模型-scoredoc.md)。

### 6.2 样式主线（三套尺子）

| 尺子 | 位置 | 服务对象 |
|---|---|---|
| `LayoutOptions` | `src/layout/options.ts` | `.jpwabc` 与展开档排版 |
| `PuMetrics` | `src/pu/metrics.ts` | 文本谱原样档（从原版实测得来） |
| `BookStyle` | `src/pdflayout/bookstyle.ts` | 成书（从原书统计中位数得来） |

三者互不相通（`metrics.ts` 明写「与 `jpStackGap` 那套**不是同一把尺子**」）。
`BookStyle` 已最接近类 CSS（角色选择器 + 字体间接层 + em 相对单位 + 深合并 + 校验），
但只服务成书 PDF。→ 收敛方案见 [样式机制.md](样式机制.md)。

## 7. 平台与打包

- **Web**：Vite 打包，GitHub Pages 部署
- **桌面**：Tauri 2（macOS `.dmg` / Windows `.exe`）；Windows 包内置 VC++ 运行库
- **Node CLI**：`vite.cli.config.ts` 把不碰 DOM 的模块打成 Node ESM（`dist-cli/`），供无头脚本 import
- **新增 Tauri 插件要同改四处**：`Cargo.toml`、`src-tauri/src/lib.rs`、`capabilities/default.json`、`package.json`

## 8. 工程约定

- TS 严格模式 + `noUnusedLocals/Parameters`；生成代码用 `// @ts-nocheck` 豁免
- ANTLR 生成码在 `src/jpword/parser/`，**勿手改**；重生成步骤见 [实现/](../docs/架构与实现.md)
- **PUA 码位用 `String.fromCharCode(0x...)`**，切勿在源码里写字面 PUA 字符（Write 工具会损坏字节）
- 能打开哪些扩展名**只在 `src/common/filetypes.ts` 写一次**
- 数 XML 元素的正则一律写 `<name[ >]`（否则 `<note>` 会命中 `<notehead>`）
- 测试语料与基线（`testdata/`）只留本地、不入库；提交信息用简要中文
