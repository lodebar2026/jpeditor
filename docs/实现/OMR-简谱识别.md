# 简谱图像识别（OMR，`src/omr/`）

把简谱图片（PNG/JPG）识别成 `RecognizedScore`，直出 `ScoreDoc`（`todoc.ts`）再写成 123 进编辑器核对（`App.importOmrDoc`）。
工具栏「识图」按钮 → `showRecognizeDialog`（[src/editor/dialogs.ts](../../src/editor/dialogs.ts)）选方式 →
`App.recognizeFromImage`（[src/editor/app.ts](../../src/editor/app.ts)）。**两种方式**：

**PDF 输入**（拖入 `.pdf`，见 `main.ts` 的 `RECOG_EXT_RE`）经 `decode.ts` 的 `pdfToImageData` 转位图再走
同一 OMR 管线。用 **pdf.js（`pdfjs-dist`）**：worker 经 Vite `?url` 引入，位图解码器 wasm 目录（jbig2.wasm
兼管 **CCITTFax G4**、openjpeg 管 JPEG2000）在 `public/redist/pdfjs/`，**必须**用 `getDocument({wasmUrl})`
指明——否则内嵌位图（扫描版乐谱多是 1-bit `ImageMask`）会被 pdf.js 静默丢弃、页面只剩矢量文字。**优先直接抽取
内嵌位图**（`largestPageBitmap`：`getOperatorList` 找 `paintImage(Mask)XObject` → `objs.get(id)` 拿解码好的
`ImageBitmap`）而非整页渲染——源本就是二值扫描图，直接贴白底即可（顺带甩掉赞美诗页码/栏目标题等叠加矢量文字，
如「耶稣普治」PDF 顶部的 `055/圣子耶稣`）；纯矢量 PDF（无内嵌图）退回 `page.render` 整页光栅化。多页竖向拼接。

识别只有**一条路**：**完全本地**，浏览器/桌面均可、可离线。`decode.ts`(图→二值) → `jianpu.ts`
  (连通域/几何启发式：数字块拆分、下划线 div、八度点、增时线) → `todoc.ts`(→简谱形状的 `ScoreDoc`)；
  数字/歌词/页眉 OCR 走本地 **PaddleOCR PP-OCRv6_small**（`paddleocr.ts`，onnxruntime-web 浏览器离线推理，
  逐数字格 / 歌词条 rec→CTC）。模型/字典在
  `public/redist/ocr/`（rec onnx `ch_PP-OCRv6_small_rec_infer.onnx` **~21MB** + `ppocrv6_dict.txt` **18708 字**
  + **det onnx ~4.7MB**（DBNet，仍 PP-OCRv4，页眉用；det 头与 rec 无关故可跨版混用）），wasm 运行时在
  `public/redist/ort/`（纯 wasm 单线程，免 COOP/COEP）；`onnxruntime-web/wasm` 子入口避开 26MB 的 jsep 构建。
  早期用 **tesseract.js**（`localocr.ts` + `montage.ts`），实测数字仅约 69%（常把 6 误读为 0），
  且从来没有开关能切到它，2026-08 重构时连同已废弃的 Gemini/agy 整页转写方案一并移除。
  - **rec 逐代换**（2026-07）：PP-OCRv4(6623字/无「祂」) → v5_mobile(18383字) → **v6_small(18708字)**。v4 无「祂」
    （赞美诗第三人称神）只能读成形近「他」；v5_mobile 字典含「祂」但**视觉仍偏向高频「他」**、48px 二值条上「祂」全读错；
    **v6_small 同一条子「祂」4/4 全对**（基督更美/耶稣普治），整体音符 100%、含标点歌词 ~93→**99.8%**、词曲 99→**100%**。
    前端 CTC 解码字典驱动（`_chars`=["", ...dict]）、数字类别索引 `chars.indexOf` 动态求、Rust argmax 读动态末轴，
    **换字典/模型无需改逻辑**，只换 `REC_URL`/`DICT_URL` + `tauri.conf.json` 打包映射（rec.onnx）。输入 shape
    仍 [3,48,320]、归一化不变。导出：`paddlepaddle 3.x`(macOS arm64 **必须 3.x**，2.6.2 CPU 构建卡死/段错误) +
    `paddleocr 3.7.0` → `paddle2onnx 2.1.0`（**注意** `paddlex --install paddle2onnx` 会降级到 2.0.2rc3 且报
    "Paddle2ONNX is not available"，须 `pip install paddle2onnx==2.1.0` 后直接 `paddle2onnx --model_dir …`）。
    变体实测：v6_tiny(4.4MB)「祂」读成「池」、**v6_small(21MB)「祂」4/4**、v6_medium(76MB)太大 → v6_small 最优。
  - **v6 换代的两处数字回退，用两条通用几何修复消掉**（均在 `jianpu.ts`，非针对样本打补丁）：① **矮块补高**
    （`recRects`）——连通域偶尔只截半个字（淡印断笔「1」竖笔断开、块高≈半字高 → 送 rec 成半字读作「4」），据本行
    数字带统计高度把 h<带高×0.7 的块纵向补到整字高（`cellOf` 按 rect 从二值图裁、会纳入带内断开的另一半；带
    `[topY,botY]` 由数字核算出不含下划线/八度点，补高安全）；② **空心环校验**（`midbandInk`）——简谱「0」是空心环、
    从不带斜线，糊死的「3」中间横笔连成穿心斜线被读成「内含斜线的 0」；测中央横带前景占比（真 0 各图 ≤0.47、糊 3
    恒 ≥0.7），>0.65 判"读成 0 却中带占满"= 实为糊 3，走既有 `rankDigits` 取首个非零复原。两修复后 6 曲音符 **100%**、
    slur/tie 不再受连带（0=休止会丢闭合圆滑线）影响。回归/分析：`node scripts/gen-song-analysis.mjs <歌谱名>`（单曲全流程
    HTML：原图/二值 → 逐格数字与 GT 自动对齐标红 → 歌词条含「祂/他」绿框）。

已修复初版几处 bug：连音(下划线相连)数字粘连不切分、增时线后 MusicXML `type/duration` 不一致、
montage 单行长条过大导致 OCR 超时（改网格）、**八度点过检**（约束 octave 点须水平居中且紧贴上/下方、
封顶 ±3）、**歌词行混入数字 OCR**（小节线须纵向贯穿本行才算乐谱行 → 歌词行得不到小节线，不送数字 OCR）、
**减时线层数（div）要验层距**：多条减时线是紧挨着堆叠的，只按「落在数字下方窗口内」计数会把
窗口下沿的别的东西也算进来（歌词字的横笔最常见）——《主祢真伟大》第 25/33 小节的 `6_ 5_`、
`4_` 被读成 `6__ 5__`、`4__`，小节凭空少半拍，**连 GT 都跟着错了**（导入 Dorico 后时值凑不满，
被拟合成双附点才发现）。改为自上而下逐层验距，两条判据取交集，单用哪一条都分不开：

| | 层距 / 字高 | 层距 / 线厚 |
|---|---|---|
| 《沧海一声笑》(numH 11) 真双减时线 | 0.27–0.36 | 2–4 |
| 《主祢真伟大》(numH 22) 真双减时线 | 0.18 | 1.3 |
| 《主祢真伟大》误收的歌词横笔 | 0.45–0.55 | 5–5.5 |

即 `gap <= numH*0.40 && gap <= max(prevH, curH)*4.5`，断档就停止计数。第一条另要求紧贴数字底
（≤0.45 字高）。这条改动把 14 首的**音符准确率从 99.6% 提到 100%**、对位 99.1%→100%，
并顺手订正了 GT 里《主祢真伟大》那 3 处。

**断成几截的横线要先接回一条**（`mergeBrokenHlines`，在 `classify` 之前）：扫描件里一道减时线
常被二值化断开一两个像素——227《施比受更为有福》`3·4` 底下那道共用减时线实测断成
81px + 12px + 18px 三截（缝各 1px）。后果是双份的：碎段够不着 `classify` 里横线的宽度门
（w ≥ 0.6 字号）**进不了 hlines**，长的那截又止步于 "4" 的左缘、与 "4" 只重叠 6px、过不了
「横线要盖住数字四成宽」那条，于是那个 "4" 一条减时线都没剩下，时值凭空翻倍。
判据三条：同一水平线上（上下缘各差不过一条线的厚度）、横向缝隙 ≤ max(2px, 0.06 字号)、
**两截里至少有一截短得不成线**（< 0.6 字号，即本来会被丢掉的碎渣）。最后那条不能省——
为基督赢得城市第 1 行 `3 - - 0` 的两道增时线印得几乎挨上（缝隙不到 2px），少了它就并成一道、
那个音少掉一拍（实测音符 100%→98.6%）。另外**往回找同一条线上的那一截时不能只比紧挨着的
上一个**：按 x 排序时，同一道减时线的第二层就夹在序列中间（那处四截是 x784/866/874/879，
其中 874 是下面一层），只比上一个第三截就接不回去。

### 密排粗体印刷本（迦南诗选那批）挑出来的五条

数字排版直接印的诗歌本（迦南诗选 8 首实测）与从前的翻拍/复印语料**版面特性正相反**：音符排得密、
减时线紧贴数字底、字形瘦、增时线短。旧判据全是照扫描件的宽松版面定的，在这批上一条条地翻车：

**① 增时线的纵向判据要写成字面的「重叠 + 居中」。** 两条修饰本是**对偶**的：
增时线在数字**右侧**、与数字**纵向重叠**；减时线在数字**下方**、与数字**横向重叠**。
减时线那条一直是字面写的，增时线那条却写成了「中心距 < 0.6 字号」——两头都不严，
两种减时线都能混进来：

| 横线 | Δcy / 字号（线心 − 数字心） |
|---|---|
| 真增时线（画在数字中线上） | **−0.05 ~ +0.21**（22 页 283 根，只此一根到 0.21，其余 ≤0.14） |
| 倚音底下的减时线（印在主音符左上角，落在前一个音符右侧的空隙里） | **−0.27 ~ −0.42**（偏上） |
| 下一组音符的减时线（音符排得密时从本音符右缘伸出来） | **+0.58**（偏下） |

前者让《求主引导我每一天》`1 ²⁼3 - -` 的前一个音符白得两根增时线，后者让《小小蒲草箱》
每行 2~3 处符尾组前面凭空多一根 `-`。改成 `yOverlap`（`kb.y < rbottom(d) && rbottom(kb) > d.y`）
+ `|Δcy| ≤ 0.25 字号`：门开在两簇之间，两侧各留 0.04 / 0.02 字号余量。横线块本就扁
（h ≤ 0.32 字号 < 数字高），居中那条已蕴含纵向重叠，两条并写是为了跟减时线那条对偶着读。

**「增时线比减时线粗」这条量过了，只能当旁证、不能当判据。** 22 页逐页比两类线的厚度中位数：
**20 页成立**（粗细比 1.25~2.00，迦南那批稳定在 1.67~2.00，`- ` 是 5~8px 而下划线 3~4px），
**2 页反过来**——《基督更美》0.83、《我今来就你》0.80，都是二值化把下划线泡粗了的翻拍件
（前者 减时线中位 6px 比增时线的 5px 还厚）。偏偏《我今来就你》正是 |Δcy| 最大（0.21）、
最需要第二道判据的那一页，厚度在那里恰好指反方向 —— 一卡就把真增时线judge掉。
故不写进判据；哪天几何判据在某本新谱上失手，这条可以按**页内相对**（本页两类线厚度中位数分得开时才启用）
再捡起来。

**② 增时线的宽度门要单独放：它比减时线短得多。** `classify` 里横线的门 `w ≥ 0.6 字号` 是照
减时线（要盖住整个数字）定的，这批的 `-` 只有 0.48 字号宽（23px / numH 48），整根被丢掉
——每小节末尾的长音全变短。补一条细长条通道：`w ≥ 0.4 字号 && w ≥ 3 × 平均墨厚`。
长宽比里的「高」用**平均墨厚**（面积 / 宽），不用包围盒高：线下沿挂一个毛刺像素，包围盒就高出一截
——《7606 同伴》「语，」`2 - -` 的第一条 `-` 实测 10×4、面积 25（厚 2.5），按包围盒 10 < 12 被挡，
少了一拍。近方的碎渣平均墨厚与包围盒高相当，照样挡得住。

**更短的 `-` 会掉进「小点」那道门被当附点**：1863《至暂至轻的苦楚算什么》小节末 `3 - -` 印成两根 8×4 的短横
（字号 24，只有 0.33 字号宽），过不了 0.4 字号，尺寸又在小点门（≤0.45 字号见方）里，`3 - -` 读成 `3.`，全曲
十三处长音全短。同页真附点 5×4。分在**扁度**：附点近圆（宽/平均墨厚 ≈1.25），短横 2 倍——再加一条通道
`w ≥ 0.28 字号 && w ≥ 1.8 × 平均墨厚 && h ≤ 0.2 字号`（探针 `hline.shortDash`），排在小点门之前。

**③ 上下叠着的横线一定不是增时线。** 倚音那两条减时线（上表第二行）除了偏上，还有个更硬的特征：
它们是**上下叠着**的，而 `- -` 永远左右并排。`stackedHline`（同 x 重叠 ≥50%、中心距 ≤0.45 字号）
与①的居中判据各挡一半——十六分倚音的两条线两条判据都挡，八分倚音只有一条线、只能靠居中那条。

**④ 减时线粘着别的墨要剥开——只在干净谱面上剥。** 《竭力保守》第 6 行 `2̲ 1̳ 6̳` 的第二条
减时线与那个低八度点粘成 207×15 一块，过不了「横线要够扁」（h ≤ 0.32 字号）那道门，
**线与点一起消失**：那一拍时值翻倍、音高还高了八度。`stripUnderline` 的办法是**按本页统计线粗
把横线墨迹剥掉，再看剩下的是什么**（最初只会从整条线下切一个点，见下文「减时线粘连」一节）。
**「干净」看小节线直不直**：数字排版出的印刷本，小节线是绝对竖直、墨廓填满的矩形
（bbox 内前景占比中位 0.977~1.000），翻拍/复印件的同一根线总歪一两个像素、边缘发毛，占比掉到
0.37~0.82（现有 14 首语料全部如此）。另要求线够粗（中位宽 ≥2px，1px 细线占比恒为 1、分不出干净与否）
且够多（≥4 根）。脏页上碎渣挂在减时线下沿时与八度点同形，切开就是凭空多一个八度，故一律不切。
（JPEG 噪点不影响这条：二值化后噪点改变的是碎渣数量，不是小节线的笔直程度。）

**⑤ 「极窄块纠回 1」的门要按字形收到 0.45 字号。** 原门 0.55 是照「1 占 0.45~0.55 字号、其余
≈0.9」的宽体字定的；瘦体版面里 2/3/5/6/7 也只有 0.5 字号宽（这批实测 "1" 16~18px、其余 23~26px，
numH 47），0.55 把**清清楚楚的 4 和 7** 一并改成了 1（《祷告》3 个 `4.` + 7 个 7、《主是》《天不蓝了》各若干）。
0.45 卡在两簇之间，两种版面都分得开，现有语料指标一位不动。

另外**短弧的宽度下限**（`slur.ts`）从 0.8 收到 0.7 字号：密排版面里跨两个八分音符的小弧只有
0.77 字号宽（37×9，numH 48），整条漏掉；同一首里排得松一点的同形弧 39×10 就认了出来
——《天不蓝了》八条这样的弧全丢。下面还有扁平度、「整体在数字上方」、「至少罩住两个音」三道门兜着。

这五条加拍号那两条（见「混合拍与曲中转拍号」）之后，迦南诗选 8 首**每个小节的拍数都与拍号对得上**
（`节拍自检`：除各首本就写着的弱起/收尾小节外无一例外），新立的 GT《1689 天不蓝了 水不清了》
音符/小节/slur/歌词/对位**全 100%**（改前音符 62.6、小节 64.2、slur 50.0）；14 首老语料指标不变。

### 减时线粘连、和弦字母当弧、中文段号（《5915 切慕》《7606 同伴》）

两张干净印刷谱（小节线实心笔直，`isCleanPage` 为真）各有几处错，**表面现象与根因多半对不上**，下面按根因记。

**减时线粘连：按统计线粗剥线，再看剩下的是什么**（`jianpu.ts::stripUnderline`，替掉了旧的 `splitMergedUnderlineDot`）。
页内先取**统计线粗** `lineH`：够宽够扁的横线的高度中位数（同伴 3px、切慕 2px）。只处理**高度对不上一条线**
（h > lineH + 1）的块，分两种：

| 粘法 | 实例 | 旧行为 |
|---|---|---|
| 线型：线下挂一两个低八度点 | 切慕末行 `0̲6̣̲` 27×7（numH 16）；同伴首行 `0 3̣ 6̣ 7̣` 47×7，线顶还多一个毛刺像素，线下挂两个点 | 旧函数要 `w ≥ 4h`（27 < 28）、要顶行是整条线（毛刺挡住）、只会切一个点 → 整块丢，减时线和低音点一起没了 |
| 数字型：数字尾笔碰到线（线下可能还有点） | 同伴「灵」`6̲` 19×22；第 3 行 `6̣̲` 连着线和两个点 47×26 | 线在数字块里面，`buildJpNums` 只在块外找线；块还把行带撑到线下，同行 `7` 补高后连线带点一起裁进 rec → 读成 0 → 「0 对上歌词」复原成 **1** |

- 线行：线型按「最长横向游程 ≥ 0.8 块宽」认；数字型**按数字底部窄、减时线要盖住整个数字**来认——
  先量块上部 0.8 字号内的数字体宽 `bodyW`，线行游程要 `≥ bodyW + max(2px, 0.1 字号)`，**宽出一截**而不是「不窄于」
  （2 的底横、7 的顶横本就与数字等宽）；线带上方紧挨的那一行还得是窄「颈」（< 0.6 线宽，6 的尾巴 2~3px），
  上下一样宽的不切。实测「灵」数字体宽约 11、尾巴 2~3、线 19。
- 线带向上下吸收毛边行（墨量 ≥ 0.3 线宽），总厚不超过 lineH + 1；比这还厚的不是减时线，整块不动。
- 剥掉线带后重做连通域，**每一块都得说得清是什么**：≤3px 的毛刺丢；线下方圆而实的小块（0.1~0.5 字号、
  宽高比 0.6~1.7、填充 ≥0.6）是点；数字型线上方高 0.85~1.25 字号的块是数字。**有一块说不清就整块放弃**，
  退回原归类。数字型还要求块高 ≥ 1.15 字号：正常数字加自身笔画凑不出这个高度。
- 剥出来的数字照原路进 `splitBlock → rec`，裁剪框就是剥线后的紧包围盒，线和点都不在里面。
- **线型下方的另一截短线**也算线：长线罩着 `6̳ 1̲ 1̳` 三个音、第二条线只在 6 和末一个 1 下面各有一截，右边那截
  顶到长线上粘成一块（1776《在天上我有一位阿爸》110×12）。它在线带下方、高 ≤ lineH + 1、宽 ≥max(0.4 字号, 3 倍高），
  按线收回；原先它「说不清」，整块放弃，两个 1 的减时线全丢。线型的返回条件相应改成「有点或有这种短线」。
- 抽检：现有 GT 语料（翻拍件，或没有这种粘连）**一处都不触发**。诗歌本图片库 425 张逐张开/关对比，32 张有触发、
  其中 26 张识别结果一字不变（剥出来的线本就会被别处认到）；有变化的 6 张：切慕、同伴（本节修的）；
  《1670 竭力保守》`1̳ 6̳`（旧函数当初修的那处，照样切对）；一张简谱+五线谱对照的小字谱，多出的几条减时线对照原图是对的；
  另两张是苗文柏格理字母谱（不是简谱，`L`、`⊥` 形字母被剥成「竖笔 + 线」），开关两种结果都是乱码。
- 试过「rec 补高改用中位带高」当兜底（行里有超高块时 min/max 带会被撑到线下）：剥线后同伴已不需要它，
  而它会改变脏页上的行为——《16 爱心的功课》双声部处（上 `5 ♯4 ♭4`、下 `0`）以前补高碰巧把下声部的 0 裁进来、
  对上了 GT，改后读出上声部的 5。故不改。

**和弦字母不当弧**（`slur.ts::flatBottomShare`）。`Em` 两个字母连成一块（切慕末行 31×15）、`Bm` 的 m（17×9），
宽而扁、正在音符上方，`detectSlurs` 的每道门都过，凭空多出 `(0 6)` 这样的弧。分开它们靠**底边**：
字母立在基线上，横笔与衬线让大半列的最低墨点落在块底（末两行）；弧是拱形，只有两只脚着底。
占比 ≥0.5 即不是弧，只对 ≥0.4 字号高的块判（扁平小弧中间列本就贴着块底）。主祢真伟大实测：真弧 0.03~0.19，
`Am` 0.80~0.86。
先试过「弧的包围盒落在和弦框里就撤」——**不行**：和弦框从这个和弦一直延到下一个和弦的起点（切慕的 `Em` 框宽 152px），

以前恰被「Am 当成弧」凑成满分，已按原图订正 gt.123（25→23 条）。

**中文数字段号**（`lyrics.ts::CN_LABEL_RE`）。切慕行首印 `一、` `二、`…，旧段号正则只认阿拉伯数字；「一」是汉字，

`、.．`（没有分隔符的「一」多半就是歌词首字），字位在本谱行首音中心左侧才算；装配时跳过、不占音符；
段号照谱面原样写出（123 `w:<一、>`、诗歌本 `<一、>`、番茄 `"一、"`；ABC/MusicXML 本就不带段号）。

**休止符不接词**（`lyrics.ts` 装配之后）。切慕末行 `0̲6̣̲` 两音中心只差 0.8 字号，第 4 段「荣」的字位左缘对音符中心的

（中心距 ≤1.2 字号）且字位**明显过了休止中心**（≥0.2 字号，「荣」是 0.36）。这两条缺一不可：沧海一声笑小图上一个
被误读成 0 的真 `3`，字就正压在它中心上（差 0）、右邻远在 2.8 字号外——只按「过了中心」判会把它的字挪走（对位 100→97.2）。

块内字按格序取 x → 按 x 单调最近对齐到音符（melisma 自然留空），写 `JpNum.lyrics[verse]`。
**标点**：单元=汉字+紧随尾随标点(全角 `，。、；！？` 等，向左贴前一字、不占音符)，并入该音节串不另立格——
保持"音节数==字格数"对齐前提；rec 在自然块上下文里读逗号也准(`LYRIC_PUNCT`)。带标点 歌词档 89.6→93.0%
(忽略标点 歌词* 仍 98.9%、对齐未破)；淡印逗号 rec 捕获不到的(如 我今来就你)仍漏，属图像层面限制。
**左右结构字裂成两块**（`mergeSplitHalves`）：投影分字的偏旁门是 0.22 字号，1775「忠仆」的 亻 与 卜 隔 8px（门约 7px），
没并上，亻 落进前一个 rec 块、卜 落进后一个，读成「忠卜」。这一行字距 16~19px，门不能整体放宽。另补一道：两块
间隙 < 0.3 字宽、至少一块窄（< 0.6 字宽）、两块都够字高（≥0.8，英文小字、标点挨不上）、并起来 ≤1.15 字宽——
两个正常宽的汉字并起来远超这个宽。
**扁字「一」单独成块**：`chunkCells` 按块的纵向范围把宽折算到 48px 条高上，「一」只有 5px 高，单独算时折成 374px、
一进块就「达标」被关块，自成一块送 rec 读成 `_`（1790 末行「一生跟主」丢「一」，那个音空出来又被补了跨行 tie）。
折算高度改为不低于本行字格高的中位。连带对原图订正了两处 GT 错（当初照识别底稿抄下来的）：714「直到有一天」、沧海一声笑二房「晚照。」。
**孤立的「一」被读成 "1"**：歌词里的「一」是孤零零一根横，自成一块送 rec 时常读成 `"1"`（也见过
`-`/`—`）。这些字符走不进任何装配分支、被整个丢掉，那个音符就空出来、后面一串词跟着往前挪一格
（「因有主同在」的 `我愿/意将一生/奉献` 读成 `我愿/意将/生/奉献`；沧海二房的「一襟晚照」丢「一」）。
中文谱的歌词块里这些字符没有别的合理来源，故**整块就这一个字符**时改判成「一」。唯一例外是
**行首、落在本谱行第一个音符左侧**的那种——那是多段谱的段号 `1.`，本就该丢弃、不占音符位。
**英文歌词**（如「主祢真伟大」的 `How-awe-some-you-are`）：单元不再限于汉字——拉丁串按**连字符**
(音节边界，`-` 随音节保留)与**词间空白**(rec 不吐空格 → 按源图字距 >0.5 字宽断)切成音节，每音节
占一个音符，与汉字单元同等对齐。**对齐点取音节起始 x**（与汉字用字位左缘同一基准），宽度取实际跨度
——不能拿 `charW` 兜底：英文行的字格是整串音节合成的一个大块，`charW` 就是那个块宽（两百多像素），
用它算出的中心会把音节整体右移一个多字位（实测 `How-` 落到 x233、该在 x170 的 `5` 音上）。配套两处：① 英文字号只有汉字一半，一串音节缩到 48px 高后宽近千，
故 `mergeSmallTextBlocks` 把相邻矮块(<0.8 charH)并回一块防音节被 `chunkCells` 从中间切断
（曾读出 `How-awe-s`/`ome-you-are`），`recognizeTexts(Pos)` 对切不开的超宽条按自身宽度放宽 rec 上限
（`"auto"`，≤2048；常规条仍 320 → 与旧行为逐位一致）。② **和弦/段落标记行**(`Am`/`G/B`/`Gsus4`/
`Chorus`，印在**下一谱行音符上方**、同落在歌词带内)放开拉丁字符后会变成伪 verse，故 `isAnnotationLine`
按形态剔除：无汉字 + 整行几乎能被一串**和弦记号**从左到右贪心吃完（`CHORD_TOKEN_RE` = 根音 + 升降号 +
`m/maj/min/dim/aug/sus/add` + 数字 + `/低音` 转位；吃不动就跳一字记未覆盖，≥2 个记号且覆盖率 ≥0.85 判为
和弦行，单记号行要求吃净以免误删 `Be`/`Ah` 这种独立英文词），**不依赖大小写正确**（OCR 常把 C 读成 c）。
——旧判据按 `[A-Za-z]+` 切字母簇、要求每簇首字母是 A-G 根音，但升降号与数字会把簇切断：`C#mF#mBm7E`
切出 `mF`/`mBmBm`、`E7sus4` 切出 `sus`，首字母都不是根音 → 整行和弦当成歌词（「再次将我更新」四条
和弦行全部灌进 W2/W3）。英文歌词吃不动（`still`/`azing` 起头即失败）覆盖率立刻塌下去，故不误伤。
剔后该谱行剩余 verse 重新编号。**判出的和弦行不再只是丢弃**——同一判定顺手把和弦捞出来输出，见下面
「和弦符号」一节。判定前先**剥掉方括号里的编者注**
（`[下面一行也可用]`、`【Chorus】`）——一句中文编者注就会让整行和弦被当成真歌词（「立定心志」的 W2 曾整行是和弦）。
和弦行还会让 `JUMP_MARK_RE` 从连写的 `Em G/D C…` 里读出一个 `DC` → 凭空多出 D.C.、整首被展开成十遍；
故该正则加**词边界**（裸 `DC` 两侧不许挨字母），且注记行里就地捞出的跳转记号随该行一并作废。
**八度点两处误判**（`jianpu.ts` `buildJpNums`，均由**歌词字的顶部笔画**引起——歌词带紧接在数字下方，
字顶的短竖/点正落在数字正下方、dx≈0，与「减时线下方的低音点」几乎同高）：
① **居中阈值 0.4→0.25**：真八度点是印在数字正上/正下方的圆点，实测 |dx| ≤0.07~0.14；偏在两字之间的
字顶笔画 |dx| 0.3~0.39，旧阈值放它进来 → 凭空多出低八度点，若该音本就有高八度点还会被一加一减抵消
（实测「主祢真伟大」Coda 的 `i`(为) 丢点、`7`(我) 平白多点）。
② **低八度点要求「其下方 0.3 字号内基本无墨」**（`inkBelow < 0.12`）：dx≈0 的字顶笔画（如「主」字
上方那一竖）靠位置分不开（间隙 14~15px vs 真点 3~13px）——但八度点是**孤立**的圆点、下方留白，
字顶笔画下方紧接着字的其余笔画。**先试过宽高比**（八度点 w/h≈1.0、字顶笔画 0.67~0.83），但小字号图上
真点只有 2×3 像素、比值不可靠，世上所有的民族的真低音点被误剔（音符 100→99.3）；窗口也不能大到
0.5 字号，否则大字号图会吃到下方歌词（基督更美 100→99.2）。

**附点三处修正**（`jianpu.ts` `buildJpNums`，补齐 5 首 GT 后暴露）：
① **垂直窗口 0.25→0.35 字号 + 「点不居中于任何数字」**：0.25 在扫描抖动面前太窄——「因有主同在」
第 2 谱行四个附点实测 Δcy=0.28，而同一版面第 1 谱行的同一批附点只有 0.18，整行附点全漏。放宽后
不能再靠 Δcy 挡「邻音符的八度点」（它们 0.3~0.43，与真附点重叠），改用**水平位置**：八度点永远印在
某数字的正上/正下方，附点在两数字之间的空隙里——这也正是八度点分支的判据，口径一致。
② **反复冒号不再要求两点分居数字中心两侧**：小图上冒号相对数字中线整体偏上，「爱是不保留」两处 `:|`
的点对实测 Δcy 是 -0.47/-0.06 字号（同在上方），异侧条件一卡就漏、两个假附点由此而来。能走到附点
分支的点本就在数字右侧空隙里，不会是居中于数字的双八度点，故「点对 + 紧邻竖线」已够判。
③ **「休止 0 不接附点」挪到 digit=0 复原之后**：`buildJpNums` 里的 digit 还是 CTC 原始结果，糊死的
「3」常被读成 0（正是空心环校验要复原的那种），在那里一刀切会连它的真附点一起丢（沧海一声笑行 1 的
`3._`）。改成复原完再对仍是 0 的音符 `n.dot = 0`。

**反复记号**（`repeats.ts` 识别 + `score/playorder.ts` 展开，issue #2）：以
《沧海一声笑》（`1.2.3.5.` / `4.`(带 D.C.) / `6.` 三房）为基准，识别与展开各修了几处：
- **房括线搜索窗放深到 3.4 字号**：括线到数字顶的距离随谱面松紧变化很大，行内有圆滑线时括线
  被顶到 ~2.8 字号高处，旧的 1.8 字号窗口整片漏掉三个房。放深的误检由新增的 `hasLeftHook`
  （括线左端必有下垂短竖，歌词/连音线等长横墨线没有）挡住。
- **一个房可辖多遍**：房号 `1. 2. 3. 5.` 是一串小连通块，改为从左端起收**连续同高**的块
  （按最高块 0.55 倍剔掉号后的小圆点、断在第一个 >1.2 字号的空档），逐块 OCR 后拼成
  `<ending number="1,2,3,5">`。`JpNum.endingStart/Stop` 因此从 `number` 改成 `string`。
- **D.C./D.S./Fine/To Coda**（`lyrics.ts` 的 `JUMP_MARK_RE`）：这类记号落进歌词带 →
  归 x 处或其左侧最近的音符，出 `<direction>`+`<sound dacapo=…>`。**归哪一行按 y 就近**：
  多数印在本谱行音符下方（Fine 贴在歌词行末），但 `D.C. al Fine` 习惯印在**末谱行音符的右上方**，
  那同样落在「上一行下缘→本行上缘」的带里——一律归本行会把 D.C. 挂到上一行末（「因有主同在」
  曾挂到小节 22 而非 28，整首少唱一行半、还被多展开一轮）。
  **含汉字的块也扫**（`INLINE_JUMP_RE`）：Fine 就印在中文歌词行末尾，OCR 常把它和末几个字读进
  同一块，旧的「只在无汉字块里找」整个漏掉，拉丁串还会占掉一个音符位把后面的歌词挤偏；但含汉字时
  只认形态明确的写法（完整词 `Fine`/`To Coda`、带点的 `D.C.`/`D.S.`），裸 `DC`/`DS` 仍不认。
  命中的记号连同 `al Fine` 之类后缀（`JUMP_SPAN_RE`）**从歌词流剔除**。另有一条兜底：
  **落在延音音符（tie/slur 收尾、前一音已有词）上的孤立拉丁串不是歌词**——那个位置唱的还是上一个
  音节，中文歌里冒出来的拉丁串只可能是记号；只对拉丁串生效，汉字落到延音音上多半只是对齐误差。
- **三房以上的演唱顺序**（`RepeatProcessor`）：① 本遍不唱的房，其右边界的 `:||` 不该照跳
  （否则第 4 遍永远落不到「4.」房）；② 「最后一房」须按房号判（`max(endingNum) >= passCount`），
  中间的房右边界同样没有 backward，按「无 backward 即收组」会半途把 pass 归 1 并死循环；
  ③ **房内的 D.C.** 只是这一遍的回头记号（与 `:||` 等价），回到曲首后**后续反复照常生效**，
  故不进 `inJump` 抑制模式；房外的 D.C. 仍按老规矩。④ 谱面写明 2 号以上的房时**不再**跑
  `repeatByLyric()`——遍数已由房号显式给定，再按歌词段数整体乘一遍会把本曲乘成 6 倍。
  ⑤ **有 D.C./D.S. 跳转时同样不跑** `repeatByLyric()`：跳转本身就把曲子展开成了多遍
  （「因有主同在」的 `D.C. al Fine` = 全曲唱一遍、回头唱到 Fine 为止，两遍正好配两段词），
  再乘一遍就成四遍。判据 `playData.jumpTo.size > 0`。
- **多段词只印在主歌行**：伪 verse 过滤原先只看「有字谱行数 ≥ 主 verse 一半」，而 2..N 段词
  本就只印在主歌那几行（啦…/间奏行下方没有），本曲 A 段五行词被整片当伪 verse 删光、六个房
  全唱成第一段。加逃生口：**该行字数 ≥ 同行主 verse 的 0.6 倍**（= 完整一行）即保留；噪声伪行
  只有零星几字，仍被删。去留还改成按**视觉行序整体**决定而非逐谱行：一个行序只要在某一谱行上
  是完整一行词就算真 verse，它在别的谱行上的短行（房内只唱一小节的「几多娇？」）跟着保留。
- **行首段号 → 词段映射**（`lyrics.ts` 的 `parseVerseLabel`）：多段谱在歌词行首印段号，
  **视觉行序未必等于段号**——`3.5.` 表示第 3、5 段共用这一行词，号还可能跳（`6.`）。段号是
  非汉字、装配时本就被丢弃不占音符位，只需从 rec 原文行首取回来做重映射（`versesOf`，一行词
  可同时写进多个 `lyrics[]`）。段号小、点更小，OCR 常把点吞掉（实测 `1沧海…`/`35江山…`），
  故分隔符可选、连写数字**逐位**拆号。房括号上的号码（`1.2.3.5.`）也会落进歌词带被当一行，
  按「号后须跟 ≥2 个汉字」剔掉。整套映射还要过「首行标 1 + 号不重复 + 至少两行有标签」才生效，
  否则作废退回"行序即段号"。标签通常只印在第一谱行，后续谱行按同一视觉行序共用该映射。
- **段号还要原样输出**（`StaffRow.lyricLabels` → `topu.ts`）：文本谱有「歌词行前置说明」这个位置
  （`pu/parse.ts::stripLyricAnnotation`，排在细竖线与首字之间），谱面印的 `1.` `3.5.` 就写在那儿：
  诗歌本方言 `C1:<1.>…`、番茄方言 `C1:"1."…`。它不是唱词、不对位音符，故不进 `lyricRanges`。
  **逐谱行各记各的**——号只印在哪几行就只写哪几行（73《我主耶稣是生命源》前三谱行有 `1.`~`4.`、
  后两行是副歌只有一行词、谱面没印号，输出照旧是裸 `C:`）；号本身取重映射后的规范写法，
  OCR 把点吞成 `35` 也能还原成谱面那个 `3.5.`。只在整套映射可信时才写。
- **第二段前半没印词 → 照抄第一段**（`fillLeadingVerses`）：多段谱的惯例是两段唱同一句的那几行
  只印一行词，第二段从「两段词分岔」的那行才另起（「再次将我更新」前两谱行只有一行词，W2 从第三
  谱行才开始）。若不补，导出后第二遍前半是空的。规则只补**前缀**：某段首次出现的谱行 `first` 之前、
  该段整行无词而第 1 段有词的谱行，把第 1 段的该行词**整行照抄**（连 melisma 分布一起，下游 `/`
  续记号才不错位）。附加条件「`first` 行上第 1 段也有词」用来排除反复房「二房起歌词整体上移」那类
  结构（「一房只有第 1 段」的反复约定）——那种谱在分岔行上第 1 段反而是空的，不该补。
- **房内的短歌词行**（`covOf`）：注记过滤按「行宽/整谱行宽」算 cov，房内只覆盖一小节的第 2、3 段
  词（「天知晓。」占 0.2）会被当注记丢掉、那几遍没词唱。改成 cov 取「对整行」与「对各房」的
  最大值——整条落在某房内且铺满该房的短行同样算真词。

**谱后正文的剔除**（`lyrics.ts` S1）：末谱行的下方带从前没有下界（`Infinity`），谱子后面印的
整段正文（曲子的背景介绍、版权说明）就全落进来当歌词——它同样**铺满整行、字高也够**，S4 那几道门
（cov / 矮行）一道都拦不住：1600《南非之行》一口气多出九段"歌词"，还触发 `fillLeadingVerses`
把第 1 段抄满前面六行（前六谱行各自莫名其妙地有了 10 段）。尺子用**前面几行的行距**
（`rowPitch`，相邻谱行上缘之差的中位数）：同一首里每条歌词带装的段数一样多，末带不会比别的带更宽，
故照「假想的下一谱行上缘」给它封顶，口径与中间各带完全一致。
**不留余量**——正文的头一行离末段词只有三个多字高，放宽一成就又漏进来了。
试过而否掉的三条判据：按**字号**（正文 25~30 vs 歌词 36）会误杀真的第 2 段——「世上所有的民族」
「主祢真伟大」的第 2 段词本就比第 1 段小一截（24 vs 17、29 vs 22）；按**与音符的对位率**
（歌词 ≥0.95、正文 0.38~0.75）同样误杀那些第 2 段（0.57~0.6）；按**行距**更是分不开
（正文首行距末段 3.3 个字高，而「世上」第 2 段距第 1 段 3.8 个字高）。位置是唯一干净的那条线。

**谱后单独排版的附段歌词**（`stanzas.ts`）：有的歌本谱下只配第 1 段，第 2…N 段印在谱子后面，
自成诗行、不跟音符对齐（圣徒诗歌 11《仰看穹苍浩大无穷》：段号「二」「三」各领四行）。上面那道封顶
正好把它们挡在歌词带外，而且本来也不该进歌词带：诗行没有 x 可对。另走一路：从末谱行歌词的下缘到图底
整片交给 DBNet（`recognizeRegion`，同页眉），逐行识别；整行只有段号的（「二」「2.」）或带分隔符领起
正文的（「2.夕阳…」，裸「一面运行」的「一」不算）开新段，没段号就按空行断开。每段按谱下歌词同一套规则
拆音节（收尾标点贴前字、开引号领起后字），再照**第 1 段的音位骨架**逐个填进去——第 1 段有字的音依次是
各段的起字音位，melisma 的分布照抄第 1 段。
- **判据只有一条：每段音节数等于第 1 段音位数**（容 ±2，OCR 多读漏读一两个字照填，截尾或末尾留空）。
  有一段差得多，整块都当正文丢掉——1600《南非之行》那种背景介绍是散文，字数碰不上。
  11 这首三段都是 64 个音节，逐字对上。
- 要排在 `jianpu.ts` 的「digit=0 复原」「隐含 tie 补检」之前：两者都看音符有没有词。
- DBNet 会漏掉单个的段号字（11 的「二」没检出、「三」检出了），所以段号只用来断段，不靠它编段号；
  段序按块里的先后，接在谱下已有的段后面。
- 收下的诗行存进 `RecognizedScore.stanzaRegions`，识别模式按原位整行叠加。

**附点休止**（`0.`）：「休止 0 不接附点」那条一刀切会把真的附点休止一起抹掉（714 第 4、7 谱行
各一处 `0. 5`）。加一条例外：**右侧同一小节里还有音符**的休止，那个点是真附点；噪点误判都出在
小节末／行末的尾随休止右侧（终止线碎块）。

**短弧的扁平度**：弧的 `w/h` 下限从 2 放到 1.8——跨度只有一个字号的短弧拱得相对更高，
714 第 1 行 `1̇ (5̇ 3̇)` 那条实测 38×20 = 1.9，卡在 2 上被整条漏掉。数字块是「高而窄」
（w/h≈0.67）、减时线与增时线又都不在上方带里，放宽不会把它们放进来。

**标题里的出处编号**：标题右边常印着「《旷》108」这类「选自哪本诗集第几首」的标记，
det 会把它并进标题行。按 `《…》数字$` 从标题尾巴上剥掉（曲名本身不会这么收尾）。

**八度点的三道位置判据**（`buildJpNums`）：尺寸与居中之外，还要看**点自己排得对不对**。
① **竖排叠放**：第二、三个点摞在前一个的正上/正下方——同一条竖线上、彼此紧挨着（间距不过一个
点径）。只按「落在窗口内」计数，音符上方**并排**的两个墨块就被数成双高八度（17《不失足》首音
头顶那个「羔」字的碎笔，`3.` 成了 `3̈.`）。故由近及远逐个验位，第一个不合就断。
② **左右无同高邻块**（`hasSideMate`）：八度点在数字正上/正下方孤零零一个；字的碎笔是一排挨着的。
但邻块**必须不居中于任何音符**才算碎笔——密排十六分音符的八度点彼此也会挨到 0.7 字号以内
（基督更美实测），那些邻块各自正对着一个音符，漏掉这条会连真点一起剔（那首音符 100→94.2）。
③ **`inkBelow` 的窗口只探紧挨着点下方的那一小条**（0.18 字号，原为 0.3）：这条门本是防「歌词字
顶笔画被当低音点」的，字顶笔画与字身其余笔画之间几乎不留空（1~3px），而真低音点到下一行歌词
字顶还有半个点径。窗口开到 0.3 字号就够到歌词了——17 第 2 行 `7̣ 5̣` 的低音点即因此被剔，
而同一首第 4 行的却留住了，只因那行歌词排得略低：一条判据两种结果，正说明窗口过宽。

**临时升降号**（`accidental.ts::accidentalOf`，页眉调号那个 ♭ 也用它，见下）：♯/♭/♮ 印在音符的**左上角、紧贴着**，比数字矮一截也窄一截
（17《不失足》实测记号 10×17、同行数字 15×24，间隙 1px，记号顶比数字高 10px）。不摘出音符流
就被当成一个音符送 OCR（♯ 读成 `1`、`0`，第 3 行凭空多出两个音，歌词跟着错位）。
判据的尺子是本行数字的**中位高/宽**，不能用整条带高——记号骑在数字上方，带高被它撑大
（37 vs 24），拿带高作比例右邻的正常数字反倒不达标。**「比数字矮」这一条不能当判据卡死**：
记号与数字孰高孰低随书而异，2152《就是不一样》第 5 行的 ♯ 是 14×38、本行数字中位才 12×32
（反倒高出一截），按「≤0.85 字高」一卡整个被挡在外面，那个 ♯ 就当成音符读成了休止 `0`。
高度只挡明显更高的（>1.25 字高），真正稳的是**宽度**（记号一律比数字窄）加上形状判据。形状分类：♯ 两条竖笔上下贯通、四象限
都有墨（实测四格 0.38~0.55、右上/右下 0.93~1.18）；♭ 只有左边一条竖笔贯通全高、肚子鼓在右下，
判据是**右上明显比右下空**（`rt < rb*0.62`）**且左下与右下一般满**（`lb ≥ rb*0.7`）；
**♮ 的两条竖笔一高一低——左竖在上半、右竖在下半**，判据是**左右两半墨迹的重心差**
（`rc − lc > 0.18`）。♭ 的第二条不能省：♮ 同样右上空（0.52），分开二者的正是左竖的下半截
（♭ 到底 0.63、♮ 只在上半 0.29）；而右上/右下的门要放到 0.62 才收得住小号的 ♭——页眉调号里那个
上标 ♭ 只有 11×16，紧包围盒里肚子占了大半、越过中线（227《施比受更为有福》实测
lt .81 rt .38 lb .63 rb .68，原先 0.45 的门把它判成了 ♯）。♮ 早先写作「左上空 + 右下空」的四象限判据，
方向正好反了（8《心持两意的人》第 1 行实测左上 0.43 / 右下 0.61 才是有墨的那两格，四格判据把它
读成 ♯）；中间那两条横笔一压，四格比例本就不干净，而它们左右各占一半、对重心差相互抵消。
记号挂在**右邻**那个音符上（`JpNum.accidental`），谱面上的 ♯ 是相对**调内音**的升降，
按简谱规矩**在小节内延续**到同数字的后续音符。各路都只照原样写印出来的记号（延续出来的谱面上并没有再印）：
模型那路记 `Degree.accidental`，延续交给 `model/jianpu.ts::AccidentalCarry`（导出 MusicXML 时由它算 `<alter>`）；
.jpwabc 与文本谱那路延续交给 `jppitch.ts::applyJpPitch`（那边本来就有这套状态）。

**分行（`groupRows`）要先用大块定行、小块随后挂靠**：变音记号这类块比数字矮、又骑在数字的
左上角，中心比数字高小半格。一轮贪心是按 y 中心自上而下走的，小块会先跟头顶的弧帽结成一行，
等数字来时那行的中位数已经偏高、进不去；那一行没有小节线穿过，随后被「乐谱行才送 OCR」的
判据整行滤掉，记号就此消失（8《心持两意的人》第 1 行的 ♮ 与三个弧帽结成 y=154 那行、数字行在
179，差 25 > 0.7 字号）。故分两轮：**够大的块**（高 ≥0.7 字号 = 真数字）先贪心定下各行的中位数，
再把小块挂到中心**最近**的那一行（不是第一个够近的），挂不上的才互相聚成行。

**「一个音 + 终止线」的末行要单独救**：分行后本来一刀切掉数字少于 3 个的行（歌词碎笔、标题与
页脚里的竖笔都靠它挡住），但 2157《在这希望的田野上》末行就是 `1 - - -‖`——整行只有一个数字
（减时线是 hline，不进数字核），连带下面那行歌词「望！」一起丢。救回的门开三条、缺一不可：
① 位置在所有**正经谱行**（有小节线穿过的那些）之下——不能拿 `rowMeta` 里的歌词行/页脚当界，
页脚在末行下方一大截，拿它比末行永远进不来；② 带着**两条**并排的终止线（普通小节线只有一条）；
③ 那两条与正经谱行的小节线一般高（中位高的 0.6，与行内相对判据同一口径）。实测放宽任何一条
都会在别的曲子上凑出假谱行：只卡「有高竖线」时，世上/南非的标题带被凑成一行，标题识别归零。

**谱行的小节线要跟全谱一般高**（`withBars`）：只要「有一条贯穿本行的高竖线」就算谱行，页眉里的
经文出处也能凑出一条——1123《施比受更为有福》的「♩=103」与「（徒20：35）」被 `groupRows` 并成
一行，那个全角左括号（10×41）恰好过了小节线判据，整行被当谱行读成 `1--0#3|20..350`；更糟的是
它顶在第一谱行前面，页眉 ROI 的下界跟着上移，速度记号一并丢了。真小节线在**全谱**是同一高度
（18 首实测每条谱行的线都落在全谱中位高的 0.96~1.04），伪线一概 ≤0.82（本首的括号 0.73、和弦行
的竖笔 0.45~0.55），故按全谱中位高设 **0.85** 的门。中位数按**每条线一票**算而不是每行一票：
真谱行每行贡献三五条、伪行只有一两条，中位数稳落在真线上，与伪行多寡无关。末行救回来的那些
（上一条，终止线本就矮一截）豁免。回归：18 首 `measure-all` 全档逐首一字不变。

**休止占比滤伪行，有增时线的行放宽**：和弦字母行被读成一串 0，靠「休止占比 <0.5」剔掉（真谱行 ≤18%、伪行 ≥79%）。
1780《主快来》/1773 末行 `6 – 0 0 ‖` 休止占 2/3，整行被删。有增时线的行放宽到 0.8：增时线要在数字右侧、与数字
纵向重叠且居中，1697 标题行、1717 一行歌词这类伪行实测一条都没有。**终止线不能当凭据**：汉字几道竖笔并排
就够得上 `finalBarline`（上面两个伪行都被标上了），拿它放行，两首各多一行、1697 连页眉都丢了。

**增时线顶着小节线**（`splitBarDash`，归类之前）：行末 `6 –|` 的 '-' 右端碰到小节线，粘成一块「⊣」
（1771《你曾向主许下》23×42、字号 30），小节线与横线两道判据都进不去，落进数字通道读成 `0`。这一行随之
没了行末小节线、与下一行连成一片；数字带还被它撑到 42px，同行数字 rec 补高后两个 7 都读成了 1（紧框读 7）。
判据：高 0.85~2、宽 0.4~1.2 字号的块，一侧边缘是贯穿全高（≥0.9 块高）、宽 ≤max(3, 0.15 字号) 的竖笔，擦掉后剩下的
恰是一条处在块中部（中心在 0.3~0.7 块高）、实心（填充 ≥0.8）的细横条（高 ≤max(3, 0.32 字号)、宽 ≥0.3 字号），
拆成小节线 + 横线。数字 1 的竖笔虽在边缘，剩下的旗在顶上，卡在「中部」那道。

**小节线顶上粘着表情记号**（`splitBarCap`，紧接 `splitBarDash`）：1775《十字架的路上》「渐慢rit」的「渐」印得低，
左半笔画压在下一小节开头那根小节线顶上，成了一块 30×82（字号 33），小节线判据进不去，两小节并成一个；
`untangleBridged` 要竖笔贯穿 ≥0.8 块高，这根只占七成，也不认。判据：高 1.8~4、宽 ≤1.5 字号的块，**只看本块自己的
像素**（矩形里混着右边那个 6 和它的减时线，在矩形里重做连通域取铺满矩形的那一块），从块底往上逐行，每行只有
一段宽 ≤max(3, 0.15 字号)、与最底行左右差 ≤1px 的墨，连续 ≥1.2 字号；再往上剩下的墨高 ≥0.4 字号。拆成小节线 +
上面那块。数字的竖笔不到 1.2 字号，挨不上。

**波音**（上波音 ∿，`JpNum.ornament`）：音符正上方一小段**两个尖峰的锯齿**（2152《就是不一样》
第 5、8 行）。与它同区的还有圆滑线弧帽与延长记号，三者都是「音符上方一块扁而宽的墨」，靠两条分开：
**宽度**——波音只有一个字宽（实测 29px ≈ 0.9 字号），圆滑线至少跨两个音（81~143px）；**形状**——
弧是凸的、顶点在正中间，波音正中间是两峰之间的**谷**。形状判据取每列最高墨点连成上缘线，
先找出「与最高点齐平」的那些列，要求**首尾两列拉得开**（≥0.35 块宽，弧的顶点都挤在一处），
再要求这两列之间有个**谷**（≥0.3 块高）。只比「正中间几列 vs 全块最高点」不够——波音的峰宽，
中间那几列会踩在第二个峰的上升沿上（实测差 2px、门槛 3px，正好漏掉）。

**下波音**（中间穿一道竖杠，`ornament = "lower-mordent"`）：迦南诗选 1775《十字架的路上》实测 29×21（字号 32），
竖杠穿出锯齿上下，宽高比只有 1.38、高度也超了上波音两档。另开一档（宽 0.6~1.4、高 0.4~0.9 字号、宽高比 ≥1.1）：
块中部 [0.3, 0.7] 宽内要有一道**最长竖直墨段 ≥0.85 块高**的连续列（宽 ≤max(3, 0.12 字号)，两道分开的不算），
擦掉它（两侧各让一列毛边）再对剩下的锯齿照大档判谷。原先它被 `splitOrnamentDot` 从底部切出一个「八度点」
（竖杠下端）——「肠，」的 `2` 读成 `2̇`、「路，」的 `6̣` 高低点相消成 `6`；认出来后落在它包围盒里的点一并摘掉。
→ `notations.ornaments: ["mordent"]`（123 `!xby!`）、文本谱 `&xby`。

**owner 的纵向间隙量到正下方最近的那样东西**：数字，或数字头上居中的高八度点（数字上方 0.6 字号内）。
1765《主啊，求你回来吧》`2̇` 上的波音离点 4px、离数字 21px（字号 33），按数字顶量卡在 0.5 字号上，两处全漏。

**弧尾粘着小号波音**：1771《你曾向主许下》`3⌒2̃` 的弧收尾处与波音 8-连通成 49×9 一块，两档都进不去。
对弧形块（宽 ≥0.7 字号、扁）两端各取 0.45 字号宽的窗口，照小号档判锯齿；弧块本身不动，照旧交给 `detectSlurs`。
光凭上缘线不够——弧顶一个像素的毛边就能在窗口里凑出 2px 的「谷」（1790《这条路》`2⌒1`）。加一道**笔画厚度**：
窗口里至少 1/4 的列墨厚 ≥max(1.5 倍弧笔画, 笔画 + 2)。实测纯弧端各列 ≤4px（笔画 3~4），粘着波音的窗口有 5~6 列
达 6~9px。试过「两峰外侧都要再落下」：波音靠弧那一侧直接并进弧身、落不下来，1771 第 3 行 `6̃⌒5` 会丢。

**小号波音另开一档**：迦南诗选的波音小得多——1677《祷告》16×9px、字号 48（0.33 × 0.19 字号），过不了
0.6 字号的宽度门，尺寸又正落在 classify 的「小点」档，被 `buildJpNums` 收成高八度点（`6̃` 读成 `6̇`）。
加一档「宽 0.25~0.6、高 0.12~0.3 字号」，形状判据（宽高比 ≥1.6、两峰夹谷）照用：真八度点是圆的、上缘
只有一个峰，两道都过不了。宽度封顶 0.6 字号，挡住「八度点粘着弧端」那种又宽又扁的块。认出来的块要从

**谷深在小号档按像素量**：1727《主为我》的波音只有 13×7px（字号 30），上缘线

**倚音**（`JpNum.grace`）：主音符左上角的小号数字，**底下压着一两条与它同宽的减时线**，再由
一小段弧连到主音符（2156《祢为我解读一生的道路》第 7 行的 `4 ³5`）。那个小数字比数字带矮一号、
中心又高出大半个字（实测 cy 差 42px > `groupRows` 的 0.7 字号），挂不上任何谱行，自成一「行」后
被「行里得有三个数字」滤掉——整个倚音连同减时线一起没了。判据四条：
- **只认挂不上任何带的块**。挂上了带的就是那条带的正经音符：和弦字母行、歌词行也各自成带
  （要等 OCR 完才按休止占比剔掉），不设这道门，上一带行末那个带减时线的音符会被下一带认领成
  倚音（为基督/因有主同在/主祢真伟大各因此丢掉一个真音符）。
- **底边贴着数字带的顶**（±0.25/0.5 字高）。倚音只是印得高一点，并没有离开这一行；只卡上界的话，
  上一谱行行末那个音符正好落进窗口。
- **底下压着减时线**——三连音的小 `3` 底下是括线、变音记号底下什么都没有，靠这一条分开。
  条数按**逐行扫墨**数（`graceDivLines`：块底往下 0.6 字高内，一行里有没有一段与它同宽的横墨，
  连着的算一条），**不数连通块**：第二条常与那道连到主音符的弧连成一块（2152 末行实测 15×11），
  按「扁而宽」的块判据一卡就只数得出一条，倚音的时值差一倍。
- 右边紧跟着一个正常字号的数字 = 它修饰的主音符。

候选**从 `comps` 里取，不能只看 `allCores`**：倚音的 `1` 只有一条细竖笔（2152 末行实测宽 8），
够不着 `classify` 里数字块「宽 ≥0.3 字号」的门槛，压根没进数字通道。也正因为扫的是原始连通块，
尺寸那两道门要一起卡宽和高（比数字矮一号、也比它窄），否则圆滑线的弧帽就混进来了。

八度点**只认上面那个**：连到主音符的那道小弧挂在减时线下方，断成的碎块（实测 15×11）与八度点
（13×14）一般大、也几乎正对着小数字（中心只偏 6px），认下面那个点等于给每个倚音都记上一个
低八度。低八度的倚音因此少一个点（有损）。输出：主音符之前一个 `grace` Chord（123 `{5}`，
不占拍位；导出 MusicXML `<grace slash="yes"/>`）；文本谱写成音符后的引号备注 `"yy:…"`（两家都认这个写法）。
**文本谱里减时线要少写一条**——倚音的基准时值是八分（`parse.ts::scanGraceNotes` 按 8 起算），
谱面上那条八分的减时线不写，故 `div-1`：图上两条 → `"yy:3/"`。

**延长记号（fermata 𝄐）**：音符头顶一段小弧、弧下扣一个点。整块只有半个字号宽，够不着
`detectSlurs` 的圆滑线判据（那里要求宽 ≥0.8 字号），弧本身常连归类都轮不上；而弧下那个点正落在
八度点的窗口里，于是 16《爱心的功课》末行的 `5·6̂ 7̂` 读成了 `5. 6̇ 7̇`（高了一个八度）。判据：
宽薄小弧（0.5~1.3 字号宽、扁平）+ 正下方居中的一个小点 + 再下方紧跟着数字；点随即从 `dots` 里
摘掉，不再参与八度判定。→ `notations.fermata`（123 `!fermata!`）、文本谱 `&yc`、.jpwabc `{YanYin}`。

**顿音（▼）**（`JpNum.articulation`）：音符正上方一个**实心倒三角**（1640《主要在中国掌权》整首
每音一个，实测 12×14px、字号 32）。它的尺寸恰好落在 `classify` 的「小点」档里，**本来就躺在
`c.dots` 里**，随时会被 `buildJpNums` 收成高八度点，故认出来后要跟 fermata 的点一样从 `dots` 里摘掉。
与真八度点靠**形状**分：三角逐行墨宽从满宽单调收到一个尖（顶行 ≥0.8 块宽、底行 ≤0.4 块宽、中途
不许变宽，容 1px 毛刺），圆点上下一样宽；再加填充率兜一道（三角 ≈0.5、圆点 ≈0.8，取 0.4~0.75）。
**离数字比八度点远得多**（实测 0.7 字号，八度点是紧贴），故 owner 的搜索窗放到 1 个字号。

（▼）**：简谱里数字正上方的圆点已经是高八度点，再用 `articStaccatoAbove` 画顿音两者分不开。
37 张实拍图里只有这一首命中，没有误检。

**整页简体里的孤立繁体字按候选改判**（2026-09-20，`src/omr/hanvariant.ts` + `lyrics.ts::simplifyStrayTraditional`）：
PP-OCR 的字典繁简同收，字形只差一角的一对常读错边——76《天上有粮》十来行歌词里只有「别」被读成
「別」（而同一页的署名「詞曲：巧兒」倒真是繁体，所以**只按歌词区统计、页眉不参与**）。两条判据叠起来：
- **孤立**：整页歌词至多 2 个繁体字，且简体字数 ≥ 繁体的 10 倍（繁体谱面整页都是繁体，碰不到）；
- **简体形必须在该字的 OCR 候选里**——新增 `OcrBackend.rankTextChars`，走 `inferLogits` 那条整张
  `[T,C]` 的路（`rankDigits` 同款；常规识别在原生侧就把 logits 压成了索引，拿不到次优），按与
  `recognizeCharsPosMany` 相同的 run 划分逐字取 top5。只对含孤立繁体的那一两条重跑，代价可忽略。
- 繁简表**必须用 opencc 的 `from:"t"`（纯字形），不能用 `from:"tw"`**：后者连台湾用词一起归一，
  「么」会被当繁体改成「幺」，《再次将我更新》的「人算什么」就这么被改坏过——而且模型候选里恰好
  有字形相近的「幺」，第二条判据挡不住。踩过一次，表头写死了这条。
- 收益：76 歌词 99.1 → 100，1776《在天上我有一位阿爸》99.4 → 100（另一处同类误判），其余 36 首一字不变。

**减时线的连断（文本谱的 `~` / `^`）**：一条减时线连到哪儿，本项目的排版端是按**拍组**算的
（`pu/layout.ts::beatGroups`，认拍号，复拍子三个八分一组），不写记号也排得对；但**诗歌本 app
那边要照谱本的写法把记号写出来**，故 `topu.ts` 照它的范式生成。两种情形：

- **复拍子**（分母 8、分子是 3 的倍数：3/8 6/8 9/8 12/8），一组 = 三个八分 = 1.5 个四分拍：
  **组界**上，两个音符若按 `floor(绝对拍位)` 落在同一整拍里（不写就会连着）写 `^`——9/8 的
  第二个组界在 2.5→3.0，本来就跨了整拍，那里不写；**组内**以组首为原点，每跨一个四分拍写
  一个 `~`（即每组第三个八分之前）。一小节九个八分因此写成 `1/1/~1/^2/2/~2/3/3/~3/`，
  6/8 写成 `1/1/~1/^2/2/~2/`。拍号取页眉那个、曲中由 `timeChange` 改写，跨行接着算。
  《8 心持两意的人》（9/8，`5/4#/5/ 1 2/ 3.`）就靠组内那个 `~` 把 `5 #4 5` 连成一条。
- **切分音**（非复拍子）：小节里音符从非整拍起、又跨过整拍线之后拍位整个错开，读谱的一方
  最容易在「减时线层数变了」的那个交界上连错——那里写 `^` 强制断开。714《我说算了吧》全曲
  恰好两处这样的切分（`2g/ 2g` 与 `7/ 7` 领起的两小节），与人工订的谱面完全对上。先试过
  「凡跨整拍都写」，全曲写出五处、多了三处；也试过按**源图**判两音符的第一层减时线是不是
  同一条横块——分不开：实测同组内两段横线的间隙 10px、该断开处 15px，几何上没有界。

**诗歌本方言的排版细节**（`topu.ts`，都是照实际谱本的写法来的）：曲行**紧排**（`Q:3/5/|"p:5/4"6-…`，
音符与小节线之间不加空格）、头部与各组之间**不空行**；跨行小节的续行开头**什么都不写**
（换行不断小节，读回来自然接上；`|/` 是隐藏小节线，不是跨行记号，写了行首反倒多一条小节线）；收弧的 `)` 紧跟音符**本体**，
附点写在括号外（`(1.1).` 而不是 `(1.1.)`，增时线本来就在括号之后）。番茄那边一概照旧。

**诗歌本的房号**（同上，2026-09-16 按谱本写法订）：`[]` 前后**都不留空格**（紧排；番茄那边 `[` 前
那一个空格必须留——紧贴音符的 `[` 在番茄里是倚音语法）；收口的 `]` 写在小节线**后面**
（`…2-:|]`，故 `topu.ts` 攒 `pendingVoltaClose`、等下一条线落笔时再补，行末开口收尾才就地写）；
`[` 落在**行首**时先补一条虚拟小节线 `|/`（行首没有线可倚，谱本拿虚拟线把房号左端立住——
这是「跨行小节续行不补 `|/`」那条的唯一例外）。回归 `omr-pu-check.mjs`（《沧海一声笑》《爱是不保留》
两首带房号）两方言均通过。

**装饰记号下的八度点**（`splitOrnamentDot`）：波音 ∿、涟音这类记号画在音符正上方，常与那个音的
高八度点 4-连通粘成一块——块进了数字通道，又因远离数字带被 `groupRows` 丢掉，点也跟着没了
（1600 末小节的 `2̇` 掉了一个八度）。故对**没进任何谱行**的块，自下而上找一段窄行（宽 ≤0.5 字号
= 点宽）、其上紧接着明显更宽（≥0.7 字号）的记号主体，墨宽突变处切开，把圆点交回 `cls.dots`，
八度归属仍走 buildJpNums 原有那套（居中于数字、间隙 <0.8 字号）。记号本身模型里没处放，照旧丢弃。

**隐含 tie 补检**（`jianpu.ts`，在歌词识别之后）：**无歌词的音符若与前一个音同音高，就是延音**。
简谱里同音延续本该画连音线，但**跨谱行的弧原图上就没有**（画不出来），行内的淡弧也可能漏检。
有歌词的音是新音节、不算延音；纯器乐行（前奏/间奏，整行无词）缺"有无歌词"这条线索，跳过以免把
重复音连成一片。实测补上「主祢真伟大」副歌跨行的 `1'_|1'`（两次副歌的行结构因此完全对称）、
「从前所珍爱」漏检的一条 → slur/tie 档 80→100%，平均 97.1→**99.6%**。
**衬词行按「有词率」判，不是 `some()`**：「啦 …… 啦 …… 」这种一行二十来个音只印四个「啦」
（其余是省略号、不成字），有词率两成——和器乐行一样没有线索，却因为"有那么几个字"过了 `some()`
这道门，行里凡是重复音都被连成延音（沧海一声笑末行 `1_ 1-` 凭空多一条 tie）。改成有词率 <0.4 即
视同无词行。
**圆滑线里面不补**：一字多音的 slur 罩着的同音重复是重新发音，不是延音。1782《祝福新人》`2⌒3 3⌒2` 外面再套一条
大弧，两个 3 之间没字，被连成延音。前一音收弧、后一音起弧，或两音都在一条还没闭合的 slur 里（按顺序累计
起止条数），都跳过。

**长弧**（`slur.ts`）：弧高上限 1.05 字号只够跨相邻两音；跨多音的长弧拱得更高（`5__|5---|5` 的 tie
实测 w205 h28、numH22）会被整条漏掉。故 w>3 字号时上限放到 1.6 字号，但**高过 1.05 字号的块另要求
w/h≥4**——弧越长越扁（7.3），段落方框（"Chorus" 带框 w98 h36）接近方正（2.7）被挡在外。

**多连音（三连音 ⌒3⌒）**（`slur.ts::tupletCandidates`，`JpNum.tuplet`）：音符上方一条**中间断开的
弧**，缺口里嵌着一个小号数字。1《以色列的圣者》实测（numH 36）：左弧 54×23、数字 19×21、右弧 54×23，
三块紧挨着排在数字带上方 0.6 字号处，弧的墨占比只有 0.16（细线）、数字是 0.56（实心笔画）。
判据：① 小号数字块（高 0.35~0.8 字号、宽高比 0.4~1.3、墨占比 ≥0.35，整块在数字带上方）；
② 左右各有一段细弧（与数字纵向重叠、墨占比 ≤0.4、宽 ≥0.6 字号、横向缝隙 ≤0.6 字号）。**两侧都要有**
——手头只有这一种谱面写法，别的形状（直括线、光秃秃一个 3）不照着猜。「几连」靠 OCR 读那个小号数字，
且**读出的数要与括线罩住的音符个数对上**才采信：这一条同时当误检的兜底，凑巧的三块墨很难恰好
又是个数字、又与音符数吻合（37 张实拍图里只在这一首命中两处，无误检）。
**必须先于 `detectSlurs` 认**：括线的两半自己就够得着圆滑线的判据（54/23=2.35 ≥1.8、高也够矮），
眼下只因各自单独罩不住两个音才没变成假 slur——认出多连音后把这两块从 slur 的输入里摘掉，别留隐患。
输出：模型里组内每个音都带 `duration.timeMod`、首尾一条 `tuplet` Mark（123 `(3:`），时值记名义值，
导出 MusicXML 时由 `xmlproject.ts` 按比例缩 duration、`<type>` 不动；文本谱写 `(y…)`，`topu.ts` 的拍位计算也跟着缩，
否则本小节后面的音全被算成跨拍、`~`/`^` 乱写。时值单位 48 一拍（=16×3）：三连音每音 2/3 拍，16 时算出 10.67，
round 完一小节凑不满（3×11≠32）。文本谱的 `(y…)` 与圆滑线的 `(` 同用一套括号，解析端按**队列**（先开先闭）配对，
故多连音的 `(y` 写在圆滑线 `(` 之前、`)` 也先收；两者真交错嵌套时这套写法表达不了，手头没有那样的谱面。

**嵌套的双弧**（`slur.ts::splitNestedArcs`）：两条弧共用一个端点时（外弧罩三个音、内弧只罩后两个），
内弧的收尾一截与外弧交叠、被连通域粘成同一个块，包围盒只剩外弧那一条，内弧整条被吞
（「2146 奉献的心志在燃烧」第 1 行 `2 3 2` 就是这么一对）。拆法是**逐列数竖向墨段**：单条弧每列
只有一段，两条弧交叠的那段 x 里每列有上下两段（内弧跨得窄、拱得低，必在下面），取下面那一段
拼出内弧的包围盒。内弧在交点处**并进**外弧（两段的竖向间隙缩到笔画粗细内）而非在空中断掉时，
说明余下那截与外弧重合、真正的端点在外弧那一头 → 该侧延到母块边缘（否则覆盖不到末音，
实测差 4.5px 就少一条弧）。

四道门挡住假拆（缺一不可，实测「主祢真伟大」「我说算了吧」共误加 10 条）：下面那一段要
①几乎每列都在（≥80%）且相邻列不跳变（>3px 即弃）——断续的多半是破损横线凑出来的假象；
②笔画细（≤0.3 字号）；③有拱高（顶边高低差 ≥0.15 字号）——减时线/增时线/三连音括线一路平着走；
④双段区间的**某一头两段合拢**——两条弧本是一个连通块、必在某处相交，交点不在两头就说明
它粘的是别的东西。

**一块里套着几条内弧**：1782《祝福新人》`2 3 3 2` 一条外弧罩四音，左右各一条内弧（`2⌒3`、`3⌒2`）分别并进外弧
两头，三条弧一个块。双段列按「中间单段列连着超过两列」切成几个区间，每个区间各认一条。长度门看**延伸之后**的
内弧（≥0.8 字号），原始区间只要 ≥max(6, 0.25 字号)：1777《福音传到你那里》`2 3 3` 的内弧 `3⌒3` 双段只有 25 列
（字号 35），并进外弧右端后实为 51px；1782 两条内弧双段只有 18、11 列。拱高门对短区间放宽成
max(3, min(0.15 字号, 0.3 × 区间长))（1782 右内弧 11 列、起伏 5px），直线仍一路平着过不了。

**两条内弧首尾相接**：1863《至暂至轻的苦楚算什么》四处 `5 3 3--` 型——外弧罩三音，底下 `5⌒3`（圆滑）与
`3⌒3`（延音）左右各并进外弧一头、在中间那个音上脚碰脚。双段区间一路连通，下面那一段是 M 形，当成一条
内弧就与母块同宽被「≥0.95 母块宽」那道门丢掉。整段认不出时按下面那一段的**尖谷**切开再各认一条：谷点取
区间中部（两头各让 25%）顶边最低处，比左右两侧各自的拱顶都低出 max(3, 0.15 字号) 才算交脚（1850 第 3 行左内弧左脚并进外弧、露出的只有一截，
谷只比拱顶低 6px / 字号 33，0.2 过不了；单条弧的最低处必在区间一头，中部取不出两侧都更高的谷）。中间那个音既收
`5⌒3` 又起 `3⌒3`，123 写作 `((5_ (3_) 3--))`——按 ABC §4.11 `(c d (e) f g a)` 的意思读，见
[源格式-123](../模块/源格式-123.md)；`j123/parse.ts` 原先让 `)` 收栈顶（即本音符上刚起的那条），读成了单音弧，已改。

**交脚与弧脚压着高八度点**：1850《最难的事主已做成》`6 1̇ 1̇` 同样三条弧，两条内弧的交脚正压在第一个 1̇ 的点上、
外弧与右内弧的右脚一起落在第二个 1̇ 的点上，两个点与三条弧 8-连通成一块，全曲七处 1̇ 丢了八度，内弧也拆不开。
`splitArcEndDots` 只从两头往里找（中间那个够不着），右端那个又过不了「点比弧低」（外弧左脚比点还低 1px）。
另加 `splitArcInnerDots`（探针同名）：逐列量**最低那一段墨**——弧线与交脚只有笔画粗细（1863 交脚 2~4px），点那几列
是实心一整段（1850 点 7×6、笔画 3px）。连续几列厚过 max(1.8 倍笔画, 0.15 字号)、宽 0.12~0.45 字号，这几列最低那段的
框够圆（宽高比 0.5~1.7）、够实（墨占比 ≥0.6）、两侧 0.3 字号内的列最低墨点都不比它低，才另收成一个点；弧块原样保留。
块本身得**拱起来**（上缘两头比最高处低 ≥0.3 字号）：减时线下沿挂低八度点的块也宽而扁，上缘是平的，不设这道
1801 的 `7̣` 就被切出一个重复的点、高低相消。点挖不出弧块，`splitNestedArcs` 数竖向墨段时就把弧包围盒里的小点
（≤0.45 字号见方的块）**遮掉**不算，否则点那一坨让「下面那一段」又厚又跳、整块拆不开。
顺带 1801 那三处溶进弧脚的点补回两处（音符 98.6→99.5）。

**汉字的底部部件不是弧**：上一行歌词挨着本行时，「想」字底下的「心」是独立的扁弯块（1790《这条路》29×13、
字号 36），正落在本行弧带里罩住两个 6，凭空一条 tie；「架」字底部同样凑出过一条 `(2 3)`。它矮于 0.4 字号，
`flatBottomShare` 不查。真弧**正上方是空的**，汉字部件头上紧贴着同一个字的其余部分：候选正上方有一块字号大小
（高 ≥0.5 字号）、近方形（宽 < 1.8 高，拱得高的长外弧扁而宽，不算）的墨，横向罩住它一半以上、底边压到或贴近
（0.2 字号内）它的顶，就剔掉。模型侧 `JpNum.slurStart/slurStop` 因此改成**条数**（末音要同时收两条），
一路到模型里两条收在同一音符上的 `slur` Mark（123 的 `))`）、文本谱的 `))`、`.jpwabc` 的 `(2_ (3__ 2__))`；
编辑器 `Chord.slurEnds` 同样是计数，配对由 `ParserTemp.pairSlur` 栈式做（后开先闭）。

**副标题**（`header.ts`）：标题正下方那行小字（多是曲名英译，"The spirit of devotion is burning"）。
判据是**贴着标题、与标题居中对齐、字号不大于标题**：页眉 ROI 里还有第一谱行的和弦（`Am`、`G/D`
一个个也居中），靠「离标题比离首谱行近」把它们挡开（另有和弦文法兜底）；印在两侧的调号与
出版方（迦南诗选每页的「迦南诗歌」）离标题中心远，天然不入选。→ `Work.subtitles`
（123 第二条 `T:`）、文本谱的第二条 `B:`/`T:`；**`.jpwabc` 的 `.Title` 段没有这个字段**
（既定，不扩语法），那一路会丢——`jpscore.ts` 因此显式跳过 subtitle 类 credit，否则英译会被
当成作者印进 `WordsByAndMusicBy`。det 把一行切成两块的写法（「主祢真伟大」的
"How Awesome / You Are" 分居标题两侧）目前不认。

**空格的 advance 别信 `getComputedTextLength()`**（`common/measure.ts`）：SVG `<text>` 里
**整串都是空白时它恒返回 0**（浏览器把纯空白的文本节点当空的，加 `xml:space="preserve"` 也一样），
而 `compressRun` 是**逐字**量 advance 的（字体没有 chws 之类特性时走它），于是空格宽度为 0——
`Z:John Laudon 词曲` 排出来是 `JohnLaudon词曲`。canvas 的 `measureText` 对空白是准的，
整串空白时拿它兜底。识别侧把空格补对了，排版端不跟上就白补。

**整句英文的词间空格按真实空白列补**（`header.ts::recoverSpacesByInk`，著作者行也走这条）：
PP-OCR 的 rec 不吐空格，早先那套「按 CTC 帧位算字距」在整句上不够用——帧位是等宽量化的，
一句话里词内间隙和词间空白常同量级（实测出 "T he spirit"、"It's justdifferent"）。改成在源图上
查本行的空白列：把空白段按宽度排序、在**跳变最大处**切开定界（另要求 ≥0.12×行高，
防整行只有一个词时把字母间隙切成空格），落在界以上的空白**两侧都是字母**才插空格
（撇号两边的白也很宽，但 "It's" 不能拆）。迦南诗选 5 首带英文副标题的实测全对。

**中文的段落方框词**（`chordline.ts` 的 `CN_SECTION_RE`：`副歌`/`前奏`/`间奏`…）要与英文的
Chorus/Intro 一视同仁地先剥掉，再判是不是注记行。1《以色列的圣者》第 2 谱行上方的和弦行末尾就印着
一个方框「副歌」，`isAnnotationLine` 的「含汉字即真歌词」一条卡在它上面 → 整行 8 个和弦全丢，还给
上一谱行多出一条伪 verse（`C2:Em/D//B m//A/Bm Esus E副歌`）。只收方框里印的那几个词：真歌词行
除了这几个字还有别的汉字，剥完仍判为歌词，故不会误伤。

**段落标记**（Intro/Verse/Chorus/Coda 方框）：与和弦同处歌词带，被 cov 过滤当注记丢弃——但它标出了
段落起点，对乐句排版有用。故被丢弃的短行（≤5 格）也送 rec（`Chunk.mark`，只提词不参与歌词装配），
在任何块的 rec 原文里用 `SECTION_MARK_RE` 就地捞词（Chorus 常与和弦同块）。落位：方框印在**下一谱行**
音符上方 → 归到该行、标记 x 所在**小节的首音**（`JpNum.sectionMark`）→ `Chord.sectionWord`（123 `"^Chorus"`）。
以前经 MusicXML `<direction><words>` 转手，读回 123 时整个丢了。
### 六首新语料挑出来的七条（1801/1806/1811/1812、92/95）

迦南诗选四首 + 爱主颂两首（小图、厚印的老本子）一次性暴露的七处，根因互不相干，各立了一首 GT 看护。

**① 贯穿整页的墨不算小节线。** 1801《活水的江河》那张图最右一列（x=1399）整列全黑——扫描时蹭上的
页边，1977/1977 个像素。它又细又高，过了 `classify` 的「细高竖条」判据进了 barlines；而 `buildRowMeta`
分小节用的是**行内相对门**（`h ≥ 0.6 × 本行最高的那根`），最高的那根成了 1977，于是**全曲每一行的真
小节线（h48、字号 31）一根不剩**，每行只剩那条边框。两处各加一道高度上限：`classify` 里 `h ≤ 4 字号`
（真线实测 1.5~2.2 字号：1801 是 48/31=1.55，基督更美 118/55=2.15），`buildRowMeta` 的贯穿候选
另按行高卡 `h ≤ 4 × 行高`。被挡下的边框列成了未归类块留在 comps 里，下游哪条通道都够不着
（弧要 w ≥ 0.7 字号、波音 ≥0.25 字号、歌词带要 w ≥ 0.4 字宽、拍号补位池要 h < 0.55 字号），不必另清。

**② 谱行必须自上而下单调有序。** `groupRows` 二轮把挂不上任何行的小块聚成「孤儿行」**push 在数组尾部**，
行序就此断了。下游一律按下标取相邻行——歌词带的下界取 `staff[i+1]` 的上缘（`lyrics.ts`），段落标记/和弦挂
`staff[rowIdx+1]`，跳转记号按 `staff[rowIdx±1]` 就近归行。95《灵同胞》末谱行（y1460）的「下一行」成了
y380 的碎块行，歌词带算出 `yBot < yTop`、整条带直接 `continue`，**末行歌词一个字都没挂上**。
`groupRows` 返回前按行 y 排序即可。

**③④ 伪行的几何剔除**（在 `buildJpNums`/OCR 之前，免得污染 `medBarH`、`staffY` 与歌词带）：
- **扁块行**：数字一律高瘦，行内多数核却是「扁而矮」（w ≥ 1.5h 且 h < 0.7 字号）的 → 歌词汉字的底部
  笔画被当成了数字块。95 实测 46×19、49×19（字号 32），两行凑在歌词行下沿，OCR 读成 `0 2 7` / `1 0 7`
  混进曲末（用户看到的是「结尾多出一堆音符」）。
- **贴着谱行的装饰碎块行**：核少（<4）又紧挨在另一条像样谱行上缘 1.2 字号以内的 → 那一行的弧帽/八度点
  碎块自成一「行」。1801 实测 15×22、58×24、15×21，topY 1432 距下方谱行 1461 只 0.94 字号，读成 `2. 0. 5`。
  真谱行之间隔着一整条歌词带，挨不了这么近。

**⑤ 谱后正文/边注要「截行」，不能整行丢。** 伪行判据原本按休止占比一刀切。1811《心愿》末谱行
（y1760~1815）与右侧那段注记正文的首行（y1778~1805）同高，`groupRows` 并成一行，注记汉字全读成休止
→ 占比 0.8 → **整行连歌词「处处是春天」一起没了**。改成先截后判：行内**连续 ≥5 个读作 0 的核**当正文剔掉
（真休止零星出现，相邻总隔着音符或小节线，连不成串），剔完剩 ≥3 个音符且占比过门就留下。
**截行只对第一条正经谱行以下的行开**——页眉那条带（曲号 + 标题汉字）是同一个形，截完剩下的曲号数字
足以冒充一条谱行，第一谱行位置上移、页眉 ROI 被吃掉，1697《温州的水 温州的山》的标题/曲号/词曲/调号
会一起归零（实测过）。

**⑥ 波音只罩一个音。** `mordent.big` 档误收「跨两音的短弧」：92《麦子若生了虫》第 1/4 行那两条实测
42×18（字号 31），宽高比、谷深都与波音重合——同一行另外三条同形弧（41×18~19）只差一两像素的谷就分到了
另一边，**光靠形状分不开**。补一条位置判据：块的 x 跨度内除 owner 外不得有第二个音符中心（间隔 ≥0.5 字号）。
波音印在单音头上，圆滑线至少跨两个音。小号档/下波音/弧尾档窄得多（≤0.6 字号），罩不到第二个音，不加这道。
真阳由 2152《就是不一样》看着（第 5、8 行 `2` 头上各一个大号波音，收紧后两个都还在）；假阳由 92 看着。

**⑦ 延长记号得是拱形。** `fermata.arc` 这一路原先只卡「宽而扁」（`fermata.cap` 那一路反倒有弧脚判据）。
1812《在世不属世》末音 `1'` 头上那道**斜直短笔**（22×6，字号 32）条条都过，把正下方的高八度点
（7×6，间隙 8px＝0.25 字号，正卡在门上）当成延长记号的点吃掉，`1'` 读成了 `1`。补一条：上缘两端都要比
最高点低 ≥0.12 字号（口径同 `capOk`）。斜笔一头到一头单调下降，过不了；那道笔本身照旧不识别（宁可留空不编造）。

顺带两条同批挑出来的：

- **剥线带留下的毛边不是第二条减时线**（`stripUnderline` 的 extraLine 分支）：1811 末音那根增时线 24×7、
  统计线粗 5，被剥成「6px 的线 + 1px 的线」两条，`stackedHline` 判成双减时线 → 增时线整根不算数、末小节少一拍。
  补一条厚度下限 `≥ max(2, 线粗/2)`——真的第二条线不会细过统计线粗的一半（1776 那两条同粗）。
- **又短又粗的增时线**（`classify` 的细长条通道）：比值从 3 放到 2.6。92 第 2 行行首那根实测 19×7（字号 32，
  比值 2.71），宽度差 0.2px 够不着 0.6 字号那道门，比值又卡在 3 上，整根被丢、那个音少一拍（同一行另外两根
  20px 的就认了出来，可见是卡在噪声上）。近方的碎渣比值多在 1~2，2.6 仍挡得住。
- **弧脚罩住的高八度点**（`splitArcEndDots::asDot`）：宽高比下限从 0.6 放到 0.5。切出来的框里除了点还含着
  弧的一小截尾巴，框被拉高一两像素——1801 第 6/8 行那两个点实测 5×9=0.56，卡在 0.6 上整个丢掉（点自己是 5×7=0.71）。
  同一首第 7/8/10 行还有三个点**整个溶进了弧脚**（`endRun` 连候选都凑不出），`splitArcInnerDots` 补回两处，剩一处仍缺，已写进 GT。

### 跨行圆滑线（`slur.ts::detectSlurs`）

一条弧跨过换行时谱面上画成两半：上一行行末一段拖到右界，下一行行首一段从左界起笔。两半各自都罩得住音符，
按行内判据会各自闭合成一条弧，**跨行那条就丢了**——1806《因着耶稣我最富有》末行 `6 5 6` 上那条本是倒数第二行
`6̣.1̇` 接下来的，识别成了 `((6 5 6-))` 两条同罩三音的弧。两头的形是可分的：

| | 判据 | 1806 实测 |
|---|---|---|
| 上一行的**开口弧** | 右端顶到本行右界（末条小节线/终止线）之内 0.3 字号 | 1333 对 1334.5；行内正常收尾的弧离右界还差一个音（同首 1278 / 1066 / 1051） |
| 下一行的**收口弧** | 左端起在首音**左缘之前** | 66 对 68；行内起弧的那条从首音**质心**附近起笔（同行另一条弧的左脚在 80，首音质心 81） |

两条都满足才配对：`slurStart` 记在上一行那个起音，`slurStop` 记在下一行收口弧罩住的末音，两半都不再各自闭合
（`probe("slur.crossRow")`）。**单有一头不算**——同首第 3 行行末那条拖到右界的弧，下一行并没有对应的半弧
（那处是同音延续，交给隐含 tie 兜底）。已认作跨行半弧的整块**不再拆内弧**：续弧与同罩这几个音的行内弧收在
同一只脚上、粘成一个连通块（1806 末行实测 x66~230 一块），`splitNestedArcs` 分不出哪条是续弧的下半截，
拆出来的两条会同起同止、变成一对重复的弧。宁可只记跨行那条——**代价是同块里那条行内弧跟着丢**
（1806 的 GT 里记着它，slur 档因此是 18/19）。

改完 1773《那美好的仗每一天都要打》的 slur 档从 94.1 升到 100（GT 本就记着一条跨行弧，此前少认一条）。

### 整体右偏的圆滑线：歌词裁决（`slur.ts::resolveSlurRefits`）

圣徒诗歌 11《仰看穹苍浩大无穷》这套排版的弧整体右偏半个音：从起音**右缘外**起笔、盖过收音。弧都检出来了，
错在配音——按「质心落在弧跨度内（左右各放宽 0.5 字号）」罩音：

- 两音短弧 `(7̣ 1)`：弧 x1016~1053，7̣ 右缘 1007、质心 998.5，出了容差，只罩到 1，**整条漏掉**（第 1、2 行共 5 条）；
- 三音弧 `(3 4 5)`：弧 x645~721（宽 76 正好是 3→5 两个音距），3 的质心 629.5 出了容差，**认成 `3 (4 5)`**。

另一种读法是按**两端**配：左端对起音质心的偏差 dL、右端对收音质心的偏差 dR，代价取 `|dR−dL| + |dL+dR|/2`
——宽度对不上罚全额，整体偏移只罚一半；单用 `|dL|+|dR|` 时 `(1- 7̣) 5̣` 那条右偏 20px 的弧右端离 5̣ 反而更近，会多罩一音。

但两端法不能直接替换质心法：1677《祷告》行末拖向下一行的半弧 `6̣ (5̣ |` 只罩一音（留给跨行/隐含 tie），
两端法会把前面的 6̣ 拉进来。分开它们靠**歌词**——一字多音的弧，起音有词、其后各音**各段**都没词：

- 两种读法的起止音不同时，detectSlurs 照旧按质心法落弧，把这条记下来；
- 歌词（含谱后附段）落位后，两端法那组是一字多音的形、质心法那组不是，才撤掉旧弧改记新弧（`probe("slur.refitByLyrics")`）。
  `4 5` 起音 4 没词，不成形；1677 那处 6̣、5̣ 各有词，两端法那组不成形，不改。

没配词的谱没有证据，一律不动。全库只有这首命中，slur 档 75 → 100，其余曲目逐项不变。

### 按 y 聚成行的五个阈值（`geom.ts::clusterByY`）

「把墨块按纵向中心聚成一行」这个操作在管线里出现五次。实现只有一份（`omr/geom.ts::clusterByY` /
`findLineByY`），但**容差 tol 一律由调用点传入、不设默认值**——五处语义不同，统一会改识别结果：

| 位置 | tol | 聚的是什么 | 尺子 |
|---|---|---|---|
| `lyrics.ts` S2① | `numH*0.7` | 汉字主体归 verse 行 | numH（音符数字高） |
| `overlay.ts::clusterLyricLines` | `lyrH*0.7` | OCR 文本区域归 verse 行 | lyrH（歌词字高） |
| `header.ts::splitBlocks` | `numH*0.6` | 页眉连通域分行（几何法 fallback） | numH |
| `lyrics.ts` 细横笔补收 | `numH*0.45` | 把「一」这类矮而宽的笔画并入**已有**行 | numH |
| `lyrics.ts` 句末标点补收 | `numH*0.9` | 把坐在基线、中心偏低半字高的标点并入已有行 | numH |

前两个 0.7 是同一判据、只是尺子不同，本就一致。后两个是刻意的**双向偏离**：0.45 严于主体，
因为细横笔没有字高可依、放宽会误挂到相邻 verse 行；0.9 松于主体，因为句末标点中心比本行字心低
约半个字高（实测 dcy 差 ~9~11px），卡在 0.5 边界上时 JPEG 解码的 ±1px 抖动就足以让它时收时漏
（同一图在无头 Edge 收得到、在 tauri WebView 却漏 W1 句号）。这两条**不要统一**。

页眉的 0.6 与主体的 0.7 曾试着并成一个值：14 首夹具下 `measure-all` 全档一字不变。但那个结论是空的
——`splitBlocks` 只在 DBNet 检测返回空时才走，14 首全都走了 det 路径。用 `globalThis.__headerDet=false`
强制走几何法再 A/B，标题/词曲逐首输出**仍然完全相同**。即：现有语料区分不了 0.6 与 0.7，
没有证据支持改动，故**保持 0.6 原样**。

### 和弦符号（`chordline.ts`）

吉他和弦（`Am` / `G/B` / `Gsus4` / `F#m7`）印在谱行音符**上方**，与段落方框同处歌词带。文法判定
（`isAnnotationLine` / `CHORD_TOKEN_RE` / `chordCoverage`，见上）连同切词、归一、落位一并搬进
`src/omr/chordline.ts`；`lyrics.ts` 只调不判。识别到的和弦挂上 `JpNum.chord`，由两路 emitter 输出：
`todoc.ts` → `Chord.harmony` / `Sustain.harmony`（原文，导出 MusicXML 时由 `score/harmonyxml.ts` 解析），`topu.ts` → `"hx:…"`。
**`.jpwabc` 装不下和弦**，jpwabc 那路输出会丢（与力度、渐强渐弱现状一致）——这是有意的，
不为和弦扩 jpwabc 语法。

- **文法（四道闸）**：① **根音必须大写** `[A-G]`——印刷体和弦的根音从来是大写，而小写字母遍地都是，
  `Coda` 的 d/a、`Verse` 的 e 一旦算根音就凭空长出 D、A、E；宁可漏掉 OCR 把 C 读成 c 的那几个。
  ② 切词前把**段落方框词、方括号编者注、跳转记号**（`D.C.`/`D.S.`/`Fine`/`To Coda`）抹成**等长空格**
  （等长才保得住字符下标 → 源图 x）——`D.C.` 的字母恰好都是根音，不抹就切出 D、C 两个和弦。
  注意句点仍是**分隔符**：和弦之间的点多半是 OCR 把字距读成的噪声（`Em F C/E G` → `EmF.C/EG`），
  一律当未覆盖会把整条和弦行判没。③ **调号与拍号也整段等长抹除**（`KEY_METER_RE`：`1=C`/`1＝bE` 与
  `4/4`，连拍号左邻的裸根音一起）——调名本身就是合法根音。旧版只有「记号前面紧跟 `=`」这一条，
  升降号一插就失效（`1=bE` 仍切出 E），`1=` 被 OCR 吞掉或与拍号连读时更是直接切出一个 `C4`
  （「为基督赢得城市」页眉的 `1=C 4/4` 与首行和弦同处上方带）。等号只收 `=＝:：`，短横不算，
  否则 `Am7-D` 会被当成调号抹掉真和弦；拍号只认「数字/数字」，转位低音 `C/E` 两边都是字母碰不到。
  ⑤ 文法只兜得住成形的写法，**残片靠几何拦**：`recognizeHeader` 排在 `recognizeLyrics` **之前**跑，
  把它**已采纳**的字段框（标题/词曲/调号/速度/拍号）当禁区传下去，落在框里的块不产和弦。
  第一谱行的上方带与页眉 ROI 几何上本就重叠，OCR 把 `1=C 4/4` 读成 `-C4`（`1=` 塌成一个短横）时
  文法上它就是个合法的「根音 + 数字」，怎么抹都抹不掉——「为基督赢得城市」那个凭空的 C4 正是如此。
  禁区只用**采纳过**的字段：页眉 det 框里那个真和弦 `Am` 不会被 header 采纳，故不在禁区内。
  ④ **整首和弦数 < 小节数 × 0.4 时整批作废**——真配了和弦的谱子基本上每小节至少一个（14 首实测最稀的
  一首也有 0.56 个/小节）；稀稀拉拉几个多半是页眉/注记误检，漏几个只是少个记号，混进假和弦却会印在
  谱面上误导演奏。
- **谱行上方带**：第 i 行的「下方带」就是第 i+1 行的「上方带」，本是同一条带；唯独第 0 行的上方带
  原先没有任何一条带覆盖（那里的和弦落进页眉 ROI，被 `header.ts` 的 `hanziCount<2` 静默丢掉）。
  故 `recognizeLyrics` 的行循环从 **i=-1** 起，那条带从第 0 行上缘往上量 **numH*3.5**
  （3.5 才够得着「再次将我更新」第一谱行的和弦——它与谱行之间还隔着一排圆滑线，距顶 2.54 个字号；
  一并卷进来的调号/表情记号由上面那四道闸挡掉）。这条带只走和弦通道：
  **不产段落标记、不产跳转记号、不进歌词装配、不参与段号映射**——它本不在旧管线的视野里，让它产出
  别的就等于凭空改动既有行为。两条实测教训：
  - 放它捞段落标记 → 噪声命中 `SECTION_MARK_RE`，给首行安个假段落起点，乐句排版据此硬换行，
    「沧海一声笑」六段词的歌词从 99.4% 掉到 80.8%。
  - **段号映射必须跳过 rowIdx<0**（`verseLabels` 那段）：`rawByKey` 按插入序迭代，上方带的 `-1:0`
    排在最前，不跳过就顶掉真正的 `0:0`（标着 `1.` 的那行）占住 `seen`，整套段号映射随即作废、退回
    「行序即段号」——同一首的 `3.5.` 跳号失效，W5/W6 整体错位（同样是 80.8%，症状与上一条一模一样，
    别只查一处）。
- **和弦与圆滑线同行**：和弦与其下方的弧 deslant-y 只差十几像素，常被并进同一行；弧被列投影切成的
  碎段又矮又碎（w10 h4），把行的中位字高压到几像素，整行随即被「矮行剔除」丢掉（「主祢真伟大」
  九行里有五行的和弦这么没的）。故行内有 **≥2 个正常字高的块**时，单把这些块拎出来送 rec
  （走 `Chunk.mark` 通道，不参与歌词装配）。**不能改为放回 kept**：这类行的内容未必是和弦
  （「世上所有的民族」row3 的弧线行也凑得出 4 个够高的碎块，rec 出来是一串乱码），放回歌词会多出
  一条伪 verse，噪声字落到休止音上触发「有词的 0 必是误判」把休止复原成音，那首音符从 100% 掉下来。
  「够高」的门槛按 **0.5 字高**而非矮行剔除用的 0.6——`charH` 统计自**汉字**，而和弦是拉丁字母，
  天然矮一截（「再次将我更新」汉字 41px、和弦 22px，卡 0.6 一个都不算数）。
- **判定用的整行原文取「一」改判之前的**：改判把弧线碎块读出的 `-`/`1` 一律当成歌词的「一」，
  和弦行上方常有圆滑线，一个凭空的「一」就让整行「含汉字」，和弦行判定当场失效。装配那步照旧用
  改判后的文本，两者分开存。
- **切词前先抹掉段落词与方括号注**（等长空格，保住字符下标）：`Verse` 里的 `e`、`Coda` 里的 `C/d/a`
  都是合法根音，会被贪心吃成 E、C、D、A 四个凭空的和弦。
- **跳转记号优先于块级和弦判定**：`D.C.` 的两个字母恰好都是根音、点算分隔符，覆盖率满分，
  会被切成 D、C 两个和弦（「沧海一声笑」的 D.C. 就这么变出两个）。整行和弦那一支不受此约束——
  那里的 `jumpSpan` 本身才是误检。
- **落位**（`placeChords`）与 `sectionMark` **刻意不同**：段落总从整小节起、要回退到本小节首音；
  和弦不回退，它可落在小节内任意一拍。比较基准取音符**左缘**而非中心（和弦记号左缘对齐所辖音符
  左缘；用中心比会给行首和弦凭空算出 0.35~0.40 的假偏移，密排行里音符半宽就占相邻间距近四成）。
  和弦落在两音符之间时按 x 线性插值出 `JpNum.chordOffset`（本音符时值内的比例 0..1），
  模型那路正落在某条增时线那一拍上就挂增时线，否则就近挂本音符；文本谱 `"hx:"` 挂不住偏移，同样就近挂本音符（有损）。
  同一音符已有和弦时顺延到右邻空位（限一格），但**同名的不顺延**——同一拍点不会连奏两个相同和弦，
  那只是 OCR 跨 rec 块边界把一个记号读了两遍。
- **一个音符可以带多个和弦**（`JpNum.extraChords`，tok + 拍内比例）：长音里逐拍换和弦时，后几个印在
  **增时线上方**（「世上所有的民族」第二行 `1 - - 0` 的第三拍上另有一个 C/G）。判据是 `frac > 0`
  ——记号明明落在本音符时值之内，就不是「字距挤在一起」，顺延给右邻会把它整整挪后一拍。

**调号不写 `1=` 的谱本**（`parseMeta` 最后那条兜底）：旷野人声那本把调号与拍号并排印在**标题

带升降号的那种原本就认得（判据是「升降号紧贴音名」）；**单个音名**没有任何前缀可依，只能靠
**右边紧跟着一个合法的斜杠拍号**定下来：短碎片（去空白 ≤8 字）里 `([A-G])(\d{1,2})/(\d{1,2})`，
分子 1~16、分母 2 的幂。音名前面若是字母就不认——`16bE4/4` 的 E 前面是降号的 b，那种归前一条，
否则会读成 E 调。这条只在前面几条都没认出调号时才走，testdata 19 首的调号/拍号逐首不变；
旷野人声 4 首（7 活水江河 F 6/8、8 心持两意的人 F 9/8、16 ᵇE 4/4、17 ᵇE 4/4）现在全对。
**调号里的升降号读成残字 → 回头看形状**（`repairKeyAccidental`）：`1=♭B` 的 ♭ 印成上标、只有
数字的三分之一大（227《施比受更为有福》实测 11×16），PP-OCR 常读成引号一类的东西——那首读成
`1=″B`，`parseMeta` 的 `[b#♭♯]` 一条都对不上，整个调号落回默认的 C。此时按 det/CTC 给的**逐字位**
找到那个残字位置上的连通块（页眉里 `=` 的两横、音名字母各是独立块，取离它最近的那个即可），
交给 `accidental.ts::accidentalOf` 判 ♯/♭，把残字改写成 `b`/`#` 再解析一遍。**只在 parseMeta
什么都没认出来时兜底**——认出来的（`1=bB`、`1=G`）一概不动，免得给已经对的结论添乱。
按字形而不是按「OCR 会把 ♭ 读成哪几个字」办：同一个残字换本书就换个样，而 ♯/♭ 的形状是死的。

**升降号印在音名右上角的写法**（`E♭ 3/4`、`1=E♭`）：5《我今来就你》页眉左上角印着 `E♭ 3/4`，
det 读成 "Eb3/4"。前缀形（`♭E`）的判据是「升降号紧贴音名**左侧**」，后缀形一条都对不上 → 读成
C 调。两处放开：① `1=` 锚定的形里认后缀（`1\s*[=＝]\s*([A-G])([b#♭♯])`）；② 上面那条「不写
`1=`、靠右邻拍号定位」的兜底允许音名与拍号之间夹一个升降号。**裸后缀形（不带 `1=`、不带拍号）
一律不认**——"Ab"、"Fb" 这类在英文著作者/副标题碎片里遍地都是，一放开就满页误判。

**标题 = 最大字号的中文行，字号差不多（15% 以内）时取更宽的那一行**：det 给的框高只是个近似，
迦南诗选每页右上角都印着「迦南诗歌」，忽而比标题矮（2157：61 vs 77）、忽而比它高（2156：79 vs
68），单看框高 2156 的标题就成了「迦南诗歌」。整行宽度在这里是压倒性的（892 vs 289）——标题是
一整句、出版方只有四个字。

- **锚点一 `=`**：两道扁横（宽 ≥ 2.5×高、高 ≤ 0.25 字号），x 向重叠 ≥ 0.6、上下相距 ≤ 半个字号；**一侧紧挨一个
  读得出 1 的窄块**（宽 ≤ 0.75×高、间隙 ≤ 0.8 字号、`=` 的中线落在它的高度范围内），音名组取另一侧。
  「必须有个 1」挡掉 `二`/`三` 的横笔；`♩=76` 那个 `=` 左边的音符头偶被数字模型读成 1（日光之下），
  右边读出 `76` 不是音名，照样放弃、接着找下一个 `=`。
- **锚点二 拍号**：几何法认出的页眉分数拍号（`geoMeters`），或斜杠式——一块墨集中在右上–左下对角带
  （带外墨 ≤ 带内 15%）、左右半个字号内各有一块同高的数字；音名组取拍号**左侧**紧挨着的块。
- **音名组**（与 `rereadKeyName` 共用 `readKeyGroup`）：1~3 块、块间空当 ≤ 0.6 字高；上标且 `accidentalOf`
  判得出 ♭/♯ 的是升降号，其余并起来送 rec，读出 `[♭♯]?[A-G][♭♯]?` 才采纳（rec 常把 ♭ 与音名连读成 `bE`）。

核对办法：`__keyGlyphProbe` 让每首强制走一遍这条路、只打日志不采纳（`dev/scripts/key-layout.mjs`）。
testdata 26 首里，文本路认得的 25 首单字符路**全部一致**，另读出耶稣普治 D、从前所珍爱 C（原先是默认值碰巧对）。
上线口径只在文本路认不出时才走，measure-all 除耶稣普治调号 0→100 外逐项不变。

**只印一个名字、不带「词/曲」的署名**：迦南诗选每页右上角的「迦南诗歌」与调号同排，位置正是别的歌本印
「作词/作曲」的地方，职能词规则一条都挨不上，原先整行丢掉。判据五条：纯汉字 2~8 字、整行在页面右侧
40% 里、与调号行同一排、**在标题下一排**、本页没认出别的署名；另剔「第X首」。后三条是抽各歌本样张
各两页收紧出来的——第一版只有前两条，「敬拜赞美」「颂赞」「救主耶稣」这类分类标签全被收成署名，
「世上所有的民族」词曲档从 100 掉到 0。分类标签的歌本是「调号 · 标题 · 分类」挤在同一排，迦南诗选是标题
单独占一排、署名在下一排，版式上一分就开。「调号行」det 漏读时（1765 那排 `1=C 4/4` 只读出个 `à`，调号是
`keyByGlyphs` 按字形认的）拿字形法的调号框比同排——所以这段放在调号认完之后，字形法返回的框也连同 `1=` 一起给
（原先只框音名 `C`，11×13，拿来比同排太悬）。

det 漏检时退回**连通域几何法**(大/小字分层 + `splitBlocks` 按 x 间隙切区 + `mergeStackedColumns` 把粗体复杂字
如 督/赢 上下裂块竖向并回整字)。实测 5 首测试曲标题 100%、词曲 99.0%（det A/B 对几何法只赢不输：日光之下
词曲 100 vs 几何 92.9；几何法标题曾因 督/赢 裂块丢字、按大间隙切半只剩"得城市"）。
**后缀式著作者**（`creditSuffixRe`）：中文谱很常见把职能写在名字**后面**、不带冒号——「盛晓玫 词曲」
「卢永亨词曲」「黄霑作词、作曲」。只认前缀式时这 4 首词曲整档 0 分。判据是整行恰好等于
「人名(2~4 字，可顿号并列) + 职能词组」。两处易错：
① 名字组要**非贪婪** + 职能组锚 `$`，否则「卢永亨词曲」的「词」被名字吃掉、只剩「曲」→ `作曲：卢永亨词`；
② 职能词之间的分隔符要**可选**，「词曲」是连写的，强求分隔符则职能组只吃得下一个字、又被名字回溯吞掉。
另要求**不是最大字号行**，免得短标题被当著作者、连标题一起丢掉。改后 14 首词曲 71.4→**100%**。
回归 `node scripts/measure-all.mjs` 的「标题」「词曲」两档。

**后缀式一律照谱面原样输出**，不再归一成 `<职能>：<名字>`：谱面怎么印就怎么写、不调换次序
（`盛晓玫 词曲`、`黄霑作词、作曲`）。前缀式（`作词：叶薇心`）本就是原序，不动。**GT 的口径同步
改过来**（`testdata/简谱/{脚步,爱是不保留,沧海一声笑,立定心志}` 的 `WordsByAndMusicBy`），
否则「词曲」档会从 100% 掉到 80.6%。

**名字与职能之间的那道空当要回源图量**（`gapWideAt`）：rec 从不吐空格，而这道空当**有的谱面有、
有的没有**——脚步印的是「盛晓玫 词曲」，沧海一声笑印的是「黄 霑作词、作曲」（空当在名字里，
名字与职能之间反倒没有）。一律补或一律不补都错，故按墨列量：本行空白段宽度的中位数的 1.6 倍
以上算一道真空当。这也正是「John Laudon 词曲」那个空格的来源。

**后缀式的名字也可能是英文名**（1《以色列的圣者》的「John Laudon 词曲」）：上面那条正则的名字组
只收汉字，整行落进"非著作者行"、词曲整档为空。另走一条——先按**行尾的职能词组**切开，剩下的
前半必须是**以字母打头的拉丁名**（另收数字与括号，`Felice de Giardini (1769) 曲` 这类带生卒/
出版年份的写法很常见；纯数字符号的碎块因此仍进不来），再补回词间空格。名字里但凡有一个汉字
就不走这条，与中文名那条互不重叠。实拍 37 张里另捞回 3 条（`Reginald Heber(1826) 词`、
`John B.Dykes(1861) 曲`、`Felice de Giardini(1769) 曲`）。

**词间空格一律按源图空白列补**（`recoverSpacesByInk`）：著作者行从前走的是「按 CTC 帧位算字距」
那条（`recoverLatinSpaces`，已删），帧位等宽量化的毛病在这里同样致命——`JohnLaudon` 的字母间隙
就有 1 个基元与 2 个基元两档，而门是「>1.5 倍中位」，中位恰是 1 个基元时 2 个基元的那些全过，
读成 `Joh n La ud on`。改走空白列后，同一批语料里的 `B.E.W arren`→`B.E.Warren`、
`G eistlich e K irchen gesan g(1623)`→`Geistliche Kirchengesang(1623)` 一并修好。
**定界只在字母↔字母的空白上算**：括号、连字符旁边的白又宽又不成比例（"Assisi (1182- 1226)"），
算进来最大跳变就落在那处 outlier 上、门被抬到词间空白之上，整行一个空格都插不出来
（15《赞美真神》的作词行）。

## 节奏音符 X

迦南诗选 1717《不怕劳累 不怕饥寒》每小节末印着一个 `X`（有声无音高，6 处）。rec 其实读得很干净，
整格就是一个 "X"；错在后面两层：`recognizeDigits` 只收 `[0-7]`，读不出数字一律给 0；
这个「0」底下又对着歌词（到、是），于是被「有词的 0 必是误判」那条复原成候选里首个非零数，6 处全成了 `3`。

- 识别端记作 `JpNum.digit = RHYTHM_DIGIT`（9，同文本谱 AST 里番茄 `9` 的口径）。取 9 而不另开布尔字段：
  各处「`digit !== 0` 即实音」的判断（伪行休止占比、休止复原、附点清零、弧端点）照旧成立，不用逐处补。
- **只有谱行音符那一路开 `{ rhythm: true }`**。拍号、倚音、连音数字、房号都复用 `recognizeDigits`，
  其中拍号的合法值里有 9（`9/8`），不能让 X 混进去。
- 只认**整格就是** `X`/`x`/`Ｘ`/`×`，不认夹在别的字里的 x。
- 同音判断要排除它：隐含 tie 补检、`slur.ts` 的 tie/slur 分流、`todoc.ts` 的 tie 配对——两个 X 挨着不是延音。
- 输出：模型 `Chord.rhythm`（123 `X`，导出 MusicXML 时 `model/toxml.ts` 写 `<unpitched>` + `<notehead>slash</notehead>`，
  `fromxml.ts` 读回 `Chord.rhythm`）；文本谱按方言写 `rhythmToken`（诗歌本 `X`、番茄 `9`）。

## 混合拍与曲中转拍号

《714 我说算了吧》（偶遇的清泉）这类混合拍谱有两处要认：页眉并排印着的一串拍号
（`4/4 3/4 5/4 混合拍`），与谱行**当中**印着的转拍号（小节线右边的 `3/4`）。

**谱行里的转拍号（`jianpu.ts::meterCandidates`）**：判据只用几何——一条与数字同宽量级的短横块，
正上方与正下方各紧贴一个数字格（x 居中、间隙 < 0.55 字号，且分子分母都不宽于分数线的 1.5 倍），
数值再由 OCR 定、按 `validMeter` 校验，读出来不合法就当误判、把两个数字格放回音符流。
增时线 `-` 与减时线也是短横块，但前者上下没有紧贴的数字，后者上方是数字、下方是歌词
（歌词不在 cores 里），三者分得开。

**为什么非摘不可**：不摘出去有两害——① 分子分母被当成两个音符混进音流；② 分子在数字带上方、
分母在下方，**整行的 y 跨度被撑到两倍**（该行 76px vs 常规 35px），于是贯穿本行的小节线过不了
「覆盖 70% 行高」那道判据（实测线高 53 差 0.2px），`withBars` 把整行滤掉——**那一行的音符连同
歌词一起消失**，而丢掉的歌词带又被上一行当成第二、三段词收走（识别结果凭空多出 W3）。
一处没摘干净的转拍号，赔进去的是一整行加两段假歌词。

**落位**：转拍号归到纵向范围罩住它的谱行（`StaffRow.meters`，留 bbox 供识别模式原位叠加），
值同时锚到**其右侧第一个音符**上（`JpNum.timeChange`）——谱面上转拍号总印在小节线右边、
新小节的头一个音符之前。本行右侧没有音符了就锚到下一行的头一个音符。

**页眉的多拍号（`header.ts::parseMixedMeters`）**：DBNet 是按**行**切的，一整排分子连着调号读成
一行（`1=D435`）、一整排分母连着说明文字读成下一行（`444混合拍`）。故从分子行取**末尾**的连续
数字、分母行取**开头**的连续数字，个数相等才认，再按逐字 cx 就近配对（没有字位时按序配）。
**不能按行距卡这两行**：det 给的两个框上下重叠得厉害（实测中心只差 18px、不到四分之一个字高），
按「分母在分子下一排至少 0.3 字高」一卡就永远认不出——改判「框顶更低 + 中心更低」。
分母行数字后面剩下的短文字（`^[^\d]{1,5}拍$`）收作 `meterNote`。

**几何法读出的页眉拍号优先**：det 按行切，`1=C 3/4 4/4` 这种调号与拍号挨得紧的页眉会被切成
一整块（2156 实测读成 `1=Cz` 加孤零零一个 `4`），分子分母根本对不上，`parseMixedMeters` 无从
下手、只落下一个 4/4。而 `meterCandidates` 那套判据（一条短分数线、上下各紧贴一个数字）在页眉上
同样成立，两个拍号都干净地读了出来——它们落在第一谱行上方、归不进任何谱行，`recognizeJianpu`
收起来当 `geoMeters` 传进 `recognizeHeader`。只在**几何法数出来的不比 det 少**时接管：det 那路认得斜杠式
与调号同块的写法，几何法对它们不触发，仍归 det（714 那首三个拍号连着说明文字，两路都是三个，读数一致）。

**个数打平也归几何法**：迦南诗选 1773/1784 竖排 `4/4` 被读成 2/4。rec 没认错，是 det 的框只套住了上面那个 4
的中下截——整片页眉（1400×268）要缩到 960 边长再检测，20×26 的数字缩到 14×18，概率图上只剩一小团，
小框的 unclip 外扩又与面积成正比、扩不回整字（给出 {155,195,14,14}，字实为 {153,187,20,26}）。换个区域送 det
两个 4 都完整。几何法按连通块紧框逐个读，读出的是 4/4，但原来只在「数出来的更多」时接管，1 对 1 打平就用了 det。
38 张（全部 GT + 迦南诗选 10 张）加探针实测：几何法认出的竖排拍号**无一读错**；两路不一致的只有这两首，都是
几何法对。修 det 本身（框贴合连通块、调大缩放上限）也试过：贴合在 38 张上页眉逐字不变，但既然几何法在竖排上
可靠就不动 det；调大上限不可取——1280 时调号与拍号整个没了，1440 时曲号框又变窄。

**页眉拍号的分数线要从「小点」池里也捞**（`jianpu.ts`）：`meterCandidates` 原本只在 `hlines` 里找
分数线，而拍号那道线**与数字同宽、比减时线短得多**（《天不蓝了》实测 19px / numH 48），过不了
`classify` 里横线的宽度门、落进了「小点」那一类 —— 页眉的 `6/4` 一个都认不出来，整曲退回默认 4/4，
24 个小节每个都对不上拍。故把「扁而短的小块」（`w ≥ 0.3 字号 && w ≥ 2.5h`）也放进候选池：
`meterCandidates` 要求正上、正下各紧贴一个数字，八度点/附点凑不齐这两条，不会误判；
认下后要同时从 `hlines` 与 `dots` 两个池子里摘掉。

**贴着弧线端点的高八度点**（只在干净谱面上，`isCleanPage`）：1697《温州的水 温州的山》一房 `1̇⌒6`、二房
`1̇ 2̇⌒1̇ 1̇⌒6⌒6` 的 4 个高八度点全丢，是三件事叠在一起：
- **点与弧粘成一块**（`splitArcEndDots`，归类之前做）：弧线笔画 2~3px，点那几列是实心的 6~9px。从块的两端
  往里数「≥1.6 倍笔画」的列，其中要有列厚过 max(2.2 倍笔画, 0.15 字号)，宽 0.12~0.4 字号，切出来的块要圆
  （宽高比 0.6~1.7）且底边低于弧的其余部分（点挂在弧脚上）。原块换成「去掉点的弧」加「点」——只往点池里
  加不行，整块弧的底边就是点的底边，下一条会把点剔掉。量点范围不能直接用门槛：点左右边缘的列墨少
  （实测 `6,8,8,9,8,8,5`），会从第一列就断掉。厚列门槛原为 2.5 倍笔画：1780《主快来》「头」`1̇⌒7` 的点 8×7、
  弧笔画 3px，最厚处 7 差半像素够不着 7.5，1 丢了高八度；降到 2.2。
- **「弧脚碎片」判据在干净页上不开**：它是照翻拍件断开的弧脚定的（基督更美），干净页的弧不会断，只会误伤
  ——`2̇⌒1̇` 右端的点被垂到点高度的弧脚判成碎片；二房第一个 `1̇` 的点被房号括线判成碎片（括线宽扁，过得了
  弧候选的门，左端竖钩垂到点旁）。
- **干净页上八度点要实心**（包围盒填充率 ≥0.6，高低音点都判）：房号「2.」在识别用的二值图里糊成一块（9×8px，
  笔画泡粗、「2」与「.」连着），正摞在 `1̇` 的点上方，被数成第二个点。几种判法在各歌本样张上的实测对比：

  | 判法 | 房号「2.」 | 翻拍件上的真点 |
  |---|---|---|
  | 总像素数 vs 本页中位数 | 37 / 48 = 0.77，挡不住 | —— |
  | 实心面积（腐蚀一次）vs 中位数 | 4 / 27，挡得住 | 《感谢》等 5 页误剔 15 个真点（小点腐蚀完不剩几个像素） |
  | 填充率，不分页 | 0.51，挡得住 | 十来页误剔（翻拍件的点边缘发毛，《感谢》真点 0.39~0.59），含有 GT 的《南非之行》《不失足》 |
  | 大小 + 填充率双重（都不达标才剔） | 挡得住 | 《感谢》仍误剔 2 个 |
  | **填充率，只在干净页** | 挡得住 | 不涉及；样张上只有改对的变化 |

- **两个八度点要大小相近**（`stackCount`）：同一个音的双点是同一字模印的，包围盒面积、实心面积（点够大时）都不能
  差出一倍。《称颂主名》`1̇` 头上圆滑线的弧脚被数成第二个点（`1̈`），这条挡掉了。不分页，抽检无误伤。

三条都加开关在各歌本样张上对比过：输出只有 1697 这一页变了。

**延长记号：从点出发的补充判据**：原判据要求「点居中于弧块之下」，弧与别的弧粘成一块时就对不上——1697 末音
`6⌒6̂` 的延长记号弧脚与前面圆滑线的尾巴连着，整块 59px，中心偏到左边。补充一路：数字正上方一个小点（≤0.3 字号），
点正上方 0.35 字号内贴着墨（弧顶）；从弧顶沿着上缘往两边走到弧脚——列里有墨、且上缘没比走过的最低点重新抬起
1px 以上就继续（抬起说明接上了别的弧）——两脚离点心 0.15~0.45 字号、都比弧顶低 0.12 字号以上。长圆滑线一走就
出了半个字号。不分页；样张上触发两处，都是真延长记号（另一处是《你当预备迎见神》，原先读成高音点 `6̇`）。
「上缘没抬起」要和**走过的最低点**比，不能和上一列比：上缘每列只抬 1px，逐列比永远触发不了。

回归统计（`measure-all.mjs`）加了「延长 / 延长GT / 延长识」「波音 / 波音GT / 波音识」两组：逐音符记有无该记号，
小节线、增时线作对齐锚，口径同附点那一组（`gt123.mjs::decoFlags`）。

**MusicXML → 123 丢波音**（`abcfamily/emit.ts`）：MusicXML 读进来的波音、颤音挂在 `notations.ornaments`
（`inverted-mordent`），123 写出端原先只写 `articulations`，识别核对那条路上 1677《祷告》的两个波音就这么没了。
按 `xmlproject.ts::ORNAMENT_TAG` 反查写回简谱来源的同名记号（`!sby!` / `!xby!` / `!cy!`），对不上的写原名。
（识别现在直出模型、不再经 MusicXML，但波音同样记在 `notations.ornaments`，走的还是这一条。）

**分子分母从「没归类的小块」里补位**：拍号数字比音符小一号，高度正卡在 `classify` 数字块门槛
（0.5 字号）上下。1717《不怕劳累 不怕饥寒》页眉 `3/4 4/4 5/4` 三个分母 18/17/18px、numH 36、门是 18——
中间那个 4 差 1px 没归进任何一类，4/4 就丢了。没归类、高 0.35~0.55 字号的小块放进 `spare` 池，
`meterCandidates` 只许它当**一头**：另一头必须是正经数字格，且两头高度相差不过两成。

**同一碎片里并排写着几个斜杠式拍号**（`header.ts::parseInlineMeters`）：`1=A 3/4 4/4 混合拍` 被 det
读成一块 `1=A3/44/4混合拍`，`parseMixedMeters`（分子分母分两行）无从下手，而 `parseTime` 的单个
`(\d{1,2})/(\d{1,2})` 正则会把分母读成 `44`、判为非法拍号后**整行放弃** → 退回默认 4/4
（《主是》《祷告》全曲小节都对不上）。`parseMeterRun` 专解这种连写串：分母**优先取一位**，
取一位后剩下的必须仍是「数字+斜杠」开头或正好取完，否则才取两位——`3/44/4` → 3/4 + 4/4、
`6/16` → 6/16，两种都解得开。只在「一串里不止一个拍号」时接管，单个拍号仍归 `parseTime`。

**三条输出路各写各的**：

| 路径 | 页眉 | 曲中转拍号 |
|---|---|---|
| 模型 / 123 | `Song.time` 取第一个拍号，其余记 `Song.extraTimes`、说明文字记 `Song.timeNote`（123 一并写进 `M:3/4 4/4 混合拍`，见 [123格式](../格式/123格式.md) §3） | 该小节 `Measure.attrs.time`（123 行内 `[M:3/4]`） |
| `.jpwabc` | `KeyAndMeters` 只写得下一个 | 曲中写 `3/4`（`TimeSig`） |
| 文本谱 | 番茄 `P: 4/4 3/4 5/4`、诗歌本 `1=D4/4 3/4 5/4 混合拍`（两家头部都写得下多个） | 小节线后的引号备注 `"p:3/4"`（`parse.ts::interpretQuoted` → `BarlineElement.temporaryMeter`） |

**说明文字（「混合拍」）**：几何法读出并排拍号时（det 那路没凑出拍号 → 也没给 `meterNote`），
说明另从 det 文本里取。1727《主为我》印的是 `1=C 3/4 4/4 混合拍 ♩=75`，det 读成一块
`1=c4混合拍J=75`——「X拍」后面还跟着速度，原先那条 `$` 收尾的正则一条都对不上，
故容一段速度标记（`[♩♪J]?=\d{1,3}`）再收尾。

文本谱那一路的临时拍号由**该小节的左侧小节线**带出来；行首那一小节没有左侧小节线可挂
（换行处图上本就没线），只好丢——挂到下一根线上会整整错开一小节，凭空补一根线又会多出一个空小节。

## 输出格式：123 / 番茄简谱 / 诗歌本文本谱

识别产物 `RecognizedScore`（`types.ts`）是**格式无关**的那一份，留在 `App._recogScore` 里；
换格式的下拉只重走 emitter，**不重跑识别**（实测识别 ~3s，换格式 ~0.1s）。
下拉长在**代码区标题栏**、有识别产物时顶掉那儿的格式标签（`#recog-format-field`）——切的本来
就是代码区这份文本是什么格式，摆在工具条上离得远、还得另加一条「核对」标签解释。
选择存在 `jpeditor-render-settings` 的 `omrFormat`，下次识别沿用。两个 emitter 并列：

| 格式 | 路径 |
|---|---|
| `123`（默认） | `todoc.ts::recognizedToDoc` → `emit123` → `App.importOmrDoc`（点选映射由 `omrmeta.ts` 按 123 源区间生成） |
| `tomato` / `shige` | `topu.ts::toPuText` **直出文本谱原文**，编辑器切到 `docFormat="pu"` |

**为什么文本谱直出、不过模型**：文本谱「一行 `Q:` 就是谱面一行」，而 `rows` 正是源图的行结构，
天然对齐；逐音符的多段歌词 `JpNum.lyrics[verse]` 原样在手；小节线按 `row.barlineXs` 落位，
跨行开口小节也不用像模型那路先合并成一个小节。

**为什么 123 那路不再经 MusicXML 转手**：识别结果本来就是简谱形状（度数、减时线、增时线），
以前 `omr/musicxml.ts` 先拼成 MusicXML、读回后再由 `jianpuproject.ts` 猜回简谱形状——绕一圈丢东西：
附点加增时线（2.5 拍）`<type>` 表达不了、丢半拍；速度、副标题、段落词、歌词段号读回 123 时全丢；
还多出一份与 `model/toxml.ts` 并行的 MusicXML 写出端。改为直出后 25 首回归各档指标逐曲不变，
123 文本只多出上述几类信息。简谱识别从此不产出 MusicXML（要的话就是普通 123 文档的导出）。

**meta 的序号约定**：两个 emitter 都产出 `JpwMeta`，`noteRanges`/`lyricRanges` 一律按
**`flatten(rows[].nums)` 的下标**编号。`app.ts::_rangeOfHit` 因此不必分格式——「原图对照」
的点选定位在三种输出下都能用。

**方言取舍**（都是踩过的）：

- 调号写法**不通用**：番茄 `D:` 两种顺序都收（`bB`/`Bb`），诗歌本的 `1=` 行只认「字母在前」
  （`parseShigeKeyLine` 的 `^([A-Ga-g])([b#$♭♯]?)`）——写成 `1=bB4/4` 会被读成 B 调，
  整首差半音，而**只比数字的回归看不出来**。故 `keyNameOf(fifths, style)` 分两种拼法，
  回归里专门比 `puToScore` 出来的 `fifths`。
- 歌词音节只有「单个汉字」与「纯 ASCII 单词」能裸写，其余一律 `{}` 并字括号裹住：多字
  （粘连误切成「哆啊」）裸写会被拆成两个音节、整行对位错开；英文分音节的连字符（`How-`）
  在歌词行里与增时线同属跳过的记号，裸写会被吞掉（《主祢真伟大》第一段 16 处全丢尾巴）。
- 跳房子的 `[` 前必须留空格——番茄里紧贴音符的 `[` 是倚音语法。
- 段落标记（Intro/副歌…）写在音符**之后**：双引号注释挂的是**前一个**符号，写在前面会挂到
  上一个音符上，行首更是无处可挂被直接丢弃（`orphan-annotation`）。跳转记号 `&fine`/`&dc`
  同理，要紧跟小节线写，挂到音符上会画在音符头顶而不是小节线上。
- 圆滑线与连音线在文本谱里同写作 `(…)`。配对**用队列（先开先闭）不是栈**——`parse.ts` 的
  `)` 就是 `curves.shift()`，照它配才能「写出去什么样、读回来就什么样」；配不上对的整条丢弃，
  端点落在休止符上的（识别错误）两端一起丢，与 `todoc.ts::pairArcs` 同一取向。
- 右侧小节线不当场写、攒到下一小节的左侧再落笔：`:|` 紧接 `|:` 要合成一条 `:|:`，
  分开写会连着画出两道线。
- 歌词行末尾落单的 `}` 会被读成「联合括号」（`parse.ts` 只看行尾字符，不管它是不是并字括号
  的收口），故行末若是并字括号就补一个跳字符隔开。
- 头部字段要保证 `sniffDialect` 判得回本方言（番茄靠 `V:`/`D:`/`P:`，诗歌本靠 `T:`/`1=`），
  否则用户存盘再打开就成了另一种方言。

回归 `node scripts/omr-pu-check.mjs`：15 首 GT 曲目 × 2 方言，逐条断言方言嗅探、诊断（error 级一条不许有，
`orphan-annotation` 等几类 warning 同样不许有）、调号拍号、音符序列（数字/八度/时值/附点/增时线）、
逐段歌词、弧线条数（跨行的只数起头那条）、段落标记个数、无空小节、无两条挨着的小节线、
歌词行不被读成联合括号，以及 `noteRanges` 切出来的子串确是音符 token。
上面每条判据都能被这套断言抓住——退回任一条，对应曲目立刻报错。

## 判据命中探针（回归覆盖分析）

`src/omr/probe.ts::probe(名字)`：各条专门判据命中处计一次数，只在 `globalThis.__omrProbe` 是个对象时记，默认关闭。
私有仓库的 `probe-coverage.mjs` 逐首清零、识别、收计数，得出「GT 曲目 × 判据」矩阵并贪心求最小集合覆盖，
列出「删掉后没有任何判据失去看护」的曲目——只出报告，删不删由人定。**加新判据时顺手埋一个探针**，
否则精简 GT 时看不出哪首是它唯一的看护。探针看不见的东西（歌词 OCR 质量、翻拍件那几条「脏页」分支、
页眉措辞）要人对着各 GT 头部的 `% gt:` 注记与本篇的实测记录再判断一遍。

## 无浏览器管线（Node CLI）

`node scripts/omr-cli.mjs 图片.jpg -f shige` —— 图片进、文本谱出，全程不起浏览器，
给第三方打谱软件当命令行工具用。识别逻辑与网页端**同一份源码**，只换后端。

### 三个注入点

管线本来只有三处碰浏览器 API，各拆出一个注入点，两端各给一个实现：

| 注入点 | 浏览器实现 | Node 实现 | 抽掉的是什么 |
|---|---|---|---|
| `surface.ts` | 无（两端共用） | 同左 | `OffscreenCanvas`：建缓冲、铺白底、缩放贴图、读像素 |
| `runtime.ts` | `runtime.browser.ts`（ort-web/wasm） | `runtime.node.ts`（onnxruntime-node） | 模型/字典从哪来、用什么跑 |
| `decode.ts` | `decode.browser.ts`（createImageBitmap + pdf.js） | `decode.node.ts`（sharp） | 图片/PDF 字节 → RGBA |

装配是副作用式的：网页端 `omr/index.ts` 顶部装浏览器那套，Node 端 `cli/omr.ts` 装 Node 那套。
**`runtime.node.ts` / `decode.node.ts` 绝不能进 `omr/index.ts` 的 import 链**，否则 `fs`、`sharp`
会被拖进网页产物。Tauri 那条原生 OCR（`paddleocr.ts::nativeOcr`，张量经 IPC 交给 Rust `ort`）
不走 `runtime.ts`，是并列的第三个后端。

CLI 不吃 PDF：`decode.node.ts` 没装光栅化器，喂 PDF 直接报错。矢量那一摊
（`vector.ts`/`vectext.ts`/`inventory.ts` + `pdflayout/`）仍只在浏览器与 `cli/index.ts` 那条链上。

### 解码器必须是 sharp，不能图省事用纯 JS

判据里那些尺寸阈值**是在浏览器解码出的像素上标定的**，换一套 IDCT/色度上采样等于把所有
边界样本重掷一次。实测「我今来就你」第 4 谱行首音符（`90,1090,30×31`）右侧的附点块：

| 解码 | 全图连通块 | numH | 附点块 | `numH*0.45=13.95` | 结果 |
|---|---|---|---|---|---|
| 浏览器 / sharp | 314 | 31 | 9×**13** | ✓ | 进 `cls.dots` → 判附点 |
| jpeg-js（纯 JS） | 310 | 31 | 9×**14** | ✗ | 落选，附点丢失 |

jpeg-js 让该块底部多留一行像素（全图墨迹多 798 个，0.16%），越过 `classify()` 判小点的
`w,h <= numH*0.45`；再往下数字块要 `h >= numH*0.55`(17.05)、淡印窄块那条要 `w >= numH*0.3`(9.3，
块宽正好 9)，全部落空 → 整块被丢弃。**注意 numH 两边都是 31，判据没漂，纯粹是输入差了一行像素。**

sharp 走 libvips→libjpeg-turbo，与浏览器同一套解码，实测 18 首**逐像素、逐字符**一致
（`scripts/omr-node-check.mjs`），故不留纯 JS 回退——两套解码器就是两套精度基线。
两种装法都逐像素一致，按分发形态选：`npm i sharp`（原生，~28MB 含 libvips）或
`npm i --cpu=wasm32 sharp`（纯 wasm，~11MB，跨平台一份，**单文件分发只能用这个**，
原生 `.node` 没法被 bundler 内联）。解码 5ms / 9ms，纯 JS 43ms——但那 40ms 只占单首的 3%，
选它不是为速度。

### 重采样两端统一走 `surface.ts`，不再用 drawImage

缩放结果直接就是 rec/det 的输入张量，两端若用不同重采样，识别结果会分叉、精度基线得各维护一套。
故 `blit()` 自己实现：**缩小用面积平均(box)、放大用双线性**，分离式两趟。缩小必须是面积平均——
朴素双线性只采样两点，歌词条常缩到原高 1/3 以下，细笔画会整根丢失。

换掉 `drawImage` 后全量重跑 14 首基线：互有涨跌、无系统性下降（平均八度/小节 +0.1、
歌词\* −0.1，音符与对位平均持平；「16 爱心的功课」音符 96.1→96.6、「耶稣普治」歌词 100→99.5）。

### 线程数按张量形状分派

同一模型同一后端，最优线程数随形状**反转**（M5 实测 ms/次）：

| 输入 | wasm 4线程 | node 1线程 | node 4线程 |
|---|---|---|---|
| rec 歌词条 `[1,3,48,320]` | 25.1 | **8.7** | 16.6 |
| rec 长条 `[1,3,48,2048]` | 139.1 | **53.3** | 76.9 |
| rec 数字批 `[16,3,48,48]` | 61.3 | 63.4 | **38.6** |
| det 整片 `[1,3,960,960]` | 134.6 | 193.1 | **76.4** |

单张小图开多线程反被调度开销吃掉，成批或整片才填得满多核。`runtime.node.ts::pickThreads` 据此
判：`dims[0] > 1`（成批）或元素数 ≥ 1M（det 整片）才用多线程，其余单线程；两个 rec session
按需各建一个。浏览器侧拿不到这个收益——ort-web 的 `numThreads` 是全局 env、模型又是 21MB，
建两份不划算。

### 实测耗时

浏览器（wasm 4 线程）三首合计 8552ms = decode 290(3%) + infer 6189(**72%**) + CTC 7 + 预处理/几何 2066(24%)。
换 Node 原生后同样 18 首平均 **1169ms/首**（浏览器约 2900ms/首），约 2.5×。**推理是大头**，
所以这一步的收益几乎全来自「wasm → 原生」；`ort` crate 与 `onnxruntime-node` 绑的是同一个
ONNX Runtime，为性能改写 Rust 只能再动那 24% 的几何部分，不划算（要重写全部判据并重对基线）。
上 Rust 的理由应该是分发形态（第三方要进程内加载 native 库），不是速度。

### 线程策略随 CPU 反转，别把 M5 的结论当普适

上面那张表和 `pickThreads` 的判据（单张小图走单线程）成立的**前提是单核极强、核少**——
M5 上多线程那点并行赚不回调度开销。换到**单核弱、核多**的机器就反过来了：有 Xeon E5
（2.0~2.4GHz Haswell/Broadwell）服务器上实测 Node 版比同机浏览器 4 线程 wasm **慢 2~3×**，
且差值随曲子变长而放大（5 首里最长的两首差 10.8s / 12.2s，最短的差 4.2s）——正是逐条歌词
rec 全被按在一个弱核上、按歌词条数累积的形状。

故留了出口，三种策略输出**逐字相同**，只影响速度：

| `OMR_THREAD_MODE` / `--thread-mode` | 适用 |
|---|---|
| `auto`（默认） | 按张量形状分派；单核强、核少（Apple M 系）最快 |
| `always` | 一律多线程；**单核弱、核多（Xeon E5 那代）该用这个** |
| `single` | 一律单线程；CPU quota 只有一两核的容器，免线程池自旋空转 |

`OMR_THREADS` / `--threads=N` 定多线程时用几个核（默认 4）。`--profile` 会把实际生效的
`模式/线程数` 一并打出来。**换机器请先用这三种跑一遍对比再定**，别照搬默认值。

### 批量比逐张起进程快得多

模型 21MB、ONNX 图反序列化 + ORT 初始化 + JIT 预热约 **2.4s**（M5 实测，弱 CPU 上更久）。
逐张调用等于每张都付一遍，浏览器版页面常驻只付一次——服务端集成若是「一张图起一次进程」，
这笔固定开销足以把原生推理的优势吃光。CLI 因此支持多图/目录一次跑完：

```bash
node scripts/omr-cli.mjs a.jpg b.jpg 谱子目录/ -o 出目录/
```

或者把 `dist-cli/omr.js` 当库 `import` 进常驻服务（`recognizeImage`），只加载一次模型。

### 命令

```bash
npm run build:cli && node scripts/omr-cli.mjs <图…|目录…> [-f shige|tomato|jpwabc] [-o 出]
                       [--profile] [--thread-mode=auto|always|single] [--threads=N]
npm run build && npm run build:cli && node scripts/omr-node-check.mjs [曲名子串…]
```

后者是 Node 管线的验收依据：同一张图两端各跑一遍，比文本谱原文与结构统计，逐字符必须相同。
模型默认读 `public/redist/ocr/`（env `OMR_MODELS` 可改），线程数 env `OMR_THREADS`。

### 打包分发（`scripts/pack-omr.mjs`）

打成**自包含**分发包：解压即用，不联网、不装依赖，只要目标机有 Node ≥20。
支持交叉打包——在 mac 上就能打出 Linux / Windows 的包。

```bash
npm run build:cli && node scripts/pack-omr.mjs                     # 当前平台
node scripts/pack-omr.mjs --targets=all                            # 全部 5 个
node scripts/pack-omr.mjs --targets=linux-x64,win32-x64            # 挑几个
node scripts/pack-omr.mjs --targets=linux-x64 --libc=musl          # Alpine 那类
node scripts/pack-omr.mjs --targets=win32-x64 --no-slim            # Windows 保留 DirectML
node scripts/pack-omr.mjs --targets=win32-x64 --no-crt             # Windows 不内置 VC++ 运行库
```

脚本本身在 macOS / Linux / Windows 都能跑：外部命令只用 npm（Windows 上要 `npm.cmd`，
execFile 不走 shell 找不到裸 `npm`，Git Bash 里也一样）与 tar，体积统计走 Node 自己遍历
（Windows 没有 `du`）。**打 zip 不用 `zip` 命令**（Windows 没有）：bsdtar 能产 zip，但要显式
`--options zip:compression=deflate`，否则 `-a` 默认 store、85M 的包原样存成 85M；GNU tar 不认
zip 格式，那种环境才回退到 `zip`。

产物 `dist-pkg/jpeditor-omr-<版本>-<os>-<cpu>[-musl].{tar.gz|zip}`（Windows 出 zip），
内含 `omr.js` + 共享 chunk + `omr-cli.mjs`（Windows 另附 `omr-cli.cmd`）+ `models/` + `node_modules/`。

| 目标 | 目录 | 压缩包 |
|---|---|---|
| darwin-arm64 | 96M | 46M |
| linux-x64 | 98M | 50M |
| linux-arm64 | 78M | 43M |
| win32-x64 | 83M（`--no-slim` 123M） | 44M（`--no-slim` 61M） |
| win32-arm64 | 82M（`--no-slim` 127M） | 44M（`--no-slim` 62M） |

**交叉打包靠什么成立**：两个原生依赖都是预编译分发，不在安装时编译——sharp 按平台拆成
`@img/sharp-<os>-<cpu>` 子包（`npm i --os= --cpu= --libc=` 能精确拉到），onnxruntime-node 是
单包内含全平台二进制（装完再裁掉别的平台）。所以不需要目标平台的工具链。**但产物没在目标平台
跑过**，脚本只做静态校验（目标平台的 ORT binding、运行库、sharp 平台包在不在），到目标机上
务必 `omr-cli.mjs <图>` 自检一次。

几处踩过的坑：

- 生成的 `package.json` **不能写 `os`/`cpu` 字段**——npm 会拿它跟宿主比，交叉打包时自己
  `npm install` 到那个目录就先 `EBADPLATFORM` 挂掉。改用自定义的 `target` 字段做记录。
- vite 多入口把 `omr.js` 与 `index.js` 的公共代码拆成了共享 chunk（`lyrics.js`），只拷
  `omr.js` 会 `ERR_MODULE_NOT_FOUND` → 顺着相对 import 递归收全。
- `runtime.node.ts` 找模型**按产物位置解析，不看 cwd**（`import.meta.url` → 同级 `models/`
  → 仓库 `public/redist/ocr`），否则第三方在任意目录跑就找不到模型。
- macOS 的 `libonnxruntime.1.dylib` 与 `libonnxruntime.1.29.0.dylib` 是两个完整副本（各 42MB），
  换硬链接后 tar 存成 hardlink 记录，直接省 42MB。
- Windows 包里除 `onnxruntime.dll` 还有 `DirectML.dll`/`dxcompiler.dll`/`dxil.dll` 共 ~36MB，
  那是 DirectML EP 用的，我们只跑 CPU EP，**默认删掉**（`--no-slim` 保留）。已在 Windows 上
  实测：删后 16 张图全跑通、与 macOS 侧逐字一致。另外 Windows 上 shebang 不起作用，
  故另附 `omr-cli.cmd`。
- `engines` 写 `>=18.17`（sharp 0.35 的下限）：实测 Node 18.20.5 能跑，不必卡 20。
- Windows 的 **VC++ 运行库直接内置在包里**（app-local 部署），用户不必先装 vc_redist——见下一节。

### Windows 包内置 VC++ 运行库（`scripts/vcredist.mjs`）

`onnxruntime.dll` 与 `onnxruntime_binding.node` 动态链接 VC++ 运行库——查导入表，实际要的是
`VCRUNTIME140.dll` / `VCRUNTIME140_1.dll`（arm64 没有 `_1`）/ `MSVCP140.dll` / `MSVCP140_1.dll` /
`MSVCP140_ATOMIC_WAIT.dll`，都不在系统自带的 UCRT（`api-ms-win-crt-*`）里。**sharp 那几个二进制
是静态链接的，不依赖 CRT**（扫描包内所有 PE 得到的结论，不是猜的）。

**静态链接这条路走不通**：那两个文件是 ORT 官方用 `/MD` 编好发到 npm 的预编译产物，要静态就得
自己重编 ONNX Runtime + N-API binding（要 Windows + VS 工具链，还废掉交叉打包）。改走 **app-local
部署**：把 CRT 放到用它的二进制旁边，效果等价，代价约 0.7M（x64 目录 82M→83M，zip 仍 44M）。

- **凭什么能生效**：Node 的 `process.dlopen` 走 libuv 的 `uv_dlopen` →
  `LoadLibraryExW(..., LOAD_WITH_ALTERED_SEARCH_PATH)`，被加载的 `.node`**所在目录**先于系统目录
  参与依赖搜索。包里 `onnxruntime.dll` 本来就是靠这条被 `onnxruntime_binding.node` 找到的。
  注意搜索的是**加载者自己那个目录**，所以脚本是按目录分别算需求、分别放，不是往包根扔一份。
- **DLL 从哪来**：`scripts/vcredist.mjs` 直接从官方 `vc_redist.<arch>.exe` 里抠，**全程纯 Node，
  不依赖 7z / cabextract / bsdtar**（跨平台打包的前提）。vc_redist 是 WiX Burn 自解压 exe：PE
  后面附着一个 CAB，里面 `a0…aN` 中有几个又是 CAB，CRT 以 `msvcp140.dll_amd64` 这种「名字 +
  `_架构`」的形式躺在里面。CAB 用 MSZIP = 分块 raw deflate，块间沿用前一块输出的末 32K 作预置
  字典，`zlib.inflateRawSync` 的 `dictionary` 选项正好对得上；解出的字节与 bsdtar 解同一个 cab
  **逐字节一致**（已对拍 sha256）。下载缓存在 `node_modules/.cache/vcredist/`。
- **拷哪几个是算出来的**：扫包内所有 `.dll`/`.node`/`.exe` 的导入表 → 落在 redist 提供范围内的
  就是需求 → 再对 CRT 自身递归求闭包（`MSVCP140_1` 还要 `MSVCP140`，它又要 `VCRUNTIME140_1`…）。
  `verify` 阶段再扫一遍，**任何目录还缺 CRT 就打包失败**——这类问题不拦住就得到 Windows 上才炸。
  故意漏拷一个 `msvcp140_1.dll` 验证过，确实会报「缺 msvcp140_1.dll」。
- **代价**：app-local 的 CRT 不跟 Windows Update 走安全更新，升级要靠重打包（删掉
  `node_modules/.cache/vcredist/` 重跑即可）。不想内置就 `--no-crt`，README 会自动换回
  「请装 vc_redist」那套说法。分发本身没问题——这些是微软明示的 redistributable files。

### 桌面版（Tauri）也内置 VC++ 运行库（`scripts/win-crt.mjs`）

同一个坑在**桌面安装包**上也踩了一次：干净的 Windows 上装完 NSIS 包，一开就弹
「由于找不到 MSVCP140_1.dll，无法继续执行代码」。原因是 `ort` 静态链进来的 ONNX Runtime 是
微软用 `/MD` 编的，`jpeditor.exe` 于是**自己**导入 `MSVCP140*`/`VCRUNTIME140*`。（CLI 包那套只
管 `dist-pkg`，跟桌面包是两条打包路径，别指望其中一条覆盖另一条。）

做法与 CLI 包同源，都用 `vcredist.mjs` 抠 DLL，只是投放方式换成 Tauri 的资源机制：

- `src-tauri/tauri.windows.conf.json`（Tauri 按平台自动合并的那份）把 `crt/*.dll` 列进
  `bundle.resources`，**目标路径写成纯文件名** → NSIS 装到 `$INSTDIR`，正好是 exe 同目录；
  exe 的隐式依赖搜索第一站就是自己所在目录，所以 app-local 直接成立（不必像 CLI 包那样按
  加载者目录分别放）。这份 conf 是 **DLL 清单的唯一真源**，加减 DLL 只改它。
- 它同时覆盖 `beforeBuildCommand` 为 `npm run build && node scripts/win-crt.mjs`，打包前先把
  DLL 落到 `src-tauri/crt/`（该目录**不入库**）。`win-crt.mjs` 会顺带断言两件事：清单对自身
  依赖闭包是完备的（列了 `MSVCP140_1` 就必须也列 `MSVCP140`…），以及清单里那几项非 CRT 资源
  跟主 `tauri.conf.json` 一字不差（免得主 conf 加了资源、Windows 包悄悄少一个文件）。
- CI 在**上传之前**先 `cargo build` 一遍再 `win-crt.mjs --verify=<exe>`，拿真实导入表比对清单；
  依赖换版本后多要一个 DLL 就在这里红，而不是等用户装完才发现（tauri-action 那步是增量编译，
  不会重编一遍）。
- 目前只打 `x86_64-pc-windows-msvc`。要加 arm64 得另列清单——arm64 的 redist 没有
  `VCRUNTIME140_1.dll`，而平台 conf 分不了架构。
