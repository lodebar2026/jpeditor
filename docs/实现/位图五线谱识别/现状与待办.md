# 现状与待办（位图五线谱识别）

> [位图五线谱识别](../位图五线谱识别.md)的分篇。

**已落地**：取图（三种数据形态 + 极性自检 + 弯曲扫描的分带推平）、谱线与基本单位、去谱线、
几何原语（横段/竖段/符杠/符号块）、符头按性质判 + 剪加线 + 补加线、
形状字典（模板 + 位置自举 + 人工表）、单页识别接进 `staffomr` 全链、
逐页事实（`chorus-report.mjs`）、GT 逐声部对拍与基线（`chorus-diff.mjs`）、
按识别坐标裁图标注（`raster-crop.mjs`）、
**contour 层与认领账本**（`contour.ts` / `ledger.ts`，无主报表 `raster-unclaimed.mjs`）、
松叶与力度（`wedge.ts` / `dynamics.ts` → `<wedge>` / `<dynamics>`）。

**基线**（`testdata/合唱谱/raster-baseline.json`，干净位图 4 份、其中 2 份有 GT）：
音符 **82.3%**、**含游离 82.1%**、音级 **82.6%**、歌词 **74.3%**、
不靠 GT 的小节自检 **55.0%**；**按谱行（GT 推导）音符 93.2%、音级 93.4%、歌词 95.2%**。
逐首（按谱行）：宁静的伯利恒 **93.6%**、破碎 S014320OC **93.0%**；
无 GT 的主治万方自检 73.1%、你要等候 33.1%。
**真扫描件那一档也进基线了**（5 份，含新加的望十架三份）：
音符 **44.7%**、含游离 37.5%、音级 48.2%、自检 23.5%。
一度只守干净那一档，于是「干净档涨、扫描件塌」的改动可以一路绿灯过去
（实测收竖笔画的宽度闸就是这样：干净 92.31% → 92.74%，扫描件 29.6% → 19.8%）。
现在两档都守，扫描件那几个键带 `scan` 前缀。

> **小节自检 56.0% → 55.6%**：「摘符干块里的头」把八分整批补了回来，
> 符尾窗口收窄之后大半跟上了（`eighth→quarter` 224 → 309 → **191**），
> 剩下的缺口是补回来的音记满了原先空着的小节。
> 判时值看的是下面那个对着 GT 逐音比的时值档，不是这个自检。

> **歌词那一档掉一点先别当退化**：OCR 缓存按**条的内容指纹**寻址，识别判据一动、
> 条的像素跟着变，缓存就落空（实测命中率 78.8% → 74.9% 时歌词掉约一个点）。
> 判歌词好坏要先重跑 `gen-rasterlyrics.mjs`。

> **含游离** 那一档才量得出跨系统连接（`noteAcc` 会奖励碎片化，见[度量与跨系统连接](度量与跨系统连接.md)）。
> 两个数一起看：`noteAcc` 高而 `noteAccAll` 低，就是谱表碎了。

### 三个数各管一段账

**产物**一直是 `buildScore` 连好声部的 MusicXML（`browser.ts` → `scoreToMusicXml`），
人工映射只在 `chorus-diff.mjs` 里当尺子用，`src/` 一处引用都没有。三个数这么读：

| | 按 staff（人工映射） | 含游离（产物） | **连接损失** |
|---|---|---|---|
| 宁静的伯利恒 | 74.8% | 74.1% | **0.7 点** |
| 破碎 | 67.2% | 61.8% | **5.3 点** |
| 歌词·破碎 | 59.9% | 47.4% | **12.5 点** |

- **按 staff** = 识别档，是 `buildScore` 修到完美时的天花板；
- **含游离** = 产物档，该守的还是它；
- 两者之差 = `buildScore` 当下的代价。宁静只剩 0.7 点没什么可捞，破碎还有 5.3 点。
  **谱表数对上不等于每一行都连对**——破碎连成 7 条（与 GT 一样多、零游离）之后
  仍差 5.3 点，错的是连接的内容。

> **连接错对歌词的惩罚远大于对音符**（17.9 点 vs 5.3 点）：歌词挂在谱行上，
> 一条谱表连错，整段词跟着跑到别的声部去。

> **小节自检从 33.2% 掉到 32.5% 不是退化。** 时值一改准，原先「两处错误正好抵消、
> 一小节凑巧凑满」的那些就露馅了（与剔掉假全音符时自检下降是同一回事）。
> 判时值的准不准，看的是下面那个**对着 GT 逐音比**的时值档，不是这个自检。

### 和弦档：把和弦当**集合**比

只比最低音时，「和弦少认了一个成员」与「整个和弦没认出来」看不出区别。
所以另比一份：先按最低音那条序列对齐，再在**对上的位置**上比两个和弦的**成员集合**
（`chorus-diff --v` 的「和弦档」）。

实测破碎：**对上的 2142 处里成员命中 2154/2249（95.8%）、整枚全对 2043（95.4%）**
——**和弦成员的取舍不是病因**，钢琴的缺口是整音漏掉。这一档把方向定死了：
往「多认出符头」使劲，别再调和弦的取舍。

> 顺着这条又量出一笔账：GT 钢琴右手**纸上 1188 个符头**（947 主音 + 241 和弦附加），
> 我们检出 856（补上「上下贴着的三度」之后 911）。逐级看：
> 带内符头 911 → 归属 900 → 成音符 905 → 进度量 818（和弦附加 67、第二声部 20 不入分母）。
> **归属与下游都不丢，缺口全在检出。**

**逐谱行**（`chorus-diff --v`，版式从 GT 的 `print` 标志推出来，见[度量与跨系统连接](度量与跨系统连接.md)）：

| | 宁静 | 破碎 |
|---|---|---|
| 人声行 | 80.9 / 93.1 / 95.3% | 96.6 / 97.0 / 98.3 / 97.6 / 96.7% |
| **钢琴右手** | 93.0%（读错 20、漏 9） | **87.9%**（读错 32、漏 **79**、多 5） |
| 钢琴左手 | 94.4%（读错 15、漏 13） | 91.5%（读错 11、漏 29） |

> **钢琴的读错要看「偏高还是偏低」。** 把 `[识别→GT]` 逐个折成全音阶级差
> （`chorus-diff --secdump=P6.1 --dump` 的输出拿去统计）：破碎钢琴右手
> 167 处读错里，**识别比 GT 高的占了八成**，而且集中在 **+2~+7 级**
> ——正好是和弦音程。病因不是「音高读偏」，是**和弦最低那个音丢了**，
> 剩下的成员顶上来当了主音。顺着这条查出「落单的头被推成第二声部」那一条
> （见下面第 4c 条），读错 167 → 145。

> 声部拆分**不是**钢琴的病因：全关掉实测只涨 0.12 点（85.36% → 85.48%）；
> 无主 contour 在钢琴带里也只剩碎点——漏掉的符头**并不留下没人认领的墨**，
> 它们与邻居的符干符杠连在同一团里，账本看不见。这一条限制记在这儿，
> 免得下次又拿覆盖率去找漏检。

**钢琴两行仍是仅剩的大洞**（破碎 84 / 86%），但病灶已经从「几乎全是漏检」
变成**读错与漏掉各半**——「摘符干块里的头」补回来的那一批把漏检砍掉了六成
（破碎 P6.1 漏 101 → 61），剩下的读错要另找成因。
钢琴占了全部音符的一多半（4635 个里 2660 个）。

**逐符号**（`scripts/chorus-symbols.mjs`，只量干净位图那一档）：
松叶 **54/77 检出**（序列 47.2%）、力度 **21/54**（序列 37.9%）、圆滑线 **39.4%**、
谱号 **98.9% 认出**（349 行只有 4 行认不出；宁静另有 1 行 G/F 认反）、
时值 **92.1%**（只在音高对上的位置比）、附点 **97.8%**、
临时升降 **78.9%**（GT 71 个，凭空多出 1）、拍号 **100%**。
**符头认领率 97.4%**（6247 个符头块，没归到谱行的 165 个；剩下的多是符杠堆里的假符头）。

> 报表里那个「谱号 87.6%」是**逐谱表**口径（拿 `buildScore` 的谱表比 GT 的谱表），
> 跨系统连接一错就算到谱号头上——**谱号本身不是瓶颈**，别照那个数去调谱号。

**错型：漏掉远多于读错。** 宁静配得最好的那条 GT 319 音，读错 13、漏掉 23、多出 16、
对上 283——音高读得没问题，缺的是音符本身与声部的完整性。
