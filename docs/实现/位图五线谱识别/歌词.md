# 歌词（位图五线谱识别）

> [位图五线谱识别](../位图五线谱识别.md)的分篇。

## 歌词：切字格 → 整行 OCR → 挂音符

扫描件缓存用 `node scripts/gen-rasterlyrics.mjs --scan` 补齐（先构建网页与 CLI），
默认仍只生成干净位图缓存。生成与评测都要加载同一份符号模板，否则认领差异会改变歌词条指纹。
缓存仅来自歌词条像素的 OCR，不从 GT 填答案。

GT 评测共用 `node-harness.mjs::xmlLyricVerses`：除数字段号、缺省第一段外，
还识别 Sibelius 的 `partNverse1`。`<lyric-font>` 和 `<lyric-language>` 不能当作 `<lyric>`。
这曾让三份《望十架》静默漏出歌词统计；回归见 `node scripts/xml-lyrics-check.mjs`。
仍按第一段中文词对拍，英文版不能当作同语言准确率样本；汇总需同时看配对覆盖。

位图没有文字层，歌词字要 OCR 出来。三步：

1. **切歌词带与字格**（`lyric.ts`，思路照简谱那条路的 `src/omr/lyrics.ts`）：
   每个谱行下方一条带（本行下缘 → 下一行上缘）；带内按**块的纵向中心**分 verse 行
   （不能按包围盒重叠判——「一」那种只有一横的字与相邻字纵向不重叠，会被分到别行去）；
   行内按 x 邻近把块并成字格（**汉字常由多个偏旁连通块组成**，这一步不能省，
   复用 `src/omr/lyrics.ts::mergeToChars`）。
   带里先把**音乐符号剔掉**（符头与查得到音乐字典的），否则谱表内的符号会混进来。

2. **整行送 OCR，不逐格送**：PP-OCR 的 rec 是序列模型，一整条歌词的上下文能把
   单字认不准的救回来；`recognizeTextsPos` 顺带给出每个字在条内的 x，按 x 映回字格。

3. **合成文本对象**（`font: "#ocr"`）交给 `buildLyricLines` / `attachLyrics`——那两步原样跑。
   **不走 `analyzeText`**：那一步靠「带连字符的音节」「音节间的延长线」当锚点认歌词，
   中文逐字一个音节、既不连字也不拉线，一整行一个锚点都没有。位图这边本来就是
   **按位置**切出歌词带的，身份已经确定，不必再认。

### 断行要按**间隙**，不能用定宽窗口——这是歌词档最大的一个洞

`splitRows` 原来的判据是「块的纵向中心离**本行第一个块**不超过 0.9 格算同一行」。
一行歌词里各块的中心本来就散得开——「宀」的头在上、「，」在下、「一」在中间，
字高又常有 1.2 格，整行的中心跨度轻松超过 0.9 格。于是**同一行歌词被劈成两行**，
两边各拿到半拉偏旁，OCR 出来是同一句词的两个残本：

```
（宁静 p3，改之前）
谱行#5  格4   f1寧靜的
谱行#5  格9   y1.寧静的伯利          ← 与上一条是同一行词
谱行#9  格13  安的夜已深.郊外有一群
谱行#9  格12  恆，平安的夜已深。郊外有一群牧羊人，   ← 同上
```

两条都挂到同一个谱行上，成了 verse 1 与 verse 2，字格宽度也全是碎片
（一行里既有 5px 的残片又有 37px 的两字连体）。

改成**相邻两个中心拉开一段空白才断行**（`ROW_GAP`，按线距算）：

| | 歌词（产物档） | 歌词（按 staff） | 宁静 | 破碎 |
|---|---|---|---|---|
| 定宽窗口 0.9 格 | 44.2% | 53.2% | 66.3% | 40.1% |
| **按间隙断行** | **64.9%** | **71.3%** | **82.4%** | **59.9%** |

门槛扫过 0.45 / 0.6 / 0.75 / 0.9 / 1.1 / 1.4：71.14 / 71.19 / 71.34 / 71.34 /
71.34 / 71.39%——0.75 往上是一整片平台，取中间的 **0.9**。再往上会把相邻两段词
并成一行（两段的中心差约 1.5 格），平台就到头了。音符各档纹丝不动。

> **拿「全页字宽」去剔假字格，两条都试过，都是净亏。**
> 汉字等宽，本以为能砍掉混进歌词带的非歌词墨块（弧线端头、符干尾、简谱数字）：
> ① 宽度闸（丢掉 `w` 不在 0.55~1.7 字宽的格）：歌词 71.3% → **67.2%**；
> ② 中心 y 对齐闸（丢掉偏离行中位数超过 0.35 字高的格）：71.3% → **65.6%**。
> 原因是同一个字的偏旁**并不总能并成一格**，按宽度或对齐去砍，砍掉的多是真字的一半；
> 而整行送 OCR 时那些碎片有上下文兜着，本来就认得回来。
> 全页字宽仍然留着——用来把**字号**量准（只拿宽度接近一个字的格去量字高，
> 逐行那个初值是偏旁块高，偏小）。

### 字符映回字格：字数相同按序号，否则**单调对齐**（不是各取最近）

字数与字格数相同时按序号一一对应，这一条最稳。**不同的时候原来是「逐字各取最近的格」**
——那是错的：字与格的次序本来是一样的（都是从左到右的一句词），
各取最近会**乱序**（两个字抢同一格时后一个直接丢掉，而它本该落在下一格里）。

改成一趟 DP 的**单调对齐**：保序地把字摊到格上，允许跳过空格（字少于格）、
也允许丢字（字多于格，多半是 OCR 多读了一个，`DROP_COST` 0.08 比摊到最近的格贵一点
——宁可丢，也别把整句往后顶）。

### 标点并进相邻的字，不另占一个格

「，」「。」自成一格会**占掉一个音符的位置**，整句词往后错一个音。
所以字符这一侧照简谱路 `omr/lyrics.ts` 的口径折：尾随标点（，。、；：！？…—”’））
并进前一个字，开引号（“‘（）领起后一个字。一个字格于是拿到「字 + 尾随标点」。

| | 歌词（产物档） | 歌词（按 staff） |
|---|---|---|
| 各取最近 + 标点自成一格（原来） | 64.93% | 71.34% |
| 单调对齐 | 67.22% | 73.53% |
| **单调对齐 + 标点并前** | **67.67%** | **73.99%** |

> **「按全页字宽切方块字格」试过，净亏 3 个点。** 汉字等宽，本以为可以拿字宽当尺子
> 把粘连的两三个字等分开（`mergeToChars` 只按间隙并，粘连字并成一格，
> 字格数与 OCR 字数对不上）。结构指标确实好了——每行「字格数与字数之差」的平均
> 从 3.73 降到 **1.08**（字宽取全页块高的 85 分位数，间隙 0.35 字宽、
> 超过 1.75 字宽才等分；这几个门槛都扫过），可歌词档反而掉：
> **新格 67.67% → 64.56%**（按 staff 73.99% → 71.02%）。
> 等分的切点是估的，落在字里的时候「按序号一一对应」那条准路会整句错位，
> 比格数多几个、由单调对齐去摊还要糟。**字宽仍然留着**——量字高要用它挑
> 「宽度接近一个字」的格（块高的中位数是偏旁的高度，偏小）。

**不能要求「`xFrac` 落在字格区间内」**——那是 CTC 估出来的位置，误差常有半个字，
实测那样会丢掉近一半的字（1221 个里丢 566）。

### **不做形状聚类，直接用 OCR 的文本**

试过「字格 → 32×32 签名聚类 → 每类投票定字」（照 `gen-staffocr.mjs` 的每类只送一次
OCR 的账），**净损耗**：5985 个字格聚成 1866 类，只定下 969 类、覆盖 52%，歌词 35%。
门槛往松扫更差（把不同的字并成一类，票散开、过不了半：覆盖 44.6% / 32.9%），
往紧扫也只到 58.7% 覆盖。直接用 OCR 文本，宁静一首歌词 53.2% → **58.2%**。

> **量歌词档之前，必须先把缓存跑全**（`node scripts/gen-rasterlyrics.mjs`）。
> 缓存是**按条的内容指纹**寻址的，任何动到 blob 抽取的改动都会让指纹变、缓存落空
> ——那一条就成了空歌词，歌词档假跌。反过来，缓存**不全**时也会假涨：
> 没命中的条不注入任何字，而 `acc` 对「多出来的字」是要扣分的。
> 实测在提交状态上补全缓存（新增 271 条**都是真歌词**），
> 破碎的歌词从 33.6% 掉到 22.2%、全语料 50.0% → 44.2%
> ——**掉的那一截不是退化，是原先虚高**：认出来的歌词多了，
> `attachLyrics` 把一部分挂到了错的谱行上，这才是真实水平。
> 线上没有缓存、每条都现跑 OCR，等价于缓存跑全的状态。
>
> 判断改动时：动了 blob 抽取就先重跑缓存，再看歌词；不然只看音符/音级/小节自检。

缓存按**条的内容指纹**寻址（`stripKey`，FNV-1a），不按「第几页第几行」：
几何判据一动行的编号就全变了，按位置存的缓存整份作废；按内容存的只要那一条的
像素没变就还能用。命中缓存时识别仍然不起浏览器。

**只收汉字与全角标点**：PP-OCR 认不出时会吐拉丁字母或占位符，收进来就成了歌词里
凭空多出的字（实测 `l` 一个就出现二十几次）。查不到字的格**留空**，不编造。

## 歌词条的 OCR 缓存：**生成器必须与识别走同一条路**

`gen-rasterlyrics.mjs` 原来自己复制了一份流程（另一套 `findStaffLines` / `findBlobs` /
`findLyricRows`）。识别这边一改判据，两边切出来的条就不一样、指纹全变、**缓存整份落空**
——而落空的表现是「歌词档暴跌」，看上去像识别退化（实测 85.0% → 42.7%，查了半天）。

现在条子由 `RasterPageResult.lyricStrips` 从识别里直接出，生成器只管送 OCR。
对齐之后**歌词 85.0% → 95.7%**（按谱行档）——原先那个数是**缓存早就没对上**的虚低，
两边同路才量得准。

## 拉丁歌词：**绕开方块字格**

汉字那一套（`mergeToChars` 按字高并格 → `mapCharsToCells` 把 OCR 的字摊到格上）立在
**汉字等宽见方**这个前提上。英文词宽差着数倍，照搬必错位。
所以拉丁行直接拿 OCR 的 `{ch, xFrac}` 逐字造盒，断词断音节交给矢量路现成的
`splitSyllables`——那一步本来就是给拉丁歌词写的（遇空格断词、遇 `-` 断音节并记下
`hyphen`），一行不改就能用。字格那一层仍然保留：`ledger.claim(cell, "lyric")` 的记账靠它。

### 词界按**条子里真的空白**判，不按 `xFrac` 的间距判

PP-OCR 的 rec **不吐空格**（字表里没有），词界只能自己判。`xFrac` 是 CTC 估的位置，
一个字常差半个字宽，按它判出来的词界一半是错的（实测 `bul-wark nev-er` 判成
`warkney- er`，音节一错位整行就对不上音符）。改成量条子的列投影：连着
**0.7 个字号**没有墨就是一个词界。

这个 0.7 不是排印意义上的词距（0.3~0.5 em）：歌词是**逐音节排在音符下面**的，
词与词之间拉开的是音符间距。实测十二行英文歌词的空白游程中位 2~5px、七成位 7~15px、
九成位 18~35px（字号 13~17px），两头分得很开。按排印词距取 0.28 个字号，整行碎成
单字母（`w orld`、`M an`）。

### 判「这是拉丁行」要三道闸，**一道都不能省**

拉丁字母在成字的字符（字母 + 汉字）里占 **≥0.9**、整行字母 **≥20 个**、
并且**至少有一个连字符**。

- 前两道挡 OCR 的垫背字。汉字行只收 CJK，认不出的墨迹吐出来的拉丁字母自然被滤掉；
  拉丁行一开，它们就成了假英文行。只按「过半」判，合唱谱那批的噪声行整片被判成英文
  ——歌词一变，`score.ts::assignSlots` 定谱行身份的「有没有词」跟着变、跨系统连接跟着变，
  **音符档 85.23% → 82.53%、扫描件 67.07% → 62.17%**。
- 第三道挡**页眉页脚与版权行**：那是货真价实的整行英文，前两道拦不住。实测破碎那份
  六页的书眉（`NEWHEARTMUSICMINISTRIES73REVEREYOURGLORY`）与版权行整片被收成歌词，
  扫描件音符档 67.07% → 66.72%。判据是连字符：歌词逐音节排在音符下面
  （`Mas-ter`、`Up-on`、`bul-wark`），一整行下来必带；书眉、版权、脚注一个也没有。
  代价是整行全是单音节词的歌词行会漏掉（实测《主，差遣我》有一行 `take up the cross;`）。

### 顺带修掉的两条

- `splitSyllables` 里那条「整字见方却只读出一个 ASCII 字符 = 这套字体的全角空格」
  **对合成字体不适用**（位图路造的 `#ocr` / `#raster`）。合成对象的盒是按 `xFrac`
  摊出来的，一个拉丁字母的盒轻易就过 0.8 em——实测《坚固保障》四行英文歌词整片被它
  吃掉，一个音节都没剩。
- `buildLyricLines` 收歌词行：**第一段**不过三个谱表高，**后面几段按「接着上一段」收**。
  独唱谱一页能印八段（中文四段 + 英文四段），第五段起就出了三个谱表高，文本对象造得
  好好的却一条也不收；而单把上限放大会让合唱谱多收进页脚。段与段本来就是等距排下来的，
  中间没有空当，页脚离最后一段远得很，链断在那里。
  `rasteromr/lyric.ts::TAIL_BAND`（末行谱下方的歌词带）同步放到 24 个线距。

  **这条链只对合成字体开**（`#` 打头，位图路自己造的文本对象），与上一条认的是同一个记号。
  一开始没加这道闸，矢量路也跟着链——赞美之泉的歌词档从 94.95% 掉到 94.88%，
  连带「同一版」那一档的曲目集合也动了（时值 97.71% → 97.62%）。
  那本每首最多两段，用不上链式；**多收进来的行都是本不该收的**。
  这笔账是新立的 `staff-measure-all.mjs` 让 `staff-diff.mjs` 一起跑起来才露出来的
  ——改了共用代码，三条守门（`staff-diff` / `chorus-diff` / `staff-measure-all`）要一起跑。
