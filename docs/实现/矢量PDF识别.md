# 矢量 PDF 识别（`src/omr/vector.ts` 等，纯 Node CLI）

印刷歌本的 PDF 常常是**文字全部转曲**：没有文字层、没有嵌入字体，整页只剩路径。
过去这种 PDF 只能栅格化后走光栅 OMR（`decode.ts` → CCL → PaddleOCR）。
本篇是另一条路：**直接读 PDF 的矢量对象**。

样本是 `~/Documents/诗歌/500首/诗歌500首内页校再校对编定稿2019年2月.pdf`（666 页），
配套 GT 有 568 份 `.musicxml`（含 `<harmony>`）+ 568 份 `.jpwabc`。

## 为什么值得单开一条路

1. **重叠对象在矢量层根本不存在。** 每个字/数字/点/线各自是一个
   `save → transform → constructPath → restore`。光栅路里最费劲的那一摊——八度点与数字粘连、
   圆滑线跨过数字、小节线搭桥——在这里是天然分开的。`jianpu.ts` 的五处拆粘连启发式全都用不上。
2. **快两个数量级。** 全书 666 页抽取 + 归类，Node 里 **6.5 秒**，不起浏览器、不跑任何 OCR 推理。
   光栅路是约 3 s/首 × 568 ≈ 28 分钟。
3. **字形可以只认一次。** 同一个字在整本书里的轮廓坐标逐位相同 →
   全书 36.6 万个路径对象只有约 6200 个形状类。给这些类各定一次字符，识别就是查表。

## 数据流

```
PDF → extractVectorPage      src/omr/vector.ts       路径对象 + ctm + clip + 虚线参数
    → detectProfile          src/omr/bookprofile.ts  字号族 / 版心 / 页眉页脚带
    → classifyPage           src/omr/inventory.ts    每个对象归一个语义类，列出归不掉的
    → shapeKey + 字典        src/omr/glyphdict.ts    形状 → 字符
    → 与 GT 逐项对比          pdf-diff.mjs            差异清单 + 准确率矩阵
```

命令（全部纯 Node，只有 `vector-shot.mjs` 因为要像素比对才起浏览器）：

```bash
npm run build:cli                  # 把 src/ 打成 dist-cli/index.js 供 .mjs import
node vector-shot.mjs 60            # 矢量重绘 vs pdfjs 光栅渲染，逐像素核对抽取正确性
node gen-pagemap.mjs               # 页 → 曲 映射 → testdata/500/pagemap.json
node gen-glyphdict.mjs             # 字形字典自举 → testdata/500/glyphdict.json
node pdf-diff.mjs                  # 全书对比 → pdf-diff.csv + pdf-diff/<曲号>.txt
node gen-glyphocr.mjs              # 字典的 OCR 兜底（唯一要起浏览器的建库步骤）
node page-report.mjs               # 逐页排版信息 → pdf-layout.json + pdf-pages.csv + pdf-pages/
node relayout.mjs --mode=outline   # 保真复现 + 对象级核对（验收）
node relayout.mjs --mode=text      # 出 666 页文字版 PDF（可选中/可搜索）
```

## pdfjs 的路径编码

`node_modules/pdfjs-dist/**/pdf.mjs` 的 `DrawOPS` / `makePathFromDrawOPS`：

```
argsArray[i] = [paintOp, [Float32Array 路径数据], minMax]
路径数据是扁平流：0=moveTo(2) 1=lineTo(2) 2=curveTo(6) 3=quadraticCurveTo(4) 4=closePath(0)
minMax = [minx, miny, maxx, maxy]，路径自身坐标系下的紧包围盒
paintOp 为 endPath 时这条路径只用于裁剪，不落墨
```

两个必须做对的地方，做错了会静默出错：

- **`lineWidth 0` 是「最细可见线」（1 设备像素），不是「不画」。** 直接写成 SVG `stroke-width:0`
  会让减时线、小节线整条消失——实测整页少一成墨迹（差异 12.12% → 1.11%）。
- **clip 必须真的施加。** 不裁剪就会把原件上根本不可见的内容当成对象收进来
  （p36/p39 会凭空多出方框和黑块）。

`vector-shot.mjs` 就是守这两条的：把抽出的对象重绘成 SVG，与 pdfjs 自己渲染的位图逐像素比。
纯路径页平均差异 ~1%（都是 SVG 与 canvas 的抗锯齿差，不是结构差）。
封面（渐变）、p6（整页内嵌位图）、p358/p359（**未转曲的真实文字层**）另行单列。

## 这本书的字体分族（实测）

扫第 40–560 页按字宽分桶，各桶取最常见字形肉眼核对：

| 桶宽 px | 实例 | 类 | 内容 | 字体面貌 |
|---|---|---|---|---|
| 18 | 845 | 258 | **歌曲标题** | **魏碑类**（方笔起收、横画右上斜）——不是歌词那套宋体 |
| 11 | 61,275 | 5,116 | 主歌词 | 宋体 |
| 10 | 22,355 | 1,476 | 次号歌词 | 宋体（小一号） |
| 9 | 5,842 | 644 | 段落词 / 署名 | 粗细两种混在一桶 |
| 8 | 1,669 | 273 | 词曲署名 | 宋体细 |
| 6–7 | 10,091 | 317 | 和弦符号 | 衬线（Times 族） |
| 5 | 56,615 | 396 | **音符数字** | 衬线（Times 族） |
| 3–4 | 25,215 | 344 | 三连音数字、上标 7、休止 0、括号、标点 | 衬线小号 |

曲号那一族是**无衬线**，与音符的衬线数字是两套字形。

本机唯一的魏碑字体 `WeibeiSC-Bold.otf`（Apple）渲染出来偏行书、笔画飘逸，
与这本书标题的方正端庄**不匹配**——同族不同款。真要做字体比对需另找方正/汉仪/华文的魏碑。
另注：`opentype.js` 2.x **不支持 `.ttc`**（Songti / STHeiti / Kaiti / Lantinghei 一律报
`Unsupported OpenType signature ttcf`），而 macOS 的中文字体大多是 ttc，且散落在
`/System/Library/AssetsV2/**/AssetData/` 下——要做字体比对得先解 ttcf 头或改用 fontkit。

## 归类判据（`inventory.ts`）——每条都是拿具体页换来的，动前必看

硬指标是 `unclassified`：**全书 365,694 个对象，未归类 1 个**。

- **不能用「有没有曲线」判断是不是字。** 这本书数字字体里的 1/4/7 等是纯折线（`curves = 0`），
  拿 `curves >= 1` 当门槛会把整行音符漏成未归类。按**宽高比**认结构线，其余按字号认字。
- **同一个字画了两遍**：一个 fill 一个 stroke（描边加粗），bbox 差约一个线宽。两份都要归类
  （重排核对要逐对象配对），但把描边那份标成 `dup`，下游计数/取文本只认非 dup。
  **配对必须查 3×3 邻域**：只查自己那一格会漏掉骑在格边界上的一对——
  实测漏配让识别出来的音符串出现成对重复的数字，音符准确率卡在 91%，修好后直接到 98.6%。
- **谱行的基线要用带内音符统计**，不能用小节线底：小节线（13.8）比数字（8.3）高一大截，
  拿它当基线会把增时线和减时线判反。
- **同一谱行的音符共一条基线。** 只按「落在小节线的 y 区间内」收音符，会把上方的和弦字母
  （h≈7.0，正好落在音符的高度区间里）也收成音符——实测页面音符数中位数比 GT 多 20 个。
  按带内音符 cy 的中位数二次筛，偏离超过 0.45 字高的退回。
- **小节线明显比字高**（13.8 vs 8.3，比值 1.66）。门槛设在 1.15 字高，正好把拉丁人名里的竖笔
  （D/l/d，与字等高）挡在外面——那是词曲署名行被误判成谱行的根因
  （p300 曾因此多出两个假谱行、40 个假音符）。
- **减时线要卡死上下界**（音符底线下方 0～0.9 字高）。不卡下界会把歌词里的「一」吞成减时线。
- **圆滑线不能只看宽扁**：整行合成的文字对象（见下）也宽扁，`segs > 12` 的一律不是弧。
- **不是每个字都是一个 path**。歌词/音符是逐字一对象，但**花边框里的小字注解整行合成一个 path**
  （p42 底部那段圣诗故事：一行 = curves 548 的单个对象）；**标题和多位曲号有时也整行合成**
  （p474 的标题、p383 的「327」）。故版面带那一步允许改判 `textLine`。
- **曲号贴版心左右边缘、标题居中**（对开页左右交替）。只按宽高比分会把标题里的窄字
  （「!」「(」「了」）判成曲号；而多位曲号合成一个 path 后宽高比又会大于 1。**纯按位置判**。
- **页脚判据要锁在全书页脚带内。** 只按「本页最底部的空隙」找会翻车——前言/目录页行距大，
  最靠下的那个大空隙可能出现在版心中部，于是整块正文被判成页脚（p30 曾误收 581 个对象）。
- **无谱行的纯文字页**（目录 / 首句索引 / 前言，全书约 40 页）要单独兜底，否则整页落进未归类。

### 花边框（`detectOrnamentFrames`）

歌谱后面常附一段带花边框的注解（圣诗故事 / 经文），如 p42《主耶稣再临那日》、
p300《宣教的中国》、p605《我宁愿有耶稣》。

- **花边不是虚线。** 全书 145 页有 `setDash`，但这些框一个都不是——它们是拿装饰字形
  沿矩形四边**重复平铺**出来的（p42 是 5.0×10.8 的纹样，p300 是波浪星纹，p605 是密排小点）。
- 判据是**同一形状连续密排成线**（相邻间距不超过自身宽度的 2.5 倍，一条边 ≥8 个），
  再把横线与竖线拼成框。先试过「同形状重复多次 + 包络中心为空」，在 p300 翻车：
  框内的高频汉字（的、一…）也满足「重复多次 + 尺寸小」，把中心占满了，整框被判掉。
- **检测必须排在结构线之前。** 点线花边的每个点都是细高小块，会被小节线判据收走——
  实测 p605 收了 60 条假小节线 → 造出 21 个假谱行 → 框内那段故事被当成音符和歌词。
- 识别出框以后，**框内对象一律归 `storyText` 并跳过后续判据**：框里是注解正文，不是乐谱。
- **那道锁要连 `ornament` 一起守。** 只守 `storyText` 时，紧接着的「整行合成的文字对象」
  会把刚定成 `ornament` 的合成边改判成 `textLine`，那条边于是以正文首行的身份印出来
  （p92/p591/p633…）。

#### 整条边合成一个 path 的花边边（`collectSolidEdges`）

同一本书里，有的页花边每一片是独立对象（走密排线那套），有的页**整条边被合并成了一个
path 对象**——「≥7 片」的判据根本看不见它，那条边就落在框外：框的包围盒只由剩下三条边
定出来，顶边连同它压着的正文一起流回谱面判据。全书 13 页栽在这上面
（92/286/287/351/355/379/451/463/591/614/618/633/635），**清一色缺的是顶边**。

判据三条，拿全书扫描标定（873 个「长宽比极端且够长」的对象里只命中这 13 个，零误报）：

| 条件 | 值 | 为什么 |
|---|---|---|
| 够长 | 长边 ≥ 版心宽 × 0.85 | 这批边实测 287~294，版心 307.6 |
| 够扁 | 短边 ≤ `noteH` × 0.85 | 这批 2.8~6.6；注解正文整行合成的 path 高 7.8+，就此分开 |
| 段数够多 | `segs ≥ 60` | **要害**。普通结构线（通栏横线、双细线框的边）`segs` 恒等于 5 |

**不要改用 `curves`**：这批合并边的 curves 从 0（p351/p451）到 1372（p287）都有，
拿它当判据会漏掉一半。分开「花边合并边」与「结构线」的是段数，不是曲线数。
合成边只补边、不立框——全靠它凑出来的「框」没有密排线背书，那是两条无关的宽扁 path
撞在一起。

#### 四角那枚独立纹样（`collectCornerTiles`）

四角印的**不是**横竖两条边的母题，而是第三枚字形（p42 角片 7.7×7.6，边片却是 10.8×5.0）。
每框只有 4 个，永远够不着密排线的门槛，于是全书 **427 个角片**一路落到框内正文里被当成字
读出来——「X」44 个、「S」19 个、「米」18 个、「K」11 个……110 条注解里有 103 条正文
混着这种垃圾字。（`bookmeta.ts` 那条「1~2 个拉丁字母独占一行就丢掉」的过滤只挡住了
独占整行的那部分。）

判据拿全书 110 个框实测标定：

- **贴角**：中心距框角 ≤ `noteH*1.2`（实测 3.1~9.6，中位 5.4，p90 只有 7）。这条是主力
  ——框内正文离角至少隔着一圈内边距，第一个字的中心距角 14 以上。
- **够小**：bbox ≤ `noteH*1.35`（实测 4.8×4.8 ~ 10.6×10.5）。放到 1.35 是为了 p149/p555
  那两个框的角片（10.0×8.8 / 10.5×10.4），卡在 1.2 上它们会整框漏掉。
- **四角同源**：四个角位上至少两个的 `curves/segs` 一致。角片是同一枚字形的四种旋转，
  旋转不改段数——实测每种 `curves/segs` 的计数都是 4 的整倍数。少了这条，尺寸上限放宽后
  框内贴着角的正文字就会被当成角片吞掉。
  **同源要按四个角位一起看**：角片与边片同形状时（p633 的 `12/29`），三个角早被密排线
  当边片收走了，只剩一个孤角——只数它自己永远凑不够两票。

补角之后 box 按所有件的并集重算（角片会外突一点）。全书 427 个角片，补完剩 0 个流进正文；
注解首行是垃圾的框 **73 → 4**（剩下 4 个是真缺字，不是花边）。

## 页 → 曲 映射（`gen-pagemap.mjs`）

- **起始页必须印着曲号。** 只看「有没有标题」会把扉页里的大字当成一首（p4 吃掉了 001，
  其后整本错位一格）。
- **一页可能不止一首**（J/D 短歌两首挤一页，p612 有三个标题带），故标题与曲号各按 y 聚组再配对。
- **页顶可能是前一首的续尾**（p65 顶部是 32 首的末三行，33 首从 y≈320 开始）。
  第一个标题带明显不在页顶时，顶部那一段要归给前一首。
- **续页必须紧接着上一页**，否则书末的索引页（偶尔也判出谱行）会一路挂到最后一首身上
  （D28 曾吞进 6006 个「音符」）。

结果：637 个乐谱页，**568/568 曲目全部映射**，一条告警（p358，该页有真实文字层）。

## 字形字典自举（`glyphdict.ts` + `gen-glyphdict.mjs`）

形状键：轮廓按 **bbox 高度**归一（不能宽高各自归一，那会把「一」和「口」压成同一形状）、
坐标量化到 50 格后哈希。量化粒度 50 是实测选的：再细会把同字的坐标抖动拆成不同类，
再粗会把形近字并到一起。

标注来源与可信度：

- `manual` —— `testdata/500/glyph-seed.tsv`，**按字形肉眼判定**的种子（把字形轮廓渲染出来直接认）。
  只种了曲号的十个数字和音符族的常用字符，作用是把页映射到曲目，作为自举的起点。
- `gt` —— 用 568 首的 `.jpwabc` 语料回标：GT 的音符 / 歌词 / 标题序列与页面的形状序列对齐，
  对上哪个位置就给那个形状记一票。

迭代两条通道：

- **长度完全相等 = 无歧义直配**，一次就定案（权重 3）。标题尤其依赖这条：一首一个标题、
  字几乎不重复，靠投票永远凑不够票（只走 DP 投票时标题准确率卡在 73%，加上直配后到 85%）。
  前提是这条序列里已经认识的字大体对得上（≥60%），否则说明整条错位，不能信。
- 长度不等的走 **DP 对齐**（已知字符匹配得高分，未知形状给中性偏正的分当通配），权重 1。
  加权票满 3 分且多数占比 ≥70% 才采纳。

⚠️ DP 回溯的分数表**不能用 `Float32Array`**：它会把双精度加法的结果截断，
回溯时的等值比较永远不成立，整个自举一票都投不出来。

结果：4~5 轮收敛，**6186 个形状类定出 4343 个，覆盖 96.97% 的字形实例**。

## 逐页排版信息（`src/pdflayout/spec.ts` + `page-report.mjs`）

把每一页整理成「足以照着排回去」的结构化描述：页型 / 曲目落位（曲号、标题、署名、逐谱行的
小节线 x 与逐音符 x、和弦行、逐段歌词行）/ 页眉 / 页脚 / 花边文字框 / 线框 / 其它文本行。
所有文字都带**逐字 x**，重排时按位置摆放而不是重新算版。

硬指标是 `coverage.unplaced`：页面上每个对象都要落进某个字段，**全书为 0**。

|---|---|
| score（乐谱页） | 605 |
| toc（目录） | 37 |
| index（首句索引） | 14 |
| front-matter（前言/扉页） | 6 |
| blank | 3 |
| cover | 1 |

| 边框类型 | 数量 |
|---|---|
| rule-h（横线） | 3283 |
| rule-v（竖线） | 1098 |
| bracket（房号/三连音括线） | 267 |

需要特别处理的页：**p1 / p358 / p359 含未转曲的真实文字对象**（要另走 `getTextContent()`）；

判定页型时**不能只看读出来的文字**：目录页的字有相当一部分还读不出（见下），
拿「行尾是不是页码」判会因为读不出而失效，得叠加 `tocEntry` / `leader` 的几何计数。

### OCR 兜底（`gen-glyphocr.mjs`）

自举只能标出 GT 里出现过的字。目录页的曲名、首句索引、花边框里的注解正文都没有 GT，
字典盖不到。这些类**每类送一次 OCR**：两万个实例只要跑两千多次推理，全书 11795 个未定类
用时 213 秒。这是矢量路里唯一要起浏览器的建库步骤（PaddleOCR 走 onnxruntime-web），
跑完产物落盘，之后的识别与对比仍是纯查表。

字典最终 16233 类、已定 12776、**覆盖 95.28% 的字形实例**。

**签名模糊匹配这条路试过，不通**：同一字符跨字号的 32×32 签名距离 p90 达 315，
而不同字符之间的距离 p50 才 230，两个分布重叠，找不到能用的阈值。

### 整行合成的 path：OCR 按**整行**送，收多字符结果

`gen-glyphocr.mjs` 原本一律把字形挤进 48×48、只收「恰好一个字符」的结果——
整行文字送进去就是一团黑，两千多类全被「多字符丢弃」扔掉了。改成两种形状分开送：

- **单字**（宽高比 <3）：照旧，48×48，只收一个字符。
- **整行**（宽 ≥ 高的三倍）：按原比例摊成 48 高的长条（宽上限 2048），收整串。
  这本来就是一行字，行识别比逐字送准得多。

2427 个整行类里补上了 2384 个，字典覆盖从 89.6% 跳到 **97.6%**，
`relayout` 的「读不出的字」从 11695 降到 9086。

归类那边也要放它进来：`textLine` 在第 10 步允许参与，但**只在谱行上方那一侧**
（署名、经文都印在那儿），且门槛放宽到 5 个字高——署名印在第一谱行上方三四个字高处，
按和弦那 1.6 字高的门槛够不着。让它也去当歌词行反而更糟：一整行歌词是一个对象，
归段/折行那套按字数算的判据全失灵（实测歌词 98.29% → 98.17%）。

### 署名靠什么认：字号与高差，不是位置

署名的版面位置其实很固定——**标题之下、第一谱行之上、靠右半边**（左半边是「1=F 4/4」）。
照这个框去收试过，署名反而从 87.3% 掉到 83.6%：同一带里还夹着页眉分类词、经文、副标题，
而且下界一路收到谱行顶时会把第一行的和弦整排吃掉（和弦 97.6% → 86.4%，留出 1.6 个字高才好）。
左右对齐也分不开：署名行左缘中位虽在版心 57% 处，但长署名（外文人名 + 生卒年）从 15% 处就起排，
而经文也顶到右边界；门槛设 0.15/0.22/0.30 三档，署名分别掉到 81.5/80.5/80.5。

真正管用的是两条与**位置无关**的判据，外加几道闸——每一条都是拿具体曲子换来的：

| 判据 | 为什么 |
|---|---|
| 与和弦基线的**高差** > 1 个字高 | 署名印在和弦线上方；和弦连同上标 `♭`/`m`/`7` 都贴同一条基线 |
| **字号**（一行的 3/4 分位 ≤ 0.92 个歌词字高） | 署名 6.5~8.1，经文/正文是歌词那号字 10.3~11.1。**用 3/4 分位不用中位数**：行里夹着标点与上标数字（才 2.9 高），中位数会被拽到 9.6 蒙混过关（105 首曲末那句经文） |
| 字号按**整行**量，不按 run 量 | 一行经文里挑七八个字凑出来的一小段，中位数比整行低 |
| **密排**（墨迹宽 / 跨度 ≥ 0.3） | 房号（一房二房）会把那一行的和弦整排抬高一个字，抬上去之后同样「比和弦基线高一个字」，于是被当成署名接到人名后面（037 首尾巴上多出 `CFFCCF`）。署名是挤在一起的一串，和弦是隔着大半个小节的孤立记号 |
| 密排那条（≥7 个字）也要过字号闸 | 031 首曲末那句经文正好七个字，卡在门槛上 |

读法上还有两处坑：

- **GT 字段取最后一条非空的**：有的文件写了两条 `WordsByAndMusicBy`，第一条是空的；
  `=` 后面若用 `\s*` 会吃掉换行、把下一行整条卷进来。
- **同一行的容差放到 5 点**：生卒年 `(1820-1915)` 的基线比人名高四五个点，卡在 3 点上会被切成
  另一行，而行是按基线排序的，年份于是跑到人名前面（197 首读成「18201915作词美芬尼…」）。
  这一条单独就值 5 个百分点（89.5 → 94.9）。
- **等号必须左邻一个窄字**（调号永远写作「1=X」，那个 `1` 宽只有高的四成），
  且「往外长」有上限：署名里的 `W`（6.2×4.3、横平竖直 curves=0）会被当成等号，
  把半行人名吞成调号（290 首的 `EHewitt(1851-`）。

### 半页起的曲子：**大字标题就是分界**

一页印两首时，下半首的调号、拍号、词曲署名都夹在上一首的末行谱与本首第一谱行之间，
离上一行谱更近，于是被判成上一首的歌词——102 首的署名一个字都读不出，
调号拍号当年也栽在这儿（那时给 10e/10f 开了道「候选也收 lyric」的口子兜底）。

**隔着一条标题就不可能是上一首的东西**：第 10 步判「上方那一行谱」时，
若两者之间夹着 title 对象，直接把这个选项掐掉。一条判据同时解决三处：

| | 改前 | 改后 |
|---|---|---|
| 词曲署名 | 82.7% | **86.3%** |
| 歌词 | 98.29% | **98.58%** |
| 调号 / 拍号 | 97.0% / 99.1% | **97.4% / 99.6%**（没读到 1/1 → 0/1） |

10e/10f 那道旧口子跟着撤了——撤掉之后调号拍号反而更准，可见它自己也在误伤。

### 歌词里的「一」——四次试错才捞回来

「一」在矢量层是 **10.4×1.0 的扁横条（curves=4, fill）**，
**与跨一个音符的短圆滑线尺寸完全一样**。拿 GT 的上下文回查，全书 584 处「一」有 352 处
被判成了圆滑线。四次尝试：

1. 只按尺寸放行 → 真圆滑线一起被放走，歌词 86.9% → **72.7%**。
2. 要求「必须挂在某个谱行上」→ 跨行的长弧本来就挂不上，同样崩。
3. 按「在谱行下方多远」分流 → 上一行的圆滑线正好落在那个区间里，仍崩（79.4%）。
4. **按「有没有与它同行的汉字邻居」分流** → 成。判据是：字格中心相差不超过 0.28 个字高、
   水平间距不超过 1.5 个字宽、参照物必须是满格汉字（标点不算）。全书捞出 617 个，
   与 GT 的 584 高度吻合。

还有两个坑，少一个都不成：

- **裁定要排在「剩余的字」那一步之后**，并把候选从那一步里排除。否则候选会先被当成普通歌词收走，
  连同真圆滑线一起进歌词序列（这就是第 3 次尝试崩掉的直接原因）。
- **「一」不能进字典**，要按几何直接定案。它的轮廓在字典里跟减时线等扁横条撞键，
  自举投票被冲散——试过，全书只学出一个「一」，还是标题里的那个。
- **归行要用参照汉字的下缘**。「一」只有一横、悬在字格中部，自己的下缘比同行汉字高四五个点，
  按自身下缘聚行会被分到别的行去（这一条没做时，歌词只有 79.4%；做了立刻回到 91.4%）。

## 重排（`relayout.mjs`）

从版面规格把 PDF 排回去，两种模式：

### `--mode=outline` 保真复现（验收用）

按**形状键**取回原件的那条轮廓，摆到规格记下的位置。它把「规格是否记全了」变成可判定的：
逐对象配对原件与重排结果，`unplaced`（原件有、重排没有）和 `spurious`（重排多出）都必须为 0。

全书 666 页、**308,278 个对象**：

| | |
|---|---|
| unplaced | **21**（0.007%） |
| spurious | **0** |
| 位置偏差 > 0.5pt | **15** |
| 用时 | 约 10 秒 |

做到 0 之前踩的三处：

- **不能走「字符 → 代表字形」**取字形，要按形状键取回原件那一条。前者对读不出的字没有代表字形，
  同一个字的不同字号也会互相串（那一版缺字形 673，正好等于读不出的字数）。
- **逐字记自己的 y 与高度**，不能用整行的中位数。标点只占字格下部、歌词里的「一」悬在字格中部，
  拿行中位数去摆，位置差出好几个点，配对就落空（那一版 170 个对象对不上）。
- **规格要自足**：乐谱记号（减时线/小节线/圆滑线/点）单列成 `marks`，不能让它们混进
  「剩余的文本行」——否则重排时记号那条路径和文本那条路径会各画一遍
  （那一版凭空多出 651 个对象）。花边纹样也别提前标成已用，否则谁都不收它们（少 9324 个）。

### `--mode=text` 文字版 PDF（原位替换版）

**位置照原件、把曲线换成真文字**：输出可选中、可搜索、可复制的 666 页 PDF，页序与页数照抄原件。
歌词/标题/署名/和弦/页眉页脚/音符数字都落成真实文字对象，
减时线/增时线/小节线/圆滑线/八度点/花边纹样仍画矢量图形。

与另一条路（`rebuild.mjs`，从数据重排）共用两样东西：
**书籍样式 `BookStyle`**（字体·字号·间距，见下节）与**中间格式 `DrawList`**。
`relayout.mjs` 的活因此只剩「PageSpec → DrawList」这一步（`src/pdflayout/drawlist.ts::specToDrawPage`），
写 PDF 的事全在 `scripts/pdfwrite.mjs`。

**用 pdf-lib 直接写 PDF，不经浏览器。** 先试过 Chromium 打印（把 SVG 的 `<text>` 打成 PDF），
不成：printToPDF 经 CDP 把整份 PDF 传回来，页一多就 `Printing failed`，两三百页后干脆
`Page crashed`；只能分批打印再合并，而**每一批都会各自嵌一份字体子集**——
666 页合出来 43.5 MB、跑 4 分 22 秒，还因为 Chromium 的 ToUnicode 映射偏差，
提取出来一堆康熙部首（`⼼` 而不是 `心`）。

| | |
|---|---|
| 页数 / 尺寸与原件一致 | **666 / 666** |
| 体积 / 用时 | 17.4 MB / 约 20 秒 |
| 落成文字的字数 | 255,437 |
| 字体缺字（画不出的） | **0** |
| 仍读不出的字（写成空位） | 8,140，来自 **1,188 个形状类** |

读不出的那 8,140 个字里，乐谱页 6,938、目录 1,015，其余在前言与索引。
按角色看：歌词 3,685、注解正文 1,262、调号拍号 845、目录行 867、页眉 563、署名 691。
**GT 回填帮不上大忙**（`gen-backfill.mjs` 只补回 19 个字）：这些字多半落在 GT 覆盖不到的地方
——调号拍号、段落词、目录索引、花边框正文本来就不在 musicxml 里。
剩下的走人工：`relayout.mjs --db` 把它们按形状键落进 `校对.db` 的 `unread_glyph` 表，
**补 1,188 个字就能全清**。

写 PDF 这一步的四处要害（都在 `scripts/pdfwrite.mjs`）：

- **只嵌真正用到的字体**。嵌进去却一个字都没画的 CFF 字体，子集是空的，
  pdf-lib 保存时崩在 CFF 编码里（`RangeError: value argument is out of bounds`）。
- **缺字要自己判**，不能靠 `font.encodeText` 抛错——pdf-lib 对缺字不报错，
  静默画成 `.notdef`，回读出来是 U+0000。用 fontkit 的 `hasGlyphForCodePoint`，
  缺了就按字体链回退（`♭` 只有 Bravura 有、`祂` 那几个字方正字库没有）。
- **pdf-lib 的 `drawSvgPath` 不支持二次贝塞尔 `Q`**，它把 Q 派给三次曲线的处理函数、参数少两个，
  直接崩在 `numberToString` 里且看不出出处。矢量抽取器与字体轮廓都会产出 Q，统一升成 C（`quadToCubic`）。
- **字距用 Tc 撑开，一段一次 `showText`**。逐字画的话，pdfjs 一类的提取器会按字距插空格，
  「神配受崇拜」变成「神 配 受 崇 拜」，搜索直接落空。简谱歌词的字距是为对位撑开的（比字宽宽 40%），
  Tc 也救不了，所以含汉字的行**再补一层不可见的紧排文字**（`Tr 3`）当搜索层——扫描件 OCR 的文本层就是这么做的。

字体：macOS 的中文字体几乎都是 `.ttc`，而 pdf-lib 和 opentype.js 都只吃单个 sfnt
（直接喂会报 `Unsupported OpenType signature ttcf`）。`scripts/ttc.mjs` 负责从 ttc 里
按名字抽出一个独立 sfnt——**不能整段切**，ttc 的各子字体常共享同一份表数据，得按表记录重新拼。

## 书籍样式（`src/pdflayout/bookstyle.ts` + `gen-bookstyle.mjs`）

两条重排路唯一共享的东西：这本书「长什么样」的完整参数集——页面/版心、各角色的字体与字号、各处间距。
值全部由 `src/pdflayout/stats.ts` 从 `pdf-layout.json` 统计**中位数**得来
（`node gen-bookstyle.mjs` → `testdata/500/bookstyle.json` + `bookstyle-report.md`）。

**角色判定用 PageSpec 的字段位置**，不是 `BookProfile.families[].role`（那个字段全书恒为 `"unknown"`，
没有任何回填方），也不重跑 `classifyPage`——spec 的具名字段本身就是归类判据的产物。
`tuplet` / `verseNum` / `sectionWord` 这三个 ObjClass **只在类型里声明、从没被赋值过**，
所以 tuplet 从音符带里按字高分档取，另两个按印刷惯例从 lyric 派生（报告里逐条标明来源）。

统计的两个口径坑，都是拿肉眼看出来的：

- **字号要剔掉标点与上标再取中位**。标点只占字格下部（逗号高 1.5pt，正文 10.5pt），
  混进去会把中位数拉偏——次号歌词那一档的离散度从 0.54 掉到 0.16 就是这么来的。
- **量到的是墨迹高度，不是 font-size**。两者差一个「墨迹占 em 的比例」，而这个比例各族不同：
  Times 的数字约 0.66em、宋体汉字约 0.9em。直接把墨迹高当字号灌进排版器，
  数字会比歌词多缩三成，**音符与歌词的大小关系就跟原书对不上**（一眼就看得出别扭）。
  `browser.ts::fontSizeFor` 实测样本字的墨迹比例再反算字号。

同样的道理适用于**绘制厚度**：`slurTieThickness`(6) / `jpBeamWidth`(1.5) / 小节线(2/3.5)
是排版引擎按 `fontSize≈28` 调出来的**绘制参数**，而原书量到的 `ink*` 是印刷成品的**描边宽**（0.19pt 上下）。
把后者塞给前者，圆滑线会退化成一条等宽细线。所以：
**弧与小节线按字号等比缩放，减时线用原书的墨迹宽**（它本来就是一条细线）。

`metrics` 里 `*Em` 后缀的随字号缩放（基准是音符墨迹高），其余为 pt；
`titleBlock` 存的是页内绝对 y（原书整本一套版式，实测离散度 0.002）。

## 数据重排版（`rebuild.mjs`）

**从 musicxml / 文本谱 / .jpwabc 重新排一本书**，乐句优先、页数由排版决定。

```
musicxml → loadMusicXml → Score → computePhraseBreaks → applyPhraseBreaks（写 LineBreak）
        → JinpuPainter（applyBookStyle 注入样式）→ pageItemsToDrawPage → DrawList
        → scripts/pdfwrite.mjs → PDF
```

排版引擎依赖 `common/measure.ts` 的 `getBBox`，只能在浏览器里跑；pdf-lib 只能在 Node。
中间格式因此是 **DrawList**（`src/pdflayout/drawlist.ts`）：页内把页面树扁平化成绝对坐标 + 逐字笔位，
Node 侧照着画，两端不必共享字体度量。**不用 SVG 字符串**——那要在 Node 侧反解嵌套 transform
与字体度量，等于把 painter 再写一遍；而页面树本来就只有三种叶子
（`GraphicPath` / `GraphicLine` / `TextFrame`），照着 `painter.ts::renderPageItem` 的递归扁平化一次就完事。

### 多段歌词：叠排，而且不展开反复

原书是**一行谱下叠几行词**（行首带「1.」「2.」段号），而排版引擎的老行为是
**逐段重复整条谱行**（jpword/musicpp 那套，流行敬拜谱常见）。照老行为排，568 首要 1400 页。

`LayoutOptions.lyricStack > 0` 打开叠排（默认 0，编辑器行为不变），它做两件事：

1. `addLyric` 把这个音符底下的各段歌词一行行摞起来，段间距取原书的 `lyricToLyric`；
   行首挂段号——段号**挂在行上、用绝对坐标**，挂进 NoteEntry 的话随后的 `update()` 会把那点负 x 归一掉。
2. `fromScore` **按原谱排一遍，不展开任何反复**。反复本来就是用记号表示的（`‖:` `:‖`、房号、D.S.），
   而 `playData` 是给试听用的展开序列：多段歌词在那里被摊成好几遍，
   064《啊！圣善夜》甚至摊成 10 遍（歌词只有 3 段）——照着它排，一首歌能排出十几页。

叠排之后：**568 首 648 页**（原书乐谱页 605），492 首一页排完，最多 3 页。

### 容量：一行放得下几格

> **口径已变**（2026-08）：行长与行数**不再进评分**，纸张只管「排不排得下」。
> 见后面的〈断句只看内容，纸张只管「排不排得下」〉与〈整首的排版模式阶梯〉两节。
> 本节留下的是**容量怎么量**——那部分没变，而且是模式选择唯一的输入。

`computePhraseBreaks` 的行长常量（`MAX_MEAS=7` / `MAX_CELLS=25`）是拿具体曲子调出来的，
**成书这条路不改它们的默认值**，而是按参数覆盖：

- **上限来自纸张**：一行放得下几格由 `browser.ts::measureCellsPerLine` **空排一遍量出来**——
  排版器空排时按宽度塞满再折行，「装得最多的那一行」就是容量。
  不能拿字宽估（高估一倍），也不能拿相邻音符 x 差的中位数算（会被八度点、附点这些同格里的
  小东西带偏，实测算出 98 格、实际只放得下 13）。三处要害：
  1. **空排前要 `clearSystemBreak()`**。不清的话排版器照 musicxml 的 `<print new-system>` 分行，
     量到的是「原书每行几格」而不是「一行放得下几格」（005 原书那几行 30/26/27/17 格）。
  2. **按页 + 基线分组**数，只用 y 会把各页落在同一条基线上的行并成一行、计数翻倍。
  3. 取**最大值**而不是中位数：塞满折行后每行都顶着版心宽、只有末行短，中位数被末行拖低
     （005 因此量成 27 格，「赞美主…」那两句 30 格并不到一行去，实排核对过其实放得下）。
  即便如此「格」仍只是近似——同样的格数，歌词字多的行更宽，量出的容量对某些曲子偏乐观
  （297《让神儿子的爱围绕你》量出 50 格、实际约 30），靠下面那轮迭代收敛。
- **行长目标也来自纸张**（`phrase.ts::targetMeasForCells`，`bookstyle.phraseTargetMeas = 0` 即走它）：
  容量 ÷ 本曲「每小节几格」= 一行该放几小节，上限跟着目标走（`×1.3` / 整句 `×1.4`）。
  原来给死 4 小节，靠排完「两两并短行」去凑满版心，但**并行只能成对**——一段里落单的那一行
  并不进去，同一首里就会出现一行 12 小节、下一行 6 小节（377《我宁愿有耶稣》副歌 16 小节，
  DP 按 4 小节的目标切成 5+5+6 三行，并完是 10+6）。目标直接按容量定，DP 一次就挑中了
  全段最强的那个断点（「…所苦害，」的长音 tie 收尾，强度 22），排成 8+8。
- **目标按容量定之后，`lenWeight` 要反过来调小**（4 → **0.25**）：目标行长本身已经是版心宽，
  行长代价再重就会压过「断在乐句收尾处」，把行末从标点上挪走。`breakWeight` 同时提到 3。
  （`contentOnly` 之后这两个只在**方案选优**那几遍 DP 里还起作用，第一遍传 `lenW = 0`。）
  全书 568 首实测（只算乐句分析的计划行，不含排版器折行）：

  | 口径 | 谱行 | 行末收标点 | 过短行 | 超容量行 |
  |---|---|---|---|---|
  | 目标 4 小节 + 两两并短行（旧） | 2271 | 92.9% | 34.8% | 0.4% |
  | 目标按容量 + `lenW 0.25` / `brkW 3`（今） | 2249 | **94.1%** | **29.5%** | 0.4% |

  四项全不劣于旧口径。整本：乐谱 606 → 604 页、总 655 → 653 页，二次折行仍 0、注解 164/164、缺字 0。
  （`lenWeight` 更小如 0.15 能把收标点推到 95.0%，但过短行退回 34.1%、谱行反涨；0.25 是拐点。）
- **两两并短行仍留着**（`phraseMergeShort`）：目标按容量定之后它很少出手，但短小节的谱
  （005 每小节 3.2 格）仍靠它兜底。
- 旧口径的加权说明留档：`lenWeight` 放大行长代价。16 小节的歌在默认权重下会排成 4+6+6
  （行长代价 8，但比 4+4+4+4 少断一次、正好省回来，打平），权重调到 4 才让长音上的那个断点胜出、选 4+4+4+4（权重 2 仍打平）。
- **歌词字距与前置标点**（`LayoutOptions.lyricGap`）：引擎的 `calcXPos` 只保证歌词**不重叠**，
  字距会压到 0——001 曾排成 2 行、字距 9.1pt 小于 11.8pt 的字宽，字是叠着的，
  排版器却以为一行塞得下三十几个字。成书给 `lyricGapEm = 0.1`（原书的字距更大，
  但我们的其它间距也比原书紧，0.1 时全书行数最接近原书）。
  反过来，**开头的标点要悬挂**：`“凡` 这种带前引号的字整体宽是两个字，按整体去避让上一个字
  就把这个音符整个往右推、一行的音符间距全拉开（190 首）。避让只看主体（`Lyric.leadWidth` 之后那截），
  让引号伸进左边的空档——它压在小节线那一带没关系，只要不压到字上；右标点仍照算。
  但**上一个字自己带尾标点时不许悬挂**（2026-08-25）：引号会正好压在那个标点上
  （376《将心给我》末行的 `呼召:“将心给我。”`）。悬挂的前提是左边那一带是空档。
  连带补了 `Lyric` 标点表里漏掉的**半角冒号 `:`**（Kotlin 原文也漏了，是这次的一处刻意背离）——
  漏收它就把冒号当成正文的一部分，上面那条判据认不出来。
- **叠排的各段歌词要一起算宽度**（2026-08-25）：`calcXPos` 原来只按 `NoteEntry.lrc`（第一段）
  留位置，字更多的那几段就互相压上去——156《百只羊有九十九》第 2 段「主说那只亦我所有,」
  比第 1 段长出好几个字。改成取各段里最靠左的左缘、最靠右的右缘（`lrcs`）。
  全书「相邻歌词墨迹相压」由 121 处降到 **0**，代价只有 1 页。
  （标点的宽度后来改由 [歌词标点挤压](歌词标点挤压.md) 那套统一管，不再换字符。）
- **增时线按墨迹与数字对齐**：Times 的连字符墨迹比数字中线低 1.37pt（数字墨迹中心 −4.08、
  小节线中点 −4.03、增时线 −2.71），一排音符里高一道低一道。但这一下**只能补在绘制上**
  （`DrawText.dy`，`pdfwrite` 画的时候叠加）：改 `NoteEntry` 的 y 会让 `countStaffRows` /
  `measureCellsPerLine` 把增时线当成另一条谱行，实测全书从 619 页涨到 **1529 页**、478 首判成二次折行。
- **行内断点开着**（`useMidBreaks: true`）。原书每一行都在小节线上收尾，但那是固定版式的结果：
  弱起谱（005《荣耀归与天父》，每句都收在小节中间的 2 拍长音上、后半小节是下一句的弱起）
  一条小节末断点都找不到，关掉行内断点等于把整曲交给容量保险每 6 小节机械切一刀，
  句子被拦腰截断（「…为救我们 / 罪人赐下独生子，」）。phrase 的 DP 本就给行内断点加罚 6、
  只有句号/长音级的强信号才用得上它，比在这里一刀切更准。全书实测：
  行末收在标点上的谱行 **60.7% → 89.3%**、过短行 9.4% → 7.3%，代价是谱行 +7%（乐谱页 648 → 682）。
  逐曲只有 070、448 两首各多出一行不在标点上收尾。
- **排完两两并短行**（`applybreaks.ts::mergeShortLines`）：行长目标以**小节数**计，而每小节几格
  随拍号而变——005 每小节才 3.2 格，4 小节只有 13 格，版心却放得下 27 格，一句一行只用了半幅
  版心还要被 justify 拉开（原书这首就是**一行两句**）。故相邻两行都短于容量 × 0.6、并起来仍
  放得下时，删掉中间那个断点。**只删断点、不新造断点**，行末仍收在标点上（保留后一个断点）；
  段界与末行不参与；**只并一轮、成对推进**，连锁并下去会把三四句挤成一行。
  001 一句 16 格、两句 32 格 > 容量 31，并不动，仍是一句一行。
  全书实测（2026-08-25 那一版口径）：谱行 2731 → 2327（比不开行内断点的 2500 还少）、
  行末收在标点上 93.4% → **94.0%**、过短行 8.1% → **1.5%**，且**没有任何一首**
  「不在标点收尾的行」变多。后来容量口径又修过几轮（附点计数、歌词字距），
  绝对数字会变，但三项的相对关系一直成立。
  005 因此排成 4 行（每行两句、都收在标点上；原书是 6 行，`…为救我们罪 | 人赐下独生子…`）。
- **两道保险**，因为「格数」与排版器的「像素宽度」只是近似对应：
  1. `applybreaks.ts::enforceLineCapacity` 在写 LineBreak 之前按容量与小节数补几刀。
     它数行边界时**要把行内断点所在的小节一起算上**（并与调用方的 `useMidBreaks` 保持一致），
     否则在已经够短的行上再补一刀——005 那种一条小节末断点都没有的谱，等于整曲被当成一行。
     光看格数会漏掉「九小节一行」——增时线在乐句分析里按 0.7 折算、排版器却是整格
     （006《颂赞归与耶稣圣名》的主歌就是这样，排版器随后硬折，甩出一行只剩 "3 2 1--"）。
  2. `rebuild.mjs` 排完数一遍谱行数（`countStaffRows`），多出来就再排一轮，**收紧的格数取
     「折完之后最长的那条行」**（`browser.ts::maxStaffRowCells`）——那才是这一首真的放得下多少。
     原来是按 `cells × expect / rows` 的比例收，但**一条行只要溢出一格也会折成两行**，
     比例立刻变成 2 倍：022《凡有气息当赞美》因此从 30 格一步收到 15 格、排成 10 行
     （原书 6 行、DP 本来给的是 8+8+8+9）。改成按实测最长行收之后它收在 27 格、5 行。
     （更早还有一档「先给并短行加 `slack` 余量、再收格数」的阶梯，一并去掉了：
     `slack` 会让本该并的两行并不上——022 收紧后的 8+7 格两行就是被 `slack=6` 挡住的。）
     `countStaffRows` **要按页分组数**：各页的谱行落在同样几条基线上，把全书的 y 混进一个集合，
     第二页起的行会被当成第一页那几行、行数少算 —— 这道保险因此长期漏判。

- **`enforceLineCapacity` 要均分，不能贪心**：原来是从左往右塞满就切一刀，9 小节 / 容量 4 小节
  切成 4+4+1，末尾甩出一个只有一小节的行。改成先算这一段至少要几行 `k`
  （`max(ceil(总格数/容量), ceil(小节数/hardMeas))`），再按「每行 总量/k」找最接近的小节边界落刀，
  同样的 9 小节切成 3+3+3。**放得下就一刀不切**（`k ≤ 1` 直接返回）——这一步只是兜底，
  分行的主力是 DP。

  **容量到底准不准**：按实测 `cells` 排一遍再点对点核对（568 首），12 首与计划行数对不上，
  其中 5 首是容量高估导致的真溢出：007 量出 32 格但 30 格的行就被折了（`[19,30]` → `[19,24,3]`）、
  016（35→33 折）、285（37→32 折）、J09（38→36 折）、J21（41→39 折）。同样的格数，
  歌词字多的行更宽，所以「格」永远只是近似；全书「最长行 ÷ 实测容量」中位 82%、最大 108%。
  上面那轮迭代兜得住：全本 568 首里 **六七十首**要重排，重排后**没有一首**还剩二次折行
  （rebuild 每次跑都会打印这行自检）。当前乐谱 **607 页**（原书 605），总 656 页、缺字 0、568/568。
  注：这两个数会随判据调整小幅浮动，以 rebuild 每次打印的自检行为准，别把它们当成硬指标。

### 和弦

`loadMusicXml` 原本整个跳过 `<harmony>`（CLAUDE.md 记的「Score 装不下和弦」说的是 **jpwabc 那条路**，
Score 这边只是一直没做）。现在 `src/score/harmonyparse.ts` 把它读成 `Chord.harmony`，
`NoteEntry.addHarmony` 排到音符正上方，富文本分段复用 `layout/harmony.ts`（与五线谱、文本谱同一套）。
导出侧的既定约束不变：`musicxmlpatch` 仍然不碰 harmony。

两处要害：

- 和弦**按基线对齐**（同一行的和弦要齐平），不能按墨迹顶或底摆：带升降号的用 Bravura 的 csym 字形，
  em 框比字母高得多，按墨迹摆会比邻近的和弦高出十来个点。`g.update()` 之后 `g.y` 正好是
  「墨迹顶相对基线」的偏移，所以**累加**目标基线而不是赋值。
- 和弦里的 SMuFL 段要用**紧包围盒**（`TextFrame.inkBound`）。Bravura 的 `ascent − descent` 是 **4.02 em**，
  一个和弦里夹一个升号，这一行就凭空高出四个字号——行距全乱、一页少装两行。

### 反复记号、房号、三连音括线

引擎原本一处都没画过：`Barline` 只有「细线」「细 + 粗」两种，`layout.ts` 里没有一行读
`repeatForward / repeatBackward / endingNum`（原 Kotlin 版也没有，不是移植遗漏）。成书要照原书排，
所以补了这一层，画法与五线谱同一套：

- **`Barline` 接 `BarlineSpec`**（`style` / `repeatBackward` / `repeatForward`），按 bar-style 决定粗细组合
  （`light-heavy` 细+粗、`heavy-light` 粗+细、`light-light` 双细线），反复点画在**细线那一侧**
  （`:‖` 左、`‖:` 右），两个实心圆用四段三次贝塞尔画在小节线中线上下。
- **小节开头的 `‖:`**（MusicXML 的 `<barline location="left">`）以前根本不进 entries，现在会额外插一条。
- **相邻的两条小节线只留一条**（`dropDoubledBarlines`，在 `layout()` 开头统一扫）：`‖:` 画在小节开头，
  而上一小节末尾本来就有一条细线，挨在一起就是「细 粗 细」**三条竖线**（010 第一行）。
  普通的那条让位；两条都不普通（`:‖‖:`）就都留着。放在 `load()` 里边插边弹是不行的——依赖调用顺序，实测弹了也还是三条。
- **`Barline.entryWidth()` 要算整组**。基类只看 `entryItem()`（第一条竖线），于是 `‖:` 右边那两个反复点
  没有占位，后面的音符直接压上来（037 第三行的 `‖:5` 里点与 5 叠在一起）。终止线（细+粗）同理。
- **房号**（`Line.addEnding`）是行级装饰，与 tuplet 一样在 x 定稿后画：`⌐1.` 的横线 + 左端下垂 + 数字。
  三条要害：
  1. **长度遵照 musicxml**——房号线到**第一个** `<ending type=…>` 就收，`stop` 封口、`discontinue` 敞着。
     二房常写成「`start` + `discontinue` 在同一小节，逻辑上的 `stop` 在几小节之后」（037 的二房 m9 就地
     discontinue、m11 才 stop），一路延伸到最后一个 `endingRight` 就会画出跨三小节还封口的长横线。
  2. **排在最上方，而且全行一个高度**：扫过该 x 区间里所有已画好的东西（和弦、三连音括线、圆滑线
     都在音符上方那一带）取最高点再往上放，只按音符墨迹顶算必然叠在一起。
     高度取**全行所有房里最高的那个**、一起施加——这一条与端点那一条（见下）都照
     **文本谱那一路**（`src/pu/layout.ts`，那边是按印刷原版做的：横线走一条统一车道，
     要让开下方内容时整行一起抬）。逐房各算就会错开：169《全新的你》的一房上方有和弦、
     二房没有，两条线曾差着几个点；扫描时还会扫到**前一个已经画好的房**，把二房整个抬起来。
  2b. **端点贴着两侧的小节线**（起点贴前一条的**右缘**、终点贴后一条的**左缘**，
     各让 `endingSize × 0.12`），不贴房内首末音符。
     贴的是小节线的**墨迹**（`Barline.inkLeft` / `inkRight`）而不是 `group.x`：
     `:‖` 会先画反复点再画线，两者差着 `dotR × 2 + dotGap`（实测 4.8pt），
     拿 `group.x` 当线位，房号横线就短一截、看着没对齐（158《一件礼物》的一房终点差 4.3pt）。
     按音符各向外扩 `0.35em` 时，相邻两房之间没有任何缓冲，158《一件礼物》的一房二房就顶在了一起；
     贴小节线之后两房天然隔着一条小节线的宽度。找不到小节线（行首/行末截断）才退回音符外扩。
  2c. **房号数字里只许数字与半角句点**（`1.2.`）：原来多房号之间用的是 U+00B7 中点（064《啊！圣善夜》）。
  3. 房号数字归 **`verseNum`** 那一档角色，**不能算成 `note`**——`countStaffRows` / `measureCellsPerLine`
     数「占一格的音符」时会把 `1.` 当成音符，一个房号就凭空多出一条谱行（010 曾因此每轮都判成折行、
     迭代六轮都收不住，全书 19 首二次折行）。字号用 `tuplet` 那一档（原书房号与三连音数字同号，
     墨迹高 4.92pt，对应 musicxml 里的 `<ending font-size="6.25">`）；`verseNum` 是歌词那么大的段号，会大三倍。
- **括线的线宽与脚长取原书统计**：房号/三连音的括线在 `inventory` 里归 `bracket` 类，
  但它们落在 `spec.ts` 的**线框**那一档（`frames`）而不是 `marks`，`page-report` 原先不导出，所以统计不到。
  补上之后 n=233：**线宽 0.425pt**（小节线是 1.009，细一半多）、**脚长 5.32pt**（`bracketFootEm` 0.653 字高）。
  线宽要取**几何短边**——`frames[].lineWidth` 是 PDF 的笔宽默认值 `1`，不作数。
  三连音的脚按 `bracketFoot × 0.55`：那 5.3pt 主要来自房号（整段乐句的括线），三连音只是三个音的括号，照抄会高出一截。
  三连音数字**按墨迹与横线垂直居中**（`SmuflText.bound` 给的是相对基线的墨迹上下缘，取中点对到横线上），
  按字号估偏移对不准；括线起点比音符墨迹顶再抬一个 `jpStackGap`，不然像长在数字上。
- **转拍号的分数线**：引擎默认 `strokeWidth = 1.5` 是按屏幕 `fontSize≈28` 调的，缩到成书字号就是一道黑杠。
  原书量到的才 **0.3pt**（`bookparts.ts::keyMeterItems` 画书首拍号时早就用着这个值），
  经 `opt.timeSigRuleWidth` 传进去，编辑器那条路不变。

### 调号里的升降号

`1=♭B` 不能连成一串文本画：`♭` 会跟音名同基线、同字号，位置就塌下来了（还得靠字体回退到 Bravura，
字形基线又与 Times 不同）。`keyMeterItems` 把升降号**单独成项**，字号与抬升量按原书 002 实测反推——
**换算必须走 Bravura 的字形盒**，拿基线去凑墨迹会差一半：

```
原书 002：♭ 墨迹高 6.3、音名 8.0，♭ 的墨迹顶比音名顶高 3.9pt
accidentalFlat 的墨迹在基线上方 0.448em、下方 0.168em（高 0.616em）
  KEY_ACC_SIZE = 6.3 / 0.616 ÷ 音名字号 12.3 ≈ 0.83
  KEY_ACC_RISE = (8.14 + 3.9 − 0.448 × 10.2) / 8.14 ≈ 0.92 个音名墨迹高
```

抬得不够（先前按 0.45）就成了「♭ 与音名顶部对齐」，竖线该高出去的那截没了。
括号里的移调建议 `(1=♭E)` 走同一个 `putTonic(prefix, tonic, suffix, x)`。

### 一行的头尾长什么样：几条判据 + 常驻断言

（2026-08-25。起因是逐首看下来的一批「排出来就是难看」：020 一行只有半小节休止、
372/402 各行弱起长短不一、373 的「跟随我」没收在行末、125/404 末两行一长一短、
22/319/374/378/390/419 中间挤出只有两三个格的短行。）

判据都做成**断点代价**（`phrase.ts::headPenalty`，加进 DP 的 `bc`），不是事后搬音符：
这一行放不下时 DP 会自己改在别处断，「排不下就重新断句」。三条都只看断点后紧跟的那点内容，
所以每个候选断点一次算好。

- **(a) 行首残小节里一个音符都没有**（半小节休止 + 小节线）→ +12。一行开头是个空拍，
  唱的人不知道要等谁（020《向主歌唱》第 4 行）。**整小节的休止不在此列**——整节归上一行
  或下一行都行（用户口径）。
  同源的一处是段界：`retreatPastPickupRest` 原来一律把段界从弱起休止上回退到休止之前，
  休止**正好收在小节线上**时那样回退就造出了这种行，现在那种情形不回退。
- **(b) 行首是「半拍及以下的休止」且这一行的弱起与本曲多数行不一样长** → +8。
  372《跟随耶稣》弱起是整 1 拍（附点八分 + 十六分），第 2/4 行却从 `0_ 今. 已_` 起头（1.5 拍）；
  罚过之后那半拍休止留在上一行，四行齐头。402 同型。
  **「半拍休止 + 半拍音符」本身没问题**——只要它与本曲的弱起一样长就不罚（用户口径）。
  四分及以上的休止也不在此列：那是上一句唱完的收气，本来就该留在上一行。
  这一条曾写成「行首残小节与本曲弱起不一样长就按差额罚」，范围太宽：15 首编辑器基线里
  「一生中最可 / 贵」被劈成两行（那一行的行首是**四分休止**，罚了它反而把词拆开了）。
- **一行不许长到顶别人两个** → `quality` 的 `outlier` 项（权重 60）。
  用户口径：「拆开的依据是现在一行相当于其它行的 2 倍长度了」。
  三处要害：
  0. **匀度按全曲算，不按段**。试过按段各算各的（主歌一把尺子、副歌一把尺子——用户口径
     「副歌可以接受比主歌长比较多，主歌内/副歌内每行尽量相近的长度」），口径本身是对的，
     但它会放过「整段偏长」：374《跟随救主》段 2 的两行各 23 格彼此很匀，可段 1 每行才
     13 格，那两行本该各拆成两行；全书行长悬殊也从 5 首涨到 10 首。段内匀度日后单独做。
  1. **按时值比**（Σ `Chord.duration`），不是小节数也不是格数。小节数太粗
     （070《天使歌唱》那一行按小节只有 5 vs 4）；格数是视觉宽度，掺着增时线与歌词字数
     （`Chord.beats` 本身就是增时线格数、不是时值）。时值才是这一行在音乐上到底有多长。
  2. **拿中位数作基准**（均值会被那一行自己抬高），超过 1.4 倍才算。
  3. **评分只能在 DP 排得出来的方案里挑**。曾经 DP 常常排不出指定的行数
     （374《跟随救主》的 `want [4,4] → got [4,3]`），那套方案被「行数对不上」丢弃，
     候选池里压根没有「把那一行拆开」的选项；当时靠一步事后局部改良 `splitLongest`
     顶着（找出过长的那一行、在它内部切一刀）。**那是个补丁，根因在下面两条判据上，
     修好之后已经删掉**——374 现在 DP 直接排出 8 行各 2 小节。
     根因都是「拿错了尺子」，两条：

     - **「这个断点是不是落在句末」不能拿 `punctAfter` 的分数去比 6**，要问 `endAfter`
       （`isSentenceEndAt`）。「很短的分句减半」（`SHORT_WORDS`）会把「跟随！」「主！」
       这种呼语句的 6 折成 3，于是它们一律不算句末；374 段 2 整段都是这种短句，
       `splitSentence` 因此认定「后面还有个句号、整句放得下」，给每一处 2 小节的断法
       压上 24 分的重罚。`endAfter` 早就算出来了，只是从来没有人用。
       **只改 `endsAtSentence` 那一处**：`crossedEndPunct` 与前瞻找下一个句号那两处仍按
       `punctAfter === 6`——放宽了会把整首末尾那个句号也算进来，378《主耶稣我爱祢》
       的最后 8 小节就被锁成「一句」（实测第 2 行 16 拍 → 11 拍）。
     - **「这句放得下吗」要与容量判据用同一把尺子**：`cellsAreItems`（成书那条路）下
       容量数的是格子个数（`cellsIntUpto`），而 `splitSentence` 原来拿的是折算过的小数格。
       215《同心合意》第 2 段整段是一句「…主爱无尽。」，小数格 32.8 ≤ 33 判成「放得下」，
       于是从任何位置断开都罚 24 分、DP 排不出 2 行（`want [x,2] → got [x,1]`）；
       而它按格子数其实是 34 格、根本放不下，那一行只好交给容量保险按宽度硬折，
       折点落在「人，」的头上。（同一个坑在 `cellsIntUpto` 的注释里已经写过一次。）

     DP 排得出的行数变多之后，`quality` 那边要补上两项——原来「多断一刀甩出个短行」
     是靠 DP 排不出来挡着的，不是靠评分挡着的：
     - **短的那头也要有 outlier**（`shortOutlier`，与长的那头共用权重 60）：
       最短的一行（末行除外）不到中位数 0.6 倍就罚。cv 管「相近」、`outlier` 管
       「长到顶别人两个」，短的那头原来没人管（实测 D8 行长悬殊 7 → 8 首）。
     - **末两行别一长一短**（`lastPair`，门槛 0.6、权重 60，与 D8 的末两行那一支同一口径）：
       DP 里那个 `lastPair` 是一遍之内的前瞻，方案与方案之间比不了。
- **(b3) 各行的行首残小节要一样长**（凑整拍）→ +12，**只在成书那条路、且本曲确实有弱起时**：
  (b) 只认「行首是半拍及以下休止」，行首是**音符**的弱起它管不着——363《倾听我的心》
  的行 1/2/4 从 1 拍起头（`0_ 5,_` / `3_ 4_`），行 3/5/6 却只有半拍（`5,_` / `3__ 4__`），
  上一行行尾那个 `0_` 该挪下来凑成整拍，六行才齐头。两处收窄：
  **只罚比标准弱起短的**（比标准长的是另一回事，一并罚就太宽，实测末两行悬殊 7 → 14 首、
  收气休止被甩到行首 12 → 28 处）；**从整小节起唱的谱不罚**（`pickupStd = 0` 时没有
  「标准行首残小节」可言，一律罚等于禁掉所有行内断点）。
- **(b2) 句末标点之后的那个休止是上一句唱完的收气，该留在上一行** → +8：
  上一行行末带句读标点、下一行却从休止起头的话，那口气就被甩到了行首
  （077《耶稣我主荣耀王》的「历风霜；」之后那个休止）。
  **行首那个字自成一句时不罚**（(c)/(c′) 两条都是）：它前面那个字就带着标点，说明这一句
  从它起唱、不是上一句的尾巴——131《无他，只有耶稣宝血》的「血！」是感叹词长音，
  142《圣灵请来》的「来，」是命令语气，两个标点之间只有一个字（用户口径：这种可以接受）。
  D3 / D4 两档同步豁免。

  与 (b) 的分工：(b) 管「半拍休止的弱起长短不一」，管不到四分及以上的收气休止
  ——(b) 那一条的注释早就写着「本来就该留在上一行」，却一直没有对应的罚。
  **例外：这样起头正好凑成本曲的标准弱起时不罚**——那时休止是下一句弱起的一部分、
  不是上一句的收气，挪下来反而齐头（363 的 `0_` + `5,_` 正好一拍）。
  用户口径：「休止后有音符的残小节是可以接受的」。(b2) 与 (b3) 会打架，靠这一条分开：
  **能凑成标准弱起的就挪下去，凑不成的留在上一行**（077 的「历风霜；」）。
  D5 那一档的判据同步跟上，否则它会把正常的弱起也报成毛病（实测虚报 24 → 3 处）。
- **例外：「照本曲的起唱样式」起头的不罚**（(b) 与 (b2) 一起豁免，2026-08-27）：
  本曲**没有弱起**（从整小节起唱）、而首小节开头就是一个短休止时，那个休止是这首歌
  **每一句**的起唱样式，不是上一句唱完的收气——144《求圣灵吹我》六句全是
  `|0 3 2 3 5 6 1|2 3 2--|`，每一个乐句开头都被 (b)+(b2) 罚 16 分，断点只好落到句子中间，
  排成「求主圣灵向我吹气：赦我一切罪过…」两句挤一行。判据（`phrase.ts::startsLikeSong`）
  只认**小节头上、与首小节一样长**的休止，短了长了仍旧照罚。
  D2 那一档同步跟上：**与本段首行一样长的行首一律不算毛病**，哪怕它不是众数
  （144 两种行首各占一半，众数一挑就把「与首行一模一样」的那几行报了出来）。
- **休止就是乐句的气口** → 四分及以上 +4、八分 +2（成书那条路；编辑器维持原来的 +1）。
  唱的人在休止处换气，断在那儿天然合适。原来那 +1 弱得几乎不起作用。
  实测「句末标点之后的收气休止被甩到行首」17 → 12 处。
- **标点要看各段歌词，不能只看第 1 段**（`lyricPunctScore`，成书那条路）：多段共用同一条旋律，
  各段的收句位置本来就该在同一处。**取中位数**——先试过最大值（一段点了句号就算落点，
  可那多半是那一段的抄写差异），再试过均值（把分稀释得太狠，一个真落点的分能掉到零头，

- **(c) 行首那个字带着句读标点** → +8（成书那条路；编辑器不变）：一句话的最后一个字落到了
  行首，上一句的尾巴被甩过来了——077《耶稣我主荣耀王》的「厌弃难当；」曾被劈成
  「…难」＋「当；…」。**这一条只看行首那个字自己**，与 (d)「别把一句的最后一小截甩到下一行」
  不同：(d) 要往后数几个字才到句号，判据宽、牵动面大，改它会连累别处的断点

- **(c′) 行首是「带句读标点的长音」**（≥2 拍）→ 再 +10：那是上一句真正的收尾，该留在上一行。

  「主祢真伟大」从 9 行涨到 10 行、还多出一行只有 2 小节）。
- **(d) 别把一句话的最后一小截甩到下一行开头**（`tailWeight`，成书传 1、**编辑器默认关**）：
  断点之后没几个字（不到一行的三成）就到句号了的话，那截尾巴属于本行

  ——077 的「难当；」从上一个标点起只唱了「厌弃难当」四个字，分被折成 3。

  实则是缺了一条例外——**断点本身就是句末时 (d) 不成立**，下一行开头那一小截是自成一句的

  终于并回上一行。分量也跟着 `punctAfter` 走（短呼语句只罚一半）。

  「留。」拖着 `2--- 2--` 七格，13.65 格的上限一减，罚几乎归零。

  （`PUNCT_END` / `PUNCT_MID` 都以标点结尾锚定，`”` 挡在后面），于是引文的收尾处认不出乐句落点。
  判标点前先剥 `”’"』」）〉》〕】`。这一条对 15 首编辑器基线零影响（逐行比对过）。
- 与之配套的还有一条**标点顺延**的修正：句子收尾的长音后面跟半拍休止、再接下一句的弱起时
  （`…呼， | 0_ 今. 已_ |`），标点原来只顺延到**四分及以上**的休止上，八分休止拿不到分，
  于是「断在长音后」比「断在休止后」还便宜。现在八分休止也顺延，并且**把长音的分带过来**

### 断句只看内容，纸张只管「排不排得下」

> **试过把容量彻底赶出断句层，不成——结论记在这里，别再试第二遍。**
> 口径本身是对的（「容量不能卡断句，排不下就换非断句的方案」），做法是把 `quality` 的
> 超容量硬伤（`+100 + over²×8`）与 `lenCost` 的超容量罚都关掉。结果：
> 断句本身确实更匀了（357《祈祷》末两行终于并成一行，cv 10.2 → 3.7），
> 但**难看的事整批搬到了 C 档**——全书「行首带着上一句的标点」0 → 190 处、
> 「行首是带标点的长音」0 → 146 处、「行末断在拖腔上」2 → 41 处。
> 把补刀改成按乐句凭据挑（上面那条 `cutScore`）能收回大半（190 → 14、146 → 6），
> 但 λ 怎么调都差基线一大截（λ=1 时行长悬殊 7 → 80 首，λ=6 时行首带标点 0 → 71 处）。
> 根子是**两者能动的范围差着一个量级**：DP 能重排整首，补刀只能在那一行内部挑一条小节线。
> 让全局规划器自己躲开版心，天然比「先排坏再局部补救」强。
> 而且 374《跟随救主》也塌了（6 行、两行 23 格）——`quality` 的超容量项对它同样是承重墙。
> 最后一击是：这条改动本来要救的 357，**物理上根本放不下**——强排 28 格，排版器照样折行，
> rebuild 的容量收敛循环自己把它收回 26。版心在那个字号下就只有 26 格。


用户口径（2026-08）：**与纸张大小相关的指标一律不进评分，只有反映乐句工整度的才进**；
「排不排得下」只用来做**整首级的模式选择**。原来 `phrase.ts` 的评分里混着三种纸张相关的分：
行长目标 `(meas − target)²`（target 由版心容量折算）、`ROW_COST × 行数`（每多一行 20 分）、
以及 `MIN_CELLS` / `MIN_MEAS` 那一路「行太稀」的罚——等于让版心宽度替作曲家决定乐句断在哪儿。

开关是 `PhraseOptions.contentOnly`（`bookstyle.layout.phraseContentOnly`，成书默认开）。
**编辑器那条路一字不动**（`phrase-lines.mjs` 的 15 首基线逐行比对过）。

#### DP 里留下什么

| 项 | contentOnly 下 |
|---|---|
| `lenW × (meas − target)²` | 第一遍 DP 传 `lenW = 0`；方案选优那几遍的 target 是「本段小节数 ÷ 行数」，**相对量、不含纸张**，只是让 DP 排得出指定的行数 |
| `meas > maxMeas` 的 ×40 | 删（maxMeas 也是从容量折算的） |
| `cellsInt > maxCells` | **留**，这是唯一的纸张项：排不下是硬伤 |
| `MIN_MEAS` / `MIN_CELLS` 的稀疏罚 | 删；DP 里只留「中间行不许只剩一小节」这一条硬禁 |
| `ROW_COST × 行数` | 删（行数不算分） |

#### 断点强度要真的分得出高下

`breakCost` 原来是 `max(0, BASE_BREAK − sc × breakWeight)`，`breakWeight = 3` 时
**`sc ≥ 3` 之后一律钳成 0**：「断在长音 + 标点上（13 分）」与「断在一个普通小节线上（9 分）」
代价一模一样，断哪儿全由别的项说了算——175《人惟以信得称义》的「能大力，」就是这么被让掉的。

改成把强度**归一化到 `[0, BASE_BREAK]`**：`BASE_BREAK × (1 − sc / 24)`，24 是实测最强断点的量级。
两条不能动的：

- **不许负收益**。代价在 DP 里是累加的，允许挣净收益就会一路狂断——068《天使报信》试出来排了
  10 行，其中四行只有一小节。
- **总量程仍是 0~8**。`headPenalty`（行首判据）、`lastPair`（末两行）、`crossedEndPunct`
  都是按这个尺度调出来的，量程一放大它们就被稀释（实测全书 D1~D8 六档一起变差）。

#### 两个新的内容指标

- **平行乐句开头**（`headFpOf`，`phraseParallelWeight = 6`）：一行的头 6 个音与另一行相同时，
  把它们各自排成行首，两行就对齐得上——原书的分行大量是这个样子。重复段检测（`repeatEdges`）
  管的是「整段重复」，管不到这个：平行的两句往往只有开头几个音相同，后半句各走各的。
  095《复活良辰》/ 118《高歌和散那》因此排成一二四行同开头的四行，175 的一二行、070 的副歌两行同理。
  **要求断点本身先是个像样的乐句收尾**（句读标点 / 长音 / 休止 / 延长号）：只看旋律指纹会把词
  拦腰切开——096《哈利路亚！感谢主》的「哈利路亚」唱好几遍，「路亚」的开头旋律自然与别处相同，
  于是「哈利｜路亚」之间被判成平行乐句、拿到 14 分。**旋律重复只是佐证，断不断得看乐句收没收尾。**

  这一条踩过三个坑，都是拿 363《倾听我的心》换来的（那首是三对平行乐句，六行两两开头相同）：

  1. **奖励只进方案评分，不进 `scoreAt`**。在断点强度上给分，DP 会为了凑一个平行开头
     断出短行（实测全书中间行过短 4 → 18 处、行长悬殊 6 → 12 首）。它该影响的是
     「几套断法里挑哪套」，不是「这一刀值不值得断」。
  2. **潜在行首不能只认「小节起点」**。弱起谱整个漏掉——363 六行全是从小节中间的弱起起唱
     （`3_ 4_ |5- …`），三对平行开头一个都没进候选池。判据改成「上一个音符是个乐句落点
     （小节末 / 带标点 / 长音 / 休止）」，与 `startsParallel` 的门槛同一口径。
  3. **指纹要先跳掉行首的休止**。同一段旋律有的行从休止起头、有的直接从弱起音起头
     （363 第 1 行 `0_ 5,_ |3. 3_ 2.`、第 3 行 `5,_ |3. 3_ 2.`），不跳过就对不上。
  4. **别用固定长度的指纹，按最长公共前缀算**（`parallelLen`）。长度定多少都不对：
     定短了噪声大（随便两处开头几个音相同就算平行），定长了又漏——072《信徒欢唱》
     的两处平行开头是 `5 6 5 4 | 3 2 1`，第 8 个音就分岔，10 音指纹认不出来。
     改成两两比公共前缀、**重复得越长得分越高**（`quality` 里按 `min(len,12)/12` 计），
     至少 4 个音才算数。全书基线因此还变好了一档。
  5. **允许一个音的出入**（2026-08-27）。同一段旋律在两处只差一个装饰音是常事——
     158《一件礼物》的「生命有限，时光也会走…」与「礼物，虽然好，如果你不要…」
     从第 5 个音起差一个（`5 1 2 3 7…` / `5 1 2 1 7…`），严格前缀只有 3 个音、
     连 4 个的门槛都够不着，那一对平行乐句整个判没了。差的那个音**不计入**长度，
     且前后都要接得上（各至少 2 个音）才算，免得随便两处「开头两个音相同」靠一次豁免攀上亲。
- **平行乐句开头也是「乐句在此收尾」的凭据**（2026-08-27）：DP 里那条
  「整句放得下就别在句中拆」的 24 分罚（`splitSentence`）原来只认音乐凭据
  ——够长的长音、延长号、休止，**歌词逗号不算**。可 169《全新的你》副歌
  「…体会你的心情，｜耶稣能够改变…」的落点是个 2 拍的 tie 尾巴，被罚了 24 分，
  DP 只好改断在下一句的「够」上（`5--` 是 3 拍长音、白拿凭据），整个副歌的断点全体错开一句。
  `startsParallel` 本身已经要求断点先是个像样的乐句收尾，再加上「后面那段旋律在别处原样重来」，
  比一个 3 拍长音硬气得多。**但要重合够 8 个音**（`PARALLEL_STRONG`）：4 个音那档只够当
  加分的佐证，拿它去顶掉 24 分的罚太松——169 的 `m14·` 只重合 7 个音，
  「期待有人能够了解你心，｜能够爱你赐你力量更新。」就地被拆成 8 拍 + 27 拍两行。
- **跳转记号处强制断行**（`PhraseOptions.jumpMeasures`）：Fine / D.C. / D.S. / To Coda
  只存在 `score.playData.jumpTo` 里（供 `play()` 展开），排版层原来完全看不见。
  两条要害：
  1. **只取记号本身**。`segno` / `coda` 是跳转的**目标**不是换行处，把它们也算进来，
     497《这世界非我家》就被强断成 7 行、其中一行只剩 2 格。
  2. **后面剩不下半行（8 格）就不强制**。Fine 常写在临近曲末处（`D.C. al Fine` 的谱），
     在那儿硬断一刀只会甩出个两三格的尾巴（018 实测末两行 21 / 2 格）。
  强制断行走 DP 的分段边界 `cuts`（**不写 `sectionStarts`**——那是「另起一页」），
  并记进 `PhraseBreaks.forced`，后续的并行/补刀一律绕开。光靠 `scoreAt` 加分压不住：
  断点代价量程只有 0~8，而行长匀度那一项能到几十分。

#### 出几种方案再评分选优

`evenWeight > 0` 时以第一遍 DP 的行数为底，每段各试几档行数，逐个组合跑 DP，再按同一把尺子选优。
两处随新口径改了：

- **候选要双向**（`−2…+2`）。第一遍已经不受行长目标约束，行数是照内容断自然涌现的，
  既可能偏多也可能偏少——117《祂名称为奇妙》头三句各有一个 24 分的强断点，第一遍照着断出
  7/7/13/27/24/25 格六行，而更匀的四行方案压根没被生成过。旧口径下第一遍按行长目标排，
  行数只会偏少，单向就够（编辑器那条路不变）。
- **评分改成无量纲、与行数无关**：

  ```
  分 = evenWeight × 100 × 变异系数(各行格数)      // 标准差 ÷ 均值，不含容量
     + 8 × (Σ断点弱度 ÷ 行数)                      // 均值，不是总和
     − parallelWeight × 平行开头占比 × 10
     + 超容量硬伤（100 + 超出² × 8）
  ```

  三处都是拿具体曲子换来的：

  - **弱度取均值**：去掉「每多一行 20 分」之后，总和会让「多断几刀」平白变好
    （每一刀都挑最强的断点，总弱度反而降），于是每首都摊成一堆短行。
  - **行长不匀用变异系数**（标准差 ÷ 均值）而不是方差：方差是「格²」，容量大的谱天生分高，
    等于又把版心宽度请了回来。试过在 contentOnly 下干脆不算这一项，全书立刻崩
    （中间行过短 5 → 70 处、行长悬殊 6 → 51 首）——**行与行的长短差异确实要算权重**。
  - **弱度要乘 8 才压得过匀度**：DP 第一遍（代价非负、累加）总是交出「行数最少、每行顶着
    容量」的那一套，而它的行长天然最匀（都填满就都一样长），不加权就永远赢。
    配套把 `phraseEvenWeight` 从 2 调到 **1**：2 的时候 077《耶稣我主荣耀王》仍塌成 5 行
    （19/23/19/24/21，「宝座｜亲来」「忍｜饥」都断在词中间），0.5 又太松（中间行过短涨到 20 处）。

  **断点代价一律非负**。试过把零点摆到量程中间让强断点挣净收益，全书立刻碎化
  （中间行过短 5 → 61 处）——DP 里代价是累加的，一给负收益就一路狂断。

### 整首的排版模式阶梯（`chooseLineLayout`）

「排不排得下」只在这里用。先断句，再按 **B → A → C** 取第一个可行的档
（原书绝大多数是一行两句，所以两句一行是首选）：

| 序 | 档 | 做法 |
|---|---|---|
| 1 | **B** `pairs` 每 2 句一行 | `mergePairsUniform`：段内从头起两两并，段界处重新起对 |
| 2 | **A** `phrase` 一句一行 | 断点原样用 |
| 3 | **C** `even` 均匀排版 | 乐句断点**不丢**，只把放不下的行按容量均分补刀 |

「可行」= 每行都放得下，且中间没有只剩一小节的碎行。评分**不在档之间裁决**（档序是硬的），
只用于同一档内多套断点方案的选优。

两条曾经踩过的坑：

- **B 档不能逐对局部判**。原来的 `mergeShortLines` 是「相邻两行都短于容量六成才并」，
  同一首里于是有的地方并了、有的没并，行长反而更不齐。改成全首一个口径：要么都并要么都不并。
- **B 档「并不成」就不是 B 档**。`mergePairsUniform` 返回 0（不能全首一致地并）时，
  原来照样返回 `"pairs"`——行数一行没少却标成并了，全书 40 首都是这样。
  常驻断言 **D9**（`pairsFrom` 记并之前的行数，全并的结果必然是它的一半）现在守着这条。
- **B 档要么全并、要么整档放弃**。原来是逐行推进、遇到不能并的就重新配对，结果一半并
  一半不并，行长反而更不齐——020《向主歌唱》前四行各 4~5 小节没并、末两行并成 8 小节，
  那一行就明显比谁都长。
- **B 档只在一句一行明显太稀时才考虑**（中位行长不到版心六成）。用户口径：「排不排得下
  只用于……是否采用每 2 句放在一行的按乐句排版」。不设这道闸，凡是并得下的都会去并
  ——实测全书 184 首改走 pairs、行数直接减半，那不是「原书一行两句」，那是把谱压扁。
- **B 档要看「并出来那一行的行末」**。删掉 a 的断点等于让 a+b 合成一行，那一行的行末就是
  b 的行末——b 没收在乐句落点上就别并（096 的「哈利」曾这样被留在行末）。
  判据是**行末收在标点上、或收在长音上**（`LineTail.punct` / `beats`）：长音收尾
  （一字多音唱完、行末那个音没有词）同样是乐句的落点，只认标点会把它们也挡掉。
- **C 档不能丢开乐句断点**。试过完全按容量机械均分，169《全新的你》排出 13 行、
  215 甩出一行只有 9 格，比原样还难看。现在只在超容量的行上补刀，落刀点若会切断
  圆滑线／反复房就往后挪一节（用户口径：「尽量避免 slur/ending 等跨行，尽量主歌副歌不同行」）。
- **「一行放不放得下」按真实坐标判，不按格数**（用户口径：「不要算格数，真实坐标排一遍，
  放不下再补刀」）。`layout.ts::Line.naturalSpans` 交出每个和弦的自然横向区间——那正是
  排版器折行时用的那把尺子（`group.x + maxX`），且**与断点无关**（`calcXPos` 在
  `doLineBreak` 之前跑），所以整首量一次就够；`browser.ts::measureChordSpans` 把它连同
  版心宽度包成 `applybreaks.ts::FitMetric`，断句/选档/补刀/合并全用它。
  格数是近似——同样 30 格，歌词字多的行、带八度点与附点的行都更宽；照它判，排版器会在
  断点之外又折一刀，`rebuild.mjs` 的容量收敛循环再把容量越收越小（064《啊！圣善夜》本来
  7 行的方案被一路收成 9 行 13 格）。**接上真实坐标之后那个循环基本停摆**：要重排的从
  80 首降到 4~5 首。

- **补刀的落点是挑出来的，不是量出来的**（`applybreaks.ts::pickCuts`）。原来纯按
  「格数最接近理想位置」挑一条小节线，一个内容判据都没有；中间试过「凭据 − λ·偏移」的
  线性折算与「理想位置 ±22% 的硬窗口」，都在「挑好落点」与「行长别悬殊」之间**对角摆动**，
  没有拐点（λ=1 行长悬殊 7 → 80 首，λ=6 行首带标点 0 → 71 处）。**别再拧那个旋钮**，
  根子是两条：

  1. **落点不该只在小节线上**。乐句的自然子句断点常落在小节中间，而 `PhraseBreaks.cuts`
     原来只带小节末的候选。现在全部候选连同凭据（`scoreAt` − `headPenalty`）一起带出来，
     「后带小节线」降格成一项加分（`BAR_END_BONUS`）。
  2. **贪心逐刀落不出整体工整**。改成**一行内部一次 DP** 把 k−1 个落点一起挑，
     代价 = Σ 工整项（按**时值**）− Σ 凭据×`EVIDENCE_W` − 平行加分；容量是 DP 里的
     不可行标记（真实宽度），不是补完再验。

- **`k` 只是下限，不够就自己往上找**（`K_SLACK`）。60 格 / 容量 30 的 `k=2` 要求切得分毫
  不差的 30+30，落点上没有那条线，于是要么切不出来、要么切出 31 格的一半、下一轮再各切
  一半：224《献上你虔诚的祈祷》就这么从「12 小节一行」一路劈成 3 小节一行（原书 4 小节）。
  让 k 往上找一格，60 格就是 20/20/20，正好每行 4 小节。

- **工整的段落要整段一起断**（用户口径）。段内 `min(时值)/max(时值) ≥ UNIFORM_RATIO`(0.8)
  且段内有行排不下 → 段内**每行都断成同样的份数**（整段一个 k）。有任何一行断不出合格的
  落点就整段放弃统一，退回逐行补刀。与 B 档 `mergePairsUniform`「要么全并、要么不并」
  是同一条道理的反向。

- **两半都不许太短**：各占原行 ≥30% 时值（`SPLIT_MIN_FRAC`）、且各 ≥ 版心四成
  （`SPLIT_MIN_CELLS_FRAC`，与 D7 同口径），都是**硬闸**。试过改成重罚、让强落点买下一个
  略短的一半，全书 D7 立刻 0 → 18~38 处——**别再试**。

收尾还有一步 `mergeSliverLines`：**按容量补刀留下的碎行**（只剩一小节又唱不满一句）并回上一行。
断句本身不会那么断，那是 `applyCapacityCuts` 补刀留下的尾巴
（497 曾切出一行 2 格）。段界与 `forced` 断点不动。

全书 568 首：`phrase` 550 / `pairs` 13 / `even` 5，一小节碎行 **0**。

`rebuild.mjs` 顺带把逐行事实（`applybreaks.ts::describeLines`：格数、小节数、行首残小节、

#### 断句这一层的几条口径（本轮定下的）

- **版心不影响断句**（用户口径）。`phraseFitSlack = 0`：DP 只按内容评分，排不下全交给补刀。
  试过让纸张在平局时开口（「放得下的方案优先」），全书判据确实更好（断句族 20 vs 29 处），
  但那违背口径，已关掉；开关留着（`PhraseOptions.fitSlack`）。
- **候选池与断点分数拆开**（`scoreBase` / `scoreAt`）。`scoreBase` 是「这里像不像一个乐句
  落点」——**候选池按它收人**；`scoreAt` 是「断在这里有多好」= `scoreBase` + 平行奖励。
  原来两者是同一个函数，于是平行分既是奖励又是**入池门槛**，抬高一点就有大量没有气口的
  位置涌进候选池、DP 结构整个变样（实测平行分 2 → 8：定点断言 12 → 18 条不过）。
- **平行乐句开头优先于标点**（用户口径：不管成书还是其它排版）。`PARALLEL_SCORE = 8`
  （逗号 4、句号 6）。374《跟随救主》靠它排出每行 2 小节。
- **候选行数搜 ±3 不是 ±2**。363《倾听我的心》第一遍断出 3 行，而它该是 6 行
  （三对平行乐句各自成行）——6 = 3 + 3 在 ±2 的窗外，那套方案**压根没被生成过**，
  平行奖励再高也选不到。搜多宽是内容层的事，与纸张无关。
- **要几行就真排出几行**（2026-08-27）。方案选优是「按行数列几套候选、交给 `quality` 评分」，
  可 `runWith` 只是把行长目标改成「本段小节数 ÷ 行数」、权重才 2（`RUN_WITH_LEN_WEIGHT`，
  调高全书散架，见它的注释），断点代价一压就把行数拉回去，**那套方案于是从没被评过分**
  ——144《求圣灵吹我》的 `[3,1,4]`（每句一行，正是原书的排法）DP 交出的是 3 行。
  改法：**排不出想要的行数就把行长项加重四倍再排一遍**，让它真排出来，
  好不好交给 `quality` 说了算（权重本身一分没动）。
- **`naturalSpans` 一个和弦要取各 entry 的并集**（2026-08-27 修）：`5---` 在排版器里是
  音符 + 三根增时线**四个 NoteEntry 共用一个 `Chord``，而**歌词挂在头一个 entry 上**——
  照直 `set` 会被最后那根增时线覆盖，右缘只剩一根 `-` 那么宽。065《马槽圣婴》因此把
  24 拍的一行量成 309 宽（版心 312、看着放得下），排版器照真实坐标一量却放不下，
  把行末那个 `7-` 连同三段歌词折成了**单独一行**（中间行只有一个音，用户口径：
  「这种绝对不能出现在中间行，只有尾行长音才可接受」）。修好之后 065 排成四行 12 拍。
- **没有任何乐句信号的小节线也要罚**（`breakCost` 的 `noEvidence`，+3，成书那条路）：
  「简谱通常在小节线处换行」只说明小节线**可以**断，不等于哪条小节线都行。
  355《你已否祷告》段 1 十小节排两行，`m3|`「…祷告？」凭据 19、`m4|`「基督｜圣名」凭据 0，
  DP 却选了后者——5+5 小节比 4+6 匀，`lenCost`（+4）与 DP 里的 `lastPair`（+4，
  **未归一的小节差平方**）加起来盖过了凭据那 6.33 分的差。**根子在量程**：凭据只有 0~8
  （`BASE_BREAK`），行长那几项却是没有上界的平方，零凭据的落点白拿一条不花钱的小节线
  就成了漏洞。罚一半（行内断是 6）：小节线终究比句中好断，只是不该白拿。
- **「跨了几个句号」也要问 `endAfter`**（`crossedEndPunct`，与 (d) 同一处坑）：
  `punctAfter` 的分会被 SHORT_WORDS 折半，`=== 6` 漏掉短句——355 的「是否已祷告？」
  只有五个字、折成 3，于是「…家前，是否已祷告？是否已奉基督圣名，」挤成一行也不算跨句，
  DP 反倒去挑后面那个凭据更高的逗号落点。改完 355 排成原书那样的 4+6+4+4 小节四行。
- **硬排出来的方案不许细成一条线**（`notTooThin`，版心三分之一）：`quality` 里的项
  全是**相对**量（cv / outlier / shortOutlier 都是同一套方案里的行互比），把整首均匀切碎
  天生满分——355《你已否祷告》被硬排成九行、每行 2 小节只占版心三成（105 / 312），
  cv 0、每行都是平行乐句开头，分数反倒最好。原来靠「DP 自己排不出那么多行」挡着
  （`breakCost` 累加且非负），加重行长项就把那道闸拆了，得补一条**绝对**下限。
  三分之一而不是 `fitsPaper` 的四成：144《求圣灵吹我》一句一行的八行正落在 40% 上
  （124 / 312），那是用户认可的排法。**只取下限不取上限**——「排不下」照旧交给补刀。
- **行末收在长音上**（`phraseTailLongWeight = 3`，2026-08-27；编辑器不开）：
  与「平行乐句开头」是**一对**——那条管「下一行从哪儿起」，这条管「这一行在哪儿收」。
  一行收在长音上，唱的人有地方换气、看的人一眼看得出乐句到头了，原书的分行大量是这样。
  用户口径：「应该通过平行句 + 长音结尾让 4 行赢过 3 行」。
  061《坚固保障》：三行方案按**时值**是完美均匀的 24 / 24 / 24（`cv = 0`），可按**宽度**
  是 313 / 262 / 262 —— 第一行超版心 1 个点，补刀只好把「永不动摇之｜保障；」劈开
  （池子里「障；」凭据 23、v=104 遥遥领先，但切完后半截只有 96 宽、撞上「两半都不许
  太短」的硬闸）。四行方案有一个平行开头、两行收在长音上，靠这条终于赢了那 7.4 分。
  与 `parallel` 同一形式（按行取均值、行数中性、`lineFits` 同一道闸），**两条例外**：
  1. **标点被顺延走了的长音不算**（`carriedAway`）：那一句真正的收尾在后面那个收气休止上。
  2. **后面紧跟收气休止的也不算**：`carriedAway` 只管本小节内的顺延，休止落在下一小节
     头上时它看不见——139《主爱有多少》每句都是 `|5-多 5-深？|0 3主 1恩 3有|`，
     少了这条，四行全被拽到长音后面断开、那个 `0` 全挂到了下一行行首（D5 3 → 6 处）。
  权重实测：2 太轻（061 治不了）、4 太重（D5 又涨），取 3。两条例外加上之后全书
  断句族 24 → 19 处、D6 2 → 1、D8 14 → 13。
- **平行的两行要一样长，一对句子最好都收在主音上**（2026-08-28，用户口径：
  「平行句需要尽量长度相等或相近（**重要**），落在主音上（**次要**）」）。
  061《坚固保障》的前两行是**一模一样的四小节**，原书排成 16 / 16 / 24 / 16 拍，
  而断句交出的是 16 / **24** / 16 / 16——第 2 行多吞了后一句的两小节。
  两套方案的行时值多重集一样、cv / outlier / lastPair 全一样，平行奖励也一样
  （两套的第 2 行都从同一个音起头），**分不出高下**。三件事一起才治得住：

  1. **`parallel` 按「与伙伴一样长」打折**（`evenOf`）。奖励属于「下一行从一段重复的
     旋律起头」，那就再乘上「它与那个伙伴一样长吗」（短 ÷ 长）。行首在这套方案里
     没有同源伙伴的不打折（`parallelAt` 认的是**任意**潜在行首，不限于成了行的那些）。
     **别另立一项加分**：试过给「平行且等长」单独加分，355《你已否祷告》立刻从原书的
     16/24/16/16 变成 16/8/16/16/16——凭空多出来的奖励会奖励「多切几行等长的平行行」，
     切碎反而更划算。折扣不加总量，只把**不等长**的平行削掉。
  2. **平行的一对句子双双收在主音上**（`tailTonic`，权重 2；简谱的 `1`，八度不限，末行不算）。
     **必须成对**：只有一边收在主音上不算——那说明两句的收束本来就不对称，给了分反而会把
     好好的两行拆开（125《主名至宝》原书 24 / 36 两行，单边算分时被拆成 24 / 24 / 12，
     只为让其中一行收在 `1` 上）。061 靠这一条补上了「行末收在长音上」那边的 7.5 分差
     （16/24/16/16 的行末多收在一个 `5--` 上）。
  3. **照平行伙伴补一套候选**（`alignParallel`）。前两条都只能在**已有的候选方案里**挑，
     而 DP 那几遍压根生成不出「两行等长」的那一套：061 的 4 行方案里，第 2 刀落在
     「恐慌，」还是「撒但，」两个逗号上，断点强度分不出高下。所以在评分之前，把每一行
     ——只要它的开头与前面某行同源——的收尾挪到「与那一行等长」最近的候选断点上，
     差额推给下一行（**行数不变**），补出来的方案好不好照旧由 `quality` 说了算。
     两道闸都是拿具体曲子换来的：挪过去的地方**本身得是个像样的乐句落点**
     （`scoreAt` 减行首罚为正），且**差不多长就别挪**（差距至少砍掉一半、且至少差一拍）
     ——403《救主子民还在世间》曾为了挪半拍把断点推到拖腔中间，描出一行 0.5 拍；
     补出来的方案还要过 `notTooThin`（版心三分之一）那道地板。

  全书：D8 11 → 9，其余各档持平，12 首断句改样（061 与原书一致，248《赞美基督圣名》
  24/30、J09《祢的话》前四行也回到了原书的分行）。061 收进断句快照。
- **行末也不留半个小节的休止**（`tidyLineTails`，2026-08-28，用户口径：「避免残小节全是
  休止，不管是在行首还是行尾」）。`tidyLineHeads` 管的是行首那一半（把空拍并到上一行），
  行尾这一半原来没人管：J09《祢的话》第 4 行收在 `1--- |]0` 上，行末挂着个只有休止的

- **(b3) 在「断点落在一个自己带句读标点的字上」时不成立**（2026-08-27）：那一条的道理是
  「差一点没凑齐、该把上一行行尾那点挪过来」，可上一行行尾那点是个**带标点的字**，
  挪过来就把它从句子上劈下来了——根本挪不动，罚了只是把断点顶到别处去。
  459《让我们在主里常喜乐》每一句都从小节末那半拍起唱（`…常喜乐，5虽|6然遭遇了…`），
  而本曲弱起是 1 拍（首小节那个「哦，」），「乐，」之后那个正确的落点被罚 12 分，
  DP 只好改断在小节线上，「虽|然」「冲|击」「胜|死」四处词全被劈开。
  **「挪不动」= 那个字自己带标点，或是那个字的拖腔**：J29《神必照各人的行为》的落点落在
  「…行善的人，」后面那个**无词的拖腔**上（标点顺延过来），挪到下一行就把「人，」
  和它自己的拖腔拆开了，同样挪不动——不改的话行末挂着「因为」两个字、下一行才是
  「神不偏待人，」。**休止不在此列**：那是挪得动的，363《倾听我的心》要挪的正是上一行
  行尾那个 `0_`（它拿的也是顺延过来的标点，所以不能只看 `punctAfter`）。

  「行数多优先」排序就等于「在放得下的方案里挑行数最多的那一套」，好坏一概不论——
  459 放得下的方案里 4 行 16/16/16/16（cv 0，q=7.9）与 6 行 8.5/12.5/11/13/11.5/7.5

#### 断句方案快照

档位断言判通例、定点断言判「这一首该长什么样」的几条要点，两者都留了余地；
**快照**（`testdata/500/line-snapshots.json`，`node line-check.mjs --write-snapshots` 重写）
把整套断句钉死：逐首逐行记**这一句收在哪个字上**与**这一行有多少拍**，一处对不上就报。
改断句算法时这是最硬的那道门槛。

只记这两样，是因为断句说到底就是这两件事——断点落在哪儿（尾词认得出来）、每行多长（时值）。
格数、小节数、坐标都是派生物，记了反而让快照因无关的改动而失效（换个字体、调个字距，
格数就变了，可断句一点没动）。

收进快照的是逐首核对过、认可了的那 16 首：020 064 068 070 077 095 096 118

### 转调标记要让开和弦（`Line.liftKeySigOverChords`）

`KeySig` 的「转1=X」固定摆在音符基线上方一个字号处，正是**和弦那一带**（`chordGap`），
而它的 `entryWidth()` 是 0、左右各伸出半个词宽——撞上就直接压字（144《求圣灵吹我》的
「转1=G」压在和弦 G 上）。排版口径是「转调在上方」：撞了就把整个标记抬到那些和弦的墨迹顶
之上一个 `jpStackGap`（与八度点/圆滑线共用的那把尺子）。

两处要害：**判避让要用 `TextFrame.bound`** 而不是 `height`（`y` 是基线，`bound.top` 才是墨迹上缘；
`KeySig` 构造里原本没调 `update()`，width/height 都是 0，判据整个失效）；
**排在 `addEnding` 之前**——房号的高度是扫全行已画对象算的，抬起来的转调也得算进去。
标记打了 `key-change` 类，透到 `DrawText.cls` 供 V4 断言。

### 段落词（「（副歌）」）

**音符数据区的东西不在整本那一层落位**：段落词挂在 `Chord.sectionWord` 上（与 `Chord.harmony` 并列），
`rebuild.mjs` 只负责按 `校对.db::section_word` 的 `note_ordinal` 注入，排版全交给
`Line.addSectionWords` + `Line.spreadForSectionWords`。

锚点（`rebuild.mjs`）：

- 含「副歌」的**优先挂到第一个带 `refrain` 标记的和弦**。`note_ordinal` 是按原书音符序号记的，
  重排后（断行不同、反复展开方式不同）常差几个音——023 首就落在了副歌前一个音上。
- 挂在**行末那个音符**上的移到下一行行首（`Layout.layout()` 在 `doLineBreak` 之后扫一遍）：
  「（副歌）」印在主歌最后一行的行尾没有意义，副歌是从下一行开始唱的（013 首）。

摆放（`Line.addSectionWords`，在 x 定稿后跑）：

- 与**和弦同一条基线**——原书就是 `G（副歌）C` 这样左右并排的（190 个含括号的段落词行实测：
  音符墨迹顶 − 基线中位 7.03pt，与和弦那一档的 7.10 同源）。抬到和弦上方另占一层是错的。
- 撞上和弦就沿 x 让：右移到那个和弦右缘（可**连跳多个和弦**找空档，和弦密的行上第一个空档
  往往在两三个和弦之后）→ 右边不行再左移到那个和弦左边 → 再不行就整个挂到**锚点音符左边**
  → 都让不开才抬到和弦上方一层。
  **右移可以越过小节线**（2026-08-25）：只要落点不压字（`hit` 本来就是按**全行**的和弦判的，
  越线后撞上下一小节的和弦会继续往右跳空档）且不出版心。越线比撑开整条小节省地方——
  405《信靠顺服》副歌那个「（副歌）」原来要把一整个小节撑宽一个词，现在贴在 F 和弦右边就完了。**不许跨过小节线**，跨过去这个标记就成了下一小节的；
  但**行首那一条例外**，左边没有小节线，最远到**版心左缘**（`hangLeft = 0`）。
  （2026-08-25 收紧：原来准它伸进左边距九成，那等于挂到离纸边 6pt 的地方——024/371/381 三首
  实测就挂在那儿，用户口径是「一个字都不许出版心」。右边同理，落点一律钳在
  `[hangLeft, rightLimit − 词宽]` 内，`rightLimit` 是**行宽**：`group.width` 只有 justify 过的行才有，
  末行是 0，106 首末行那一条因此伸出版心 25pt，所以行宽要从 `layout()` 传进来。）
  两处往左让都认这条界：
  - 399《祂所赐的十架虽甚重》副歌起在弱起的 `0 5`（休止 + 一个音）上，锚点音符自己带和弦。
    往左让到那个和弦左边，段落词正好盖住休止符那一段空白（原书也印在这里）；
    旧判据按「不许越过 barLeft=0」把它否掉了，只能再往左挂一整个词，伸出去一大截。
  - 381《进深进深入主仁爱深渊》副歌起在**行首**的弱起音上，右边就是下一小节的和弦。
    让不开时旧判据只能靠 `spreadForSectionWords` 把弱起小节撑宽一个词的宽度；
    挂到音符左边（伸进左边距）不用撑开，省下来的地方全给了谱面。
- 地方不够时**按小节均摊撑开**（`spreadForSectionWords`）：段落词本身**可以横向伸出锚点音符的范围**
  （它只是个标记），撑开只为躲开和弦；撑开量不能全堆在锚点那一个音符上，那一处的间距会突兀地大出一截。
- **撑开不许把整行拉出版心**（120《耶稣是我亲爱救主》）：`spreadForSectionWords` 撑开时
  会把小节线右边的东西整体右移 `need`，**整行跟着变长**，而原来一点越界检查都没有——
  实测那一首的谱行越出右缘 **57pt**，正好等于撑开量。段落词本身还在版心内，所以 V1 一直报 0，
  看 PDF 才发现是**整行**出去了。撑不下就别撑：维持 `placeSectionWord` 给的抬起落点，
  把段落词摆到和弦上方一层（用户口径：「排不下的时候就把文本放到和弦上方」）。
- **抬起来那一层同样一个字都不许出版心**（120《耶稣是我亲爱救主》）：落点原来是
  `max(hangLeft, min(anchorX, rightLimit − 词宽))`，外面那个 `max` 会在「词比 hangLeft 到版心右缘
  还宽」时把落点顶回去，于是仍旧挂出去。改成先按右缘钳、再按**版心左缘（0）**钳——
  `hangLeft`（不许越过上一条小节线）是**就地摆放**时的口径，抬起来这一层已经离开了和弦带，
  越过小节线不会被读成上一小节的标记，而「出版心」是硬伤。
- **同一个 `Chord` 只画一次**：一个 Chord 在一行里会对应好几个 `NoteEntry`（长音的每根增时线各占一个；
  不展开叠排时整条谱行还会按遍数重复装载），逐 entry 画就叠出两三个「（副歌）」（131 首）。

**落点只有一份代码**（`placeSectionWord`，纯几何函数）：撑开那一步先拿它**预演**一遍、据此算要撑多少，
`addSectionWords` 再拿它**定案**。两处各写一套就会错配——129 首《荣耀的一天》的锚点音符自己带和弦、
那一小节又是密排和弦，撑开那边只按「锚点到小节线放不放得下这几个字」算，差 2pt、撑完仍让不开，
结果被抬到和弦上方。三处要害：

1. **撑开要在分行之后、justify 之前**（`updateXPos` 里，`adjust` 之前一步）。分行之前撑的是**错的锚点**：
   段落词落到行末时会被挪到下一行行首去（371 首就是这样，撑了上一行、这一行照旧让不开）；
   而 justify 只会往空档里**加**距离、不会收窄，所以撑开时放得下，justify 之后也放得下。
2. **要的是「撑多少才够」，不是「差多少」**。均摊是整条小节一起拉伸，末尾那个空档只分到 `1/steps`，
   照差额撑等于白撑。所以按落点判据**二分**求最小的撑开量（上界 `shortfall × steps`：空档更靠前的话
   分到的更多，这个上界一定够）；撑到上界仍让不开就别白撑（左右都是密和弦），维持抬起。
3. **压不压字看全行的和弦，让位只能在本小节内**——这两件事口径不同。段落词本来就可以伸出小节线，
   撞的往往是**下一小节**的第一个和弦（023 首）；那种撞法右移左移都没用，只能撑开本小节：
   小节线右边的东西整体右移、段落词留在原处，空档就出来了。
   只看本小节的和弦会漏判（全书 52 处压到下一小节的和弦上），只看落点不撑开则会抬起来（45 处）。

全书 190 个段落词：与和弦同基线 **190**，抬到上方 0，压字 0。

### 圆滑线：方向与弧度

两处都出在 musicpp 那条弧高公式 `log10(dist) * 17 − 16` 上，它是按 `fontSize≈28` 的绝对像素调的：

- **方向**：短弧（`dist < 8.7pt`）算出来是负值，弧就翻过来开口朝上了。
  简谱的圆滑线/连音线**方向固定**（弧在音符上方、开口朝下），所以先钳住下限再取负。
- **弧度**：换成成书的小字号后，若按字号等比缩（0.42 倍）弧会压成一条平线，几乎看不出弧度。
  所以给一个**物理目标** `metrics.slurArcEm`（弧的凸起高度 × 音符字高，默认 0.9），
  由 `applyBookStyle` 按「典型跨度（3 个音符步距）」反算 `slurHeightScale`。
  这个值**不从原书量**：那边量到的 `slurHeight` 是 slur 对象的包围盒高（含描边外扩、且短弧居多）。

### 成书骨架

曲号 / 标题 / 词曲署名 / 调号拍号 / 页眉 / 页码不经排版引擎，由 `rebuild.mjs` 在整本那一层按
`style.titleBlock` 的绝对 y 摆（`LayoutOptions.pageFurniture = "none"` 关掉引擎自带的「本曲第 i/n 页」）。
**对开页镜像**：奇数书页页眉靠装订侧（左）、曲号靠切口侧（右），偶数页反过来——实测原书就是这样。

首页要给标题块让位，做法是**在页内平移**（`pageItemsToDrawPage` 的 `offset`）：
先排一遍量出首行音符的墨迹上缘，再整页挪到原书那条线上。事后去改 DrawList 不行，路径的坐标已经烘进 `d` 里了。

### 对开页镜像：谱面也要跟着换边

排版引擎只知道一个版心宽度，不知道奇偶页要镜像：它一律从 `margin.inner` 起排。
装饰层（曲号/页眉/页码）是 Node 侧按页号摆的、本来就镜像，**只有谱面没有**——
于是偶数页的谱面整体偏右 `inner − outer`（本书 12.24pt），装订侧的边距窄了那么多。

平移只能在**页号定下来之后**做（装订前不知道一页是奇是偶），而那时路径坐标已经烘进 `d` 里了，
所以 `drawlist.ts::shiftDrawPageX` 连 `d` 一起搬：`d` 的数字是 x/y 交替的（`M`/`L` 两个、`C` 六个），
逐个数按下标奇偶决定加不加。调用点在 `rebuild.mjs` 的装订段，**在 `decorate` 之前**。

### 字体

按角色配置（`bookstyle.json` 的 `fonts` + `roles[].font`），本机用的是原书那四款方正字体：

| 角色 | 字体 |
|---|---|
| 标题 | 方正魏碑简体 `FZWeiBei-S03S` |
| 歌词 / 正文（注解） | 方正报宋简体 `FZBaoSong-Z04S` |
| 词曲署名 / **目录条目** | 方正楷体简体 `FZKai-Z03S` |
| **目录的分类标题** | 方正行楷 `FZXingKai-S04` |
| 曲号 / 分类页眉 | 方正黑体简体 `FZHei-B01S` |
| 音符 / 和弦 / 调号拍号 / 页码 | Times New Roman |
| SMuFL 记号 | Bravura（走轮廓，见下） |

- 方正那四款是印刷字库，字表**不含**「祂」「衪」「捨」这些（歌本里真的会用到），
  所以留了一个 `fallbackCjk`（Songti SC）兜底，用不到就不会被嵌进 PDF。
- `FontRef.mode = "path"` 让某个字体**走轮廓**而不是嵌字体。给两种情况用：
  SMuFL（免嵌 Bravura，也绕开 PUA 码位在子集 cmap 上的编码风险）；
  以及子集化后不合规的字体——系统自带的 `WeibeiSC-Bold.otf` 是 CFF，
  pdf-lib 的子集产物 poppler 与 pdfjs 都报 `Unable to detect correct font file Type/Subtype`。
  轮廓取自 **fontkit**（就是算度量那一份），不用 opentype.js：后者对这套魏碑的少数字形
  会吐出带 NaN / 参数不全的路径（实测「作」「渣」「你」三个字）。
  走轮廓的行没有可见文字层，隐藏搜索层会借一个能嵌的中文字体补上。

### 字号统计的两处口径

`roles[*].size` 是从原书量到的**墨迹高**，`browser.ts::fontSizeFor` 再按该字族样本字（CJK 用「国」）
的墨迹比例反算成字号。两条容易量偏的：

- **汉字档只按汉字量**。一档里混着数字、标点和「一」这种扁字（墨迹只有 0.094em），中位数会被压下去——
  目录条目因此从 9.25 掉到 7.83，与歌词的比例就跟原书对不上了。反算时的样本字是「国」，
  统计侧的口径必须与它一致。
- **扉页/前言的正文不进目录那几档**：它们也是「以数字结尾」的普通行，会被 `entry` 判据收走。

修完之后与原书的比例（歌词＝1）：音符 0.771、目录条目 0.876、目录二级标题 1.195、
分类标题 1.388、标题 1.600、注解正文 0.928、词曲署名 0.851。
另外一级分类标题按 `size ≥ 13.5` 收（原来的 12.5 会把索引页那一档 12.x 的小标题也收进来，
中位数被压到 12.99，真值是 14.6）。

歌词字号与行距核对过 326 首同页：原书墨迹高 10.47~10.63、行距 15.2pt，
我们 11.75 × 0.896 = **10.53**、行距 **15.0** —— 都在 1~2% 以内。

### 目录与页眉的版面

- **目录条目与标题的字号要按墨迹比例反算再排**（`tocPages` / `indexPages` 接 `sizes`）。
  直接把统计到的墨迹高当字号用，行楷比黑体扁，大小不一、行距也跟着错。
- **分类标题上下的留白取原书实测**：`headingGapAbove` **42.1pt** / `headingGapBelow` **39.14pt**
  （行距才 19.41，原书上下各留了两行多）。这两个是**基线到基线**的净距，
  而条目循环末尾已经推过一个 `lineGap`、标题基线又被摆在 `y + hs` —— 三处 y 语义要对齐，
  少算一次就是「上方多一整行」或「下方少一个字高」。
- **页眉的分类名长的排两行**：原书「信徒生活（灵交）」印成「信徒生活 / 灵交」两行，**没有括号**
  （括号是语料里的写法），行距 `HEADER_LINE_GAP = 1.56`（原书 p382 两行墨迹顶差 13.9pt ÷ 墨迹高 8.9）。
- **歌词段号**（行首 `1.` `2.`）三档：`always`（编辑器那条路的老行为）/ `never` / `auto`，
  `auto` 是段数**多于 3** 才标。成书用 `auto`——两三段的谱一眼看得清哪行是哪段，
  标了反而在每行行首多出一串序号。

## 书级内容（`src/pdflayout/bookmeta.ts` + `bookparts.ts`）

B 路一开始只排得出 musicxml 装得下的东西，原书上另外那一半全丢了：
调号拍号原文、目录、首句索引、花边框里的圣诗故事与经文注解、扉页前言、段落词。
这些内容 `page-report.mjs` 早就抽出来躺在 `pdf-layout.json` 里，只是没人消费。
现在 `bookmeta.ts` 把它们提成结构化数据落进 `校对.db`，`bookparts.ts` 再排回去。

### 提取判据（每条都是拿具体页换来的）

- **调号拍号**：`=` 那个字形在字典里被学成「二」——**按位置认，不改字典**，
  「二」在歌词里是真字，全局替换会误伤。拍号是**上下叠排**（中间一条 12.3×0.3 的细横线，
  那条线不是字、读不出），按 y 分上下两簇、簇内按 x 拼串，12/8 拍上排是两位数。
  括号有时读不出（019 就是），所以头段的右界要切到**第二个等号前一位**，
  否则「1=♭A 4/4 1=A」会算出 44/1。分母只认 1/2/4/8/16，算出别的宁可留空。
  568 首全部解析出，拍号只缺 3 首。
- **段落词**（副歌/间奏/结束句）印在**和弦带**里，与和弦同一条 run。按汉字段认
  （和弦里没有汉字），锚点取**右侧最近**的音符——取最近的话，落在小节线左边一点点时
  会挂到上一小节的末音上。存音符序号与小节序号两个锚点，全书 206 处。
- **花边框正文**要**重新聚行**：`spec.ts::groupLines` 固定 4pt 的容差对花边框偏紧，
  p46 那一框里混着 8.2 与 10.5 两档字，同一条视觉行被拆成两组、拼出来是乱序。
  改按框内行距中位数的 0.45 倍聚行。框四角的纹样偶尔被读成 `X`，一两个拉丁字母
  独占一行在注解里不可能出现，丢掉。
- **未装框的经文**（p36/p39 那种）要与「掉出谱行的一」分开：乐谱页 `textLines` 里
  467 行是纯粹的「一」（歌词里的一悬在字格中部，聚行时会掉出来），
  所以要求 8 个以上汉字、不同的字 4 个以上。
- **目录**：**带尾页码的一律算条目**——曲号读不全的（「掰生命饼(300)」）不这么判
  会被当成分类标题。分类标题的字号门槛按**本页条目**定（大 1.15 倍以上）：
  目录条目字号本身就在 7.7~10.5 之间浮动（原书为了塞下长曲名会压字），
  拿全书一个常数判会把读残了的条目残片当成小标题。
- **索引**：尾数是**曲号**不是页码（「一百只羊有九十九156」= 156 首），
  所以两份索引都不必等页码定下来。两栏要按「一串非数字 + 一串数字」成对切，
  **不能按 x 缺口**——页码紧挨着下一栏的头一个字，缺口只有半个字宽。
  分节标题是 `5画`（笔划索引）与孤立的大写字母（首句索引的拼音字头，常粘在上一条末尾）。
- **带谱的前置页不算前言正文**：p4 是配了曲调的主祷文、p664 是简谱旋律索引，
  抽出来的「正文」是一串音符数字。两条判据：小节线/减时线 ≥5 条，或汉字占比 < 50%。

### 空格：矢量层没有对象，只能按字距还原

转曲 PDF 里空格不产生任何对象，OCR 行识别也读不稳。`runText` / `regroupBoxLines` 改成
**两侧都是西文**（拉丁字母或数字）且间隙 > 0.22 字高时补一个空格
（037 的 `Martin` 与 `Luther` 之间空 4.5pt，字号才 8.8）。只对西文补——汉字之间本来就疏，
照这个补会到处塞空格。

### 注解框有两种：花边纹样框与双细线矩形框

原先只认**花边纹样框**（`ornament` 拼的那种），矩形线框的注解落进了「不装框」分支——
全书 164 条注解里有 **53 条**是线框（022/023 那种经文），整框就丢了。

原书的线框是**内外两圈**：外圈约 1.5pt、内圈 0.4pt，中间空 1.3pt。它们在 `spec.ts` 里被拆成
四条一圈的 `rule-h` / `rule-v`，所以 `clusterRuleFrames` 把页面上的直线按「互相挨着」并查集聚成矩形
（≥4 条线、够大才算框），再从簇里的线宽分布反推外圈/内圈粗细与间距。
`Annotation.frame` 记 `tile` / `line` / `none`，`annotationBlock` 按 `line` 画双线矩形，
内边距按 `外圈 + 空隙 + 内圈` 算。

校对.db 的 `annotation` 表因此加了 4 列（`frame_kind` / `frame_outer` / `frame_inner` / `frame_gap`）。
**老库要先 `ALTER TABLE` 补列**——列不存在时 `replaceTable` 会静默插不进去，整张表变成 0 行、
注解全没了（PDF 直接掉 5MB）。

### 注解正文重新折行

`gen-bookmeta` 存的 text 是**按视觉行拼**的，那些换行是原书那一框的排版结果、不是内容分段。
`annotationBlock` 照着它 `split("\n")` 再各自折行，每行就只有原书那么长，右边空掉一大截
（037 的故事框只排到半幅宽）。要先把软换行抹平、整段重新折。

### 补字：整行 OCR（`gen-storyocr.mjs`）+ 人工确认表（`gen-glyphsheet.mjs`）

`gen-glyphocr.mjs` 是**逐类**送识别，花边框正文与目录剩下的 1188 类正是它啃不动的残渣
——单字孤立送识别，宋体小字的「日/曰」「未/末」分不开。改成**整行送**：
一行的字形按原位摆进一张长条（高 48）送行识别，已知元素当**锚点**在结果里定位，
锚点之间的残余文本分给那一段里的未知元素。

**不能按字对齐**：花边框正文里一段连排的字常常合成**一个** path 对象（`gen-glyphocr`
的整行分支已经给它标了多字符的 char），一行的元素序列里有的代表 12 个字、有的只 1 个，
按字做 DP 会把长度算错、整条判成错位（实测 30 行里 18 行被 `alignSeq` 判 null，
识别结果其实好得很）。

三道保险，防「一个 OCR 小错被写成整类的定案」：字数要与元素宽度对得上；
标点大小的位置只收标点；**孤立一个拉丁字母不收**（`James·Black` 的中点被读成 M，
不挡的话全书的中点都会变 M）。

第三道是**反向**的：**句读点不许收在高元素上**。原先只管「矮元素只收标点」，
却没管反过来——括号又窄又高（h/body≈0.9），宽度只有三分之一格，`want` 因此算成 1，
OCR 把它读成「。」时一路畅通。全书 11 个类这么被标成了句号，其中 2.5×10.5 / 3.0×9.1
明显是括号，9.5×9.9 / 10×9.9 那几个干脆是整个汉字——真正的「。」只有 3.1×3.1。
这些错标后来还会成为形近补字的参照，把错扩散出去。

#### 经文出处那一行（数字、冒号、开头的引号）

022 首框里印的是「“全地都要向耶和华歌唱，天天传扬他的救恩。 (代上 16:23)」，
排出来却是「全地都要向耶和华歌唱，天天传扬他的救恩。(经)」——**开头的引号没了、
出处的数字全丢了、冒号成了「经」**。四条毛病叠在一起，一条条拆：

1. **双细线框里的注解压根没送去识别**。`gen-storyocr` 原来只送 `storyBoxes`（花边框）
   与目录/索引页的行，022/023 那种双细线框的经文在乐谱页的 `textLines` 里，整个漏在外面。
   现在按 `scoreAnnotationGroups`（`bookmeta.ts`，与书级元数据同一套框判据）取行。
2. **冒号被 GT 自举标成了「经」**。这本书的「：」印成上下两个小圆点，署名行「作词：」
   在 GT 里对着「经」字的位置，投票就那么定了下来——636 个实例，全书唯一一个
   「墨迹不到 1.4×4.1pt 却标着汉字」的类。投票救不了自己，**字形判据**可以
   （`gen-glyphfuzzy` 的 `source=rule-colon`）：两条子路径、各自近圆、一般大、上下分离、
   每点只占整体高的三成以内。全书 14 个类照这条判下来全是冒号（4 类已标「：」、1 类错标
   「经」、9 类未读），一个「？」「；」都没混进来——问号的钩占了大半个字身、分号的下点
   带尾巴，两条比例闸各挡一个。
3. **锚点比对要全半角归一**。`gt` 已经 NFKC 过（全角括号、冒号都成了半角），字典里那些字
   却是全角。不归一的话「(诗 150：6)」的冒号锚点永远落空，「150」那一段一路吃到「6」跟前，
   补出个「150:」来。
4. **一段里几个未知元素，按宽度切**（`splitByWidth`）。「(代上 16:23)」在矢量层是三个对象
   （「代上 」19.0pt、「16」8.8、「23」9.3），OCR 又常读不出括号和冒号，
   于是一整段「代上1623」落给三个未知元素——按字数判等于直接放弃。宽度是硬凭据：
   汉字占一个字身、ASCII 占半身，一段的字身总数与总宽度之比就定出字身宽 u，
   DP 找一种切法使 `Σ|实宽 − u·段字身|` 最小，每段再验收（偏差 >35% 一律不要）。

**字身宽要按整行估，不能按段内自估**（`uLine`）：段内自估是自洽的——多带一个字符，
u 就跟着缩，验收照样过。p54 那行的行首「“」被 OCR 读成「(」，「(」锚点匹配到前一个，
「代上」那个元素分到的是「(代上」，段内自估算出 u=7.96 一路放行；拿整行的 9.81 一量就露馅。
同理，`takeable` 的字数闸也改按字身算，不再拿「元素宽度的中位数」当格宽——
一行里元素有宽有窄（「全地都要向耶和华歌唱」98pt 与引号 3.3pt 同在一行），
中位数根本不是字格，p54 那行的中位数是 3.3，19pt 的「代上」于是被要求装下 3 个字。

**矮元素（标点、引号）聚行另走一趟**（`groupBoxRows`）：按下缘聚行只对正文字管用——
引号悬在字身上部（p54 那个「“」下缘比同行正文高 5.5pt），句读点又比正文低一点点，
一趟贪心下来「“」把整组的基准带高，同一行的「，。()：」全被甩进下一组，
排出来是「…救恩代上16 23 / ，。(：)」。现在先只拿正文高度的元素聚出行、定出每行的
字身区间，矮元素再按中心 y 认领最近的那一行。（贪心的比较基准也从「组首」改成
「组内最后一个」——组首固定的话，攒够几个 1pt 的小台阶就会把后面的甩掉。）

**弯引号只能人眼定案**：字典里只有成对的那一版（7.1×5.3，标题字号），注解正文里印小一号，
`shapeKey` 对不上，签名距离 135（判别边际虽大，绝对值已在噪声带里，放宽阈值会招进一堆
「）」宽 32pt 的假匹配）。照 `gen-glyphsheet --apply` 的人工确认表流程定案，
10 个类（8 个「“」、2 个「”」）一次填完。

**标点不靠 OCR**：行识别会把逗号整个漏掉（每一行都漏）。但它们在矢量层是干净的，
轮廓渲染出来一眼就认得——当初逐类 OCR 把「，」读成 9、「。」读成 O、年份区间的「～」留成空。
判据是**墨迹高只有正文的三成**（实测 h/body 中位 0.29，真数字与字母都 ≥0.7）
加上它当前被读成什么，两条一起才动手。

成效：story 正文读不出的元素 3146 → 802，目录/索引 3044 → 544。
剩下的出 `pdf-out/glyphsheet-*.svg`（轮廓 + 所在行上下文）与 `glyphsheet.tsv` 交人工，
`--apply` 回填；TSV 第二列填 `-` 表示**这不是字**（拍号分数线、引导点、归错类的八度点），
标成 ignored 从待补表里退场。**`--from=layout`** 让待确认的字形直接从 `pdf-layout.json` 取
——花边框正文的缺字进不了 `unread_glyph`（那张表是重排那条路落的），可它们正是最该人看的。

### 形近补字（`gen-glyphfuzzy.mjs`）

`shapeKey` 把轮廓按高度归一到 50 格再取整，**同一个字印小一号键就变了**。注解正文是
6.5~10.5pt（谱面歌词 10.4pt），于是同一个「(」在注解里拿到的键与歌词里的不同，
字典明明认得却查不到——花边框正文读不出的 565 个字里，一大半是这种
「字典里有、只是键对不上」。（`glyphdict.ts` 早就写了 `lookupFuzzy`，但一直没有调用方。）

与 `gen-storyocr` 分工：那条认字典里**没有**的字（起浏览器送 OCR），
这条认字典里**已经有、只是键对不上**的字（纯 Node）。三道闸：

| 闸 | 值 | 为什么 |
|---|---|---|
| 尺寸相近 | 宽高各 ±25%，**另留 0.6pt 绝对下限** | 中点 1.2×1.0 对字典的 1.7×1.6 只差半个点，按比例算却是 30%，一律按比例会把极小字形全卡掉 |
| 签名距离 | 单字符 32 / **窄高 40** / 多字符 12 | 多字符必须严：「1862」的次优是「1892」、「434」的次优是「404」，数字形近，一放宽就串味 |
| 判别边际 | 次优是**另一个字符**且只差 8 以内就整类弃 | 分不清就别猜 |

**横向细长条两边都不参与**：签名按 `max(w,h)` 等比缩放，「一」、引导点行、「十」字纹样边、
减时线压扁之后全是同一条横带。不挡的话 230 个类会被判成「一」，里头还有 18.5×3.0、
51×4.9 这种宽度。但**只挡横的不挡竖的**（`gen-glyphmerge` 那条不分方向，这里要分）：
窄高的括号、`！`、`；` 宽高比也在 0.25 上下（`(` 是 2.8×11.3 → 0.248），一并挡掉
恰好把最值钱的那批漏了。「一」另外单独排除——按既定决策那条路不走（见上面 `lyricYi` 一节）。

**第二条路是上下文规则**（`source=rule-dash`）：生卒年份之间的连接号，字典里
`-`/`—`/`～` 一个都没有，签名匹配无从下手，但上下文强到不用猜——**横条，两侧紧邻都是数字**。
全书 26 个这样的横条里 18 个两侧都是数字（`1872⟦?⟧1958`、`1483⟦?⟧1546`…）。
画出来是**直的实心横条，不是波浪线**，所以是连字符不是「～」（上面那句「年份区间的『～』
留成空」按字形该改口径）。宽度按字身分档：不到 0.95 个字身是半角 `-`（实测 0.52~0.81），
到了就是全角 `—`。

**第三条路也是字形规则**（`source=rule-colon`）：两个上下分离的小圆点 = 冒号。
判据与反例见上面「经文出处那一行」一节——这一条同时**纠正**了字典里的错标
（GT 自举把冒号标成了「经」，636 个实例）。

成效：补 174 个形状类，花边框正文缺字 **565 → 357（3.51% → 2.22%）**，
全书未识别 29 → 19；`pdf-diff` 各档不退步（歌词 99.31% → 99.32%，其余一字不差）。
再加上「经文出处那一行」那一轮（双细线框送识别 + 冒号规则 + 按宽度切段 + 引号人工定案），
花边框正文缺字降到 **128（0.79%）**，乐谱页注解（含双细线框）25/1430（1.75%）；
`pdf-diff` 各档一字不差（音符 99.96%、八度 99.53%、歌词 99.32%、标题 99.66%、
和弦 99.16%、弧线 96.90%），`rebuild` + `line-check` 定点断言全过、全书基线持平。

### 排回去（`bookparts.ts` + `rebuild.mjs`）

- **调号拍号**的各处比例基准是**墨迹高**（`roles.keyMeter.size`），不是字号。
  两者差一个「墨迹占 em 的比例」——Times 的数字只占 0.66em，拿字号去乘，
  分数线会长出一半、分母被线压住（005 首实测）。
- **段落词**按音符序号锚在 `Chord.sectionWord` 上（`rebuild.mjs` 只管注入），
  落位与撑开都在排版引擎里（见上面「段落词」一节）——原书是排版时人工避开和弦的，
  重排的断行不一样，撞不撞只能现算。
- **注解优先排在本曲末页**——注解讲的就是它跟着的那首歌，甩到后面几页去等于跟别的曲子
  放在一起。三级阶梯，一级不行才下一级：
  1. **缩字号**（9.7 → 6.0pt，步长 0.25）。原书本来就是这么干的，同一批花边框里
     6.5 到 10.5 都有。所以库里存的是**每框的字号**，行距按「行距 ÷ 字号」的比例复现，
     存绝对行距会错。
  2. **缩行距**（`annGapRatio` 1.846 → 1.15）。
  3. **压谱面**（`squeezePage`）：只压**行与行之间的空隙**（最多 25%），每行整体刚体上移
     ——行内的音符/歌词/和弦相对位置分毫不动，那是简谱纵向栅格算出来的，动一下八度点和
     slur 就全错位。实测能腾出 42~95pt。
  三级都不行才顺延，且**逐条记账**（哪首、本曲末页是哪页、实际排在哪页），不静默滑走。
  全书顺延 32 条 → **16 条**。剩下那些是真放不下：版心下界已无余量可挖
  （`footerTop` 544.9，而原书框底最低 542.7，只差 2.2pt），重排的谱面比原书占得高一点，
  那点差额就是这 16 条。
- **花边框逐框存八片母题**（四条边 + 四个角），不是全书通用一套。
  「全书 110 个框同一母题」这句是错的：把八槽路径平移归一后**量化到 1pt 仍有 107 套不同**
  （10.8×5.0、10.7×3.6、4.2×4.5、9.2×8.8…，不是抖动是真不一样）。老代码只存了第一页的
  横竖两片，重排里 **109 个框的花边全画错了**，四角更是没有——靠边的端片重叠糊过去。
  - `extractOrnamentTiles` **按位置分槽**（`top/bottom/left/right` + `tl/tr/bl/br`），
    不再按 `box.w > box.h` 分横竖：四角是第三枚字形、尺寸与边片不同，按比例分只会塞错槽；
    近方形的母题（4.2×4.5、9.2×8.8）横竖之比在 1 附近打转，分出来纯看抖动。
  - **不做形状聚类**，按路径内容并 id（量化到 1pt 都不收敛，聚类是另一个课题）。
    全书 106 套 / 809 片，落库约 1MB。
  - `ornamentFramePath` 先摆四角、边再排在两角之间，`n` 向上凑使**首末片贴死两角**，
    `step ≤ pitch`，交叠不小于原书（原书步距 10.674 而母题宽 10.771，本来就微叠）。
    `edges` 掩码里没有的边不画（原书有的框就是缺一条边）。
  - `annotationBlock` 的内边距**逐槽取边厚**——四条边厚薄能差一倍（2.5~8.8），
    老代码一律拿横母题的 `h` 当四边厚度，薄边那侧的正文会贴到花边上。
- **注解归给「框上方最近的那一首」**，不是「y 落在 `[yFrom, yTo)` 里的那首」。
  后者在框恰好压过区间边界、或框在页顶（上一首跨页续排）时会归错。
  本书上两种口径结果一致（0 条 `song_no` 变化），改的是口径的正确性。
- **版心下界按页脚基线算**，不是 `footer.band`——band 是「页脚出现过的 y 范围」的下沿，
  比可用高度保守 30pt，花边框会排不下（原书的框压到 535，band 才 518）。
- **目录从曲目表生成**，原书目录只提供「分类标题落在哪个曲号之前」。
  一级分类标题**按名字挂到该分类的第一首**（album.txt 有权威的分类区间）：
  原书附录那几页把经文短歌重新从 1 编号，一律「挂到下一个条目的曲号」会让
  「附录」「短歌」跟着挂到 001 上，三个标题堆在目录开头。
- **页码两套**，照原书：前置页（前言 + 目录）自成一套，乐谱页从 1 重新起，
  后附索引接着乐谱页往下数（原书 PDF 638 页印的是 606）。所以目录里的曲目页码
  **不随目录页数变化**，两遍法一轮就收敛——循环还是留着（上限 3 轮）并记账。

整本：**655 页**（前置 31 + 乐谱 606 + 索引 18），568 首，注解 164/164 排入，字体缺字 0。

## 对比（`pdf-diff.mjs`）

**目标是找出 GT 与 PDF 的真实数据差异**（音符录错、歌词录错），
排版层面的不同要记下来但不能混进去。所以报告按三类分节：

```
## 内容差异 N 项（GT 与 PDF 不一致）      ← 要找的
## 未识别 N 处（字形没读出来，不是差异）   ← 本工具的局限
## 版面（记录，不算差异）                 ← 折行、标点位置、段数、旋律重复
```

为把版面噪声从内容差异里剥出来，做了这么几件事，每一件都是拿具体曲目换来的：

- **段落按相似度配对，不按下标硬对。** 谱面常多出 GT 里没有的歌词行（副歌另起一行），
  错位一位之后按下标比下去每段全错——068 首因此报出 230 项假差异，其实只是多了一行副歌。
- **折行归并**。歌词排不下会折到下一行，那不是新的一段。归并要保守，只动字数明显零碎的
  （试过按「每谱行歌词行数的众数」整体归并，段数是齐了，歌词准确率反而从 91.4% 掉到 88.3%）。
  归并了多少字单列一栏。
- **旋律重复检测**。各段词长不同时谱面会把旋律印两遍，而 `.jpwabc` 只记一遍靠多段歌词表示。
  先试 GT 重复 k 遍取最贴合的，重复本身当结构差异记账（024 首因此少报 71 项）。
- **歌词只比汉字**。和弦印在谱行上方、与歌词只隔一线，总有一部分被归进歌词
  （`#334`、`7:235`，还有一串 F/C/D/G）；标点的位置随排版走，一进一出各四百来处。
  两者都不是「录错」，标点差异单列一栏。
- **非歌词行剔除**：读出来一个汉字都没有的「歌词行」是和弦行/音符行归错了，单列。

### 和弦：以 musicxml 的 `<harmony>` 为基准

`.jpwabc` 根本装不下和弦，这是「musicxml 为主、jpwabc 为辅」里 musicxml 独有的那一块。
两个把整串比对带偏的坑：

- **升降号在前**。谱面与 musicxml 侧都写作 `#Fm`、`♭B`；正则若写成「音名在后跟升降号」
  （`[A-G](?:#|♭)?`），`G` 后面跟着 `#Fm` 就读成了 `G#` + `Fm`，整串跟着错位
  （实测 028 首八项差异里六项是这么来的）。
- **调号拍号会混进和弦带**。「1=F 4/4 (1=D)」跟和弦印在同一带里，
  里头的 `F`、`D` 会被当成两个和弦塞进序列开头，让整首从头错位。

  **别拿位置切**：第一谱行的头一个和弦本来就印在最左，试过按「右缘在版心左 22% 以内」切，
  和弦准确率从 80.8% 掉到 66.3%。

  分得开的是这两点——**和弦一行有好几个，调号整页只有一处；而调号的音名左边紧挨着等号。**
  等号的几何很好认：两条平行横线，实测 `5.8×3.3`、`curves=0`；
  和弦带里其它没有曲线的字（`A`、`4`）高度都是 7~8，差得远。
  以等号为锚，把左右一个字宽内、同一行的对象一并收成 `keyMeter`
  （`inventory.ts` 第 10e 步）。这一条把和弦从 80.8% 提到 **86.4%**。

  数字后缀只认真实存在的 6/7/9/11/13，免得拍号的 `F4` 被当成一个和弦。

- **跳转记号的「点」要真挨着那一撮才算**。`D.C.`/`D.S.` 靠撮里有没有小圆点来认，
  但房号括线的端头在矢量层是 `0.4×0.4` 的碎点，也落在和弦带里——它隔着大半个小节、
  甚至隔着一整行谱，照样把刚读到的那一撮判成跳转记号（037/084/116/158 首各丢两三个和弦，
  084 那个点还在下一行谱上）。判据用与并撮同一把尺子：**同一谱行、横向间距 ≤4 点**。
- **啃到单词就吐掉那一个词，接着往下啃，别整撮不要**。跳转记号常与真和弦挤成一撮
  （J21 首那一撮是 `D` `Fine` `D`），撞上小写字母就整撮放弃的话，后面那个 `D` 也跟着没了。

### 另外三项：圆滑线、调号拍号、反复房号

- **圆滑线/连音线**：两边都表示成「覆盖了第几个到第几个音符」。矢量层分不出圆滑线与连音线
  （都是一条弧），故 GT 侧把 `<slur>` 与 `<tied>` 合起来比。
  取音符要拿弧的**两个端点各找最近的音符**——先前用「音符中心落在弧的横向范围内」来框，
  短弧常常一个音符都框不住（弧画在两个音符之间，两头都够不着中心），全书少认了近千条。
- **拍号是上下叠放的**：分数线之上是分子、之下是分母。不能按「文本里的先后」取前两个数字——
  那串是按 x 排的，上下两个数字 x 几乎相同，谁先谁后全看零点几个点的抖动，
  实测 3/4 有 98 首被读成了 4/3。也不能一个数字只取一位，否则 12/8 会变成 1/8。
- **调号**谱面常写两个（「1=F (1=D)」主调 + 括号里的替代调），musicxml 只记一个，命中任一即算对。

### 转曲会把左右结构的字拆成两个 path

「祂」在标题里是 `礻` + `也` 两个对象，「像」是 `亻` + `象`。拆着查字典只查得到右半边，
于是读成「也」「象」——那些看着像「GT 与 PDF 用字不同」的差异，很大一部分是这么来的
（`像→象` 37 处、`祂→也` 8 处）。

合并判据（`inventory.ts` 第 12 步）四条缺一不可，每条都踩过：

- **必须有一个部件明显窄于字格**（偏旁才窄，「祂」的礻旁只有 0.44 个字宽；两个挨着的整字都是满格）。
  少了这条，歌词里相邻的字会被成对并掉——形状类从 1.6 万炸到 5.1 万，自举只认得出 197 类。
- **按 x 排序**。按下缘排会打乱 x 顺序（同一行里各字的下缘本就差着几个点），
  相邻两项在横向上可能是反的、`gap` 算出负值，一路把「拥戴祂为王」并成一个 102.9 宽的对象。
- **合并后宽度上限 1.55 个字格**。实测「祂」的 礻+也 是 1.47 个字格，
  而挨着的两个整字最少 1.74 个——余量只有这么点，1.45 就会漏掉「祂」。
- **必须排在「标记重复描边」之后**。那之前每个字都有 fill/stroke 两份几乎重合的对象，
  它们的横向间距是负的，会被当成偏旁并掉。

## 差异标记版 PDF（`pdf-mark.mjs`）

把每一处差异盖回**原件**上，供人工核对：

```
node pdf-diff.mjs && node pdf-mark.mjs      # → pdf-out/diff-marked.pdf（只出有标记的页）
node pdf-mark.mjs 279 135                   # 只出这几首所在的页
node pdf-mark.mjs --all                     # 全书 666 页
```

- **红** —— 页面上这个对象与 GT 不符（录错，或页面多出 GT 没有的）。做法是把该对象的轮廓
  原样用红色再画一遍，正好盖住原来的黑字。**要连描边一起盖**：书里每个字都画了 fill 与
  stroke 两份，只填色会留一圈黑边（`borderWidth: 0.45`）。
- **黄** —— GT 有、页面没有的内容，黄底黑字补在左邻居右侧。**连着缺的一串并成一条**，
  否则整段没印时几十个字会叠在同一点上；太长的截断加省略号，黄底半透明让原文仍看得见。
- **橙** —— 字形没读出来（`�`）。是本工具的局限，不是录错，与红分开。

位置由 pdf-diff 写的 `pdf-diff-marks.json` 提供，那里只记「哪一页、`inv.objs` 里第几个」；
轮廓由 pdf-mark 现取（只跑要标的页），**不写进 json**——全书两千多处，写进去就是几 MB。
取轮廓要用 `toSvgPathTransformed(data, ctm)`：`data` 是局部坐标，不乘 ctm 会全堆在页角。
pdf-lib 的原点在左下、y 朝上，页面坐标是 SVG 那套，故 `drawSvgPath(d, { x: 0, y: 页高 })`。

**改了归类判据就要重跑 pdf-diff**，标记里的对象下标才对得上。

## 基准只用 musicxml（`.jpwabc` 那一路已停用）

音符、歌词分段、标题、词曲署名、和弦、圆滑线、调号拍号、反复房号——**全部从
`500/*.musicxml` 来**。`.jpwabc` 装不下和弦与 slur，段落写法（`W1-3` 这类共用副歌）
还得另做口径对齐，两套 GT 并存只会各错一半。换过来时踩到的三处：

- **曲中转调**：`<fifths>` 会出现第二次（021/137 首 ♭E 转 F、144 首 F 转 G），
  简谱数字按当前调记，只认第一个调号会让转调之后整段全错。
- **`<note\b` 匹配到 `<note-size>`**：`\b` 在 `<defaults>` 里那个 `<note-size>` 前也成立，
  一匹配就吞到第一个 `</note>`，把开头的调号和首音一起吃掉。写 `<note[ >]`。
- **`<creator>` 要按「先词后曲」排**：全书 485 首把两行塞在一个 `type="composer"` 里，
  个别几首拆成 composer + lyricist 两条，顺序与谱面相反。

## 与 GT 的口径对齐（`pdf-diff.mjs`）

这些不是识别错误，是两边表述方式不同，必须先对齐口径才比得准：

- **段号「1.」谱面上每个谱行都重印一次，`.Words` 里只有一处**（`{1.[圣]}` 那个壳）。
  两边都剔掉：GT 只留字，识别侧按几何认出行首「窄数字 + 小点」剔除。
  做完这一条，字典覆盖率从 93.5% 跳到 97.0%、歌词准确率从 84.9% 到 89.8%。
- **歌词行要按下缘（基线）聚**，不能按顶边：标点「，」「。」只占字格下部，
  顶边比同行汉字低一大截，按顶边聚会把每行的标点拆成独立的一行。
- **升降号不参与音符序列比对**：谱面上它印在音符左上方、归类时落在和弦带里，
  与 `.Voice` 的写法口径不一致。
- **圆滑线在 `.Voice` 里写成 `(` `)`，谱面上却画成弧**（另有 slur 对象），两边都剔除括号。
- `.Voice` 里 `{(3}` 是三连音标记，**没有右括号**——正则写成 `\{\([^)]*\)?\}?` 会让 `[^)]*`
  一路吃到远处圆滑线的 `)`，把整段音符吞掉（272 首因此只解析出 17 个音符，实际有 50+）。

### 拉丁小字号：不是 OCR 的问题

署名里的英文人名一度读成 `Wm11mam`（William）、`Brosby`（Crosby），看着像 OCR 的锅，其实全是**口径**问题：

- 未定的形状类只有 15 个，**全是标点**（`：` `.` `(` `)`），一个字母都没有。
  它们被留成 `�` 混在序列里，凭空多出九百多处「未识别」。
- 建库时按宽度一刀切剔标点，把 `i` `l` 这两个只有 1.9 宽的字母一起剔了；
  GT 那边留着，序列一长一短对不齐，自举于是永远学不会它们。
  改成「点/冒号又矮又窄、括号又高又窄」两维一起判之后，自举一轮就学会了
  （`i`/`l`/`C` 的标注被 GT 覆盖掉 OCR 的错标）。

剩下的窟窿是**整行合成一个 path**：一整行文字是一个 path，字典按字形查不到东西。
全书这样的形状类有 2427 个（乐谱页上 3050 处对象，169 页）。**这一类才轮得到 OCR**，
已经做了（见下节）。

**归类一改就要重跑一次 `gen-glyphdict.mjs`**（再把上一版的 OCR 标注并回未定类）：
字形自举是拿 GT 序列与页面序列对齐投票的，归类错位时学到的字符也跟着错
（标题里的「心」曾被学成「）」）。这一步在标题那项上单独值 2 个百分点。

### 已知差异（不是 bug，是取舍）

- **歌词里的「一」**：判据已经很准（见上），剩下的是个别位置放错。
- **调号拍号混进和弦序列**：见上节，按位置切反而更糟。
- **和弦剩下的 4.5%**：多半是 GT 与谱面的固有差异——musicxml 把反复段的和弦记了两遍
  而谱面只印一遍（299、464 首末尾整段「GT 有 PDF 无」），或谱面根本没印和弦
  而 musicxml 配了（305 首 GT 20 个、页面 0 个）。
- **调号剩下的 17 首**：全是谱面与 musicxml 不同调（330 首页面印 `1=♭E`，GT 的 musicxml
  与 jpwabc 都写 `1=D`）——是这本书重新排版时转过调，不是读错。
- **反复与房号只记录、不计进内容差异**：识别侧只有几何（反复冒号的点、房号括线），
  三连音的括线脚、别处的小圆点都会混进来（全书 GT 54/92，识别 153/267），
  数量对不上是判据太粗，不是 GT 与 PDF 不一致。
- **OCR 兜底后仍读不出的字形**（对比涉及约 938 处）：PaddleOCR 也认不出的形状。
  宁可留空也不编造——认不出时它会吐 `■` `□` 之类的占位符，收进字典就成了歌词里凭空多出的字
  （实测 `■` 一项多出 337 处），故回写时按字符白名单过滤。
- **OCR 的形近字误判**：如「像」→「象」37 处。这是 OCR 兜底的固有误差，GT 能覆盖的地方
  自举优先级更高，覆盖不到的（目录、索引、注解正文）只能这样。
- **标点互换**（，。；！之间约 100 处）与**升号/上标 7 混进歌词**（约 400 处）：小项，未处理。
- **多声部/前奏**：部分曲目谱面印了 `.jpwabc` 里没有的内容，属于 GT 与谱面的固有差异。


## 与光栅路的关系

两条路**共用** `RecognizedScore` 与全部 emitter，互不干扰：

- 矢量路只在 `isVectorPdf` 为真时启用（文字层为空 + 路径占算子绝大多数），否则原样退回
  `decode.ts` 的光栅路。
- `src/omr/` 的老文件**一行未改**，光栅路 14 首基线零退化
  （`node measure-all.mjs`：音符 100.0 / 对位 100.0 / 歌词 99.5 / 标题 100 / 词曲 100）。
- `src/omr/vector.ts` 及其 import 链**不得触碰 canvas / OffscreenCanvas / document**——
  Node CLI 要在没有浏览器的情况下 import 它。需要位图时另走 `decode.ts`（浏览器专属）。
