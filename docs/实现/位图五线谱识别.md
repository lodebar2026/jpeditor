# 位图五线谱识别（`src/rasteromr/`）

**整页乐谱是一张位图**的印刷五线谱 PDF → MusicXML。

与 [五线谱识别.md](五线谱识别.md) 那条（`src/staffomr/`）的分界：

| | 矢量路 `src/staffomr/` | 位图路 `src/rasteromr/` |
|---|---|---|
| 底本 | 文字层齐全，音乐符号是**真字符**（Maestro/Opus/Anastasia） | 整页乐谱是一张 **1-bit 位图**，文字层只剩页眉页脚 |
| 输入 | 路径对象 + 字形（码位 + 轮廓） | 像素 |
| 谱线/符干/小节线 | 路径里现成的线 | 按**游程**从像素里分笔画 |
| 符头 | 查字形字典 | 按**性质**判（填充率 + 有没有符干） |
| 谱号/休止/升降/拍号 | 查字形字典（轮廓 → SMuFL） | 查形状字典（32×32 签名 → SMuFL） |
| 歌词 | 读文字层 | 要 OCR（**尚未接**） |

**下游全部共用。** 本模块只负责把位图变成 `Staff` / `Seg` / `Sym`，装进 `SPage` 之后
`page.ts` 往下那一整条（符头归属 → 符干 → 符尾 → 小节线 → 谱号调号拍号 → 系统 →
小节 → 符杠 → 音高与时值 → 和弦层与声部 → MusicXML）**一行不改**。

## 底本与语料

语料路径只写在 `scripts/node-harness.mjs` 一处（`CHORUS_ROOT`，env `CHORUS`）。
一曲一个子目录，里面是 PDF，有的还有同名 `.musicxml`（GT）。

**一曲可能有好几份 PDF**，形态也不同。`chorus-report.mjs` 逐页量出来分三档：

| 档 | 实测 | 归属 |
|---|---|---|
| **干净位图** | 线距 17~19px、线宽 1.5~2.6px、倾斜 ≤1.23px | 本轮的目标 |
| **真扫描件** | Xerox 300dpi：线宽 5.1px、倾斜 3.94px；JPEG 200dpi：线距 11.4px、倾斜 3.78px | 有 GT，另记，不入基线 |
| **矢量** | 文字层里有 50 个以上音乐字体字形 | 走 `src/staffomr/`，位图路不碰 |

干净位图那一档是 PageMaker 6.5C 排版、Distiller 输出，**不是扫描件**——
整页乐谱作为一张位图贴进内容流，所以线宽整齐、没有噪点、几乎不倾斜。

## 取图：`rasterpage.ts`

**不复用 `src/omr/decode.ts`。** 那条是给简谱光栅路写的，两点不合用：
它靠 `OffscreenCanvas`（浏览器专属），而本模块要能进 `src/cli/index.ts` 那条纯 Node 链；
它把整页缩到 `PDF_W = 2000` 宽，而合唱谱原始就是 1917 宽、线距 18px，
再缩一道符头与谱线就分不开了。**位图路按原始像素识别，一格都不缩。**

pdf.js 在 Node 下对这批 ImageMask 直接返回逐行 1-bit 打包的字节，
解包即可——**不需要 canvas**。

### 三种数据形态靠**数据长度**分辨

`ImageMask` 根本没有 `kind`，而长度是三者唯一都给得出、且互不相同的量：

- **ImageMask**（无 `kind`）：逐行 1-bit 打包，置位 = 盖住 = 墨。干净位图那一档是它。
- **`kind: 1`（GRAYSCALE_1BPP）**：同样 1-bit 打包，但置位 = **白**。Xerox 扫的那份是它。
- **`kind: 2/3`（RGB/RGBA）**：每像素 3/4 字节，先算亮度再 Otsu。JPEG 扫的那份是它。

认错**不报错**，只得一幅噪声——这正是要防的那种静默失败。
所以取完按墨迹占比自检一次极性：整页乐谱的墨不可能过半（实测约一成），过半就整幅取反。

## 去倾斜：逐斜率数「能看到几条谱线」（`rasterpage.ts::deskew`）

后面每一步都建立在「谱线是一整行几乎全是墨的横带」上，页面一斜横带就抹平了
——真扫描件倾斜 3~4 px，`findStaffLines` 找不齐谱线，整条链跟着废。

判据是 OMR 里的老办法：谱线与扫描行平行时，行投影在谱线处形成又高又窄的尖峰。
实现上只对**墨点**做直方图，不对每个候选角度重排整幅图（一页的墨约一成，
逐斜率算一遍是几十万次加法，四十个候选也就千万级；列再抽稀一半）；
定下来之后**按列整像素错切**，不旋转也不插值——位图是 1-bit 的，插值只会把谱线糊宽。

三条都是拿页面换来的：

- **门槛必须取高（0.75）**，不能照搬 `staffline.ts` 那边的 0.3。门槛一低，
  曲线是**反的**——谱线越糊、过闸的行反而越多（歌词行被算进来了）。
  实测宁静 p2：0.3 门槛下 s=0 处 145 行过闸，而歪到 ±0.004 时有 341/349 行，
  「最优角度」于是指向歪的那一边；0.75 门槛下只有真谱线过得了闸，峰又尖又正。
  一度改用行投影的**平方和**当陡峭度（文献里的常用法），一样会被歌词行带偏
  ——破碎那份扫描件的两页直接顶到量程 ±0.01。
- **错切方向别弄反**。估计器里像素 (x, y) 记在直方图的 `y + s·x` 行，
  所以校正后的图要满足 `out[y] = data[y − s·x]`；反过来写是把倾斜**加倍**
  （实测扫描件的谱行从 63 掉到 40，比不做还差）。
- **没有明显好过「不动」就不动**（1.15 倍）。封面、纯文字页上这条曲线全是噪声，
  跟着它切只会把图切坏。

真扫描件那一档：音符 **20.4% → 29.8%**、音级 24.5% → 34.9%、小节自检 9.4% → 15.7%；
破碎那份的谱行 63 → 97（每页十二组全找齐），残余斜率一律 0。干净位图那一档不动。

## 弯曲扫描的拉直：**竖着看黑白游程的规律**（`dewarp.ts`）

`deskew` 只会给整页找**一个**斜率，而真扫描件不是斜那么简单——书脊附近的页面是**弯**的，
一页之内谱线的高度随 x 起伏好几个像素，一个斜率对付不了。而后面每一步都建立在
「谱线是一整行几乎全是墨的横带」上，弯一点横带就抹平了（实测主，差遣我 p2
行投影只找出 **35** 条线，页面上明明有十几行谱）。

**判据是逐列的黑白游程**：谱表在**任何一列**上都是「五段黑（线）夹着四段白（间）」，
四段白几乎等长、五段黑几乎等厚——这个规律与页面斜不斜、弯不弯**无关**，因为它是逐列量的。
逐列扫黑游程，凡是能凑出这样一个五连（间距互差 ≤22%、每段黑不超过 0.45 个线距）
的地方，就是一行谱在这一列的位置；线距取全页候选的中位数，偏离两成的丢掉。

> `staffline.ts` 开头那条「不靠白游程众数量线距」的教训在这里**不适用**：
> 那条说的是拿**全页白游程的众数**当线距（符头内部、歌词笔画的空隙数量远超谱线间隙，
> 众数落在 3~5 px）。这里不取众数，而是要求**五连等距**——歌词笔画凑不出五段等距的
> 黑白相间，噪声更凑不出。

### 位移是**二维**的：逐行谱各有各的弯法

把逐列的命中按「x 相邻、中心 y 挨着」串成轨迹（一条轨迹 = 一行谱），
每条轨迹自己一条偏移曲线（本列的 y 减去它自己的中位数，滑动中位数平滑）；
像素落在两行谱之间就按 y 在两条曲线之间**线性插值**，页面上下两头沿用最近那条。

**只给一条逐列曲线（各行谱取中位数）不行**：越靠书脊弯得越厉害，页面上下两端的形变
并不相同，按同一条曲线推，弯得多的推不平、弯得少的反被推歪
——实测那一版扫描件音符 29.95% → **28.97%**。

### 行投影漏掉的谱行，拿逐列游程**补出来**（`completeStaffLines`）

行投影要求「一整行几乎全是墨」，扫得糊、线又细的底本过不了那道闸——实测
主，差遣我 p4 印着 12 行谱只找出 **7** 行（200 dpi、线距 11.5 px、线断成一节一节）；
而逐列游程在同一页上明明看得见那 12 行（它只要求「这一列上五段黑夹四段白」，
实测每行有 233~318 列支持）。

做法：把逐列命中按中心 y 聚成带（容差 0.4 格），**支持够多**的（取样列的两成半以上）
且**没被行投影的谱行盖住**的，就按各列的中位数合成五条线。

两条讲究：

- **支持要够多**。同一行谱在别的窗口上也会凑出「五段黑」（错开一条线的那种），
  但那些只有十几列支持：实测干净页的假带 11~54 列、真行 260~420 列。
- **谱行要直接给出来，不能把合成的线丢回 `groupStaves` 重凑**。行投影在这种页面上
  留下一地散线（主，差遣我 p4 有 52 条线却只凑出 7 行谱），合成的五条线混进去
  会被那些散线搅得凑不成一组——实测补了 25 条线、谱行只从 7 涨到 **8**；
  直接给谱行才是 7 → **12**（与印在纸上的一样多）。

干净位图那一档**一条都不补**（每一条带都被行投影的谱行盖住了），各档分毫不动。

### 通长的加线会**顶掉一条谱线**，整行谱的音高整段低两级

密集的八度跑动上下各有一排短加线，行投影把它们连成**一条通长的线**
（实测宁静 p5 那条 y=1004、x[244,1906]，只比谱线短一截）。它与下面四条真谱线
恰好等距，`groupStaves` 的「等距 + x 交集」两道闸都拦不住——于是它顶掉了
真正的第五线（1095，被三层十六分符杠压着，行投影看不见），整行谱**上移一条线**，
那一行的音高整段**低两级**：GT `C5 C6 C5 C6…` 被读成 `A4 A5 A4 A5…`。

三条一起才修得干净：

- **`groupStaves` 加一条「五条线的左缘要一致」**（差不超过三个线距）。
  真谱线从系统线起画，一个系统里五条的左缘几乎相同；加线从音符处才起。
- **只把分好组的线交给 `findStaves`**（`staffLines: groups.flatMap(...)`）。
  真正建谱行的是 `findStaves`，它拿 segs 自己再分一次组——不过滤的话
  那条加线照样被它捡回去。
- **四条等距、缺一条就外推补上**：第五条被符杠压着时行投影与逐列游程都看不见，
  但四条等距已经把它的位置定死了；外推之后验一验那儿有没有墨（半数以上的列见到墨才认）。
  只补这一条的话那一行会**整个丢掉**（实测宁静 p5 的钢琴右手行就是这样）。

宁静 P4.1（钢琴右手）**58.0% → 64.1%**，而且**读错 124 → 9**——音高全对了，剩下的是漏检。
全语料音符 71.6% → **72.6%**、按 staff 74.6% → **75.6%**、谱号 86.3% → **87.7%**（认不出 0 行）。

### 分档按**底本的数据形态**，不拿「线宽/线距」当代理量

`chorus-diff` 原来按 `lineThick <= space * 0.2` 分「干净位图 / 真扫描件」。
那个比值随谱线判据一动就翻：实测主，差遣我（线距 11.5px、线宽 2.3px）正卡在门槛上，
改一条谱线判据就整份从扫描档跳进干净档，把干净档的平均从 71% 拖到 55%——
**度量本身在跟着改动漂**。改用 `RasterPage.kind`（`mask` = 排版软件贴的 1-bit ImageMask、
`gray1`/`rgb` = 扫描件），那是底本的事实，不随识别改动。

### 没成组的那些线**要当加线用**，不能整个丢掉

上面把「通长的加线」从谱线里剔掉之后，它就**整个没了**——而它确实是加线：
密集八度跑动上方那一排短加线被行投影连成一条通长的线，上方那些符头
（`C6` 要两条加线撑着）于是一条加线都找不到，`findLegers` 全判否，
**符头认出来了却一个都归不了谱行**（实测宁静 p5 那七个 C6 全是「未归属」）。

所以没进任何一组的行投影线要接着走加线那一路：交给 `sharedLegers` **按符头切成短段**
（`findLegers` 有一道「加线不超过符头宽三倍」的闸，整条通长的过不了）。
`ledgerGrid` 的锚点也要只用**分好组**的线——混进没成组的线，五条一组的下标就全错位。

| | 音符 | 音级 | 小节自检 | 按 staff |
|---|---|---|---|---|
| 丢掉那些线 | 72.66% | 73.23% | 49.74% | 75.65% |
| **当加线用** | **74.99%** | **75.56%** | **51.72%** | **77.98%** |

宁静 P4.1（钢琴右手）**64.1% → 76.1%**（读错 8、漏 123），P4.2 → 93.1%、P3.1 → 92.8%。

### 谱线漏检自检（`scripts/raster-lines.mjs`）

逐列游程还有一个用处：**当行投影的独立证据**。逐列命中里落不进任何已检出谱行的，
按 y 聚成带（二十个以上取样列支持才算），就是「疑似漏了一行谱」。

实测 53 页：补线之前 525 行谱、疑似漏检 10 行（全在主，差遣我：p4 缺 5、p6 缺 3、p7 缺 2，
实地数图 p4 印着 12 行只找出 7 行）；**补线之后 536 行谱、漏检 0 行**——
干净位图、Xerox 扫的破碎、JPEG 扫的主，差遣我，全语料一行不漏。

> **不能拿「逐列看得见几行」直接与谱行数比**：轨迹会被符号打断、带也会被倾斜拆碎，
> 那个数两头都不准（实测干净页 100 行谱只串得出 33 条轨迹、却聚出 175 条带）。
> 只有「落不进已检出谱行的命中」才是硬证据。

### 两道闸：只在**行投影明显不够**的时候动图，动完还要**自己验**

- **动图的前提**：逐列游程看得见的谱行数（轨迹数）比行投影找出来的成组谱行数多出
  四成以上，才判这一页是弯的。差不多的页面（干净位图、只是整页略斜的扫描件）
  交给 `deskew` 就够——无条件推平实测扫描件音符 29.95% → **29.67%**，
  还把「干净/扫描」的分档搅乱了（`chorus-diff` 按线宽/线距分档，推平会改变这两个量，
  主，差遣我 整份从扫描档跳进干净档，把干净档的平均拖到 54%）。
- **动完自检**：照 `deskew` 那条「没有明显好过不动就不动」的规矩，
  拿**成组的谱行数**（不是散线条数）比一比，没多出一成半就整幅还原。
  按散线数判会采纳一批「线更多、谱行没多」的推平，扫描件那一档反而降。
  门槛扫过 1.0 / 1.05 / 1.15：音符 26.92 / 31.11 / **31.11%**。

**实测**（只动真扫描件那一档，干净位图**一个像素都不动**、各档分毫不差）：

| | 音符 | 音级 | 小节自检 |
|---|---|---|---|
| 只有 `deskew` | 29.95% | 34.84% | 16.03% |
| **加分带推平** | **31.11%** | **36.0%** | 15.71% |

主，差遣我 p2 行投影从 35 条线修到 60 条、p4 从 52 到 64；那一份整体音符 27.1% → 30.0%、
音级 34.5% → 36.9%。

## 谱线与基本单位：`staffline.ts`

### **先找线、再从五条一组反推单位**

musicpp `omr/pixel.cpp::findUnit` 的办法是取逐列黑白游程的众数，
假定最多的白色纵向游程是两条谱线之间那一段。**这本书上不成立**：
符头内部、歌词笔画之间、和弦图格线的小空隙数量远超谱线间隙，
白游程众数实测落在 3~5 px，而真线距是 17~19 px——差了四倍，后面所有门槛全废。

反过来做就没这个问题：谱线是「一整行几乎全是墨」的横带，行投影一次就找齐
（实测宁静的伯利恒 p1 一次找出 50 条 = 10 行谱，分毫不差）；
五条一组分出来之后，组内相邻线的间距就是线距，取全页中位数。

### 端点要**连续有墨**才算

行投影见到一个墨点就算起点的话，系统的花括号、乐器名擦到谱线那一带
就把谱行的左缘拉到页边（实测宁静 p1 十行谱里六行的左缘跑到 x=2），
`makeSystems` 判系统线、`makeBars` 切小节全跟着偏。要求连着若干列有墨之后，
系统数从 85 降到 26（100 行谱）。

## 去谱线：**上下都没墨才抹**

经典的「保符号去线」判据：谱线那一带的某一列，紧邻的上方与下方都是白的，
才说明这一段是**孤立的谱线**；只要有一侧连着墨，它就是某个符号穿过谱线的那一截。

一度只判「纵向游程短」，那会把**骑在谱线上的细笔画一起抹断**：
拍号数字、休止符、谱号都压在谱线上，笔画细的地方游程正好短，一抹断成两截，
同一个符号按断法不同散成好几个形状类（四分休止散成四类、拍号数字散成一堆碎块）。
换判据之后 4/4 拍号、低音谱号、升降号都完整了。

## 几何原语：`prims.ts`

### 靠**游程**分笔画，不靠连通域

直接对整幅图做连通域没有用：一行谱的五条线、压在上面的符头符干符杠、
穿过去的小节线全连成**一个**块。得先按「这个像素属于横笔画还是竖笔画」分开：
纵向游程短的是横笔画、横向游程短的是竖笔画、两个方向都在符杠区间的是符杠，
分完再各自做连通域。

### 「细」的上限**卡在谱线与符杠之间**

谱线约 0.15 个线距厚，符杠约 0.5 个。一度写成 `lineThick * 3`，
那正好撞上符杠的厚度——符杠混进横笔画、与它压着的谱线连成一块，
块高一超限整条谱线跟着被剔掉（宁静 p1 五十条谱线只剩十一条，且都不是谱线）。
改成 `max(3, min(lineThick*2, space*0.4))`。

### 笔画要沿自身方向做**闭运算**

符干穿过谱线的那几个像素，纵向游程一下子变成整根符干的长度，于是被踢出横笔画
——一条谱线因此被每根符干断成十几截，后面「长度 ≥ 最长横线的 35%」那道闸一截都过不去。

### 笔画要判**孤立性**

谱号的中央竖笔、升号的两道竖笔、拍号「4」的竖笔，横向游程都很短，
一律被当成竖笔画抽走，于是**符号被自己的笔画切开**——高音谱号切成上下两半，
位置自举取到的一多半是它的上半截，高度不到 3.8 格，整批误判成低音谱号
（你要等候 76 行谱认出 69 个「低音谱号」）。

判据：沿笔画取样，两侧（横段则上下）的邻墨超过一半就判它属于某个符号，不当原语。
真符干、真小节线两侧是空的，只在符头、符杠那一小截有邻墨。

### **加线免检孤立性**——它只出现在谱线网格的延长线上

加线总有个符头压在上面，孤立性判据一律判它「属于某个符号」，
于是既抽不出来（`findLegers` 没得用）、也抹不掉（符头连着加线，
宽度从 1.3 格涨到 1.77 格，字典里凭空多出两个三百多实例的「符头」大类）。
加线有一条更硬的判据：**只可能出现在第一线上方或第五线下方整数个线距处**（容差四分之一格）。

### 符杠要够**扁**

光靠「够长、不太高」拦不住符头：实心符头约 1.3×1.0 个线距，
纵向游程落在符杠区间里、横向游程也过线，宽度还差一点点就够。
符杠是 3:1 往上的长条，符头是 1.3:1 的椭圆，长宽比一刀分得开。

## 符头：**不走形状字典，按性质判**（`notehead.ts`）

位图上符头的形状最不稳（去谱线会在骑线的符头上切一道、符干相接处留缺口、
加线粘上来），拿 32×32 签名聚类实测被切成十几个类——宁静一首里前八个大类
全是符头的残缺变体，字典越滚越大而语义还是那三个。

换成按性质判，三档一刀分得开，而且**与字体无关**（形状签名是跟着字体走的）：

- **填充率**分实心与空心：实心符头是个实椭圆，墨占包围盒的四分之三（门槛 0.62）；
  空心符头只有一圈，实测 0.45 上下。
- **有没有符干**分二分与全音符：空心且没有符干的是全音符（全音符本来就不带符干）。

尺寸闸：宽 0.85~1.7 格、高 0.55~1.35 格。高度下限放得低，因为骑在谱线上的符头
被去线切掉一道，实测能矮到 0.6 格。**宽度上限试过放到 1.95、更差**：
多检出两百多个块，但接进 `findNoteheads` 之后归属数只涨个位数——落不到任何谱行上，
是噪声不是漏检。

### 剪掉加线再量

高音谱表下面带一条加线的音（C4 一类）整批认不出来——实测宁静人声行开头
GT 是 `C4 C4 B3 C4`，只认出 B3。符头与加线连成一块之后宽度涨到 **1.71 格**
（刚越过上限）、填充率被稀释到 0.59（掉出实心那一档）。

修法**不是抹加线**：加线压在符头底下，照抽出来的段去抹会把符头一起啃掉
（实测音符 28.5% → 27.0%）。改成**按列剪**：那一列的墨迹高度不超过两倍线宽
就是加线自己的列，从左右两侧削掉。

### 几个音**共用**的那条长加线，要按符头切成短段补进去

相邻几个音落在同一条加线上时，谱面上画的是**一条通长的横线**
（实测破碎 p4 两个音共用的那条 x[616,723]、长 **6.25 格**）。
而下游有两道长度闸都是按「一个符头的加线」定的：`findNoteheads` 只收 ≤ 6 格的横段、
`findLegers` 还要求不超过符头宽的三倍。通长的那条两道都过不了，
于是这些音**一条加线都找不到**——实测这是符头认不领的头号成因
（「需要 1 条、找到 0 条」占 155/259）。

不去动那两道闸（它们防的是「和弦图的格线被当成加线」，是拿具体页换来的），
改成在位图这边**按符头把长线切成短段**补进去：加线本来就是给符头垫的，
一个符头配一小段（符头宽的一倍半），语义与「剪出来的加线」那一路一致。
只切**落在谱线网格延长线上**的横段。

窗口要放到**三格**，不能只看符头脚下那一条：谱表外两三格的音，
**里面那几条加线上并没有符头**（「需要 2 条、找到 1 条」占 66 处，缺的就是里侧那条）。
放宽不怕误收——`findLegers` 自己还要判「加线落在符头与谱表之间」。

符头认领失败 **4.4% → 2.6%**（276 → 165 个），音符 65.9% → **67.3%**。

### 剪出来的加线，**y 要取那几列的墨、不能拿符头中心代替**

`trimLedger` 剪掉的那几列就是加线，把它按原块的宽度补一条推进 `pg.segs`。
一度拿**符头中心**当这条加线的 y：符头骑在加线上时两者的确差不多，
但符头落在加线**上方那一间**时差半格，`ledgerGrid` 的四分之一格容差一卡，
加线就被丢掉。改成取剪掉那几列的墨的平均 y。

> **`ledgerGrid` 按下标「五条一组」取锚点，这一条是脆的，但改了不划算。**
> `findStaffLines` 的结果不保证是「组数 × 5」条（实测 46 页里有 16 页不是，
> 宁静 p7 是 53 条对 10 组），多出一条，后面所有谱行的锚点就全错位。
> 改成传 `groupStaves` 分好的线（严格正确）实测**略降**：
> 音符 66.85% → 66.59%、含游离 66.73% → 66.48%，而小节自检与歌词各涨 0.2~0.3
> ——错位的锚点多半仍落在**同一行谱的另一条线**上（组内五条线等间距，
> 推出来的网格一模一样），只在跨谱行时才不同，那点差别是双向的。
> 再把网格容差从 0.25 格放宽到 0.35 / 0.45 格：音符能到 67.03%，
> **但歌词垮到 43.99% / 30.57%**（假加线把符头认领到别处，歌词跟着散）。
> 三条路都试过，现状最好。

### 剪出来的加线要**补给 `findLegers`**

剪完符头认出来了，`findLegers` 却仍判否：加线的**外露部分只有三四个像素**
（其余被符头盖住，那里的纵向游程是整个符头的高度、不算细笔画），
过不了长度闸。而剪的那一步恰好知道剪掉了哪几列——那就是加线，
按原块的宽度补一条推进 `pg.segs`。

> **试过更差**：把水平闭运算的半径从 0.6 格放到 1.0 / 1.5 格，
> 想把被符头切断的加线两截接起来——音符 28.5% → 25.2% / 21.8%。
> 半径一大，别处不相干的横笔画也被连成一条。

## 空心符头：**按内腔（洞）找**，不靠外圈

`notehead.ts::hollowHeadsFromHoles` + `contour.ts::findHoles`。

空心符头在位图上最不稳：去谱线会把它的圈切断、符干残根粘在旁边、**叠置的和弦还会碎成
四五片**——实测宁静 p2 钢琴右手那个二分和弦碎成 0.66×0.50 / 0.77×1.10 / 0.99×0.39 /
0.83×0.33 四块，一块都判不成符头，整条右手序列只剩 **8** 个音（那条谱表逐 staff
只有 56.2%，全曲最大的一个洞，GT 660 音）。

**但内腔一直在**：外圈再破，只要没破到透，中间那团白就还围着。所以反过来找——
在**去谱线之前**的图上取全页的孔，尺寸像内腔的往外扩一圈（0.22 格）就是符头盒。

四条讲究，都是拿数换来的：

- **在去谱线之前的图上取孔**。去谱线会把骑线符头的内腔豁开一道口子，洞就漏了。
  骑线的头内腔被谱线切成上下两半（实测 0.77×0.28 两个），所以先把
  「x 上重叠六成、纵向缝不到 0.45 格」的孔**并回一个**。
- **并之前先按尺寸筛**。页面上最大的一批「孔」是**谱线之间被小节线围住的那些间**
  （实测 28×20 格一个），不筛就会顺着它们连锁并成整页一个盒（实测并完只剩 155 个巨块）。
- **内腔要是横椭圆**（宽高比 ≥1.2）：字里的框、噪声的空隙多半接近方的。
- **二分符头一定带符干**（全音符才不带，靠宽度分）。放开这一条：音符 69.57% → **67.81%**。

圈的墨占比扫过 0.18 / 0.25 / 0.30 / 0.35：音符 67.61 / 69.57 / **69.60** / 69.41%，取 0.30。
带宽扫过 ±1.5 / ±2 / ±3 格，三档一样——这一路的过检不在带边上。

| | 音符 | 音级 | 小节自检 | 按 staff | 歌词 |
|---|---|---|---|---|---|
| 之前 | 68.10% | 69.13% | 40.09% | 70.97% | 67.67% |
| **按内腔找** | **69.60%** | **70.68%** | **46.72%** | **72.49%** | 66.98% |

宁静 p2 那个钢琴系统的右手 8 个音 → **15 个（含 4 个和弦附加音）**。
小节自检涨 6.6 点是因为二分/全音符补齐之后小节真的凑满了。
歌词掉 0.7 点：音符多了，`attachLyrics` 把音节重新摊了一遍——这一档的天花板本来就是音符序列。

> **逐符号各档**：时值 90.2% → 90.3%（比对的位置从 3480 涨到 3581）、附点 97.8% → 97.6%、
> 临时升降 78.7% → 78.3%、圆滑线 39.4% → **40.1%**、松叶 54 → **56**。
> 试过把全音符的宽度门槛单独抬到 1.65（`half→whole` 那 14 处）：时值 90.5% 但音符 69.52%，不划算。

> **「谱内自举的符头 mask + 在符干两端比差异」试过，不划算（已撤）。**
> 设计上两条都是对的，也照做了：**① mask 自带谱线**——分「骑线 / 在间」两类，
> 骑线那一类从骑线的符头上平均出来，谱线连同它的粗细一起在模板里，
> 粘连于是不再算「差异」（拿干净轮廓去 XOR，线穿过的那几行必然全是差异，
> 粘得越紧扣分越多）；**② 模板是统计出来的**——位图上的符头被去谱线切过、
> 被符干啃过、栅格化还糊了一圈，干净轮廓与它对不上，
> 同一页几百个已认出的符头一平均才是这一页真实的长相。
> 找的位置也收得很紧：只在**有符干没符头**的地方找，且照刻谱通例只试
> 「朝上→下端左侧、朝下→上端右侧」两处，中心还吸到线/间格上。
>
> 实测**每一档配置都低于不做**：窗口 2.0×1.8 格、门槛 0.45/0.55/0.65
> → 音符 68.75 / 69.47 / 69.55%；收成两处候选后 69.03 / 69.55 / 69.56%；
> 窗口收到 1.4×1.1 格 → 69.20 / 69.45%——基线是 **69.60%**。
> 排除了小节线（两端压在第一线与第五线上的竖段）之后仍然如此。
> 结论：**剩下的漏检不是「有符干、缺符头」那一类**——符干本身也没抽出来
> （密集符杠段里尤其），补符头这一步没有可下手的位置。
> 真要往下走，得先解决符干的抽取，或者换一条不依赖符干的候选来源。
>
> 反过来说，同一族思路里**「按内腔找」是奏效的那一条**（见上，音符 +1.5、自检 +6.6）：
> 内腔是粘连时唯一不受影响的不变量，既不用模板、也不怕谱线穿过去。

## 碎块并回之后，还要**按性质判一次符头**

「x 上重叠、上下又贴着的未识别块并起来再查字典」那一路只查字典，
而**字典里没有二分符头的类**（`rasterglyphs.json` 里 `noteheadWhole` 只有 1 类、
二分一类都没有——符头本来就不走字典，见上）。于是空心符头**骑在谱线上**时，
去谱线把它切成上下两截（谱线从头的内腔穿过，那一段上下都是白的、该抹也确实抹了），
两截都不成符头、并起来也认不出。

实测宁静 p3 那一行谱面上写的是「附点二分音符 + 四分休止」「全休止」，
只认出了休止——整行五个小节全成了「一个 0.25 的音」，小节自检自然全灭。
这一类不是个别：宁静 116 个「时值差一半以上」的小节里有 **82 个只剩一个音**。

修法是在那一路上补一句：字典认不出就拿 `judgeHeadBox` 按性质再判一次
（判据与 `findRasterHeads` 同一套，只是不再剪加线——盒是并出来的，不是连通块）。

音符 66.85% → **67.68%**、含游离 66.73% → **67.53%**、音级 67.9% → **68.72%**、
小节自检 33.5% → **37.7%**（主治万方 42.2% → 52.4%、宁静 39.6% → 43.2%）。

## 整小节休止：**先摘出来，别让符头那一路吃掉**

全休止是个 **1.34×0.64 格、填充 0.92** 的实心小矩形——**正好落在实心符头那一档里**
（宽 0.85~1.85、高 ≥0.55、填充 ≥0.62、宽高比上限 2.2），于是整批被判成 `noteheadBlack`。
实测破碎 GT 中段有 129 个全休止，我们只出 33 个休止，而那些「多出来的音符」正是它们。
字典也指望不上：破碎三页上 25 个休止大小的块只认出 11 个。

所以在 `findRasterHeads` **之前**先按形状 + 位置摘一道：
矩形（填充 ≥0.85）、扁（宽高比 ≥1.8——符头是 1.3 的椭圆）、高不过 0.8 格，
再过 `nearRestLine`（全休止吊在二线下、半休止坐在三线上）。全/半由 `notedata.ts` 按几何再分。

| | 音符 | 音级 | 小节自检 | 按 staff |
|---|---|---|---|---|
| 之前 | 69.60% | 70.68% | 46.72% | 72.49% |
| **摘出休止** | **70.25%** | **71.33%** | **50.68%** | **73.12%** |

破碎的 `restHBar` 21 → **41**。

> **放松门槛一个都不多认**（1.6/0.8/0.9 与 1.5/0.75/0.95 两档都与 1.8/0.85/0.8 完全相同）
> ——剩下的那些**不在纸上**：破碎三个女高合印一行，GT 里 P1/P2 中段的全休止
> （51 + 50 个）根本没印出来。真正印出来的（P4/P5 各 9~10 个）已经在认出来的那一批里。

## 形状字典：`rasterglyphs.ts`

键与矢量路不同：那边有字形轮廓，可以拿 `shapeKey`（轮廓归一后哈希）当精确键；
位图没有轮廓，同一个符号每次栅格化出来的像素都略有出入，精确键必然全落空。
所以这边**只有一层**：按 32×32 签名的汉明距离聚类，尺寸当粗筛。
尺寸一律归一到**线距**（同一页上可能有两种谱表大小，实测主治万方 18.5 与 15.6 并存）。

按尺寸分桶，否则是两万块 × 上千类 × 1024 格，跑不完。

`binSig` **必须反向映射**：符头只有 23×18 px，缩到 30 px 是**放大**，
正向遍历源像素时大半目标格一个源像素都摊不到，签名会变成棋盘格。

### 定案三层（可信度递增）

**1. 模板** —— 拿矢量路 `src/staffomr/glyphmap.json` 那 158 个**已全部定案**的形状类比签名。

合唱谱与赞美之泉是**同一系的乐谱字体**（Maestro 一族），而那本的形状类
全部定案、未定 0，并且存着 32×32 签名与 em 归一的宽高（em = 谱表高度 = 四个线距）。
实测尺寸逐项吻合：gClef 模板 2.75×7.45 格、位图实测 2.74×7.51。

> **签名要上下翻。** `shapeSig` 吃的是字形轮廓，那套坐标 **y 向上**，
> 归一时字形的底边落到签名的第 0 行；位图签名是 y 向下的。
> 不翻的话 gClef 的距离是 102（认成 `csymParensLeftTall`），翻过来是 **30**；
> 升号 80 → 46、降号 127 → 52。这一条不是可选项。

距离上限扫过 90 / 130 / 170 / 220，**90 最好**（音符 28.8 / 28.2 / 28.3 / 28.4）。
模板**只取 Maestro 一家**：放开到 Opus、Anastasia 更差（57.9% → 56.8% / 56.8%），
那两家的同名字形形状差着一截，放进来只是给最近邻搜索添了一批更像噪声的候选。

### 谱号：先把碎块并回一个盒，再拿模板签名验

谱号常被**自己的笔画**切开——中央那道竖笔横向游程短，孤立性判据拦不住时就被当成
竖笔画抽走（实测宁静 p7 的高音谱号断成 1.43×2.59 与 2.76×2.65 两截）。
按连通块判必然错：剩下的上半截高度不到 3.8 格，整批误判成低音谱号；
更糟的是 2.76×2.65 与 Maestro 的 fClef 模板（2.84×3.34）尺寸还挺像，字典也认成 fClef
——**认错比认不出来更糟**，整页的音高全偏。

`bootstrapClefs` 因此先把**x 上重叠的碎块并回一个盒**（谱号的碎块彼此在 x 上重叠，
后面的调号升降号在 x 上是分开的，并不进来），再拿模板签名比一次；比不出来才退回按高度分。
识别时谱号**盖过字典**：落在合并盒里的字典结果一律作废，那是被切开的半截。
实测宁静 p7 从 `FFF?f` 修成 `GGFgf`，全语料音符 61.1% → **64.9%**、音级 62.1% → 66.2%。

同一招推广成一道通用的**碎块合并**：x 上重叠、上下又贴着（不到 0.4 格）的未识别块
并起来再查一次字典，查得到才认。

> **休止符与升降号也照这个套路试过「位置先验 + 模板匹配」**（休止：谱表带内扣掉
> 符头/符干/符杠之后按墨迹列成段取盒；升降：符头左边两格同高度的窗口），
> **不划算**：匹配本身是对的（距离 25~44，很准），但那些符号**字典本来就认得出**
> ——净增几乎为零，总体还略降（音符 65.13% → 65.08%）。
> 谱号那一路之所以值，是因为它被切开之后会**认错**；休止与升降不会。代码已撤。

### 半/全休止要按**位置**再验一道

它的字形是个 1.27×0.51 格的小实心矩形，位图上这种碎块一大把（符杠断头、
粗横笔的一截）——实测宁静一首认出 43 个、全部被采纳，而谱面上根本没那么多。
它有一条硬位置：**半休止坐在第三线（中线）上、全休止吊在第二线下**，
块的纵向中心离那两条线不超过半格。加这道闸之后 43 → 5，音符 56.6% → 57.9%。

**2. 位置自举** —— 谱号、调号升降号在谱行开头的次序是刻谱的铁律。

- **谱号**：每行谱最左边（左端起四个线距以内）、又高（≥1.8 格）**又宽**（≥0.8 格）
  的那个块。宽度那一条不能省：系统线与花括号又高又窄，每次都比谱号高
  （实测取到 0.26×5.74 那种）。高音/低音按 **3.8 格**分，两类之间没有重叠。
  374 行谱只漏 20 个。
- **调号升降号**：紧跟谱号、高 1.8~3.6 格、宽不到 1.5 格。
  升与降靠**墨迹重心的高度**分——降号是上面一根细竖、下面一个胖肚子，
  重心偏下（实测中位数 0.594）；升号上下对称，居中（0.490），门槛取 0.57。
  **不自举还原号**：它与升号都重心居中，只剩宽高比可分（0.36 对 0.276），
  那是一条连续谱、分不干净；而调号里本来就几乎不出现还原号。
  自举只该断言它分得清的事。

自举**按类投票**（票数不到三票、或不到类实例数四成的不算）——
谱号取不到时，最左那个高块可能是调号升号。

**3. 人工小表** —— `rasterglyphmanual.json`，压在前两层之上。

`findBlobs` 的宽高**分别**设限（宽 6 格、高 9 格）：高音谱号 2.8×**7.5** 格，
共用「六个线距」的上限会把整页的谱号挡在外面，`bootstrapClefs` 一个也取不到。
花括号（1 × 15.6 格）仍被高度那一档挡住。

## 跨系统连接：`sameToken` 的两条**通配**，与一把不奖励碎片化的尺子

### 先说尺子：`noteAcc` 会**奖励碎片化**

逐声部对拍是「识别的谱表 ↔ GT 的谱表」贪心配对，**没配上的识别谱表一个音都不付代价**。
跨系统连接一断，一条谱表碎成好几条，配对就能给每个 GT 谱表挑一段最像的
——实测破碎碎成 13 条时 `noteAcc` 64.2%，正确连成 7 条反而 60.9%。
**照这个数调，会一路往碎里调。**

所以另加一档 **`noteAccAll`（含游离）**：把没配上的那些识别谱表里的音记进分母。
一份好的输出应当**每个音都在、且都在对的那一路上**，这个数才量得出跨系统连接。
判连接对不对看它，别看 `noteAcc`。

### 病灶：括号与谱号一时认得出、一时认不出

`StaffToken` 拿「谱号 + 谱表大小 + 在花括号的上半/下半」当一行谱的身份，
`sameToken` 原本要求这四项**全等**。位图路上后两项都不稳：

- **人声组的细括号罩几行随曲子在变**。合唱谱左端除了钢琴大谱表的花括号，
  还画着把人声组括起来的细括号；人声有几行随曲子推进而变（破碎从 1 行长到 5 行）
  ——同一条括号在两个人声的系统里罩两行、被 `findBraces` 的「恰好罩两行」留下，
  到三个人声的系统里罩三行、被丢掉。于是同一条谱行的签名一时是 `T`/`B`、一时什么都没有。
- **谱号偶尔认不出**（宁静 100 行里有 3 行），那三行把一条谱表劈成了两条。

### 修法：**认不出的那一项不参与否决**

```
size 不同        → 不是同一行
谱号两边都认出来了、又不同 → 不是同一行；有一边认不出 → 不拿谱号否决
两边都认出括号、上下半不同 → 不是同一行；有一边没认出 → 不拿括号否决
```

`T` 与 `B` 之间仍然互斥——大谱表的上行不会是下行，那一条是可靠的。

| | 音符 | **含游离** | 宁静谱表 | 破碎谱表 | 游离音符 |
|---|---|---|---|---|---|
| 原来（四项全等） | 67.25% | 62.88% | 10（GT 5） | 13（GT 7） | 323 |
| 括号通配 | 66.30% | 64.14% | 8 | **7** | 124 |
| **括号 + 谱号都通配** | 66.85% | **66.73%** | **6** | **7** | **6** |

`noteAcc` 与歌词档略降，降的正是碎片化那份虚高（破碎的 `noteAccAll` 从 61.0 到 60.9，
纹丝不动，掉的 3.3 个点全是碎着蒙来的）。矢量路各档不动（`sameToken` 是共用的，验过）。

### 两条从 Audiveris 那边印证的

[Audiveris 的 part collation](https://audiveris.github.io/audiveris/_pages/guides/specific/logical_parts/)
把每个系统的物理声部映到全曲的逻辑声部，判据是「谱表数、谱线数、小谱表属性」加声部名，
**次序上以钢琴那个双谱表声部为锚**：在它上面的自下而上配，在它下面的自上而下配，
没有钢琴就一律自下而上。

- 本仓的 `lcsPairs` 从后往前回溯、见相等就配，**等价于自下而上**——与它一致。
  别改成偏好靠前：实测掉到 57.3%（直觉上「新声部加在已有声部下面、所以该配给靠前的」
  是错的）。
- 它也是先把系统内的谱行**按括号归成声部**再配，本仓是逐行配、最后才分声部。
  这一步的差别在本语料上还没显出代价，真要动再说。

### 「一行谱写着两个 GT 声部」——**合流档试过，一次都不成立**

上面那个解释（印谱行少于 GT 声部数，所以一行上写着不止一个声部）听着顺，
但**量不出来**。做法是给 GT 的每个音算出起点（走一遍 `<measure>`/`<backup>`/
`<forward>`，按 `divisions` 归一），把**相邻的**两条 GT 谱表按起点交织成一条
——那就是它们挤在同一行时谱面的次序——再拿识别侧的谱表去配。

三条判据缺一不可，缺了就是拿度量蒙分：

- **只合流相邻的两条**。不限相邻时，度量会挑「凑得最像」的任意两条
  （实测破碎把 P2 与 P4 合流，中间还隔着 P3），合流档虚涨到 65.7%。
- **按总分比，不能只跟两条单配比**。用来合流的那条识别谱表多半已经与别的
  GT 谱表配着了，合流会把那条挤掉——收益要盖过这笔损失，否则是同一条谱表记两次分。
- 挤掉的那条分母还在、分子归零。

诚实记账之后：**破碎一次合流都不成立**（P1+P2 合到我们那条上只有 27.4%，
虽然比两条单配的 15.0% / 17.8% 高，却盖不过被它挤掉的那条 55.2%），
宁静本来就是一对一、零合流。这套机制因此没有留在 `chorus-diff.mjs` 里。

**所以缺口的成因还没定论。** 剩下两条只在七行系统里出现的识别谱表（各 45 个音）
配着 GT 的 294 与 241 音的声部——更像是**版式扩行时同一行的身份变了**
（时间上的多对一），而不是同时写着两个声部。要定论得有一份逐行的对照。

### 度量改口径：**按 staff 比，声部挂接交人工**（`testdata/合唱谱/staffmap.json`）

跨系统连接与识别是两件事，混在一个数里谁涨谁跌都看不清。所以另开一档
**按 staff 对比**：识别侧只交出「第几个系统的第几行」（`gotRows`，不经 `buildScore`），
「哪一行是哪个 GT 谱表」由一份**人工映射**给定，逐 staff 直比，不再贪心配对。

映射按**系统的谱行数**分类——同一首曲子里人声陆续进来，系统的行数从 2 变到 7，
而**行数一样的系统各行的身份也一样**（破碎、宁静都成立），所以一首曲子只要几行：

```json
"破碎/S014320OC.pdf": { "byRowCount": {
  "2": ["P6.1", "P6.2"],                                   // 只有钢琴
  "5": ["P1.1", "P4.1", "P5.1", "P6.1", "P6.2"],           // Soprano/Alto/Men + 钢琴
  "7": ["P1.1","P2.1","P3.1","P4.1","P5.1","P6.1","P6.2"]  // 三个女高 + 女低 + 男低 + 钢琴
} }
```

`null` = 这一行不入分母；`"systems"` 可按系统序号覆盖。`--genmap` 出草稿
（每一类里把「第 k 行」跨系统连起来，与 GT 贪心配一次），**再照谱面的声部标签手改**
——草稿在 2 行、3 行那几类上是错的（音太少，配到谁都像）。

| | 音符 | 音级 | 歌词 |
|---|---|---|---|
| 旧口径（`buildScore` + 贪心配对） | 68.1% | 69.1% | 64.9% |
| **按 staff（人工映射）** | **71.0%** | **72.2%** | **71.3%** |

差的那几个点全是跨系统连接吃掉的。逐 staff 一摊开，病灶各归各位：

- 宁静 P4.1（钢琴右手）**56.2%**，读错 137 —— 全曲最大的一个洞，是识别的活。
- 破碎 P1.1 **33.2%**（多出 106）、P3.1 **29.0%**（漏 245）—— 这两个不是识别的错：
  五行系统里三个女高**合印成一行 "Soprano"**，那一行按映射记给了 P1，
  P2/P3 就只剩七行系统里的那一段。

> **「一行罩着好几个 GT 谱表」试过，更差。** 映射支持写 `"P1.1|P2.1|P3.1"`
> （那一行的序列同时算给这几个谱表）。实测破碎音符 67.2% → **66.0%**、
> 歌词 40.1% → **26.6%**——那三个女高在合印的系统里**并不是齐唱**。
> 与上面「合流档一次都不成立」是同一个结论的两个方向。

### 版式：**从 GT 的 `<print>` 与 `<staff-details print-object>` 直接读**（`chorus-diff` 的正式尺子）

「这一段谱面印几行、哪几行」不必猜——MusicXML 自己写着：

- `<print new-system="yes">` / `new-page="yes"`：**这一小节起是新系统**；
- `<attributes><staff-details print-object="no"/>`：这个声部**从这一小节起不印**，
  遇到 `yes` 才恢复（Finale/Sibelius 隐藏空谱行就是这么写的）。

两条讲究，缺一条就全错：

- **首个标志是 `yes` 就说明它之前是隐藏的**。这两样只写**状态变化**，
  「隐藏空谱行」是总谱级设置，开头那段的隐藏不落成 `no`
  （实测宁静的 descant 只有一条 `m89→yes`，而谱面上它到第 89 小节才出现；
  不补这一条，宁静推出来每个系统都是五行，与谱面的 2/3/4/5 行全对不上）。
- **`<measure>` 的属性次序不固定**：首小节常写成 `<measure implicit="yes" number="1">`，
  正则要求 `number` 紧跟 `<measure ` 就会漏掉那一小节里的 `print-object`
  ——查了半天「为什么 P1 从第一小节就印着」，就是这个。

推出来的分段与谱面**分毫不差**：

```
破碎  m1-6(2行) 只有钢琴 | m7-21(3行) +P1 | m22-45(4行) +P2 | m43-48(2行) 又只剩钢琴
      m49-82(5行) P3+P4+P5+钢琴 | m83-105(7行) 全部 | m106-109(2行)
宁静  m1-8(2行) | m9-16(3行) +Women | m17-64(4行) +Men | m65-70(2行) | m71-88(4行) | m89-(5行) +descant
```

我们的系统序列与它做**一趟一对一的 DP 对齐**（行数一样才配得上，两边都允许跳过；
一个 GT 系统只配一个我们的系统——不限的话 DP 会把所有系统塞进少数几个行数相同的段里，
实测配出来全是 0%）。配上之后第 k 行就对第 k 条**在印的**谱表，
**没印出来的小节不进分母**。

| | 音符 | 音级 | 歌词 |
|---|---|---|---|
| 按 staff·人工映射 | 83.49% | 84.02% | 85.02% |
| **按谱行·GT 推导** | **85.29%** | **85.85%** | 85.02% |

两条路互证：宁静 86.4% 对 86.1%（吻合），破碎 84.1% 对 80.9%
——差的那几点是人工映射还没修干净的版式账。**这一档已进基线**，人工映射留着当交叉验证。

> 它先查出过一处真错：**破碎五行系统的女高映射写成了 `P1.1`，真身是 `P3.1`**
> （GT 说 m49-82 在印的是 P3/P4/P5+钢琴；限定这段小节比，我们那一行对 P3 是 91.9%、对 P1 是 0%）。
> 改对之后按 staff 音符 77.98% → **83.49%**、歌词 73.19% → **85.02%**，
> 逐 staff 也各归各位：P1.1 36.4% → **75.2%**、P3.1 29.6% → **91.9%**。
> **原先那两条 30% 上下的谱表不是识别不行，是尺子指错了人。**

> **「一行罩三个谱表」为什么不成立**，这回有 GT 的账：破碎三个女高在合印的段里
> **并不是齐唱**——39 小节 P2/P3 是整小节休止、35 小节三部各不相同、35 小节两部相同。
> 既不能复制给三条，也不该把没印出来的算漏检。

### 另一半：**印谱的一行 ≠ GT 的一个声部**

破碎连成 7 条谱表（与 GT 一样多、零游离）之后仍只有 60.9%。原因在版式：
GT 五个人声是**陆续进来**的（开头连续休止 P1 有 8 个、P2 有 25 个、P3~P5 各 49 个），
而谱面上那一段只印**三行**人声（实测「2 高音 + 1 低音」），
也就是**一行谱上写着不止一个 GT 声部**。这时把跨系统的同一行正确连起来，
得到的序列必然是几个 GT 声部的混合——逐声部对拍再准也就到这儿了。
要再往前，得有一份「印谱行 ↔ GT 声部」的多对一对照，那是度量的活。

## 谱号继承（改的是 `src/staffomr/notedata.ts`）

本行没认出谱号的，**沿用上一个系统同一位置那行谱的**
（照 musicpp `Score::analyzeBarData` 的 `middleStep = prev->middleStep`）。

矢量路一直没补这一条，是因为那本书的谱号几乎都认得出；位图路认不出的有一成半。
不继承就退回 `middleStep = 41`（高音谱号的口径），低音谱行整行的音高全错。

**谱号还是 `buildScore` 连跨系统谱行的主要凭据**（`StaffToken` 的第一项就是行首谱号），
缺一行那一行会另起一个声部，一个声部因此碎成好几条——实测宁静一首
GT 5 条谱表、识别出 9 条，六成的音落在没配上的那几条里，准确率逐段漂到 0。
字典查得到 85/100 行，位置自举能到 91/100，两者并起来之后 `buildScore`
的声部数降到 5，与 GT 一致。

## 对拍：`scripts/chorus-diff.mjs`

判据一律来自 `scripts/staff-metrics.mjs`（与矢量路 `staff-diff.mjs` 共用一份）。

与赞美之泉那条的两处不同：那本是一本大 PDF 切成很多首，要先找首页、切曲目、
与 GT 配对；合唱谱是一曲一个目录，配对是现成的。那本 GT 是单声部领唱谱，
一首一条序列；合唱谱 GT 是 SATB + 钢琴的全谱，**必须逐声部比**。

### GT 与识别**都按谱表拆**（`<part>` × `<staff>`）

**不能按 `<part>` 整个拼**：钢琴那种一个声部两行谱的，MusicXML 是
「本小节第一行、`<backup>`、本小节第二行」**逐小节交替**写的，
整个拼起来是两行交织的序列，与识别侧「一行谱一条序列」根本不是一回事
（宁静的钢琴声部因此只对上 29%，按谱表拆开之后开头逐音都对得上）。

**两边都只取声部号最小的那一路**：一行谱上写两个声部时同理，
把两个声部都收进来比出来的是排列差异不是识别差异（实测 28.6% → 22.2%）。

**试过更差**：按「在系统里排第几行」分声部（想绕开 `buildScore`），
音符 25% → 13%——合唱谱的系统行数并不整齐，宁静 p1 是
「钢琴前奏 2 行、2 行，然后人声加钢琴 3 行、3 行」，
「第 k 行」在不同系统里根本不是同一个声部。

### 分**干净位图 / 真扫描件**两档

混在一个平均里，干净那一档的涨跌会被淹掉。基线只守干净档。

### `--v` 出**四等分准确率**

一眼看出「开头就低」还是「越往后越漂」——两者的病因完全不同：
前者是判据错，后者是漏音符或声部碎了。宁静一首曾经是 59%/26%/17%/0%，
那就是序列短了（422 对 GT 660），而不是读错。

## 符头三档：填充率 + 宽度

- **填充率**分实心与空心（门槛 0.62）。
- **宽度**分全音符与二分音符：`glyphmap.json` 的 Maestro 模板给出
  全音符 **1.70×1.06** 格、二分 **1.32×1.10** 格、四分 1.30×1.03 格
  ——宽度一刀分得开，而高度三者几乎相同。

原来按「有没有符干」分全/二分（全音符本来不带符干），**不可靠**：
空心符头的右侧笔画与符干在竖笔画掩模里连成一块，抽不出独立的符干段
——304 个空心块里容差放到两格也只有 98 个找得到竖段，于是二分音符整批读成全音符。

**空心那一档另设宽度下限 1.00 格**：实心符头会被去线与符干残根啃窄，所以总下限放到 0.85；
空心的不能跟着放——页面上又扁又空的小块太多（歌词笔画的转折、弧线的一小段），
被收成「空心符头」的块宽度中位数**只有 0.99 格**。宁静一首原本认出 145 个全音符，
GT 只有 15 个。门槛扫过 0.85（等于不设）/1.00/1.10，取 1.00（音符 56.30/56.62/56.52）。

### 小节自检会跟着降，那是**虚高被挤掉**

`checkBars` 跳过没有音符的小节，而**一个假全音符恰好占满 4/4 一小节**
——空小节里混进一个就「通过」了。所以剔掉假全音符时小节自检从 29.1 掉到 27.7，
不是退化。**看这个数时要连音符数一起看。**

## 符干要**续到符头里**（`extendVSegs`）

竖笔画的判据是「横向游程细」，而符干与符头相接的那几行游程一下子变成整个符头的宽度
——竖段就在**符头边界前一两个像素**断掉（实测缺口中位数只有 **0.06 个线距**）。
而 `findStems` / `buildStems` 要的是符干与符头**纵向相交**，差一个像素就不成立：
实测破碎 2218 个符头里只有 642 个（28.9%）配得上符干，其余全读成四分音符；
符杠也因此接不上符干（层号 0 的占 304/1042），十六分整批读成四分。

修法是把竖段的端点**沿着墨往里续**，至多 0.6 个线距，碰到白就停。
只对竖段做——横段（谱线、加线）本来就该在符号处断开。

**续过的段只进 `SPage`，不回写 `prims`**：`blobImage` 按段的包围盒抹墨，
续进符头的段会把符头啃掉一条，符头就认不出来了
（实测直接在 `findPrimitives` 里续，小节自检 27.4% → 31.4% 但音符 65.1% → 62.5%）。

## 假符号会**吃掉整小节**，进而抢走第一声部

一个符号误检不只是多出一个音。**全音符与全休止恰好占满一小节**：
`checkFull` 于是把整小节读成「一个长音 + 另一路旋律」，`splitVoice` 按「上面的在前」
把那个假符号排成**第一声部**，真旋律整条被推到第二声部——而逐声部对拍只取
声部号最小的那一路，那一行的音就全落在分母外了（实测宁静一首因此掉 1.8 个百分点，
27 个谱行被拆出二、三声部）。**看音符准确率时要连声部数一起看。**

两头都要修：

- **`splitVoice` 加一道**（`staffomr/notedata.ts`，两条路共用）：
  **层里只有一个和弦、且它自己就占满一小节**的，不算一个声部，并回第一声部。
  真正的「一个声部整小节长音」当然存在，但那时另一层也不会是孤例。
  试过另一条「每层都要正好凑满拍号才认拆分」，**不起作用**——
  `checkFull` 成功之后各层本来就凑得满，那条判据分不开真假。
- **空心符头收紧**（下一节）。

## 空心符头：宽高比 + 谱表带，模板只当附加证据

谱表上方的声部标签（"Women"/"Men"）与曲名里的 `o`/`e`/`D` 是**接近正方**的空心块，
宽度又正好落在 1.0~1.7 格这一档里——实测宁静 p2 的 "Women" 里那个 `o`
被收成上加一线的 **A5 全音符**（`findStaffForNote` 拿文字自己的横笔当加线放行了）。

两条判据：

- **宽高比下限 1.05**。真符头是横椭圆：Maestro 模板给出全音符 1.70×1.06（比值 1.60）、
  二分 1.32×1.10（1.20）；文字里的 `o` 接近 1.0。
  门槛扫过 1.15 / 1.05，取 **1.05**——1.15 砍到真二分音符
  （主治万方音符 732 → 645、自检 47.1% → 37.4%）。
- **中心要落在谱表带里，上下各让三格**（不是一格）。谱表外一两格的空心符头是常态
  （间里的、带一两条加线的）——实测宁静 p1 那行叠置的空心和弦，有一个头的中心
  只比「一格」的边界多出**半个像素**就被拒了，整行五个小节只剩一个音。
  门槛扫过 1 / 1.5 / 2 / 2.5 / 3 / 4 / 5 格：音符 67.68 / 67.72 / 67.96 / 68.08 /
  **68.10** / 68.08 / 68.08，小节自检 37.7 / 38.2 / 39.5 / 39.9 / **40.1** / 40.1 / 40.1，
  而**歌词在四格以上开始垮**（50.0 → 46.8 → 45.1，歌词带里的字被收成空心符头）。
  三格是拐点。实心符头不受这一条限制，谱表外带加线的黑符头更是常态。

> **叠置的两个空心符头「切开再判」试过，不划算。** 和弦里三度、六度的两个符头
> 上下挨着，看着像会并成一块；实测**并没有**（宁静 p1 那对是 0.83×1.16 与 1.16×1.05
> 两个独立的块，真正拦住它们的是上面那条谱表带）。硬加「块高在 1.35~2.7 格之间就
> 在最细处切开」实测音符 67.68% → 67.04%，补上「腰要细过平均行墨一半」仍是 67.06%
> ——切出来的多是谱号残段、力度记号，不是符头。

> **模板匹配只当附加证据，不当硬闸。** 只拿 Maestro 的 `noteheadWhole`/`noteheadHalf`
> 模板收（距离 ≤ `TEMPLATE_DIST`）实测更差：音符 65.57% → 64.70%、小节自检 33.2% → 27.1%
> ——位图上的空心符头被去线切过一道、又与符干残根连着，能过闸的不到一半。
> 反过来「模板认得出就收」几乎不增不减（全语料只多收 1 个），
> 那份干净轮廓模板与位图上的空心块基本对不上。**谱内自举一份平均模板才是出路。**

## 抹符杠**只抹它自己那条带，不抹包围盒**

`blobImage` 原来照符杠的**包围盒**抹墨。符杠是斜的、还常常两三条叠着，
包围盒比它本身大得多——照盒抹会把**贴着符杠的符头一起抹掉**：
实测宁静 p8 那段十六分连桁，**一半的符头因此认不出来**（裁图上肉眼可数）。

改成沿中心线逐列抹，厚度取这一块的平均厚（`lw`）加余量。余量扫过 0 / 1 / 2 / 3 px：
音符 70.83 / 71.53 / **71.59** / 71.46%——太小会留下符杠残渣混进符号块，太大又开始啃符头。

| | 音符 | 音级 | 小节自检 | 按 staff |
|---|---|---|---|---|
| 照包围盒抹 | 70.25% | 71.33% | 50.68% | 73.12% |
| **沿中心线抹** | **71.59%** | **72.61%** | **50.93%** | **74.59%** |

临时升降也跟着从 78.3% 涨到 **81.0%**（符头认出来了，紧挨它的记号才挂得上）。

## 符杠也要**沿 x 闭一道**——它被符干切碎了

符干穿过符杠的那几列横向游程很短，出了「横向游程 ≥ 一个线距」那道闸，
**符杠于是被每根符干切成小段**。实测你要等候 p2 一条符杠碎成 1.33~1.65 格的六截，
`w ≥ 1.5 格` 那道闸挡掉大半——整页 199 个符头只认出 44 条符杠。
**音符排得密的谱子尤其吃亏**：段越短越过不了闸。

与横笔画那条闭运算是同一个道理（谱线被符干断成十几截），半径同样取两个线宽
——符干就这么粗，再大会把相邻两组的符杠连成一条。

这一条是时值的**头号修复**：逐符号量的时值 79.4% → **89.7%**，
`16th→quarter` 从 249 处降到 18 处。

## 符尾：按位置自举，不查字典

字典对符尾没用：`rasterglyphs.json` 里 4144 个类**没定名**，符尾只有 8 个类有名字。
更要命的是符尾在位图上**根本不成为独立的块**——它上半截是根粗竖笔、横向游程短，
`findPrimitives` 当竖笔画抽走了；剩下的钩尾细而弯，落在窗口里的残块高度中位数
只有 0.53 格（真符尾有一格半）。

所以改从**原始像素**上量，绕开原语划分（`recognize.ts::bootstrapFlags`）：
符尾一定长在符干**远离符头的那一端**、一定在符干**右侧**（刻谱通例，朝上朝下都在右）。
量那个窗口里的墨占比——实测没有符杠的音符里，占比要么是 0（真四分）、
要么在 0.35 以上，中间几乎没人（门槛取 0.25）。

三条限定：

- **有符杠的符干不看**：符杠也横在这个窗口里，一量必中；而符杠那一路已经把层数
  算进时值了，再补个符尾反而把十六分压回八分（`buildStems` 里「有符尾的符干不接符杠」）。
  符杠斜着搭在符干中段的也算，不只远端那一小截。
- **符尾要从符干尖端长出来**：贴着远端那一小截、紧挨符干右侧必须有墨。
  没这一条，从旁边路过的连音线、下一个音的符头都会把窗口填满。
- **只看实心符头**：空心符头本来就不带符尾，给它安一个会把二分读成八分。

**第二道钩**（十六分）沿符干再错开约一格，另量一次；门槛比第一道严
（那一段窗口里还可能扫到下一个音的符干或符头）。

> 符杠闭运算补上之后，符尾的检出数**大降**（你要等候 190 → 55、破碎 186 → 27）
> ——原先那些多半是在给**漏掉的符杠**背锅。两条一起上才对：
> 先把符杠找全，剩下真正带钩的才是符尾。

## 拍号：位置自举 + 模板验（字典里一个类都没有）

`rasterglyphs.json` 里 4144 个类**没定名**，拍号一个都没定——全语料拍号识别率
本来是 **0%**。这批曲子恰好都是 4/4、下游按缺省当 4/4 办，所以没露馅；
换一首 3/4 的就整首错。

照谱号那条路走：按位置圈出候选 → 并回碎块 → 拿模板签名验。四处讲究：

- **逐列都试，不能只试最左那一列**。行首除了拍号还有谱号切下来的碎块、
  字典没认出的调号升降号，最左那一列往往是它们
  （实测你要等候 p2 最左是谱号的下半截，真正的 C 拍号在它右边两列开外）。
- **聚列要容 0.4 格的缝**。C 拍号被自己的笔画切成好几块
  （实测破碎 p2 那个 C 是 0.76×2.16 / 0.64×0.93 / 0.58×0.12 / 0.41×0.58 四块），
  严格 x 重叠并不回来；0.4 格并得回来又并不进调号（调号离拍号有一格半以上）。
- **两个数字要按中线几何切，不按碎块自己的位置分上下半**——碎块的盒互相重叠
  （实测上半那块高 2.76 格、已经探进下半的地界）。拍号的版式是死的：
  上面那个坐在第五线到第三线之间、下面那个第三线到第一线。
- **字典认走的也要进候选**（谱号与调号升降号除外），拍号**盖过字典**：
  C 与字典里的 `csymParensRightTall`（大括号）形状相近，认错了照样要能被盖过。

距离上限单设一个 **180**，比通用的 `TEMPLATE_DIST`（90）松得多：
拍号被**五条谱线横穿**，去线在它身上切了好几道口子，退化比谱号重
（实测宁静那个 4/4 上下两半到 `timeSig4` 是 104 与 95，破碎那个 C 到
`timeSigCommon` 是 168）。松得起，是因为位置先验很硬。

四首干净位图全部认对（宁静/主治万方 4/4、破碎/你要等候 C），**拍号 0% → 100%**。

## 升降号：**被抽走的那道竖笔要并回来**

降号是「一根细长的竖笔 + 底下一个小肚子」。竖笔沿途两侧都空着，
`isolated` 判它是原语、`findPrimitives` 把它抽成竖段，`blobImage` 随后照段抹墨
——剩下的只有那个 **0.58×1.05 格**的小肚子，字典当然认不出
（实测破碎 p4 y=314 那行的调号降号：竖段 x=113 y[285,324]，块只剩 [117,304]）。

这一条把**调号**打得很惨：破碎 105 行谱有 **31 行**一个调号升降号都没认出来。

修法照「碎块并回再查」那一条，只是这回要并的是**竖段**：小肚子大小的未识别块，
左缘一带紧挨着一条比它高、上端还探到它上方的竖段，就把两者的盒并起来重查
（字典不认再拿模板验，上限放到 120——并出来的盒是块的包围盒加竖段中心线拼的，
边界不如原块齐整）。并完要把那条竖段**从 `vSegs` 里摘掉**，
不然 `findStems` 会拿它当符干、`findBarlines` 会拿它当小节线。

还原号也是同一个病，只是它有**两道**竖笔：左边那道与横笔连成块、右边那道被抽走
（实测破碎 p10 那个还原号剩下 [582,1005] 0.53×2.34 格的块 + 竖段 x=593）。
所以竖段在块的**左边或右边都要并**，尺寸按升降号卡（并出来 0.4~1.7 格宽、1.5~3.6 格高）。

模板距离上限 **90**。扫过 60/90/120：60 会把刚补上的调号又弄丢
（破碎调号 111 → 87、降号块 123 → 99），120 与 90 的临时升降档一样（都是 73.5%）
但凭空多出的「还原号」更多（破碎 121 vs 100）。

破碎调号漏行 **31 → 1**（105 行谱）、挂到音符上的临时记号 35 → 50。

> 副作用是**认出一堆没人认领的还原号**（破碎 100 个，GT 只有 24 个）。
> 它们绝大多数既没挂到音符上、也没进调号，`keyFifths` 本来就不计本位号，
> 逐音比的「凭空多出」也稳在 4 个——**不落到输出上**。真要收拾，
> 得先解决「符头没归到谱行」（见下），那才是它们无人认领的原因。

## 降号的盒要收到**下面那个肚子**上

降号的音高位置是肚子，不是盒中心：字形是「一根竖笔往上伸 + 底下一个肚子」，
Maestro 模板 0.84×2.36 格，肚子只占下面一格左右。而 `analyzeAccidental`
判「这个记号属不属于那个符头」用的是**盒中心与符头中心同高**（容差四分之一格）
——实测降号的盒中心比符头中心**高 0.55 格**，16 个里**一个都过不了**那道闸；
升号与还原号上下对称（中位数 0.03 格），33/36 与 10/11 都过。

位图这边的 `Sym.py` 是从盒算的（`adapt.ts` 造的是假字形），所以把盒收到肚子上
最省事（从盒顶往下四成五起）：`py` 跟着落到肚子中心，`overlapY` 与 x 上的判据都不受影响。
**不动 `staffomr`**——那边的 `py` 从真字形来，两条路的成因不是一回事。

这一条把临时升降从 55.1% 抬到 **67.3%**（降号漏检 8 处 → 2 处）。

> **模板不是用来「认得更准」的，是用来「把并回来的碎块认出来」的。**
> 逐音比下来，临时升降号的错法**全是「没有」——零个种类认错**
> （GT 0→没有 11、GT −1→没有 8、GT 1→没有 3），所以模板在**归类**那一步
> 无用武之地：符头左边那个窗口里的块已经被字典认走了大半（56 个里 47 个），
> 模板只多认 7 个、距离 119~378，多半根本不是升降号。
> 有用的是**检出**那一步——并回竖笔之后拿模板验，那才是上面两节做的事。

> **剩下的 26.5% 追到哪儿了。** 逐处查：14/16 是**近旁（左右五格内）根本没有升降号**，
> 1 处认出来了却被判成调号，1 处认出来没标记。而那些「没有」的实地看图，
> 记号明明印着——堵在**符头没归到谱行**上：`analyzeAccidental` 只认
> 带 `Note` 标记的符头，符头没被认领，紧挨它的记号就挂不上，
> 转而落进「紧跟小节线＝曲中转调」那条分支里当了调号
> （实测破碎 p4 x=603 那个还原号就是这么丢的：它右边 [622,634] 那个符头
> 在谱表下方 1.6 格、没找到加线，于是没有 `Note` 标记）。
> **下一步该修的是加线与符头认领，不是升降号本身。**

## contour 层与认领账本：**量得出「还有什么是我们从没看见的」**

`src/rasteromr/contour.ts` + `ledger.ts`，不参与任何识别判据——只描述、只记账。

现有的每一个数量的都是「**认出来的**对不对」（音符 68.1%、符头认领率 97.4%），
没有一个数量得出「印在纸上而我们从没看见的那些」。实测弧线、三连音的数字、
松叶、力度记号至今一个都不认，在别的报表上一点痕迹都不留。

做法：去谱线图上一团墨就是一个 **contour**（外轮廓 + 孔洞 + 形状特征），识别每认出
一样东西就按它的盒记一笔；一页跑完，**没有任何一笔的就是无主 contour**。

- **在去谱线图上取，不能在原图上**：原图上五条谱线把整行谱的符头符干小节线连成一团，
  一页只剩十几个 contour。
- **标号图（像素 → 块）必须由 `connectedComponents` 顺手落下来**（新加的 `out` 参数），
  不能拿它给的包围盒自己再 flood 一遍：面积不到下限的小块在那边被丢掉、却仍占着像素，
  照「盒里第一个没标号的前景像素」找种子会种到那种小块上，整团墨的标号就空了
  （实测 35 个块的周长因此掉到个位数、团状度算出 480）。
- **认领按盒查标号图，不按盒相交**：盒相交会把路过盒角的符干、隔壁的符号一并算进来。
  两条门槛过一条即可——落进盒里的像素占**本团墨**两成，或占**盒内全部墨**两成：
  符头的盒只盖住「符头+符干+符杠」那一大团的一小截（占团低、占盒高），
  歌词字格反过来。
- **段只记挂上标记的**（`Staff`/`Leger`/`Stem`/`BarLine`/`SysLine`/`Tail`/`Beam`），
  不记 `findPrimitives` 抽出来的原始段。横段里混着**松叶的臂、弧线的一截**
  ——照抽出来就记，要找的东西反倒成了「有主的」。
- **歌词字格不论有没有 OCR 缓存都要切、都要记**：切出字格这件事本身就是
  「这块墨是歌词」的判断，与认不认得出那个字是两回事。缓存没命中就不记的话，
  整页歌词都成了「从没看见的墨」（实测宁静墨覆盖 79.5% → **86.5%**）。
- **覆盖率的口径偏乐观**：认领过的 contour 的**全部**像素都算已解释。
  它量的是「还剩多少团墨完全没人看过」，不是像素级的解释率。

### 实测（`scripts/raster-unclaimed.mjs`，干净位图四份）

**墨覆盖 90.8%，无主 4140 团（占墨 9.2%）**（一路涨上来的：起点 86.5% / 4940 团，
认了松叶与力度 87.7%，认了弧线 **90.8%**）。
位置分布：谱表下方 1687、带内 1373、上方 991、远处（页眉页脚页边）54。

## 松叶（wedge）：按 contour 认，不拼线段

`src/rasteromr/wedge.ts`。**这一路是 contour 层的第一个用处**——无主报表里一眼看见
「又宽又扁、从没人认领」的那一批，其中一半是弧线、一半是松叶。

- **不从 `hSegs` 里配对两条臂**：`findPrimitives` 对横笔画有一道「块高不过 `thin*2`」
  （约 0.8 格）的闸，而松叶的开口实测有 1.5~2 格高——**整条松叶连着尖端是一团**，
  块高一超限整个被那道闸滤掉，压根没进 `hSegs`。它原样留在图上，
  正好是一个完整的 contour（实测宁静 p2 那条 376×30 px = 20.7×1.66 格、团状度 0.01）。
- **判据是逐列的墨迹跨度**：两条臂从尖端往开口张开，跨度近似线性地涨。
  弧线同样又宽又扁、团状度也低，但它**逐列只有一段墨**、跨度处处等于线宽
  ——「一列几段墨」（≥35% 的列有两段）与「跨度涨不涨」（开口 ≥0.55 格、
  尖端 ≤0.42 格、且开口是尖端的两倍以上）两条一起用，一刀分得开。
  实测宁静 p2 的弧线：两段列 0%、左右跨度都是 0.11 格，一条都不误收。
- 尖端在左是 `crescendo`、在右是 `diminuendo`。
- **尖端没连上的那些，两条臂各成一团**（印得细的时候常见）——单团的判据对一条臂
  无能为力（一条臂逐列只有一段墨、跨度处处等于线宽，与弧线一模一样）。
  `pairArms` 按**两条臂的关系**配：斜率一正一负、x 上盖着一半以上、
  一头挨着（≤0.45 格）另一头张开（≥0.55 格）。臂本身要**直**
  （离两端连线最远处 ≤0.18 格，弧线拱得高，一量就出局）。
- 形状闸扫过两档（`MIN_W`/`OPEN_MIN`/`TIP_MAX`/`TWO_RUN_FRAC` = 2.5/0.55/0.42/0.35
  与 1.8/0.45/0.5/0.25）：检出 **38/77 → 54/77**、序列 46.0% → 47.2%，取松的这一档。
  代价是**过检**（破碎有一条谱表识别出 15 条而 GT 只有 8 条），序列档因此涨得少。

**挂接与导出**：`attachWedges`（`staffomr/notations.ts`，与力度共用一套判据：
**先定是哪一行谱**——记号印在它那行谱的下方，而下面一行谱的上缘往往比它自己那行的
下缘还近，不先定谱行整条松叶会挂到下一行去；**那一行在这个位置没有音符就退回
「纵向够得着的谱行里 x 最近的那个」**——只按 y 定谱行、找不到就丢，
实测松叶从 38 掉到 **14**，人声那一行常常正好在休止。这一条把力度也带上去了：
检出 18 → **21**、序列 33.7% → **37.9%**）把起讫挂到音符上，`toxml.ts` 出
`<direction><direction-type><wedge>`。**止排在起之前**——同一个音符上前一条收尾、
下一条起头是常事，反过来写两条会重叠。矢量路的 `slur.ts::findWedges` 只给松叶打标
（免得被当成弧线），**从来没进过 MusicXML**，这一条两条路都是新的。

## 力度（dynamics）：字典早就认得出，缺的是挂接与**连字**

`src/rasteromr/dynamics.ts`。两件事：

1. **位图路从来没调过 `findNotations` / `attachDynamics`**（矢量路 `index.ts` 一直在调）。
   而字典本来就认得出：`rasterglyphs.json` 里 `dynamicForte` 26 个实例、`dynamicMP` 8 个，
   实测宁静 p2 那个 `f` 到 Maestro 模板的距离只有 **19**。补上这一句，力度 0 → 21 个。
2. **`mf` 印出来是两个字母**（`m` 一块、`f` 一块），只认 `f` 就把 `mf` 读成 `f`。
   `m` 那块本身认不出——它落进字典的 `dynamicForte` 类（实测距离 71~98，真 `f` 只有 19），
   或者干脆被当成实心符头（1.87×1.17 格，正在符头的尺寸档里）。

所以不靠字典认 `m`，**靠版式**：从字典认出来的那个字母往外长，按宽高比认旁边的字母
（与锚同高 = 又一个 `f`；只有 0.33~0.62 倍高、又宽 = `m`；中间那一档 = `p`），
拼不出一个像样的力度（`VALID` 那张表）就整串丢掉——**宁可少，不可编**。

> **间隙的上限卡在「贴着」（0.15 格），不是「近」。** 力度字母是斜体连写的，
> 实测 `mf` 的两块在 x 上还**重叠** 9 px；而歌词里紧挨着的汉字有半格以上的字距
> ——照 0.7 格的间隙，宁静 p2 那个 `f` 会把右边 0.5 格处的「在」字拼进来成 `ff`
> （汉字约 2×2 格，正落在「又一个 f」那一档里）。
> **纵向比中心不比底边**：斜体 `f` 上下都出头，与 `m` 的底边差 0.72 格，中心却分毫不差。

### 实测（`chorus-symbols.mjs` 新增两档，干净位图）

| | 检出 | 序列 |
|---|---|---|
| 松叶 | **54/77** | 47.2% |
| 力度 | **21/54** | 37.9% |

两档都是从 **0** 起步的。序列那一档与拍号同口径：不比位置（位图路的小节号本来就不可靠），
比**出现的次序**。识别各档（音符/音级/歌词/自检/谱号/时值/附点/升降/拍号）一分不动。

> 松叶剩下的一半多是**两条臂没连上**的（尖端断开成两个 contour，各自是一条直线），
> 与弧线在单团的判据下分不开；要认得靠配对，还没做。

## 弧线（slur / tie）：逐列一段墨、而且**拱着**

`src/rasteromr/slur.ts`。无主报表里最大的一类带外图形就是它（6~15 格宽、1~3 格高、
团状度 0.03~0.07），而位图路至今**一条都不认**——GT 里宁静 283 条、破碎 326 条。

与松叶是同一批候选里分出来的两类，判据正好相反：

| | 逐列的墨 | 直不直 |
|---|---|---|
| 松叶（整条一团） | **两段**（两条臂） | — |
| 松叶（一条臂） | 一段 | **直**（离两端连线 ≤0.18 格） |
| **弧线** | 一段 | **拱**（≥0.25 格） |

再加一条「跨度大的列不能多」（逐列墨迹跨度 >0.6 格的列不超过 15%）——
那是松叶或实心块。宽度下限扫过 2.0 / 1.4 / 1.2 / 1.0 格：
圆滑线 37.6 / **39.4** / 39.4 / 39.4%，取 1.4。

**两端的 y 只取最外那三十分之一**。弧的两头是尖的，往里取一段端点的 y 会被拉向弧背，
`validateSlurNote` 的「在符头上方/下方三格以内」就判偏了：
扫过 1/6、1/12、1/30、1/60、一列——圆滑线 34.0 / 36.6 / **37.6** / 37.6 / 37.8%。

认出来之后**交给矢量路现成的那一套**（`staffomr/slur.ts`）：`attachSlurs` 挂两端、
`reconnectSlurs` 接回跨行的、`markSlurNotes` 落到音符上，`toxml` 出 `<slur>` / `<tied>`
——那边一行不改，只是这边要造一个假 `PObj` 装着盒（与 `adapt.ts` 造假字形同一路数）。
连音线（tie）也白捡：`attachSlurs` 判两端同音级就改判成 tie。

**实测**（`chorus-symbols.mjs` 新增一档，只在音高对上的位置比，与时值同口径）：
圆滑线 **0% → 39.4%**（GT 497 起，凭空多出 25）。检出侧宁静 204/283、破碎 235/326，
其中七成挂上了端点——**挂接**才是剩下的大头，不是检出。

## 歌词：切字格 → 整行 OCR → 挂音符

位图没有文字层，歌词字要 OCR 出来。三步：

1. **切歌词带与字格**（`lyric.ts`，思路照简谱那条路的 `src/omr/lyrics.ts`）：
   每个谱行下方一条带（本行下缘 → 下一行上缘）；带内按**块的纵向中心**分 verse 行
   （不能按包围盒重叠判——「一」那种只有一横的字与相邻字纵向不重叠，会被分到别行去）；
   行内按 x 邻近把块并成字格（**汉字常由多个偏旁连通块组成**，这一步不能省，
   复用 `src/omr/lyrics.ts::mergeToChars`）。
   带里先把**音乐符号剔掉**（符头与查得到音乐字典的），否则谱表内的符号会混进来。

2. **整行送 OCR，不逐格送**：PP-OCR 的 rec 是序列模型，一整条歌词的上下文能把
   单字认不准的救回来；`recognizeTextsPos` 顺带给出每个字在条内的 x，按 x 映回字格。

3. **合成文本对象**（`font: "#ocr"`）交给 `buildLyricLines` / `attachLyrics`——那两步原样跑。
   **不走 `analyzeText`**：那一步靠「带连字符的音节」「音节间的延长线」当锚点认歌词，
   中文逐字一个音节、既不连字也不拉线，一整行一个锚点都没有。位图这边本来就是
   **按位置**切出歌词带的，身份已经确定，不必再认。

### 断行要按**间隙**，不能用定宽窗口——这是歌词档最大的一个洞

`splitRows` 原来的判据是「块的纵向中心离**本行第一个块**不超过 0.9 格算同一行」。
一行歌词里各块的中心本来就散得开——「宀」的头在上、「，」在下、「一」在中间，
字高又常有 1.2 格，整行的中心跨度轻松超过 0.9 格。于是**同一行歌词被劈成两行**，
两边各拿到半拉偏旁，OCR 出来是同一句词的两个残本：

```
（宁静 p3，改之前）
谱行#5  格4   f1寧靜的
谱行#5  格9   y1.寧静的伯利          ← 与上一条是同一行词
谱行#9  格13  安的夜已深.郊外有一群
谱行#9  格12  恆，平安的夜已深。郊外有一群牧羊人，   ← 同上
```

两条都挂到同一个谱行上，成了 verse 1 与 verse 2，字格宽度也全是碎片
（一行里既有 5px 的残片又有 37px 的两字连体）。

改成**相邻两个中心拉开一段空白才断行**（`ROW_GAP`，按线距算）：

| | 歌词（产物档） | 歌词（按 staff） | 宁静 | 破碎 |
|---|---|---|---|---|
| 定宽窗口 0.9 格 | 44.2% | 53.2% | 66.3% | 40.1% |
| **按间隙断行** | **64.9%** | **71.3%** | **82.4%** | **59.9%** |

门槛扫过 0.45 / 0.6 / 0.75 / 0.9 / 1.1 / 1.4：71.14 / 71.19 / 71.34 / 71.34 /
71.34 / 71.39%——0.75 往上是一整片平台，取中间的 **0.9**。再往上会把相邻两段词
并成一行（两段的中心差约 1.5 格），平台就到头了。音符各档纹丝不动。

> **拿「全页字宽」去剔假字格，两条都试过，都是净亏。**
> 汉字等宽，本以为能砍掉混进歌词带的非歌词墨块（弧线端头、符干尾、简谱数字）：
> ① 宽度闸（丢掉 `w` 不在 0.55~1.7 字宽的格）：歌词 71.3% → **67.2%**；
> ② 中心 y 对齐闸（丢掉偏离行中位数超过 0.35 字高的格）：71.3% → **65.6%**。
> 原因是同一个字的偏旁**并不总能并成一格**，按宽度或对齐去砍，砍掉的多是真字的一半；
> 而整行送 OCR 时那些碎片有上下文兜着，本来就认得回来。
> 全页字宽仍然留着——用来把**字号**量准（只拿宽度接近一个字的格去量字高，
> 逐行那个初值是偏旁块高，偏小）。

### 字符映回字格：字数相同按序号，否则**单调对齐**（不是各取最近）

字数与字格数相同时按序号一一对应，这一条最稳。**不同的时候原来是「逐字各取最近的格」**
——那是错的：字与格的次序本来是一样的（都是从左到右的一句词），
各取最近会**乱序**（两个字抢同一格时后一个直接丢掉，而它本该落在下一格里）。

改成一趟 DP 的**单调对齐**：保序地把字摊到格上，允许跳过空格（字少于格）、
也允许丢字（字多于格，多半是 OCR 多读了一个，`DROP_COST` 0.08 比摊到最近的格贵一点
——宁可丢，也别把整句往后顶）。

### 标点并进相邻的字，不另占一个格

「，」「。」自成一格会**占掉一个音符的位置**，整句词往后错一个音。
所以字符这一侧照简谱路 `omr/lyrics.ts` 的口径折：尾随标点（，。、；：！？…—”’））
并进前一个字，开引号（“‘（）领起后一个字。一个字格于是拿到「字 + 尾随标点」。

| | 歌词（产物档） | 歌词（按 staff） |
|---|---|---|
| 各取最近 + 标点自成一格（原来） | 64.93% | 71.34% |
| 单调对齐 | 67.22% | 73.53% |
| **单调对齐 + 标点并前** | **67.67%** | **73.99%** |

> **「按全页字宽切方块字格」试过，净亏 3 个点。** 汉字等宽，本以为可以拿字宽当尺子
> 把粘连的两三个字等分开（`mergeToChars` 只按间隙并，粘连字并成一格，
> 字格数与 OCR 字数对不上）。结构指标确实好了——每行「字格数与字数之差」的平均
> 从 3.73 降到 **1.08**（字宽取全页块高的 85 分位数，间隙 0.35 字宽、
> 超过 1.75 字宽才等分；这几个门槛都扫过），可歌词档反而掉：
> **新格 67.67% → 64.56%**（按 staff 73.99% → 71.02%）。
> 等分的切点是估的，落在字里的时候「按序号一一对应」那条准路会整句错位，
> 比格数多几个、由单调对齐去摊还要糟。**字宽仍然留着**——量字高要用它挑
> 「宽度接近一个字」的格（块高的中位数是偏旁的高度，偏小）。

**不能要求「`xFrac` 落在字格区间内」**——那是 CTC 估出来的位置，误差常有半个字，
实测那样会丢掉近一半的字（1221 个里丢 566）。

### **不做形状聚类，直接用 OCR 的文本**

试过「字格 → 32×32 签名聚类 → 每类投票定字」（照 `gen-staffocr.mjs` 的每类只送一次
OCR 的账），**净损耗**：5985 个字格聚成 1866 类，只定下 969 类、覆盖 52%，歌词 35%。
门槛往松扫更差（把不同的字并成一类，票散开、过不了半：覆盖 44.6% / 32.9%），
往紧扫也只到 58.7% 覆盖。直接用 OCR 文本，宁静一首歌词 53.2% → **58.2%**。

> **量歌词档之前，必须先把缓存跑全**（`node scripts/gen-rasterlyrics.mjs`）。
> 缓存是**按条的内容指纹**寻址的，任何动到 blob 抽取的改动都会让指纹变、缓存落空
> ——那一条就成了空歌词，歌词档假跌。反过来，缓存**不全**时也会假涨：
> 没命中的条不注入任何字，而 `acc` 对「多出来的字」是要扣分的。
> 实测在提交状态上补全缓存（新增 271 条**都是真歌词**），
> 破碎的歌词从 33.6% 掉到 22.2%、全语料 50.0% → 44.2%
> ——**掉的那一截不是退化，是原先虚高**：认出来的歌词多了，
> `attachLyrics` 把一部分挂到了错的谱行上，这才是真实水平。
> 线上没有缓存、每条都现跑 OCR，等价于缓存跑全的状态。
>
> 判断改动时：动了 blob 抽取就先重跑缓存，再看歌词；不然只看音符/音级/小节自检。

缓存按**条的内容指纹**寻址（`stripKey`，FNV-1a），不按「第几页第几行」：
几何判据一动行的编号就全变了，按位置存的缓存整份作废；按内容存的只要那一条的
像素没变就还能用。命中缓存时识别仍然不起浏览器。

**只收汉字与全角标点**：PP-OCR 认不出时会吐拉丁字母或占位符，收进来就成了歌词里
凭空多出的字（实测 `l` 一个就出现二十几次）。查不到字的格**留空**，不编造。
