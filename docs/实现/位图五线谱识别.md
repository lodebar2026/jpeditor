# 位图五线谱识别（`src/rasteromr/`）

**整页乐谱是一张位图**的印刷五线谱 PDF → MusicXML。

与 [五线谱识别.md](五线谱识别.md) 那条（`src/staffomr/`）的分界：

| | 矢量路 `src/staffomr/` | 位图路 `src/rasteromr/` |
|---|---|---|
| 底本 | 文字层齐全，音乐符号是**真字符**（Maestro/Opus/Anastasia） | 整页乐谱是一张 **1-bit 位图**，文字层只剩页眉页脚 |
| 输入 | 路径对象 + 字形（码位 + 轮廓） | 像素 |
| 谱线/符干/小节线 | 路径里现成的线 | 按**游程**从像素里分笔画 |
| 符头 | 查字形字典 | 按**性质**判（填充率 + 有没有符干） |
| 谱号/休止/升降/拍号 | 查字形字典（轮廓 → SMuFL） | 查形状字典（32×32 签名 → SMuFL） |
| 歌词 | 读文字层 | 要 OCR（**尚未接**） |

**下游全部共用。** 本模块只负责把位图变成 `Staff` / `Seg` / `Sym`，装进 `SPage` 之后
`page.ts` 往下那一整条（符头归属 → 符干 → 符尾 → 小节线 → 谱号调号拍号 → 系统 →
小节 → 符杠 → 音高与时值 → 和弦层与声部 → MusicXML）**一行不改**。

## 底本与语料

语料路径只写在 `scripts/node-harness.mjs` 一处（`CHORUS_ROOT`，env `CHORUS`）。
一曲一个子目录，里面是 PDF，有的还有同名 `.musicxml`（GT）。

**一曲可能有好几份 PDF**，形态也不同。`chorus-report.mjs` 逐页量出来分三档：

| 档 | 实测 | 归属 |
|---|---|---|
| **干净位图** | 线距 17~19px、线宽 1.5~2.6px、倾斜 ≤1.23px | 本轮的目标 |
| **真扫描件** | Xerox 300dpi：线宽 5.1px、倾斜 3.94px；JPEG 200dpi：线距 11.4px、倾斜 3.78px | 有 GT，另记，不入基线 |
| **矢量** | 文字层里有 50 个以上音乐字体字形 | 走 `src/staffomr/`，位图路不碰 |

干净位图那一档是 PageMaker 6.5C 排版、Distiller 输出，**不是扫描件**——
整页乐谱作为一张位图贴进内容流，所以线宽整齐、没有噪点、几乎不倾斜。

## 取图：`rasterpage.ts`

**不复用 `src/omr/decode.ts`。** 那条是给简谱光栅路写的，两点不合用：
它靠 `OffscreenCanvas`（浏览器专属），而本模块要能进 `src/cli/index.ts` 那条纯 Node 链；
它把整页缩到 `PDF_W = 2000` 宽，而合唱谱原始就是 1917 宽、线距 18px，
再缩一道符头与谱线就分不开了。**位图路按原始像素识别，一格都不缩。**

pdf.js 在 Node 下对这批 ImageMask 直接返回逐行 1-bit 打包的字节，
解包即可——**不需要 canvas**。

### 三种数据形态靠**数据长度**分辨

`ImageMask` 根本没有 `kind`，而长度是三者唯一都给得出、且互不相同的量：

- **ImageMask**（无 `kind`）：逐行 1-bit 打包，置位 = 盖住 = 墨。干净位图那一档是它。
- **`kind: 1`（GRAYSCALE_1BPP）**：同样 1-bit 打包，但置位 = **白**。Xerox 扫的那份是它。
- **`kind: 2/3`（RGB/RGBA）**：每像素 3/4 字节，先算亮度再 Otsu。JPEG 扫的那份是它。

认错**不报错**，只得一幅噪声——这正是要防的那种静默失败。
所以取完按墨迹占比自检一次极性：整页乐谱的墨不可能过半（实测约一成），过半就整幅取反。

## 谱线与基本单位：`staffline.ts`

### **先找线、再从五条一组反推单位**

musicpp `omr/pixel.cpp::findUnit` 的办法是取逐列黑白游程的众数，
假定最多的白色纵向游程是两条谱线之间那一段。**这本书上不成立**：
符头内部、歌词笔画之间、和弦图格线的小空隙数量远超谱线间隙，
白游程众数实测落在 3~5 px，而真线距是 17~19 px——差了四倍，后面所有门槛全废。

反过来做就没这个问题：谱线是「一整行几乎全是墨」的横带，行投影一次就找齐
（实测宁静的伯利恒 p1 一次找出 50 条 = 10 行谱，分毫不差）；
五条一组分出来之后，组内相邻线的间距就是线距，取全页中位数。

### 端点要**连续有墨**才算

行投影见到一个墨点就算起点的话，系统的花括号、乐器名擦到谱线那一带
就把谱行的左缘拉到页边（实测宁静 p1 十行谱里六行的左缘跑到 x=2），
`makeSystems` 判系统线、`makeBars` 切小节全跟着偏。要求连着若干列有墨之后，
系统数从 85 降到 26（100 行谱）。

## 去谱线：**上下都没墨才抹**

经典的「保符号去线」判据：谱线那一带的某一列，紧邻的上方与下方都是白的，
才说明这一段是**孤立的谱线**；只要有一侧连着墨，它就是某个符号穿过谱线的那一截。

一度只判「纵向游程短」，那会把**骑在谱线上的细笔画一起抹断**：
拍号数字、休止符、谱号都压在谱线上，笔画细的地方游程正好短，一抹断成两截，
同一个符号按断法不同散成好几个形状类（四分休止散成四类、拍号数字散成一堆碎块）。
换判据之后 4/4 拍号、低音谱号、升降号都完整了。

## 几何原语：`prims.ts`

### 靠**游程**分笔画，不靠连通域

直接对整幅图做连通域没有用：一行谱的五条线、压在上面的符头符干符杠、
穿过去的小节线全连成**一个**块。得先按「这个像素属于横笔画还是竖笔画」分开：
纵向游程短的是横笔画、横向游程短的是竖笔画、两个方向都在符杠区间的是符杠，
分完再各自做连通域。

### 「细」的上限**卡在谱线与符杠之间**

谱线约 0.15 个线距厚，符杠约 0.5 个。一度写成 `lineThick * 3`，
那正好撞上符杠的厚度——符杠混进横笔画、与它压着的谱线连成一块，
块高一超限整条谱线跟着被剔掉（宁静 p1 五十条谱线只剩十一条，且都不是谱线）。
改成 `max(3, min(lineThick*2, space*0.4))`。

### 笔画要沿自身方向做**闭运算**

符干穿过谱线的那几个像素，纵向游程一下子变成整根符干的长度，于是被踢出横笔画
——一条谱线因此被每根符干断成十几截，后面「长度 ≥ 最长横线的 35%」那道闸一截都过不去。

### 笔画要判**孤立性**

谱号的中央竖笔、升号的两道竖笔、拍号「4」的竖笔，横向游程都很短，
一律被当成竖笔画抽走，于是**符号被自己的笔画切开**——高音谱号切成上下两半，
位置自举取到的一多半是它的上半截，高度不到 3.8 格，整批误判成低音谱号
（你要等候 76 行谱认出 69 个「低音谱号」）。

判据：沿笔画取样，两侧（横段则上下）的邻墨超过一半就判它属于某个符号，不当原语。
真符干、真小节线两侧是空的，只在符头、符杠那一小截有邻墨。

### **加线免检孤立性**——它只出现在谱线网格的延长线上

加线总有个符头压在上面，孤立性判据一律判它「属于某个符号」，
于是既抽不出来（`findLegers` 没得用）、也抹不掉（符头连着加线，
宽度从 1.3 格涨到 1.77 格，字典里凭空多出两个三百多实例的「符头」大类）。
加线有一条更硬的判据：**只可能出现在第一线上方或第五线下方整数个线距处**（容差四分之一格）。

### 符杠要够**扁**

光靠「够长、不太高」拦不住符头：实心符头约 1.3×1.0 个线距，
纵向游程落在符杠区间里、横向游程也过线，宽度还差一点点就够。
符杠是 3:1 往上的长条，符头是 1.3:1 的椭圆，长宽比一刀分得开。

## 符头：**不走形状字典，按性质判**（`notehead.ts`）

位图上符头的形状最不稳（去谱线会在骑线的符头上切一道、符干相接处留缺口、
加线粘上来），拿 32×32 签名聚类实测被切成十几个类——宁静一首里前八个大类
全是符头的残缺变体，字典越滚越大而语义还是那三个。

换成按性质判，三档一刀分得开，而且**与字体无关**（形状签名是跟着字体走的）：

- **填充率**分实心与空心：实心符头是个实椭圆，墨占包围盒的四分之三（门槛 0.62）；
  空心符头只有一圈，实测 0.45 上下。
- **有没有符干**分二分与全音符：空心且没有符干的是全音符（全音符本来就不带符干）。

尺寸闸：宽 0.85~1.7 格、高 0.55~1.35 格。高度下限放得低，因为骑在谱线上的符头
被去线切掉一道，实测能矮到 0.6 格。**宽度上限试过放到 1.95、更差**：
多检出两百多个块，但接进 `findNoteheads` 之后归属数只涨个位数——落不到任何谱行上，
是噪声不是漏检。

### 剪掉加线再量

高音谱表下面带一条加线的音（C4 一类）整批认不出来——实测宁静人声行开头
GT 是 `C4 C4 B3 C4`，只认出 B3。符头与加线连成一块之后宽度涨到 **1.71 格**
（刚越过上限）、填充率被稀释到 0.59（掉出实心那一档）。

修法**不是抹加线**：加线压在符头底下，照抽出来的段去抹会把符头一起啃掉
（实测音符 28.5% → 27.0%）。改成**按列剪**：那一列的墨迹高度不超过两倍线宽
就是加线自己的列，从左右两侧削掉。

### 剪出来的加线要**补给 `findLegers`**

剪完符头认出来了，`findLegers` 却仍判否：加线的**外露部分只有三四个像素**
（其余被符头盖住，那里的纵向游程是整个符头的高度、不算细笔画），
过不了长度闸。而剪的那一步恰好知道剪掉了哪几列——那就是加线，
按原块的宽度补一条推进 `pg.segs`。

> **试过更差**：把水平闭运算的半径从 0.6 格放到 1.0 / 1.5 格，
> 想把被符头切断的加线两截接起来——音符 28.5% → 25.2% / 21.8%。
> 半径一大，别处不相干的横笔画也被连成一条。

## 形状字典：`rasterglyphs.ts`

键与矢量路不同：那边有字形轮廓，可以拿 `shapeKey`（轮廓归一后哈希）当精确键；
位图没有轮廓，同一个符号每次栅格化出来的像素都略有出入，精确键必然全落空。
所以这边**只有一层**：按 32×32 签名的汉明距离聚类，尺寸当粗筛。
尺寸一律归一到**线距**（同一页上可能有两种谱表大小，实测主治万方 18.5 与 15.6 并存）。

按尺寸分桶，否则是两万块 × 上千类 × 1024 格，跑不完。

`binSig` **必须反向映射**：符头只有 23×18 px，缩到 30 px 是**放大**，
正向遍历源像素时大半目标格一个源像素都摊不到，签名会变成棋盘格。

### 定案三层（可信度递增）

**1. 模板** —— 拿矢量路 `src/staffomr/glyphmap.json` 那 158 个**已全部定案**的形状类比签名。

合唱谱与赞美之泉是**同一系的乐谱字体**（Maestro 一族），而那本的形状类
全部定案、未定 0，并且存着 32×32 签名与 em 归一的宽高（em = 谱表高度 = 四个线距）。
实测尺寸逐项吻合：gClef 模板 2.75×7.45 格、位图实测 2.74×7.51。

> **签名要上下翻。** `shapeSig` 吃的是字形轮廓，那套坐标 **y 向上**，
> 归一时字形的底边落到签名的第 0 行；位图签名是 y 向下的。
> 不翻的话 gClef 的距离是 102（认成 `csymParensLeftTall`），翻过来是 **30**；
> 升号 80 → 46、降号 127 → 52。这一条不是可选项。

距离上限扫过 90 / 130 / 170 / 220，**90 最好**（音符 28.8 / 28.2 / 28.3 / 28.4）。
模板**只取 Maestro 一家**：放开到 Opus、Anastasia 更差（57.9% → 56.8% / 56.8%），
那两家的同名字形形状差着一截，放进来只是给最近邻搜索添了一批更像噪声的候选。

### 半/全休止要按**位置**再验一道

它的字形是个 1.27×0.51 格的小实心矩形，位图上这种碎块一大把（符杠断头、
粗横笔的一截）——实测宁静一首认出 43 个、全部被采纳，而谱面上根本没那么多。
它有一条硬位置：**半休止坐在第三线（中线）上、全休止吊在第二线下**，
块的纵向中心离那两条线不超过半格。加这道闸之后 43 → 5，音符 56.6% → 57.9%。

**2. 位置自举** —— 谱号、调号升降号在谱行开头的次序是刻谱的铁律。

- **谱号**：每行谱最左边（左端起四个线距以内）、又高（≥1.8 格）**又宽**（≥0.8 格）
  的那个块。宽度那一条不能省：系统线与花括号又高又窄，每次都比谱号高
  （实测取到 0.26×5.74 那种）。高音/低音按 **3.8 格**分，两类之间没有重叠。
  374 行谱只漏 20 个。
- **调号升降号**：紧跟谱号、高 1.8~3.6 格、宽不到 1.5 格。
  升与降靠**墨迹重心的高度**分——降号是上面一根细竖、下面一个胖肚子，
  重心偏下（实测中位数 0.594）；升号上下对称，居中（0.490），门槛取 0.57。
  **不自举还原号**：它与升号都重心居中，只剩宽高比可分（0.36 对 0.276），
  那是一条连续谱、分不干净；而调号里本来就几乎不出现还原号。
  自举只该断言它分得清的事。

自举**按类投票**（票数不到三票、或不到类实例数四成的不算）——
谱号取不到时，最左那个高块可能是调号升号。

**3. 人工小表** —— `rasterglyphmanual.json`，压在前两层之上。

`findBlobs` 的宽高**分别**设限（宽 6 格、高 9 格）：高音谱号 2.8×**7.5** 格，
共用「六个线距」的上限会把整页的谱号挡在外面，`bootstrapClefs` 一个也取不到。
花括号（1 × 15.6 格）仍被高度那一档挡住。

## 谱号继承（改的是 `src/staffomr/notedata.ts`）

本行没认出谱号的，**沿用上一个系统同一位置那行谱的**
（照 musicpp `Score::analyzeBarData` 的 `middleStep = prev->middleStep`）。

矢量路一直没补这一条，是因为那本书的谱号几乎都认得出；位图路认不出的有一成半。
不继承就退回 `middleStep = 41`（高音谱号的口径），低音谱行整行的音高全错。

**谱号还是 `buildScore` 连跨系统谱行的主要凭据**（`StaffToken` 的第一项就是行首谱号），
缺一行那一行会另起一个声部，一个声部因此碎成好几条——实测宁静一首
GT 5 条谱表、识别出 9 条，六成的音落在没配上的那几条里，准确率逐段漂到 0。
字典查得到 85/100 行，位置自举能到 91/100，两者并起来之后 `buildScore`
的声部数降到 5，与 GT 一致。

## 对拍：`scripts/chorus-diff.mjs`

判据一律来自 `scripts/staff-metrics.mjs`（与矢量路 `staff-diff.mjs` 共用一份）。

与赞美之泉那条的两处不同：那本是一本大 PDF 切成很多首，要先找首页、切曲目、
与 GT 配对；合唱谱是一曲一个目录，配对是现成的。那本 GT 是单声部领唱谱，
一首一条序列；合唱谱 GT 是 SATB + 钢琴的全谱，**必须逐声部比**。

### GT 与识别**都按谱表拆**（`<part>` × `<staff>`）

**不能按 `<part>` 整个拼**：钢琴那种一个声部两行谱的，MusicXML 是
「本小节第一行、`<backup>`、本小节第二行」**逐小节交替**写的，
整个拼起来是两行交织的序列，与识别侧「一行谱一条序列」根本不是一回事
（宁静的钢琴声部因此只对上 29%，按谱表拆开之后开头逐音都对得上）。

**两边都只取声部号最小的那一路**：一行谱上写两个声部时同理，
把两个声部都收进来比出来的是排列差异不是识别差异（实测 28.6% → 22.2%）。

**试过更差**：按「在系统里排第几行」分声部（想绕开 `buildScore`），
音符 25% → 13%——合唱谱的系统行数并不整齐，宁静 p1 是
「钢琴前奏 2 行、2 行，然后人声加钢琴 3 行、3 行」，
「第 k 行」在不同系统里根本不是同一个声部。

### 分**干净位图 / 真扫描件**两档

混在一个平均里，干净那一档的涨跌会被淹掉。基线只守干净档。

### `--v` 出**四等分准确率**

一眼看出「开头就低」还是「越往后越漂」——两者的病因完全不同：
前者是判据错，后者是漏音符或声部碎了。宁静一首曾经是 59%/26%/17%/0%，
那就是序列短了（422 对 GT 660），而不是读错。

## 符头三档：填充率 + 宽度

- **填充率**分实心与空心（门槛 0.62）。
- **宽度**分全音符与二分音符：`glyphmap.json` 的 Maestro 模板给出
  全音符 **1.70×1.06** 格、二分 **1.32×1.10** 格、四分 1.30×1.03 格
  ——宽度一刀分得开，而高度三者几乎相同。

原来按「有没有符干」分全/二分（全音符本来不带符干），**不可靠**：
空心符头的右侧笔画与符干在竖笔画掩模里连成一块，抽不出独立的符干段
——304 个空心块里容差放到两格也只有 98 个找得到竖段，于是二分音符整批读成全音符。

**空心那一档另设宽度下限 1.00 格**：实心符头会被去线与符干残根啃窄，所以总下限放到 0.85；
空心的不能跟着放——页面上又扁又空的小块太多（歌词笔画的转折、弧线的一小段），
被收成「空心符头」的块宽度中位数**只有 0.99 格**。宁静一首原本认出 145 个全音符，
GT 只有 15 个。门槛扫过 0.85（等于不设）/1.00/1.10，取 1.00（音符 56.30/56.62/56.52）。

### 小节自检会跟着降，那是**虚高被挤掉**

`checkBars` 跳过没有音符的小节，而**一个假全音符恰好占满 4/4 一小节**
——空小节里混进一个就「通过」了。所以剔掉假全音符时小节自检从 29.1 掉到 27.7，
不是退化。**看这个数时要连音符数一起看。**

## 歌词：切字格 → 整行 OCR → 挂音符

位图没有文字层，歌词字要 OCR 出来。三步：

1. **切歌词带与字格**（`lyric.ts`，思路照简谱那条路的 `src/omr/lyrics.ts`）：
   每个谱行下方一条带（本行下缘 → 下一行上缘）；带内按**块的纵向中心**分 verse 行
   （不能按包围盒重叠判——「一」那种只有一横的字与相邻字纵向不重叠，会被分到别行去）；
   行内按 x 邻近把块并成字格（**汉字常由多个偏旁连通块组成**，这一步不能省，
   复用 `src/omr/lyrics.ts::mergeToChars`）。
   带里先把**音乐符号剔掉**（符头与查得到音乐字典的），否则谱表内的符号会混进来。

2. **整行送 OCR，不逐格送**：PP-OCR 的 rec 是序列模型，一整条歌词的上下文能把
   单字认不准的救回来；`recognizeTextsPos` 顺带给出每个字在条内的 x，按 x 映回字格。

3. **合成文本对象**（`font: "#ocr"`）交给 `buildLyricLines` / `attachLyrics`——那两步原样跑。
   **不走 `analyzeText`**：那一步靠「带连字符的音节」「音节间的延长线」当锚点认歌词，
   中文逐字一个音节、既不连字也不拉线，一整行一个锚点都没有。位图这边本来就是
   **按位置**切出歌词带的，身份已经确定，不必再认。

### 字符映回字格：字数相同按序号，否则取最近

不能要求「`xFrac` 落在字格区间内」——那是 CTC 估出来的位置，误差常有半个字，
实测那样会丢掉近一半的字（1221 个里丢 566）。字数与字格数相同时**按序号一一对应**最稳。

### **不做形状聚类，直接用 OCR 的文本**

试过「字格 → 32×32 签名聚类 → 每类投票定字」（照 `gen-staffocr.mjs` 的每类只送一次
OCR 的账），**净损耗**：5985 个字格聚成 1866 类，只定下 969 类、覆盖 52%，歌词 35%。
门槛往松扫更差（把不同的字并成一类，票散开、过不了半：覆盖 44.6% / 32.9%），
往紧扫也只到 58.7% 覆盖。直接用 OCR 文本，宁静一首歌词 53.2% → **58.2%**。

缓存按**条的内容指纹**寻址（`stripKey`，FNV-1a），不按「第几页第几行」：
几何判据一动行的编号就全变了，按位置存的缓存整份作废；按内容存的只要那一条的
像素没变就还能用。命中缓存时识别仍然不起浏览器。

**只收汉字与全角标点**：PP-OCR 认不出时会吐拉丁字母或占位符，收进来就成了歌词里
凭空多出的字（实测 `l` 一个就出现二十几次）。查不到字的格**留空**，不编造。
