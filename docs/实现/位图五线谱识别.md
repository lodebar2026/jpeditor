# 位图五线谱识别（`src/rasteromr/`）

**整页乐谱是一张位图**的印刷五线谱 PDF → MusicXML。

与 [五线谱识别.md](五线谱识别.md) 那条（`src/staffomr/`）的分界：

| | 矢量路 `src/staffomr/` | 位图路 `src/rasteromr/` |
|---|---|---|
| 底本 | 文字层齐全，音乐符号是**真字符**（Maestro/Opus/Anastasia） | 整页乐谱是一张 **1-bit 位图**，文字层只剩页眉页脚 |
| 输入 | 路径对象 + 字形（码位 + 轮廓） | 像素 |
| 谱线/符干/小节线 | 路径里现成的线 | 按**游程**从像素里分笔画 |
| 符头 | 查字形字典 | 按**性质**判（填充率 + 有没有符干） |
| 谱号/休止/升降/拍号 | 查字形字典（轮廓 → SMuFL） | 查形状字典（32×32 签名 → SMuFL） |
| 歌词 | 读文字层 | 要 OCR（**尚未接**） |

**下游全部共用。** 本模块只负责把位图变成 `Staff` / `Seg` / `Sym`，装进 `SPage` 之后
`page.ts` 往下那一整条（符头归属 → 符干 → 符尾 → 小节线 → 谱号调号拍号 → 系统 →
小节 → 符杠 → 音高与时值 → 和弦层与声部 → MusicXML）**一行不改**。

## 底本与语料

语料路径只写在 `scripts/node-harness.mjs` 一处（`CHORUS_ROOT`，env `CHORUS`）。
一曲一个子目录，里面是 PDF，有的还有同名 `.musicxml`（GT）。

**一曲可能有好几份 PDF**，形态也不同。`chorus-report.mjs` 逐页量出来分三档：

| 档 | 实测 | 归属 |
|---|---|---|
| **干净位图** | 线距 17~19px、线宽 1.5~2.6px、倾斜 ≤1.23px | 本轮的目标 |
| **真扫描件** | Xerox 300dpi：线宽 5.1px、倾斜 3.94px；JPEG 200dpi：线距 11.4px、倾斜 3.78px | 有 GT，另记，不入基线 |
| **矢量** | 文字层里有 50 个以上音乐字体字形 | 走 `src/staffomr/`，位图路不碰 |

干净位图那一档是 PageMaker 6.5C 排版、Distiller 输出，**不是扫描件**——
整页乐谱作为一张位图贴进内容流，所以线宽整齐、没有噪点、几乎不倾斜。

## 分篇

细节（判据、阈值、试过更差的那些路）全在分篇里，**动某一块之前先翻对应那篇**：

- **[取图、去倾斜与谱线](位图五线谱识别/取图与谱线.md)**（`rasterpage.ts` / `dewarp.ts` / `staffline.ts` / `prims.ts`）——
  三种数据形态靠**数据长度**分辨 + 极性自检；逐斜率数「能看到几条谱线」去倾斜；
  弯曲扫描按**逐列黑白游程**分带推平并补出行投影漏掉的谱行；
  分系统按**左端系统线的墨**判（括号会碎，连通块靠不住）；
  **先找线、再从五条一组反推线距**；去谱线判「上下都没墨才抹」；
  几何原语靠**游程**分笔画、笔画要判孤立性（加线免检）。
- **[符头与加线](位图五线谱识别/符头与加线.md)**（`notehead.ts` / `contour.ts::findHoles`）——
  符头**不查字典、按性质判**（填充率 + 宽度 + 有没有符干）；剪掉粘着的加线再量，
  剪出来的加线要补给 `findLegers`；共用的长加线按符头切成短段；
  谱表外的符头**按自己的位置补加线**；**加线一律不抹**（抹了就把符头啃成两半）；
  **符头 + 符干（+ 符尾）并成一块的，把头摘出来**（符尾贴着符干，那条符干过不了孤立性判据）；
  空心符头**按内腔（洞）找**、再用宽高比 + 谱表带收紧；整小节休止先摘出来，
  四分休止按**位置 + 形状**自举（字典兜不住）。
- **[符干、符杠与符尾](位图五线谱识别/符干符杠符尾.md)**——
  符干要**续到符头里**（只进 `SPage`、不回写 `prims`）；假符号会吃掉整小节、
  进而抢走第一声部；抹符杠**只抹它自己那条带**；符杠也要**沿 x 闭一道**（时值的头号修复）；
  符尾按位置自举、不查字典，**窗口要贴着符尾的实际宽度**（这套底本的符尾只有 0.9 格宽的一条细弧）。
- **[形状字典与符号识别](位图五线谱识别/形状字典与符号.md)**（`rasterglyphs.ts`）——
  只有「32×32 签名聚类」一层键；定案三层（模板 / 位置自举 / 人工小表），
  模板取矢量路 `glyphmap.json` 的 Maestro 一家、**签名要上下翻**；
  谱号先把碎块并回一个盒再验；拍号位置自举 + 模板验（0% → 100%）；
  升降号**被抽走的那道竖笔要并回来**、降号的盒要收到下面那个肚子上。
- **[contour 认领账本与图形符号](位图五线谱识别/图形符号与账本.md)**（`contour.ts` / `ledger.ts` / `wedge.ts` / `dynamics.ts` / `slur.ts`）——
  认领账本量得出「印在纸上而我们从没看见的那些」（墨覆盖 90.8%，无主报表是往后取舍的证据）；
  松叶按 contour 认、不拼线段；力度靠**版式连字**拼 `mf`；弧线判「逐列一段墨、而且拱着」。
- **[歌词](位图五线谱识别/歌词.md)**（`lyric.ts`）——
  切字格 → **整行**送 OCR → 挂音符；断行按**间隙**不按定宽窗口（歌词档最大的一个洞）；
  字符映回字格用**单调对齐**、标点并进相邻的字；不做形状聚类；
  OCR 缓存按**条的内容指纹**寻址，且**生成器必须与识别走同一条路**。
- **[度量、跨系统连接与对拍](位图五线谱识别/度量与跨系统连接.md)**（`chorus-diff.mjs`）——
  `noteAcc` 会**奖励碎片化**，判连接看**含游离**那一档；`sameToken` 的两条通配
  （认不出的那一项不参与否决）；版式**从 GT 的 `<print>` / `<staff-details print-object>` 直接读**，
  按谱行比是正式尺子；谱号继承；「一行谱写着两个 GT 声部」的合流档一次都不成立。
- **[现状与待办](位图五线谱识别/现状与待办.md)**——
  已落地清单、基线数字、三个数各管一段账、和弦档与逐谱行/逐符号的实测，
  以及按收益排的待办（含几笔**算错过的账**，记着免得再算一遍）。

## 基线一眼

`testdata/合唱谱/raster-baseline.json`（干净位图 4 份、其中 2 份有 GT）：
音符 **82.3%**、含游离 82.1%、音级 82.6%、歌词 74.3%、不靠 GT 的小节自检 55.0%；
**按谱行（GT 推导）音符 93.2%、音级 93.4%、歌词 95.2%**。
真扫描件（5 份，含望十架三份）**也进基线**：音符 44.7%、含游离 37.5%。**人声行已经在 81~98%，钢琴两行是仅剩的大洞**
——病灶已从「几乎全是漏检」变成**读错与漏掉各半**，而读错**一面倒地偏高**
（识别比 GT 高 2~7 级，正好是和弦音程：和弦最低那个音丢了）。
数字的来龙去脉见[现状与待办](位图五线谱识别/现状与待办.md)。
