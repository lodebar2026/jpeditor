# 简谱纵向栅格与八度点居中（`src/layout/layout.ts`）

数字上下堆叠的东西——高音点、低音点、slur/tie 弧线、三连音括号、延长记号——
以及小节线的高度，全部落在**同一把尺子**上。改这块之前先读这篇，别照直觉调常量。

参照物是 C++ 工程 musicpp（`~/proj/musicpp`，`model/render.cpp` / `model/model.cpp` /
`util/pptutil.cpp`），它的简谱纵向只有一个步长 `octaveDotDist = 6`（`jianpuFont` 30，即 0.2 em）。

## 一个常量就是这把尺子

`LayoutOptions`（`layout.ts`）：

```ts
jpStackGap = fontSize / 6;                              // 数字**上方**那一带的纵向间隙
get jpDotRung() { return jpStackGap + numberBound(".").height; }   // 一格 = 点 + 间隙
jpBelowGap = fontSize / 9;   // 数字**下方**那条阶梯的间隙（数字↓减时线↓低音点）
get jpLowDotRung() { return jpBelowGap + 2 * jpDotRadius; }        // 低音点那一摞的一格
jpBeamTop  = jpBelowGap + jpBeamWidth / 2;   // 第一条减时线（字段记线心，故加半个线宽）
jpBeamDist = fontSize / 8;   // 减时线层间距，musicpp beamDistJP = 3.5
```

**唯一的规矩：竖着叠起来的每两样东西之间都留 `jpStackGap`，而且量的是墨迹到墨迹。**
数字顶↔第一个高音点、点↔点、最上面那样东西↔slur —— 三处全相等（28px 下实测均为 **4.67**）。

点的字形挂在自己基线之上（`.` 在 PingFang SC 28px 下墨迹 `-3.33 .. +0.11`），
所以上下两侧换算成文本基线的修正量不同，`NoteEntry.octaveDot` 里分别减
`dotBound.bottom` / `dotBound.top`。

| 元素 | 位置 |
|---|---|
| 高音点第 `d` 行（`d = 0` 最靠近数字） | `numBound.top − jpStackGap − d × jpDotRung` |
| `entryTop`（整摞东西的墨迹顶） | `numBound.top − oct × jpDotRung` |
| slur / tie（`NoteEntry.slurRung`） | `entryTop − jpStackGap` |
| tie 之上还要走 slur、三连音括号、fermata 压着 slur | 再各 `+1` 格 `jpDotRung` |

低音点是镜像（`entryBottom`），且让开减时线：起点取
`max(数字墨迹底, jpBeamBottom(beams))`，再走 `jpBelowGap` + `jpLowDotRung`。

**上下两侧的 gap 不是同一个数**（用户口径：「低音点离减时线有点偏远，改为 PPT 模式的距离，
要看起来音符、减时线、低音点之间的距离相等」）：上方那一格 `jpStackGap = 1/6 em` 要给弧与
三连音括线留手；下方三样（数字 → 减时线 → 低音点）是紧挨着排的一摞，1/6 em 会显得散，
而且原来还不等——减时线是按**线心**摆在 `jpStackGap` 上、低音点是按**墨迹**摆在减时线墨迹之下，
28px 下实测 3.92 : 4.67。现在两处都按墨迹算、都用 `jpBelowGap = 1/9 em`（PPT 档实测的
2.88 / 3.04，取整到 1/9 em），28px 下 **3.11 : 3.11**。
混排的简谱层同口径（`mixed/render.ts` 里的 `font.size / 9`，那里原来写死 musicpp 的
`35 − diff*0.8` 与 `staffHeight + beamDistJP×层数 − 2`，两处对不齐）；
成书那一路仍用原书量到的 `stackGapEm`（`applyBookStyle` 里把 `jpBelowGap` 设回 `jpStackGap`）。

**附点**（`NoteEntry.addAugDots`）也是矢量圆，不是字体里的 `·`：圆心与**数字墨迹的中心等高**，
横向落在「数字墨迹右缘 → 条目右缘」的正中（advance 仍按 `·` 保留，横向间距不变），
大小默认与八度点相同（`augDotRadius`，PPT 档另给 em/15）。

改这里之前的旧代码混了**三套**互不相干的步长：高音点用 `dotBound.height * 1.5`（≈4.2px）、
`entryTop` 在此之上再减 `numberSize/8`（3.5px）、三连音用 `numberSize/2`（14px）。
后果是「数字顶 → 高音点」只有 **2.0px** 而「高音点 → slur」有 4.4px。

### 「PPT 版面」档把这把尺子换回旧式（`jpGridLegacy`）

`LayoutOptions.jpGridLegacy = true` 时，上面这套等距栅格整体退回 2026-08 重构**之前**的
三套步长——那是导出 PPTX 的观感基准（`2a8aa85`，见 `src/layout/pptxstyle.ts`）：

| 元素 | 旧式落点 |
|---|---|
| 高音点第 `d` 行 | `numBound.top − (d + 0.5) × dotH × 1.5`（**基线**，不是墨迹） |
| 低音点第 `d` 行 | `numberSize × (d × 0.175 + 0.25) + beams × jpBeamDist` |
| `entryTop` | 同上再减 `numberSize / 8` |
| slur / tie（`slurRung`） | **就是 `entryTop`**——那个 1/8 就是当年的间隙，不再额外让一格 |
| 三连音 / tie 让位 | `numberSize / 2` 与 `numberSize / 8`，与点的步长互不相干 |

有两处换算要当心：八度点当年是字体的 `.` 字形、按**基线**摆，今天是矢量圆、按**墨迹顶**摆，
所以旧式落点要加上 `.` 自己的墨迹上缘 `dotBnd.top` 才落回同一处；`entryBottom` 旧式只看
减时线的**层号**（`beams × jpBeamDist`），与数字墨迹底无关，不走 `jpBeamBottom`。

这几个数彼此对不齐（28px 下数字↔点 ≈ 2.0px 而点↔弧 ≈ 4.4px），正是后来改成等距的原因；
**只在 PPT 档打开**，默认那条路一个数都不受影响（`node scripts/pptx-check.mjs` 守着）。

### 与 musicpp 的三处刻意背离

1. **musicpp 自己就不等距，本项目等距。** 它按 `octaveDotDist = 6` 步进高音点
   （`render.cpp:906`），却用另一个原点 `pl.y = 4 − dot*6 − jpTopDy` 抬 slur
   （`model.cpp:2649`），换算到 28px 是「数字↔点 ≈ 6.4、点↔slur ≈ 2.3」——正是肉眼可见的不匀。
   本项目改成单一 `jpStackGap`。**它的绝对高度仍是好的校准值**：一个高音点时，
   本项目的 slur 落点与 musicpp 相差 0.1px 以内。
2. **堆叠方向。** musicpp 把**最外一层**点钉死在 `octY = 2`、向下填回数字
   （`octY` 与点数无关），于是只有一个点时会和数字空开一大截。
   本项目从数字向外堆，`d = 0` 最靠近数字——这才是常规简谱写法。
3. **三连音与 fermata 收敛到一格。** musicpp 这两处用 `7`（`render.cpp:1398`、`:349-353`）
   而它自己的点步长是 `6`，两者对不齐。本项目统一用 `jpDotRung`。

### 减时线

第一条在基线下 `jpBeamTop = fontSize/6`，之后每层 `jpBeamDist`。
对应 musicpp `y = level*beamDistJP + 35`（`render.cpp:161`），其中 `level` 是 **0 基**
（`processLevelJp` 的判据是 `lev >= cnt`），数字基线在 35−5 = 30 处。
本项目的 `level` 是 **1 基**，所以写成 `jpBeamTop + jpBeamDist*(lev−1)`。

漏掉那个 5 单位的基准偏移会让第一条减时线贴在数字上（原来只有 `jpBeamDist` = 3.5px，
描边加宽到 musicpp 的 1.5 之后净空只剩 2.75px）。现在净空 3.92px，musicpp 等价值 3.97px。

## ⚠ SMuFL 字形的包围盒是**乐谱坐标**（y 向上为正）

这是本篇最容易反复踩的一个坑，**动任何与乐谱字形（fermata / 重音 / 升降号 / Segno /
力度记号 / 三连音的「3」）有关的避让之前先读这一段**。

SMuFL 元数据里的 `bBoxNE` / `bBoxSW` 是**乐谱坐标**：y **向上为正**，`NE[1]` 是墨迹**上**缘、
`SW[1]` 是**下**缘（多半是 0 或负数）。而页面树的 `Rect(left, top, right, bottom)` 是
**页面坐标**：y 向下为正，`top < bottom`。两者**反号，且 top/bottom 对调**。

`SmuflText.bound` 现在**已经翻好了**（返回页面坐标），拿它当墨迹框就行。
在此之前它直接返回乐谱坐标，于是：

- `Group.update()` / `childrenBound` 把整个记号的盒子摆到基线**下方**一截；
- 凡是拿它做避让的都多让三四个点——302《一切全奉献》的 fermata、470《出到营外》的重音、
  064《啊！圣善夜》的 Segno（一度被顶到和弦上方 21pt）全栽在这里；
- `addTuplet` 当年干脆绕开它、自己读元数据算「3」的墨迹中心（那儿的注释就是这个坑的旧案）。

配套的两条：

- **`TextFrame.y` 是基线，不是墨迹上缘**（`bound.top` 才是）。`KeySig` 与 `addEnding` 都踩过。
- **条目组 `update()` 之后子级的 `y` 是相对组原点（左上角）的**，而 `entryTop` / `slurRung`
  那套给的是**相对基线**的偏移。两套坐标混用会差出一个 ascent——换算的锚点是主数字的 `y`
  （基线在组里的位置）。

## 八度点的水平居中：`1` 偏 0.88px

musicpp（`render.cpp:906`）、Kotlin 原版（`../src/main/kotlin/mp/layout/layout.kt:1675`）、
本项目旧代码是同一行：按 **advance width** 居中。三边都带同一个偏差。

`PingFang SC` 28px 实测（Canvas `actualBoundingBoxLeft/Right`）：

| 字符 | advance | 墨迹中心 | advance 中心 | 偏差 |
|---|---|---|---|---|
| `0` `2` `3` `4` `5` `6` | 16.80 | 8.40 | 8.40 | ~0 |
| `7` | 15.32 | 7.52 | 7.66 | 0.14 |
| **`1`** | **11.23** | **4.73** | **5.61** | **0.88** |
| `.` | 7.39 | 3.70 | 3.70 | 0 |

`1` 在 PingFang 里是比例宽（11.2，其余数字 16.8 等宽），墨迹中心偏左 em 的 3.1%。
**只有 `1` 有肉眼可见的偏差，而 `1` 恰是简谱里最常见的数字。**

修法：`measureGlyphText`（`src/common/measure.ts`）本来就在调 Canvas 取垂直紧包围盒，
顺手把同一次调用里免费的 `actualBoundingBoxLeft/Right` 也收进 `bbox`（水平方向原先硬写成
`0..advance`）；`Font.inkCenter(ch)` 暴露墨迹中心；`JpNumber.cx` 改用它。
FreeType/Skija 在那条路径上给不出墨迹边界，浏览器给得起——这是本项目相对 musicpp 的便宜。

> `cx` **只**用于装饰对齐（八度点、slur/tie 端点、三连音括号、fermata）。横向排版走的是
> `JpNumber.width` / `left` / `right`，**不碰 `cx`**，所以音符与歌词的横向间距一点没动。

## 小节线高度与 slur 避让

小节线与拍号的上下缘由 `LayoutOptions.jpStaffTop / jpStaffBottom` 给出，对齐 musicpp 的
40 单位简谱 staff（`render.cpp:802`、`:1793`）：**基线以上 1.0 em、以下 0.333 em**。
设计意图是小节线正好从高音点行贯到低音点行。旧值 `23/28` 与 `5/28`（共 1.0 em）矮了三分之一，
下缘连第一行低音点都够不着。线宽同时对齐 `pptEngraver`：细小节线 2、减时线 1.5。

抬高小节线带来一个两边参考实现都没处理的问题：**无高音点时 slur/tie 端点在 -26.5px，
比小节线顶 -28px 还低**，跨小节的 tie（末音 tie 到下小节首音，最常见的一种）会被小节线
从上方穿透。musicpp 靠分层侥幸躲开（有高音点时弧线自然被抬走），`dot = 0` 时它同样会相交。

`Line.clipBarlinesUnderSlurs()` 补上这一层：凡是被某条弧线的**包围盒**横跨的小节线，
上缘压到「弧线下缘 + `jpStackGap/2`」，**只压不抬**。用整体包围盒而不是解贝塞尔在小节线
`x` 处的精确值——偏保守、恒不相交，代价只是那根小节线矮一丁点。

⚠️ `clipTop` 必须在 `Group.update()` **之后**的表示上做文章：`update()` 已经把每条
`GraphicLine` 的 `p0` 折进了 group 的 `y`、children 留在 `y=0`、`p1` 只剩长度。
再去赋 `p0` 会被 `GraphicLine.update()` **二次折叠**，线会既移位又变长（调试时表现为
小节线变成一根穿过弧线的长十字）。正确做法是移动 `group.y` 并同量缩短 `p1`。

## 弧高的上下限、扁平长连音线、和弦让位

弧高走的是 musicpp 的对数公式（`SlurTieBase.arcHeight`，**弧高的唯一算法**）：

```
h = clamp(log10(dist) * 17 - 16, minHeight, maxHeight) * heightScale   // 控制点高，弧顶约 0.75 h
```

原来两头都没有钳位，于是两头都失控。28px 字号下实测（testdata 十四首）：跨度 30px 的
弧顶 6.6px、跨度 218px 的弧顶 17.8px——差 2.7 倍。长的那头顶进和弦带（和弦与弧线**都从
「音符墨迹栈顶」起算、互不知情**），短的那头塌成一条直线。

### 上下限从原书量出来

用矢量路（`src/omr/vector.ts` + `classifyPage`）扫页 40-240，收 `cls === "slur"` 的对象
**1205 条**，按跨度分桶取弧高中位数（bbox 高，含描边），除以音符墨迹高 8.33pt：

| 跨度 | 弧高 | / 音符高 |
|---|---|---|
| 0-15pt | 3.43 | **0.41** |
| 15-25 | 3.43 | **0.41** |
| 25-40 | 4.44 | 0.53 |
| 40-60 | 4.93 | 0.59 |
| 60-90 | 5.48 | 0.66 |

**最短两桶数值完全相同** —— 原书的短弧是**定高**的，不随跨度塌；而跨度从 1.7 个音符宽
涨到 7.7 个，弧高只涨 60%。所以成书那一路取 `slurMinArcEm = 0.41`、`slurMaxArcEm = 0.66`
（`bookstyle.ts`，**手调常量、不从原书量**——`stats.ts` 量的是别的东西）。
open-fanqie（`renderer.ts:703`）干脆让弧高**恒定** 10px 与跨度无关，方向是一致的。

⚠️ 这两个字段连同 `slurFlatSpanSteps` 都是**后加的**，而 `testdata/500/bookstyle.json`
是 `stats` 实测生成的产物，**里面没有它们**。不兜底的话 `rawH * undefined` = `NaN`
（`NaN > 0` 为假 = 等于没封顶）、`undefined > 0` = `false`（等于关掉扁平），整条改动会
**静悄悄地不生效**，而且 line-check 还会报「基线持平」让人以为一切正常。
`browser.ts` 里一律写成 `m.x ?? 默认值`，字段类型也声明成可选。

### 倚音：两条简谱路共用一份几何（`src/common/gracenote.ts`）

文本谱那边早就有一套照原版矢量量出来的倚音画法（`pu/painter.ts::paintGrace`）：小号数字
（0.5 倍）+ 八度点 + 减时线 + 从减时线中点垂下再朝主音弯的连接钩，所有比例以**主音数字的
墨迹高**为单位（倚音中心在主音中心上方 0.94、离主音中心 0.665，减时线长 0.388、线宽 0.055…）。

成书这一路（`layout.ts::addGraceNotes`）**共用同一份几何**：两边的绘图原语不一样
（一边是 pu 自己的 text/dot/rect/stroke，一边是页面树的 TextFrame/GraphicPath），
所以 `gracenote.ts` 只算坐标、落笔各自去做。各路把自己的常量折算成 `GraceMetrics`
那几个数（`ink` / `scale` / 八度点位置与间距 / 减时线层距）。

横向占位走 `Entry.leadSpace`（`graceAdvance`）：倚音在拍点**之前**唱，位置也该在主音符之前，
直接往左伸会压住上一个音符。DrawText 打 `cls="grace"`，`countStaffRows` /
`measureCellsPerLine` 数格时要跳过它，否则容量凭空多出一格。

### 看着扁的就画扁平：按**宽高比**判（`slurFlatRatio`）

跨度那条阈值（`slurFlatSpan`，成书按 4 个音符步距）是**绝对宽度**，跟不上字号与弧高上限的
变化——91《我灵镇静》那几条罩着五六个十六分音符的弧，跨度还不到 4 个步距，照旧画成高高的
月牙。真正该看的是「这条弧看着扁不扁」，也就是**跨度 ÷ 弧顶高**（`SlurStyle.flatRatio`，
成书 7）。弧高是对数公式加上下限算的、长跨度那头封了顶，所以跨度一长比值就迅速变大。

另有一条按**音符个数**的（`slurFlatNotes`，数的是**和弦个数**——长音的增时线各占一个
`NoteEntry`，不能按 entry 数），成书默认关掉，宽高比那条已经够用。三条取先满足的那个。
### 超长跨度改画扁平长连音线

跨度超过 `slurFlatSpan`（成书 4 个音符步距；编辑器默认 `numberSize * 5`）改走
`SlurTieBase.initFlat`：两端各一小段钩弧、中段一条直线。open-fanqie 的
`slurStyle: 'auto'` 就是这么干的（跨度 > 100px 换成 `lianyinxian_zuo`/`lianyinxian_you`
两个钩字形加一条直线）；本项目没有那两个字形，钩自己用贝塞尔画。最常触发的是长音：
`3 - - -` 底下拖着增时线，音头没几个、跨度却很宽。

两个已经踩过的坑：

- **高度取「阈值处那条弧的弧顶」**（`arcHeight(flatSpan) * 0.75`），不是 `arcHeight(flatSpan)`
  本身——后者会让扁平版比它替换掉的弧还高 4.5px，跨过阈值的一刻突然长高一截。
- **形状要与弧同一套语言**：填充的月牙、两端收到端点上成尖角（`flatEdge` 去程画上缘、
  回程下压 `t` 画回来，两端共用 `pl`/`pr` 所以天然是尖的）。最早写成一条等宽描边线，
  两端齐头齐脑，跟满页的月牙弧摆在一起很扎眼。中段厚度成书取**小节线宽**
  （按弧厚折算的 0.45 倍在小字号下太肥）。

原书的长弧其实**不是**扁平的，是折线逼近（`curves = 0`、18~24 段）的浅弧——这里是有意
不照原书，取番茄那一路的画法。

- **让位要按扁平的形状算，别按抛物线**（2026-09-01 修）。上方带堆叠问「这一段 x 上弧有多高」
  用的是 `Line.collectBandItems` 里的 `topAt`，它按**抛物线**近似弧（两端贴着音符、中点最高）
  ——扁平式的墨迹却是中段一路平着顶在盒顶、只有两端 `hx` 那一截往下收，而那两截还是
  **贝塞尔的钩**、一出端点就贴着顶走。照抛物线算，末端附近就成了「那儿几乎贴着音符」，
  fermata 于是不让位，直接压在扁平线上（171《回家吧》末行的延长号，压了 2pt）。
  改法：`SlurTieBase.flatHx` 记下钩长当标志，扁平式**整条按盒顶算**。
  试过按钩长做线性插值——**方向是反的**：真实的贝塞尔比直线更快抬到顶，线性反而偏乐观，
  171 那处只让开了 2.2pt 里的 2.0pt，仍差 0.2pt 压着。扁平线本来只有几个点高，
  让过头也就多抬那么几个点。全书代价 2 页（678 → 680），判据全档持平。

### 上方带堆叠（`src/layout/upperband.ts` + `Line.stackAbove`）

音符上方那一带住着**七类东西**：弧 / 三连音括线 / fermata 与重音 / 和弦 / 段落词 /
表情记号（`rit.` `Fine` `mf`）/ 转调标记 / 房号。从前它们各自为政——
`liftChordsUnderSlurs` 只知道弧、`liftKeySigOverChords` 只知道和弦、`addEnding` 自己扫全行；
三连音括线**一处都不在**（456《常常喜乐》的和弦就从括线上穿过去），
房号的高度还是按**基线**扫的（`pos().y`，不是墨迹上缘，且和弦挂在音符组的子级上压根扫不到
——158《一件礼物》的房号数字因此骑在和弦 `C`/`F` 上）。

现在统一成一个扫描线分层器。**带序**（自下而上）：

| 层 | 住着谁 | 让位规则 |
|---|---|---|
| 0 | 弧、三连音括线、fermata、重音 | 层内**异类**才互避，按 x 跨度排，**跨度小的在下**；<br>fermata / 重音这类**点状标记排在最后**——撞上弧时抬的是它，不是弧（弧要贴着音符走）；<br>让位按**弧在那一段 x 里的实际高度**（`BandItem.topAt`，抛物线近似），不是包围盒顶——<br>包围盒顶是中段那个最高点，而记号多半落在两头，照包围盒让会抬到半空中（302 首）；<br>另外**要让开本音符的临时升降号**（`#` 斜挎在数字左上角、比数字墨迹顶还高，<br>只留一格的话 `>` 看着像挂在它身上，所以那一处留 1.6 格） |
| 1 | 和弦、表情记号 | 撞下层才抬（同一条弧底下让了位的取齐）；同层里和弦先定位 |
| 2 | 转调标记 | 撞和弦就抬（144 首） |
| 3 | 房号 | `addEnding` 按堆叠结果定一条**全行统一**的车道 |

三条口径，每条都是拿具体曲子换来的：

- **同类不互避**（`BandItem.kind`）。弧与弧交错原书本来就是嵌套着画的（长弧罩住短弧），
  让它们也互避会把整本从 675 页撑到 692 页。要分层的是弧与三连音括线这种**异类**。
- **只有真冲突才让位**（用户口径：「不能直接一层层堆叠」）。墨迹相交才推；
  同一条弧底下**让了位的那几个**和弦取齐到同一高度（`BandItem.spread`，一高一低比压着还难看），
  但**没被压上的一个都不动**——照直整排抬等于不冲突也往上摞。
- **一律按墨迹算**，`TextFrame.y` 是基线不是墨迹上缘（`bound.top` 才是）。
  判据那头也要有真值：SMuFL 字形的墨迹上缘随 `DrawText.inkTop` 一起写进 DrawList
  ——fermata 的墨迹高 0.3 个字号、重音只有 0.12，line-check 照字号估会差出好几个点
  （470 的重音因此一度被判成压着括线）。
  ⚠ **`SmuflText.bound` 更要小心**：它是 **SMuFL 坐标**（上为正），与页面坐标**反号**，
  top / bottom 也因此对调（`addTuplet` 里干脆自己读元数据，就是为了躲开它）。
  照直拿来当墨迹盒，整个盒子会挪到基线下方一截——302《一切全奉献》的 fermata
  与 470《出到营外》的重音因此都被顶高了三四个点。
  `KeySig` 那处从前踩过，`addEnding` 这次也是同一个坑。

段落词（`（副歌）`）的基线跟着第一个和弦走（`sectionWordBaseY`），和弦抬起来它自然跟着；
本行没有和弦时由 `liftSectionWordsUnderSlurs` 收尾（现在它认的是整个 layer 0，不只是弧）。

调用顺序：`addSlur` → `spreadChordsHorizontally` → `addDirections` → **`stackAbove`** →
`addEnding` → `addSectionWords`。堆叠必须在弧画完之后（要弧的实际位置）、房号之前
（车道读堆叠结果）。

### 跳转记号排在小节末尾（`Fine` / `D.S.` / `Segno`）

底本里 `Fine` 与 `D.S.` 标在小节**最后一个音符之后**、`barline` 之前，还带 `justify="right"`
——原书就印在小节线跟前，与和弦同一条基线并排。所以：

- **认哪些是这一类**：底本给 `Fine` / `D.S.` / `D.C.` 都标了 `justify="right"`，
  而 `rit.` 那种表情记号没有。光看「在不在小节最后一个音符之后」认不全——
  064《啊！圣善夜》的 `D.S.` 就标在小节最后一个音符**之前**。两条判据并用
  （`ChordDirection.atBarEnd`）。
- 落位贴着**本小节右侧小节线**右对齐，不居中在最后那个音符上方。
- **纵向一律留到 `stackAbove` 之后再定**（`Line.placeDirections`）：记号要跟身边的和弦排齐，
  而「和弦被弧顶起来」是堆叠里才发生的事，在 `addDirections` 里对齐就对到了抬之前那条线上
  （064 实测差 6.3pt）。基线取**离它最近的那个和弦**，不是本行第一个——同一行的和弦
  并不总是等高（八度点、被弧抬过的差半个字号）。
- **让位不许越过小节线**：`D.S.` / `Fine` 标的是**这一小节**唱到哪儿为止，挪到上一小节
  就换了意思。
- **与小节线右对齐**：记号右缘对到小节线**整组墨迹的右缘**（`Barline.inkRight`）。
  终止线是「细 + 粗」两条，对到细线左缘的话记号还落在粗线左边一大截。
- **PDF 那头整段自然排**（`DrawText.align = "left"`，见 `browser.ts::pageItemsToDrawPage`）：
  逐字笔位是浏览器量的 advance 前缀和，PDF 里嵌的字体 advance 与它有微差——单字符的和弦、
  音符看不出来，`D.C. al Coda` 这种带空格的多字词就被摆成了「D.C.a lC oda」。
- **地方不够就把小节撑宽**（`Line.spreadForBarEndMarks`，用户口径）：与段落词那套一样——
  锚点不动、小节内的间距均摊拉开、小节线右边的东西整体右移，排在 justify 之前
  （`updateXPos` 里；justify 只会往空档里加距离、不会收窄，这里放得下之后也放得下）。
  **撑开不许把整行拉出版心**，撑不下才退回下面这条。
- **撞了才让，先沿 x 让、让不开才抬一层**。挡路的和弦要按**与判压同一把尺子**
  筛（含那道净空容差）：照「严格重叠」筛的话，差 0.3pt 挨着的和弦一个都选不中、
  `left` 成了 `Infinity`，于是明明往左让一让就行，却直接抬到了上面一层
  （344《万古磐石为我开》的 `Fine`）。
- **抬那一下也要按真实墨迹算**：抬到「它那一段 x 上最高的那件东西（弧、三连音括线、
  和弦）」之上一格，不是固定抬一个字号——179《我主耶稣是生命源》的 `f` 底下就一条弧，
  照固定量抬完离弧 8pt，空落落地飘在那儿。下面什么都没有才退回固定量。
  ⚠ **和弦要按墨迹顶算**，不是按盒顶：纯文本那档 `inkBound` 是关的，盒顶是**字体 ascent**，
  比真墨迹高一截（064《啊！圣善夜》的 Segno 因此比和弦高出一大块）。
  口径与 line-check 判压那把尺子对齐：墨迹顶 = 基线 − 0.85 字号。
- `<segno>` / `<coda>` **元素**这次才读进来（从前只读 `<sound segno=>` 的属性，
  播放跳得对、谱面上什么都没印，344《万古磐石为我开》的 Segno 就这么丢了）。

### 和弦是标记，不撑开谱面

和弦按音符墨迹中心居中，**可以横向伸出音符的范围**（原书就这么印的）。两条随之而来：

- 撞上了**沿 x 让**，不是往上摞（`spreadChordsHorizontally`：后面那个往右挪，
  挪动量封顶 1.2 个字号，且一个字都不许出版心）。纯文本风格下 `E♭7` 这种宽和弦
  会顶到下一个上（全书 6 处，019 / 078 那几首）。
- **不算进「这一行放不放得下」**（`naturalSpans` 跳过 `chord-group` 与 `direction-group`，
  helper 是 `entryRight` / `entryBounds`）。算进去的话宽和弦会把整句挤到下一行——
  446《迦勒看见主》实测因此从原书的 3 行（每行两句）变成 6 行（一句一行）。
  段落词与表情记号同理，它们本来就挂在行上、不挂在音符上。
  ⚠ **只挡右缘挡不住**：`Group.update()` / `normalizeX()` 都按**所有**子级的包围盒归一，
  和弦往左伸出时整个条目的原点跟着左移，和弦于是从左缘溜回度量里（446 的容量因此在
  两种和弦风格下差出一格；试过只在右缘挡，结果是 446 好了、396《我要向高山举目》的
  行末音符挤出版心 4.4pt——两把尺子口径不一致的必然结果）。
  正解是把条目原点**归到音符内容的左缘**（`normalizeEntryX` 替掉 `calcXPos` 里的
  `normalizeX`），和弦组的 `x` 允许为负、照常绘制，横向度量则完全干净；
  `doLineBreak` 与 `naturalSpans` 从此共用 `grp.x` 与 `entryBounds(g).right` 一把尺子。

### 三连音：跨度里所有音符都要让开，和弦按局部高度让它

- **括线的高度扫全跨度**，不只两端，且把**音符自己的记号**都算进去：临时升降号
  （470《出到营外》那组三连音中间那个音符带升号，只看两端的话括线正好压在升号上）、
  fermata、重音。口径是「点状记号贴着音符走，罩住几个音符的括线在外层」——所以
  **让位的是括线不是记号**（`BandItem.skipKinds`：artic 不为 tuplet 让）。
  八度点已经算在 `entryTop` 里了；和弦不算（它在括线之上）。
  ⚠ 临时记号是 `SmuflText`（`bound` 反号，见上），而且条目组 `update()` 归一化之后
  子级的 `y` 是相对**组原点**算的——`entryTop` 那套是相对**基线**的，
  两边要换算（基线在组里的位置正是主数字的 `y`）。
- **上头的和弦按「它那一段 x 上括线到底多高」让位**（`BandItem.topAt`）：数字「3」骑在
  横线中间、上下各半个墨迹高，横线那一截只有线宽。照整体盒顶让的话，括线两头的和弦
  也要为中间那个数字多抬三四个点（456《常常喜乐》）。

## 三连音数字与括线的居中

括线中间要给数字让出一道缺口，数字**按墨迹**落在缺口正中（上下、左右都居中）：

- 纵向：数字的墨迹中心对到括线的 `y` 上，数字因此**骑在线上**。
- 横向：缺口半宽 = 数字墨迹半宽 + `0.15 em`（原来写死 `numberSize/3`，与字形无关，
  在成书重排那种小字号下会宽出一大截空）。

两者都拿 SMuFL 元数据（`opt.smuflMeta.getBBox("tuplet3")`）现算，**不走 `SmuflText.bound`**：
那个 bound 是从元数据直接换算的，y 轴还是 SMuFL 的「上为正」，与页面坐标反号
（`top`/`bottom` 也因此对调）。拿它算墨迹中心，符号会被往上推整整半个墨迹高
（≈0.37 em），看着就是「3 飘在括线上方」。按字号估一个偏移（`0.28 em` 那种）同样不准——
Bravura 的 tuplet 字形墨迹只占 em 的一小截（`tuplet3` 是 SW `[0.04, −0.032]`、NE `[1.224, 1.5]`）。
