# 简谱纵向栅格与八度点居中（`src/layout/layout.ts`）

数字上下堆叠的东西——高音点、低音点、slur/tie 弧线、三连音括号、延长记号——
以及小节线的高度，全部落在**同一把尺子**上。改这块之前先读这篇，别照直觉调常量。

参照物是 C++ 工程 musicpp（`~/proj/musicpp`，`model/render.cpp` / `model/model.cpp` /
`util/pptutil.cpp`），它的简谱纵向只有一个步长 `octaveDotDist = 6`（`jianpuFont` 30，即 0.2 em）。

## 一个常量就是这把尺子

`LayoutOptions`（`layout.ts`）：

```ts
jpStackGap = fontSize / 6;                              // 唯一的纵向间隙
get jpDotRung() { return jpStackGap + numberBound(".").height; }   // 一格 = 点 + 间隙
jpBeamTop  = fontSize / 6;   // 基线 → 第一条减时线，musicpp 35 − 30 @ jianpuFont 30
jpBeamDist = fontSize / 8;   // 减时线层间距，musicpp beamDistJP = 3.5
```

**唯一的规矩：竖着叠起来的每两样东西之间都留 `jpStackGap`，而且量的是墨迹到墨迹。**
数字顶↔第一个高音点、点↔点、最上面那样东西↔slur —— 三处全相等（28px 下实测均为 **4.67**）。

点的字形挂在自己基线之上（`.` 在 PingFang SC 28px 下墨迹 `-3.33 .. +0.11`），
所以上下两侧换算成文本基线的修正量不同，`NoteEntry.octaveDot` 里分别减
`dotBound.bottom` / `dotBound.top`。

| 元素 | 位置 |
|---|---|
| 高音点第 `d` 行（`d = 0` 最靠近数字） | `numBound.top − jpStackGap − d × jpDotRung` |
| `entryTop`（整摞东西的墨迹顶） | `numBound.top − oct × jpDotRung` |
| slur / tie（`NoteEntry.slurRung`） | `entryTop − jpStackGap` |
| tie 之上还要走 slur、三连音括号、fermata 压着 slur | 再各 `+1` 格 `jpDotRung` |

低音点是镜像（`entryBottom`），且让开减时线：起点取
`max(数字墨迹底, jpBeamBottom(beams))`，再走同样的 `jpStackGap` + `jpDotRung`。

改这里之前的旧代码混了**三套**互不相干的步长：高音点用 `dotBound.height * 1.5`（≈4.2px）、
`entryTop` 在此之上再减 `numberSize/8`（3.5px）、三连音用 `numberSize/2`（14px）。
后果是「数字顶 → 高音点」只有 **2.0px** 而「高音点 → slur」有 4.4px。

### 与 musicpp 的三处刻意背离

1. **musicpp 自己就不等距，本项目等距。** 它按 `octaveDotDist = 6` 步进高音点
   （`render.cpp:906`），却用另一个原点 `pl.y = 4 − dot*6 − jpTopDy` 抬 slur
   （`model.cpp:2649`），换算到 28px 是「数字↔点 ≈ 6.4、点↔slur ≈ 2.3」——正是肉眼可见的不匀。
   本项目改成单一 `jpStackGap`。**它的绝对高度仍是好的校准值**：一个高音点时，
   本项目的 slur 落点与 musicpp 相差 0.1px 以内。
2. **堆叠方向。** musicpp 把**最外一层**点钉死在 `octY = 2`、向下填回数字
   （`octY` 与点数无关），于是只有一个点时会和数字空开一大截。
   本项目从数字向外堆，`d = 0` 最靠近数字——这才是常规简谱写法。
3. **三连音与 fermata 收敛到一格。** musicpp 这两处用 `7`（`render.cpp:1398`、`:349-353`）
   而它自己的点步长是 `6`，两者对不齐。本项目统一用 `jpDotRung`。

### 减时线

第一条在基线下 `jpBeamTop = fontSize/6`，之后每层 `jpBeamDist`。
对应 musicpp `y = level*beamDistJP + 35`（`render.cpp:161`），其中 `level` 是 **0 基**
（`processLevelJp` 的判据是 `lev >= cnt`），数字基线在 35−5 = 30 处。
本项目的 `level` 是 **1 基**，所以写成 `jpBeamTop + jpBeamDist*(lev−1)`。

漏掉那个 5 单位的基准偏移会让第一条减时线贴在数字上（原来只有 `jpBeamDist` = 3.5px，
描边加宽到 musicpp 的 1.5 之后净空只剩 2.75px）。现在净空 3.92px，musicpp 等价值 3.97px。

## 八度点的水平居中：`1` 偏 0.88px

musicpp（`render.cpp:906`）、Kotlin 原版（`../src/main/kotlin/mp/layout/layout.kt:1675`）、
本项目旧代码是同一行：按 **advance width** 居中。三边都带同一个偏差。

`PingFang SC` 28px 实测（Canvas `actualBoundingBoxLeft/Right`）：

| 字符 | advance | 墨迹中心 | advance 中心 | 偏差 |
|---|---|---|---|---|
| `0` `2` `3` `4` `5` `6` | 16.80 | 8.40 | 8.40 | ~0 |
| `7` | 15.32 | 7.52 | 7.66 | 0.14 |
| **`1`** | **11.23** | **4.73** | **5.61** | **0.88** |
| `.` | 7.39 | 3.70 | 3.70 | 0 |

`1` 在 PingFang 里是比例宽（11.2，其余数字 16.8 等宽），墨迹中心偏左 em 的 3.1%。
**只有 `1` 有肉眼可见的偏差，而 `1` 恰是简谱里最常见的数字。**

修法：`measureGlyphText`（`src/common/measure.ts`）本来就在调 Canvas 取垂直紧包围盒，
顺手把同一次调用里免费的 `actualBoundingBoxLeft/Right` 也收进 `bbox`（水平方向原先硬写成
`0..advance`）；`Font.inkCenter(ch)` 暴露墨迹中心；`JpNumber.cx` 改用它。
FreeType/Skija 在那条路径上给不出墨迹边界，浏览器给得起——这是本项目相对 musicpp 的便宜。

> `cx` **只**用于装饰对齐（八度点、slur/tie 端点、三连音括号、fermata）。横向排版走的是
> `JpNumber.width` / `left` / `right`，**不碰 `cx`**，所以音符与歌词的横向间距一点没动。

## 小节线高度与 slur 避让

小节线与拍号的上下缘由 `LayoutOptions.jpStaffTop / jpStaffBottom` 给出，对齐 musicpp 的
40 单位简谱 staff（`render.cpp:802`、`:1793`）：**基线以上 1.0 em、以下 0.333 em**。
设计意图是小节线正好从高音点行贯到低音点行。旧值 `23/28` 与 `5/28`（共 1.0 em）矮了三分之一，
下缘连第一行低音点都够不着。线宽同时对齐 `pptEngraver`：细小节线 2、减时线 1.5。

抬高小节线带来一个两边参考实现都没处理的问题：**无高音点时 slur/tie 端点在 -26.5px，
比小节线顶 -28px 还低**，跨小节的 tie（末音 tie 到下小节首音，最常见的一种）会被小节线
从上方穿透。musicpp 靠分层侥幸躲开（有高音点时弧线自然被抬走），`dot = 0` 时它同样会相交。

`Line.clipBarlinesUnderSlurs()` 补上这一层：凡是被某条弧线的**包围盒**横跨的小节线，
上缘压到「弧线下缘 + `jpStackGap/2`」，**只压不抬**。用整体包围盒而不是解贝塞尔在小节线
`x` 处的精确值——偏保守、恒不相交，代价只是那根小节线矮一丁点。

⚠️ `clipTop` 必须在 `Group.update()` **之后**的表示上做文章：`update()` 已经把每条
`GraphicLine` 的 `p0` 折进了 group 的 `y`、children 留在 `y=0`、`p1` 只剩长度。
再去赋 `p0` 会被 `GraphicLine.update()` **二次折叠**，线会既移位又变长（调试时表现为
小节线变成一根穿过弧线的长十字）。正确做法是移动 `group.y` 并同量缩短 `p1`。

## 三连音数字与括线的居中

括线中间要给数字让出一道缺口，数字**按墨迹**落在缺口正中（上下、左右都居中）：

- 纵向：数字的墨迹中心对到括线的 `y` 上，数字因此**骑在线上**。
- 横向：缺口半宽 = 数字墨迹半宽 + `0.15 em`（原来写死 `numberSize/3`，与字形无关，
  在成书重排那种小字号下会宽出一大截空）。

两者都拿 SMuFL 元数据（`opt.smuflMeta.getBBox("tuplet3")`）现算，**不走 `SmuflText.bound`**：
那个 bound 是从元数据直接换算的，y 轴还是 SMuFL 的「上为正」，与页面坐标反号
（`top`/`bottom` 也因此对调）。拿它算墨迹中心，符号会被往上推整整半个墨迹高
（≈0.37 em），看着就是「3 飘在括线上方」。按字号估一个偏移（`0.28 em` 那种）同样不准——
Bravura 的 tuplet 字形墨迹只占 em 的一小截（`tuplet3` 是 SW `[0.04, −0.032]`、NE `[1.224, 1.5]`）。
