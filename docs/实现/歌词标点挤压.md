# 歌词标点挤压（CLREQ + OpenType）

全仓的标点分类与挤压规则只有一份：[`src/common/cjkpunct.ts`](../../src/common/cjkpunct.ts)（**无 DOM 依赖**，
浏览器排版与 Node CLI 共用；改了它要重跑 `npm run build:cli`）。度量与绘制的接线在
`common/measure.ts`（浏览器）与 `scripts/punctshape.mjs`（Node/PDF）。

## 为什么要做

全角标点占一个字宽，墨却只占其中半格——句读点号与收尾类的右半是空的，起始类的左半是空的。
两个这样的标点相邻（`：“`、`」「`）就是整整一个字宽的空洞。这是 CLREQ 3.1.6 管的事。

旧做法是**换字符**：`LayoutOptions.halfWidthPunct` 把 `。，、？！：；` 换成 U+FF61 系半角形。
账很难算：

- 印刷字库多半没有那些码位——PDF 端要靠 `PUNCT_EQUIV` 换回全角才画得出来，
  `line-check` 的 V2 因「字体回退的账判不了」全书跳过 **180 对**相邻歌词；
- 半角 `,` 是**西文逗号**（方正报宋里 0.258em），不在中文逗号该在的位置，宽度也是巧合；
- 挤压是**排版**的事，不该改内容里的字（简繁转换、导出、搜索层拿到的都是被改过的原文）。

## 两派，两档

中文排版的「标点挤压」本来就有两派，这里两派都给（`CompressMode`）：

| 档 | 派别 | 规则 | OpenType |
|---|---|---|---|
| `halfwidth` | **半身式**（开明式） | 句读点号一律占半个字身 | `halt` |
| `clreq` | **全身式 + 上下文挤压** | 标点占满一格，只在相邻标点与行首行末压掉多余的半格 | `chws` |
| `none` | — | 不压 | — |

CLREQ 3.1.6 主要描述的是全身式那一路，但它规定的是「**至少**要在相邻处压」，
并不排斥半身式——传统竖排书、报纸与各家歌本用的都是半身。

**这本书一律走半身**：谱面歌词由 `LayoutOptions.punctCompress` 定（默认 `halfwidth`），
书级正文（注解 164 框、目录、索引、扉页前言）由 `scripts/punctshape.mjs::BOOK_MODE` 定，
两处都是半身。`clreq` 那档留着——换一个档位的事，挤压量的出口只有一个。

**歌词为什么不能走全身**：歌词逐字挂音符，标点不占音符格、只挂在字后，原书印的就是半身。
改走全身会把音符间距整排撑开——实测全书 673 → **695** 页，459/363/355/446 那几首
「四行各 16 拍」式的规整分行全排不出来（定点断言 7 条不过）。

半角档比旧的字符替换宽 11 页，账在逗号上：旧的 `,` 是 0.258em 的西文逗号，
半角中文逗号是 0.5em。**多出来的那 11 页是把宽度算对的代价**，不是回退。

## OpenType：有就用，没有就自己算

- `chws`（CJK Contextual Half-width Spacing）对应 `clreq` 档，`halt`（Alternate Half Widths）对应 `halfwidth` 档。
- 支持与否**实测**：浏览器侧比开/关同一样本串（`：“`）的 advance（`measure.ts::hasFontFeature`），
  Node 侧查 fontkit 的 `availableFeatures`（`scripts/punctshape.mjs`）。
- **本书那套字体一个都没有**（方正魏碑/报宋/楷体/黑体/行楷、Times New Roman、Songti SC、Bravura
  的 `halt`/`chws`/`palt` 全缺），所以成书那条路一律走 `cjkpunct` 的等效实现。
  编辑器路用系统字体，有就交给字体。
- 两条路必须给出**同一个数**：`measure.ts::punctTrim` / `scripts/punctshape.mjs::makeTrim` 是唯一出口。

## 只压空白，绝不压墨

压缩量一律受**该侧的实际留白**（advance 减墨迹）封顶——`compressRun` 的 `slack` 参数。
道理：我们只能挪笔位，挪不动字形在方框里的位置。照规则压满半格，墨迹伸出半角格的字就会压穿：

- `》《` 相邻（注解框里 `其它著名的圣诗有《…》《…》`）——`》` 的墨在方框里占 [1.6, 5.2]（9pt 字号），
  右边只空 3.8pt，压满 4.5pt 就压到下一个字上。全书 104 处，是加 `slack` 之前的事故。
- `：；` 这类墨居中的点号同理。

**表里只收全角形**：ASCII 的 `(` `)` 与半角形 `｡` `､` 本来就没有那半格空白，收进来就是压墨——
`《有活的确据》(13首)`、`Elizabeth R.Charles(1828−1896)`、`(Fanny J.Crosby)` 曾被括号压穿。

守这条的是 `scripts/line-check.mjs` 的 **V9**（书级正文连排逐字复算墨迹，全书 0 处）。
**不挤压时本来就压的不算这里的账**（`克J` 那种是 `J` 的负左边距，字体自身的事），
判据里拿 `mode: "none"` 复算一遍豁免掉，与 V2 跳过字体回退同理。

## 半身不是「把 advance 砍一半」就完了

真 `halt` 换的是**窄字形**，我们只能挪笔位——光压 advance，字形自己带的边距还留在半格里，
两处都会露馅：

**一、字形在半格里的位置。** 方正楷体的全角 `（` 墨只有 0.26em 宽，方框里左边空 0.47em、
右边还空 0.27em。压掉「空的那半格」之后，剩下半格里那 0.27em 边距还在——
目录条目 `奇妙十架（第一调）` 的括号两侧就各多出 0.37em 的空（`（第` 3.71pt，
而普通字距 0.4~2.3pt）。所以半身档下是**把字形放进半角格里居中**：
`pen = x − inkLeft + (w − inkWidth)/2`，`w = max(0.5em, inkWidth)`（半格放不下墨就按墨宽走）。
点号本来就接近居中（`。` 的墨在 [0.117, 0.387]），这么改对它们几乎无变化。

**二、相邻标点之间摞着两截边距。** 两个标点各占半格、墨各自居中，中间就是
「前者的右边距 + 后者的左边距」——`：「`、`！」` 实测 0.27em，而字与字之间只有 0.03~0.1em，
看着散。传统印刷里连续标点是挨着的，所以再收一道：留 `PUNCT_PAIR_GAP = 0.1em`
（普通汉字之间墨间距的量级）。

汉字与标点之间不收拢——那里的 2.1~2.3pt 是**字形自身的边距**（普通汉字对 `第一` 也是 2.3pt），
不是挤压没做够。

## 挤压怎么落到坐标上

`compressRun(chars, advanceOf, em, mode)` 出**逐字笔位** `xs[]` 与总宽，一路带到绘制：

- `TextFrame.charXs` → `<text>` 的 `x` 坐标列表（`layout/painter.ts`、`mixed/painter.ts`），
  **绝不在渲染端再叠一层 `font-feature-settings`**（会挤两遍）；
- 成书那路 `pdflayout/browser.ts` 把 `charXs` 写进 DrawList 的 `xs`，`scripts/pdfwrite.mjs` 照着落笔——
  PDF 那头不必自己 shaping。

`halfwidth` 档要**分两头**算：起始类的墨在方框右半边，笔位得往左挪半格，墨才落进半角格里
（`“` 的墨从 [0.5em,1em] 回到 [0,0.5em]）；点号与收尾类的墨本来就在左半边，笔位不动、
只是下一个字早半格接上。

## 跨音符的那一对标点

一个音节 = 一个 `<text>`。`召：` 的冒号与 `“将` 的引号**分属两个元素**，OpenType 的上下文特性
管不到它们——挤压各压各的，避让由 `layout.ts::Line.calcXPos` 补一道**下限**：

> 挤完的墨迹间距，不许比这两个字排在同一个 `<text>` 里还紧。

同 text 的墨间距 = `prevBlank + headBlank`（两头的留白都已是挤压后的口径），
跨音符的 = `prevBlank + lyricGap + headBlank − hang`，两边一减，下限就是 **`hang ≤ lyricGap`**：
前引号的悬挂只许吃掉字与字之间那道呼吸，不许吃到墨迹之间的距离里去。

**`headBlank` / `tailBlank` 必须从挤压后的笔位起算**（`Lyric.charXs`）。照字形的 inkLeft 算，
就把前引号已经压掉的半格又算了一遍，避让时凭空多半格空档，上一个字的尾标点被压住——
076「说：」压「“忠」、159 两处、376「召：」压「“将」都是这么来的。

守这条的是 `scripts/line-check.mjs` 的 **V8**（全书 0 处）；书级正文那一路由 **V9** 守。

## 书级正文（clreq 档）

注解正文 164 框是全书标点最密的地方，走的是另一条落字路（`bookparts.ts::textItem` 连排）：

- 折行（`wrapText`）与落笔（`scripts/pdfwrite.mjs`）走**同一个 `compressRun`**：注入的 `measure`
  （Node 侧是 `scripts/textmetrics.mjs::advance`）量的就是挤压后的宽度。两边不一致就会处处差半格——
  折行按未挤压的宽度算，每行都短一截、右边空掉。
- 半身式下每个字压多少**与前后无关**，所以折行逐字累加就等于整行的宽度（全身式那档不行，
  它要看上下文）。
- 落笔点要让**首字的墨**对到给定的 x 上：半身档下起始类的笔位自己还左挪了半格
  （`cr.xs[0] < 0`），`lead` 得把那半格算进来，不然整段左偏。
- **行末走压缩、不悬挂**：注解在花边框里，悬挂会压到框上。谱面歌词的行末悬挂另有一套
  （`scripts/line-check.mjs` 的 V3 `HANG_PUNCT`）。

## 那几张字符表为什么不合并

`cjkpunct.ts` 里把六处零散的表集中过来，但**只集中定义，不统一语义**——差异都是拿具体曲子换来的：

- `LYRIC_SPLIT_PUNCT`（`Lyric` 三段切分）含**数字 0-9**（行首段号 `1.`）与**半角冒号**
  （376《将心给我》用 `呼召:` 引出引语）；
- `PU_LYRIC_PUNCTUATION` / `PU_LYRIC_QUOTES`（文本谱）含 `、…—～《》`，不含 `「」『』`；
- `MIXED_PUNCT`（混排判「哪些字算 CJK 主体」）含 `「」`，不含 `、…`；
- `phrase.ts` 的 `PUNCT_END` / `PUNCT_MID` 是**断句**判据（句末 6 分 / 句中 4 分），
  与挤压无关，**不要并进来**。

## 回归

```bash
npm run build && node scripts/shot.mjs /tmp/out.png              # 编辑器路
npm run build:cli && node scripts/rebuild.mjs && node scripts/line-check.mjs   # 成书：V2/V8 与断句基线
node scripts/pu-shot.mjs && node scripts/pu-parse-check.mjs             # 文本谱
```

改挤压规则会牵动歌词宽度 → 容量 → 断句 → 页数，`rebuild` 的页数与 `line-check` 的各档
都要逐条解释，别默默吞掉。
