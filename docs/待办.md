### 3.1 结构还债（R2 收尾）

**终局**：`ScoreDoc` 是**唯一**的模型，语义、版面坐标、断行都在这一层（断句也在这一层做，五线谱要用同一套）。
**没有 `Score`，也没有 `MixedScore`**——两个引擎直接吃 `ScoreDoc`，经共享的查询层取派生量：

```
                     ScoreDoc（语义 + 版面坐标 + 断行）
        ┌────────────┬───────────┼────────────┬──────────────┐
   简谱语义层     简谱形状投影    断句（按 id）  演唱顺序       调号/谱表上下文
 （唱名/八度点/   jianpuproject                 derivePlayOrder   attrsAt
  临时记号/和弦）
        └────────────┴───────────┼────────────┴──────────────┘
                 ┌───────────────┴───────────────┐
         简谱引擎（Entry/Line）            五线谱引擎（Sys/MPage/…）
         引擎内按 id 建对端索引            排版节点引用 ScoreDoc 元素
```

**派生量不存进 `ScoreDoc`、只经查询层取**：同名字段两种口径（`Chord.beams` 在 MusicXML 来源是 `<beam>` 列表、
在简谱来源是减时线条数，靠 `isXmlShaped` 分）；存了要管编辑后的失效；指针有环不能序列化。
**断行与版面坐标例外**——它们是「这份谱怎么印」的事实，要随文档保存、往返。

**`MixedScore` 删的是模型，不是排版状态**：它约一半是五线谱引擎的版面态（`Sys`/`SysStaff`/`MPage`、
`AccidentalLayout`/`DotLayout`/`LegerLayout`、`MeasureInfo.width`、`stemLen`、各处 `x/y`）。这部分留作引擎内部结构，
与简谱引擎的 `Entry`/`NoteEntry`/`Line` 同级；删掉的是其中的语义字段与「从 MusicXML 读成它」这一层。

**过渡期保留两个视图**：阶段 3–8 里 `Score` / `MixedScore` 仍在，只由 `ScoreDoc` 拼出——为的是**每一步都能新旧双跑、逐字节比**。
一上来就让引擎直吃 `ScoreDoc`，出了差异分不清是哪一步引入的。最后两阶段再删。

**路线调整（阶段 6 起）**：用户要求各 painter 拆成可组合的功能块、再拼出混排。能拼的是**绘制层**不是引擎——
混排简谱层的 x 借五线谱的 `default-x`、y 压在五线谱最高点之上，简谱引擎和 pu 引擎都自己横排断行，叠不出来；
「展开 / 原样」是输入投影的差别，不用拆。于是剩下的顺序改成：**A（6①–③ 只换输入）→ B 抽简谱绘制层先给 pu →
C 混排拆五线谱层 + 简谱叠层（C1 换画法、C2 叠层改从语义层取，原 6④ 并入，免得先改写 `MNote.number` 再在阶段 10 删掉）→
D（阶段 7）→ E（阶段 9，拆只换输入 / 只换画法两步）→ F（阶段 10）**。原则：**视觉不变**——三条简谱路的画法差异不抹平，
写成绘制层的 style 选项（每路一个预设），每步页面树逐字节一致；换输入与换画法不在同一步。唯一例外是定性过的错音（C2）。
五线谱语料的判据范围：Praise as One 只要求 kl2020 的 40 首（名单来自 `pao.db` 的 `conference` 表，导成本地
`testdata/r2-baseline/kl2020.txt`，`mixed-tree-dump --list` 读它；脚本里不写 db 路径）。

阶段 6①–③ 双跑定性、留着不补的（语料 0 例）：和弦音各自的 `print-object`/`staff`/`<type size>`/歌词（`ScoreDoc` 只在和弦上存）、
`<dynamics>` 多个子元素与 `<other-dynamics>`、`<strong-accent type>`、`<pedal type="change">`、休止上的 `<stem>`、一个 `<credit>` 多个
`<credit-words>`；`<tuplet bracket>` 混排读的是 stop 上的属性（musicpp 原样），语料都写在 start 上，从来不认——照旧。
顺带修掉的 `fromxml`/`toxml` 毛病：多声部重写后 `<backup>` 全丢（时间挤在一起）；和弦音上的 slur 起止读丢（14 份）；
`<direction>` 的 `<staff>` 当成属性读；slur 同号未收口再起按栈配出横跨几小节的弧（宁静的伯利恒）；同一音上先起后收写反（090 等 4 份重写后弧配错）。

**路线调整**（阶段 2 之后）：原 3② 让成书改走 `fromxml → scoreDocToScore`，核实后那条路经文本谱 AST，
丢 tie/并音/记号/段落/跳转/倚音/副歌判定；要不丢就得新写一层 `ScoreDoc → Score` 直译，而 `Score` 到阶段 9 就删，纯属一次性过渡。
所以改为**成书直接 `fromxml → ScoreDoc`、断句先下沉（阶段 5 提前）**，`loadMusicXml` 过渡期只当引擎渲染输入，随阶段 9 与 `Score` 一起删；
ABC 回落与转 `.jpwabc` 到阶段 8（`.jpwabc` 写出端吃 `ScoreDoc`）时一并换。原 3①（`scoreDocToScore` 补和弦）只为那条路服务，取消。

阶段 8 同样**不新写 `ScoreDoc → Score` 直译**：试听时间线与 `.jpwabc` 写出端都改成只经一组输入接口读谱（`Score` 结构上满足），
`ScoreDoc` 两侧（MusicXML 形状照 `loadMusicXml`、简谱形状照 `scoreDocToScore`）各拼一份满足接口的对象，新旧喂同一个实现、比产物。
`.jpwabc → .jpwabc` 没有调用方，不做逐字节双跑（两侧各丢一类：旧侧 `fromJpw` 丢曲末 `|]` 与曲首 `|:`，
新侧经排版行视图丢行内换行与换页），只验往返定点。原计划的乐句排版模式（`scoreToJpwabc({phrase})`）与 OMR 点选映射
（`scoreToJpwabcWithMeta`）没有调用方，不移植。
顺带修掉的：`fromxml` 吞掉小节级 `<sound tempo>`（568 份曲首速度，现记成 `type: "sound"` 的 `Direction`、原文写回）；
`fromjpw` 不带 `.Title` 速度、照抄一个八度恒为 0 的假 `pitch`（导出 MusicXML 整首掉到第 0 八度）；
写出端歌词锚点把小节末换行也算一小节（多段歌词起点错位 5 首）；`parse123` 读丢 `{多字}-` 的词内断音节（211 往返不幂等）。

阶段 3 同理：原定的验法「`fromJpw(f)` 与 `scoreDocToScore(fromjpw(f))` 深比较」走不通——`scoreDocToScore` 经文本谱 `buildPart`，
丢倚音、演奏记号、`sectionWord`、tie（并进 slur）、嵌套双弧，补齐等于在要删的 `Score` 上花工夫、还会动文本谱展开档基线。
所以改为**在 `ScoreDoc` 这一层双跑**（新 `fromjpw` 对旧 `scoreToScoreDoc(fromJpw)`），`fromJpw` 与 `loadMusicXml` 同待遇，只当渲染输入到阶段 9。

**顺序约束**：1 与其余无关，先做。
2 在 3、6 之前（两者都要换上语义层）。6 风险最高，放在 1、2 就绪之后；7 依赖 5、6。
9 要在 4、5、8 之后（`playData`、断句、试听都不再经 `Score`，均已完成）；10 要在 6、7 之后，且在 C 之后（C2 先删掉简谱叠层的语义字段）。

**不做**：不改简谱引擎、五线谱引擎与断句的阈值（本轮只换输入形状，判据全靠双跑逐项一致）；不合并两个引擎；不统一三条简谱路的观感（要改只动绘制层预设）。
