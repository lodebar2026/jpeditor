# 编辑器

## 职责

编辑器控制器（编辑 ↔ 实时重排 ↔ 翻页 ↔ 文件 I/O）、源格式适配、点选高亮与双向定位、设置、Tauri 外壳。

**谱面上直接改谱**另见 [可视化编辑](可视化编辑.md)，**试听与导出 MIDI** 另见 [播放](播放.md)。

## 入口

| 文件 | 作用 |
|---|---|
| `src/main.ts` | 装配 App、工具栏接线、拖放、双指缩放、内置样例谱 |
| `src/editor/app.ts` | 主控制器；`ViewMode`、`PAGE_RATIOS`、`PAPER_SIZES`、`_renderPagesWith`、`setPhraseLayout` |
| `src/editor/formats.ts` | **源格式适配器表**（`FormatAdapter`）——每加一种可编辑格式只该动这张表 |
| `src/editor/sync.ts` | **双向定位**（`SyncIndex`）：源文本偏移 ↔ 谱面元素（音符、歌词、增时线、小节线、挂载记号、换行） |
| `src/editor/visual/` | **可视化编辑**：谱面上选中、插入、修改（入口 `app.visual.*`，见 [可视化编辑](可视化编辑.md)） |
| `src/model/beatcheck.ts` | 小节时值自检（编辑器与简谱识别共用；识别侧 `src/omr/beats.ts` 对回源图坐标） |
| `src/editor/highlight.ts` / `deco.ts` | CodeMirror 装饰 |
| `src/editor/fileio.ts` | UTF-16LE 编解码 + Tauri 运行时探测 |
| `src/editor/settings.ts` | localStorage 持久化（**只管存取不管应用**） |
| `src/editor/dialogs.ts` | 设置面板 |
| `src/editor/help.ts` | 功能帮助与记谱法说明（事实上的 `.jpwabc` 用户手册） |
| `src/editor/omrctl.ts` | OMR 控制器（入口 `app.omr.*`） |

从 `app.ts` 切出来的几个控制器（OMR、播放、可视化编辑）各自通过一个**列全了的**宿主接口向 App 要能力——
那个接口就是「这摊事到底依赖编辑器多少东西」的清单，**加东西前先想想**。
`formats.ts` 的 `FormatHost` 也是同样的接口。

## 源格式适配器（`formats.ts`）

打开的源格式有五种（`.jpwabc` / 文本谱 / `.123` / `.abc` / `.musicxml`，`docFormat` 记当前是哪种）。
**因格式而异的那些差异全收在这张表里**：高亮扩展、读写编解码、默认扩展名、标题取法、
格式标签、档位旋钮（`jpProfile` 还是 `originalProfile`）、能力位、重排入口。

以前这些是 `app.ts` 里散在约二十处的 `docFormat === "pu"` 三目式，加第三种格式
每处都要再分一次叉。**别再往 `app.ts` 里加这种三目式**——该加的是 `FormatCaps` 的一位。

| 能力位 | 含义 |
|---|---|
| `textEditor` | 有没有代码区。`.musicxml` 没有：打开只看谱面，换成文本格式编辑走打开时的格式选择或「另存为」（`App.convertToTextDoc`，与格式下拉同一条路、切得回原文），五线谱编辑经 `App.editScoreDoc` 改模型、整份重写 XML |
| `layout` | 谱面走哪套排版：`scoredoc`（文本谱、123、ABC、MusicXML：展开档 `jianpuInputOfDoc` → `ScorePainter`；原样档看 `originalLayout`）或 `jpwabc`（`jianpuInputOfJpw` → 简谱引擎两档） |
| `originalLayout` | `scoredoc` 原样档用哪种布局（排版器都是 `ScorePainter`）：`jianpu`（123、ABC；投影成简谱引擎输入，多声部回落原样文档布局）或 `document`（文本谱、MusicXML，`layout/original/`） |
| `phraseRelayout` | 有没有「按乐句重排」。怎么写回原文由 `FormatAdapter.relayoutText` 给：文本谱搬原文片段（`pu/relayout.ts`）、123/ABC 写模型再整份重出、`.jpwabc` 只挪 `.Voice` 的 `$`（`model/relayout.ts`）；`.musicxml` 没有代码区，不给。开着时五线谱/混排另按乐句断、用五线谱的尺子（`App.staffPhraseLineStarts`） |

五线谱/混排**不是能力位**：所有格式都有。`.musicxml` 用打开时读的那份模型；文本格式（含简谱识别落地的 123）
进这两档时由 `App._ensureMixedDoc` 把当前源文经 `export.ts::sourceMusicXmlBare` 投成 MusicXML 再读回（源文没变不重做），
在这两档里代码区仍可编辑、改了就重新派生重排；打开文件时原来在这两档就留在那档（`.musicxml` 同口径）。
派生的 XML **不带**版面坐标，混排排版器见不到坐标就自动铺排（`layoutpass.ts`）；换行照**简谱视图实际排出的行**
（`App.jianpuLineStarts`：另造一个排版器按当前档与纸排一遍取各行首音，经 `ToXmlOptions.lineStarts` 落到小节上），
自动铺排拿它当优选断点。纸取设置里五线谱/混排自己那张（`App.staffPage`，主题 `staff` 出厂 A4；选长图时按 A4 宽、不分页）。**不借原样档的纸**：那边出厂是长图（宽 1000pt、页高随内容），MusicXML 转成简谱再打开时丢了 `<page-layout>`，短曲子会排成一张扁图，看着像横版。
派生缓存按「源文 + 简谱的档、纸、字号」（`_mixedDeriveKey`），这些一变就重新派生。

真正因格式而异的**算法**（`reloadPu` / `reload123` / 乐句重排 / 播放高亮走 AST 索引）
仍留在 `app.ts`，适配器只负责分派。

## 源码格式下拉（`formatswitch.ts`）

代码区标题栏的格式标签位置上是一个下拉（`#doc-format-field`，有可切的格式时顶掉标签），
**打开的文件与识别结果共用**。下拉本身（控件、显隐、「手改过会丢」的确认）只有一份，切换怎么做由来源各自实现 `FormatSource`：

| 来源 | 真身 | 切到别的格式 | 切回 |
|---|---|---|---|
| 打开的文件（`FileFormatSource`，`App.importBytes` 装上） | **原文** | 从原文的模型写出；先列装不下的（`planSave`），文件路径清空（存盘走另存为，原文件不动） | 「原文」那一项：**逐字还原**原文与文件路径 |
| 识别结果（`OmrController`） | `RecognizedScore` | 从识别结果重出文本，**不重跑识别**；选择记进 `omrFormat` | 同左（没有「原文」） |

- 目标清单是转换目标表 `model/convert.ts::CONVERT_TARGETS`（123 / JPWABC / ABC / 番茄 / 诗歌本），另存为也用它。
- **在原格式里改过再切走，以改过的文本为准**（它就是新的原文，模型重建）；在转出来的格式里改过再切，先问一声再丢——
  转出来的文本不是真身，从它再转一次只会越转越丢。
- `.musicxml` 原文没有代码区，下拉里的「MusicXML（原文）」切回去时代码区收起；从「另存为」换成文本格式进来的是同一个来源。

## 打开单声部 MusicXML 时选格式（`App.promptMusicXmlImport`）

用户**亲手打开**（打开对话框、拖入）单声部 MusicXML 后弹单选框：转成 123 / JPWABC / ABC / 番茄 / 诗歌本编辑（默认 123），
或保持 MusicXML 进五线谱档。转过去走 `convertToTextDoc`（先列装不下的，取消就留在 MusicXML）。
取消对话框 = 保持 MusicXML，不中断打开。多声部不问（照旧进混排）。
「记住选择」存进 `PersistedSettings.musicXmlImport`，设置面板「打开 MusicXML」一栏改回「每次询问」。
重开上次文件、回归脚本直接调 `importBytes`，不弹框。

## 导出与另存为（`export.ts`）

两个按钮分工：**导出 = 别的媒介**，**另存为 = 源格式**。以前导出框里还混着「转成 X 编辑」「X（源格式）」两组，
单声部 MusicXML 一开能列十几项。

- **导出**（`EXPORT_ITEMS`）：简谱档 PPTX / MIDI / MusicXML；五线谱/混排档 PNG / PDF / MIDI / MusicXML。
  MusicXML 是给第三方软件的交换件，算媒介。
- **另存为**（`showSaveAsDialog`）：当前格式另存一份 + `CONVERT_TARGETS` 里其余几种。换格式先列装不下的（`planSave`）。
  换格式时换行照简谱视图实际排出的行（`App.convertTo` → `breaks.ts::applyBreaks`，与导出 MusicXML 同一口径：
  版面宽度在小节中间折的顺延到下一小节）；走原样文档布局的（文本谱原样档）照源文的行。
  文本格式写一份新文件、编辑器仍是原文档（`App.saveAsFormat`）；`.musicxml` 没有代码区，另存成文本格式就是
  转过去（`convertToTextDoc`）再落盘，之后编辑的是新存的那份。
- 落地统一走 `App.adoptText(format, text, filePath)`（识别产物的 123 另走 `importOmrDoc`，报它装不下的东西）。

## 双向定位（`sync.ts`）

代码区光标移到某个音符上，谱面上那个音符亮起来；点谱面上的音符，代码区光标跳过去。
选区同理（区间内的音符全亮）。适用于有代码区的四种格式（文本谱、123、ABC、`.jpwabc`）的简谱两档。

索引条目分七种（`SyncEntry.kind`）：音符、歌词、增时线、小节线、挂载记号（和弦名、装饰、注记、圆滑线的 `(` 与 `)`）、换行符、页眉字段（页眉见 [可视化编辑](可视化编辑.md)）。
后四种的原文位置是为可视化编辑补记的（`AttachedSource`、`Mark.openSource/closeSource`、`Part.breakSources`，
只给编辑用，排版与写出端不读）。和弦名、装饰、注记按类名在音符格里认出自己的
（`chord-group`/`artic`、文本谱排版器的 `chord`/`ornament`/`annotation`，`App._markPartEl`）；
增时线、小节线、弧各有自己的图元，按各自的身份认（`sustainEl` / `barlineEl` / `slurEl`，那张表在 [可视化编辑](可视化编辑.md)）。
**`syncEntries()`（`sync-check` 用）只给音符与歌词**。

| 方向 | 怎么走 |
|---|---|
| 文本 → 谱面 | 光标偏移 → `SyncIndex.range()` 二分 → 条目 → 已缓存的 `<g>` → 加 `.cursor-at` |
| 谱面 → 文本 | 点击事件从 `ev.target` 往上找 `<g>` → 条目 → `view.dispatch({selection})` |

**几条判据**：

- 索引建在 `ScoreDoc` 的 `source: SourceSpan` 上，条目按**元素 id** 认；音节配给哪个音符取排版行视图
  （`pu/slots.ts::docView` 的 `syllableOwner`），与排版器、引擎输入同一份。`ScorePainter.entryEl(id)` /
  `lyricEl` / `partEls`（简谱引擎输入的和弦带元素 id；原样文档按音符 id）取 `<g>`，不必动排版；两路页面树的类名差别由排版器消化。试听高亮同样按 id。
- 谱面那侧**按 `<g>` 认、靠冒泡**，不依赖 `pickPage` 的几何拾取——原样档根本没有 `pickPage`，
  两档因此共用同一条路径。`_onSyncClick` 必须留在 `onPageClick` 最前面。
- 走 CSS 类、**不重渲染**；`.cursor-at` 排在 `.playing` 之前，试听时发声的那个盖过光标色。
- **五线谱 / 混排档（文本格式）只到音符级**：`mixedDoc` 是源文写成 MusicXML 再读回的，元素 id 另编一套。
  派生时 `sourceMusicXmlBare(app, { sourceIds: true })` 给每个 `<note>` 写 `id="jp<源 id>"`（只这条内部路径写，导出不带），
  `fromxml` 读成 `Chord.srcId`，`App._indexMixedSrcIds` 建两向对照：点五线谱和弦组（`painter.staffChordAt`）→ 源 id →
  `SyncIndex.spanOfNote`；代码区光标 → 条目 id → 五线谱和弦组加 `.cursor-at`。`.musicxml` 没有代码区，不做。
- **切档要清选中**：简谱档与五线谱档的元素 id 各编各的（都从小整数起），选中的 id 带过去会撞上别的音当起播点（`_setMode`）。
- 防回环：`_syncing` 标志；文档变更时不在监听里同步（索引还是旧偏移），
  等 `reload` 重建索引后由 `_buildSync` 刷一次。

## Tauri 外壳（`src-tauri/`，只有 2 个 `.rs`）

**不只是文件 IO 与对话框**，有三块原生能力：

| 命令 | 作用 |
|---|---|
| `export_pdf_cmd` | 各页 SVG → `svg2pdf`/`usvg` → `lopdf` 合页；载系统字体 + 随包 Bravura |
| `omr_onnx` / `omr_onnx_batch` | `ort` 跑 rec/det 模型，二进制 IPC，`mode=1` 在 Rust 侧做逐时间步 argmax。比浏览器 wasm 多线程快 ~3× |
| `midi_play_cmd` / `midi_stop_cmd` | macOS `AVMIDIPlayer`（player 必须存活，放进托管状态）；用它的是 [播放](播放.md) |

文件 IO 与对话框用**插件**（`tauri_plugin_fs` / `dialog` / `opener`），权限在 `capabilities/default.json`。
**新增插件要同改四处**：`Cargo.toml`、`lib.rs`、capabilities、`package.json`。

Windows 桌面包的 VC++ 运行库随包内置（`src-tauri/tauri.windows.conf.json` + `scripts/win-crt.mjs`），
DLL 清单改那份 conf；来龙去脉见 [实现/OMR-简谱识别.md](../实现/OMR-简谱识别.md) 的「桌面版（Tauri）也内置 VC++ 运行库」。

## 更新检查与反馈入口（`editor/update.ts`、`editor/feedback.ts`，只在桌面版）

两者都挂在帮助对话框的第三个标签页「关于」（`editor/help.ts` 的 `buildAboutPane`），
按 `isTauriRuntime()` 判：Web 版那页只剩版本号与主页——刷新即最新，也没有邮件客户端可唤起。

- **版本号**：只在 `package.json` 维护一处，`vite.config.ts` 的 `define` 注入成 `__APP_VERSION__`；
  `release.sh` 把它同步到 `tauri.conf.json` / `Cargo.toml` / `index.html` 的 JSON-LD。前端别再抄常量。
- **更新检查是「只查不装」**：查 GitHub Releases API 比版本号，有新版问一句，确定就用 `opener` 打开
  release 页由用户自己装。**没上 `tauri-plugin-updater`**——那条路要生成并保管签名密钥、改
  `.github/workflows/build.yml` 注入 `TAURI_SIGNING_PRIVATE_KEY` 并产出 `latest.json`（动 workflow），
  而存量用户照样得手动装一次新版才享受得到。要换只换 `update.ts`。
- **节流判据**（独立 key `jpeditor-update-state`，不进 `PersistedSettings`——那份是
  `App.saveSettings()` 整对象覆盖写的，从别处补字段会被抹掉）：启动后延迟 8 秒查一次，
  距上次检查不足 24h 不查，同一个新版本只提示一次，用户可在关于页关掉自动检查。
  查询失败（断网 / 限流）一律静默返回，不弹错误框。
- **反馈走 `mailto:`**：预填收件人、带版本号的主题与一段可删的环境信息；不自建上报服务——
  这个应用全程本地运行，不该为一条反馈开网络通道。唤不起邮件客户端时在关于页显示邮箱明文兜底。
- `opener` 的 `open-url` 默认 scope 为空，`capabilities/default.json` 里显式放行了
  `https://github.com/*`、主页与 `mailto:*`——**换仓库 / 换邮箱要同改那里**，否则点了没反应。

## 关键判据

- 点选高亮走 **CSS 类、不重渲染**。
- 双指缩放在 `main.ts`（ctrl+wheel / WebKit `gesture*`），按页内归一化坐标锚定；
  `--score-zoom` 设在 `#score-pane` 上，**整条 calc 不能挪到 `:root`**。
- `.jpwabc` 读时 BOM 探测、存 UTF-16LE + BOM（兼容 JP-Word）。
- 能打开哪些扩展名**只在 `src/common/filetypes.ts` 写一次**。
- `window.__app` 运行时暴露，供脚本化测试。
- **简繁转换五种格式通用**（`App.convertHanzi` → `model/hanconv.ts`，判据见 [模型-scoredoc](模型-scoredoc.md)）：文本格式只改原文里文字所在的位置、
  一个 transaction（Ctrl+Z 整体撤销），写不回的处数报在状态栏；`.musicxml` 改模型后经 `editScoreDoc` 整份重写。
